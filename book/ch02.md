# 第 2 章 [第 2 级]：整张 H200 芯片——2,304 个 CTA 派满了 132 个 SM，时间还花在哪里？

**本书地图：** 前言 → 导引一 → 导引二 → 导引三 → 第 1 章 [第 1 级] → **【第 2 章 [第 2 级]】** → 第 3 章 [第 3 级] → 第 4 章 [第 4 级] → 第 5 章 [第 5 级] → 第 6 章 [第 6 级] → 第 7–9 章 → 第 10 章 → 附录

第 1 章拿掉了 kernel 之间的空隙，但单个 `gemv_kernel` 自己的耗时没有变。现在点开它，放大到第 2 级：整张 H200 芯片。

**`v1` 的 2,304 个 CTA 已经派满了 132 个 SM，`gemv` 却要 54.08 µs，而读一遍 $W$ 只需 7.86 µs——在整张芯片这一级，这些时间花在了哪里？**

本章以 `v1 / v2` 的 `gemv_kernel`（权重 $\shape{W}{2304,\ 8192}{BF16}$，输入 $\shape{x}{8192}{BF16}$，输出 $\shape{y}{2304}{FP32}$，启动配置 `<<<2304, 128>>>`）为主线。

---

## 1. CTA 怎样分到 132 个 SM 上？最后一批为什么拖住整个 kernel？

**全卡一次最多放 2,112 个 CTA，剩下的 192 个 CTA 等空位补上后又要从头走完 64 轮串行读取。**

<!-- FIG ch02-a: 图 2-1 上方芯片画 132 个 SM（每个 SM 方块含 16 个驻留位置）、中央 L2 带与两侧 HBM；算法带画 W 的行块按 blockIdx.x 顺序流向 SM，最后 192 行标成尾波颜色；下方时间线画每个 CTA 一条 64 格的串行读取链，第 1 个 wave 2,112 个位置全满，第 2 个 wave 只有 192 个位置在算（r = 192）。读数：wave 容量 2,112、尾波 192、在用比例约 9%。步骤卡：第 1 步 派发 2,112 个 CTA（每个 CTA：$y[\text{row}] = \sum_k W[\text{row},k]x_k$，输入 W 一行 16 KiB 在 HBM、x 16 KiB；代价：每 CTA 64 轮往返）；第 2 步 第一批退出、尾波 192 个派上 SM；第 3 步 尾波走完 64 轮（代价：全卡约 9% 的位置在用）。 -->

硬件以 CTA 为单位把工作派到 132 个 SM 上（见导引三第 1 节）。一个 SM 同时能驻留的 CTA 数有上限，`v1` 是 16 个（为什么是 16 个，见第 3 章第 1 节）。这样全卡一次最多能同时驻留 $132 \times 16 = 2{,}112$ 个 CTA。

本书把**全卡一次能同时驻留的 CTA 数**定义为 1 个 **wave**（波次）。注意 wave 指的是同时在片上的容量，不是“必须齐步跑完才换下一批”：只要有一个 CTA 跑完退出，它空出来的位置马上由下一个待派发的 CTA 补上。

把 2,304 个 CTA 放进 2,112 的全卡容量里，正好是 $2{,}304 = 2{,}112 + 192$。第一批 2,112 个 CTA 同时开始；因为 `v1` 里每个 CTA 的工作量完全相同，它们几乎同时结束退出；剩下的 192 个 CTA 这时才补上来开始算。最后这一小批不满 1 个 wave 的 CTA 就叫 **tail**（尾波），余数记为 $r = 192$（图 2-1）。

为什么尾波这 192 个 CTA 会把整个 kernel 的时间拉长近一倍？看单个 CTA 内部的工作：128 个线程每轮各读 1 个 $W$ 元素，算完一行 8,192 列一共要走 $8{,}192 / 128 = 64$ 轮。每一轮都必须等读取的数据回来才能进入下一轮。这是因为一个线程的指令是按顺序发出的。在 `v1` 编译出来的循环里，下一轮的读取排在这一轮的乘加指令之后，而乘加指令要等这一轮的数据从显存回来才能执行。结果每个线程同一时刻只有 1 个 $W$ 读取在路上（指令怎样按顺序发射，见第 4 章第 2 节）。

CPU 核靠乱序执行和硬件预取重叠等待。每个 warp 按顺序发射，不会越过等待去发它后面的读取；这时 SM 可以去发别的 warp 的读取。有没有硬件预取，本书没有测。本书靠改代码多挂读取：多驻留线程（见第 3 章），或者让每个线程一次多发几条读取（见第 4 章）。

粗看之下，`v1` 的总耗时就像两条首尾相接的 64 轮串行读取链：第 1 个 wave 的 2,112 个 CTA 走完第一条 64 轮的链，尾波 192 个 CTA 紧接着再从头走一条同样长的 64 轮链。在尾波期间，全卡 2,112 个位置里只用了 192 个（约 **9%**），其余位置全都空着，但整个 kernel 必须等这最后 192 个 CTA 走完 64 轮才能结束。

至于哪 192 个 CTA 会落进尾波：CUDA 规范并不保证 CTA 的派发顺序。但在 H200 上，我们在一个 132 个 CTA 的大 kernel（第 7 章的融合 kernel）里，用全卡共用的全局纳秒计时器记下每个 CTA 开始工作的时刻：编号最大的第 131 号 CTA 比编号小于 100 的 CTA 晚 0.9–3.2 µs 才开始。这符合按 `blockIdx.x` 从小到大派发。单独的 132-CTA 小 kernel 没有专门测过。把这个顺序外推到 `v1`，编号最大的 192 个 CTA 会落进尾波（第 8 节 `v3` 的实测提速也间接支持这一点）。代码的正确性不依赖这个顺序，`v3` 只靠它提速。

## 2. 一次读取从 HBM 回到 SM 要多久？$x$ 为什么不用从 HBM 读 2,304 遍？

**空载读 HBM 往返约 0.33 µs，命中全卡共用的二级缓存约 0.18 µs；$W$ 来自 HBM，$x$ 留在缓存复用。**

<!-- FIG ch02-mem: 图 2-2 H200 四层存储位置关系图：片外 HBM（标称 4.8 TB/s，空载往返 0.33 µs）→ 全卡共享的 L2（60 MiB，往返约 0.18 µs）→ SM 内的 L1 / 共享内存与寄存器（容量见第 3 章）。动画标出：W 元素从 HBM 经 L2 到 SM（红圈①），x 第一次从 HBM 进 L2（②），之后各 CTA 读 x 在 L2 命中（③）。步骤卡：第 1 步 读 W[row,k]（输入：BF16，2 B，在 HBM；代价：约 0.33 µs 往返）；第 2 步 读 x[k]（第一次来自 HBM，以后来自 L2；代价：约 0.18 µs）；第 3 步 乘加进寄存器 acc（输出 FP32，留在寄存器，交给块内归约）。总代价：每轮约一次 HBM 往返。 -->

图 2-2 画出了从片外到计算单元的存储通路。本章只用到外面两层：最外层是片外的 HBM（高带宽显存，标称带宽 4.8 TB/s，见导引一第 4 节），往里一层是片上的 **L2 cache**（二级缓存，132 个 SM 共用，总容量 60 MiB）；再往每个 SM 内部走的 L1 缓存、共享内存与寄存器，留到第 3 章第 1 节再展开。

一次全局内存读取的路径是：SM 先去查 L2；如果数据已经在 L2 里（叫作**命中**），就直接从 L2 返回 SM；如果不在 L2 里（叫作**未命中**），才继续去片外 HBM 取回数据，经过 L2 再送进 SM。L2 是全卡唯一由所有 SM 共享的一层，这一点在第 6 节跨 SM 合并时还会用到。

为了量出从发出读取到数据回到寄存器的**往返**时间，先定义一个时间单位：**周期**（clock cycle），即 SM 时钟走一拍的时间；本书按实测的约 1.8 GHz 持续频率把周期换算成时间，1 个周期约 0.56 ns。当全卡只有一个读取在路上（空载）时，从 HBM 读一次往返约 **0.33 µs**，而在 L2 命中一次往返约 **0.18 µs**（见下图）。

```chart

note: 测法：单线程指针追逐微基准（每次读出的值就是下一次要读的地址，全卡只有一个读取在路上），用 SM 时钟周期计数并按 1.7964 GHz 换成 µs；HBM 一档读的是不在 L2 里的数据（冷读）。
data:

  series:

```

这就能回答导引三留下的两个问题。第一，在一次 kernel 里，权重 $W$（37.75 MB）的每个元素只被某一个 CTA 读一次，在 L2 里不会命中。真实运行里，下一次用到同一份 $W$ 已经是下一趟前向；中间约 9.0 GB 的固定权重（见导引一第 4 节）流过 60 MiB 的 L2，早把它挤出去了，所以计时前清空片上缓存和真实运行一致（见导引三第 5 节）。

第二，输入向量 $x$ 只有 16 KiB，远小于 60 MiB 的 L2。按容量推断，第一批 CTA 第一次读 $x$ 时把它从 HBM 带进 L2，此后其余 CTA 再读 $x$ 应在 L2 命中（`v1` 上没有测 L2 命中率）。

回到第 1 节的串行链：`v1` 的每一轮循环里，每个线程同时发出一个 $W$ 读取（来自 HBM）和一个 $x$ 读取（命中 L2），所以一轮的等待时间大约等于一次 HBM 往返。按空载往返粗算，一条 64 轮的串行链大约要花 $64 \times 0.33 \approx 21\ \mu\text{s}$，这是第 8 节估算尾波耗时的基础。两条链合起来约 42 µs，加上 4.6 µs 固定开销约 47 µs，比 `v1` 实测的 54.08 µs 少约 7 µs。这个粗模型只到量级，差的 7 µs 来自哪里没有拆开测。

## 3. 每个 SM 要同时挂起多少字节，才能跑满 HBM？

**全卡一起读时往返随在途字节变长；每 SM 挂起约 64 KiB 才到带宽平台，而 `v1` 只挂起 4.0 KiB。**

<!-- FIG ch02-b: 图 2-3 上方算法带把 W 的 1 行（16 KiB）作为 1 个在途单元，标出已算完、在途与等待中的行；中间画每行从 HBM 经 L2 流向 1 个 SM；下方画往返时间线与全卡实测带宽随每 SM 在途字节变化的曲线，曲线上标出 v1（4.0 KiB/SM）与拐点 64 KiB。读数：每 SM 在途 KiB、全卡带宽、往返时间。步骤卡：第 1 步 一个 SM 挂起 1 行（在途 16 KiB；代价：往返约 0.94 µs）；第 2 步 挂起 4 行（64 KiB；往返约 1.9 µs；全卡约 4.49 TB/s）；第 3 步 v1：4.0 KiB（代价：HBM 大部分时间空闲）。 -->

已经发出读取请求、数据还没有回到 SM 的字节数，叫作 **bytes in flight**（在途字节）。在途字节、带宽和往返时间之间满足 **Little's Law**（利特尔法则）：

$$\text{在途字节} = \text{带宽} \times \text{往返时间}$$

要让一个 SM 拿到它应得的那份带宽，它在路上同时挂起的字节数就必须盖住一次往返。

我们先看目标有多高。全卡 132 个 SM 持续流式读 HBM 时，实测能达到的**带宽平台**（再增加在途字节带宽也不再上涨的那一段）约为 **4.54 TB/s**，平摊到每个 SM 约 **34 GB/s**。如果只拿第 2 节的空载往返 0.33 µs 来算，每个 SM 似乎只要挂起 $34\ \text{GB/s} \times 0.33\ \mu\text{s} \approx 11\ \text{KiB}$ 就够了。

我们另做了一个带宽扫描微基准：让 132 个 SM 持续读 HBM，每个 SM 同时读几行 $W$（每行 16 KiB，读取方式见第 3 章第 8 节）。当每个 SM 只挂起 16 KiB 时，全卡实测带宽远未到平台（见下图），说明全卡一起读时的平均往返已经明显长于空载的 0.33 µs。

```chart

unit: GB/s
lower_is_better: false
note: 测法：132 个 SM 持续读 HBM 的带宽扫描微基准（不是 gemv），每 SM 同时读 S 行 W（每行 16 KiB）；平台约 4.54 TB/s（标称 4.8 TB/s 的 94.6%），64 KiB 已达平台的 99%，v1 每 SM 只挂起 4.0 KiB。
data:

```

顺着图表往右看：当每个 SM 同时挂起 **64 KiB**（4 行 $W$）时，全卡带宽到达拐点，再往后就停在约 4.54 TB/s 的平台上。**64 KiB 是测出来的拐点**；到平台以后再多挂起，带宽不再涨，按 $\text{往返时间} = \text{在途字节} \div \text{带宽}$ 算出的往返只会更久。在 64 KiB 的拐点处，按利特尔法则算出平均往返约 **1.9 µs**，是空载的约 6 倍。多出的时间花在哪一段没有测，常见的解释是排队。

对照这个拐点，就能看穿 `v1` 慢的第二个原因。在 `v1` 里，每个线程每一轮只有 1 个 2 B 的 $W$ 读取在路上，1 个 CTA（128 个线程）在途只有 $128 \times 2\ \text{B} = 256\ \text{B}$，1 个 SM 上的 16 个 CTA 合起来只有 **4.0 KiB**（图 2-3），落在图表最左端 16 KiB 档位之外，离 64 KiB 的拐点差得很远。

第 1 节说的是串行链有多长；本节说的是每一轮能让 HBM 忙多少。`v1` 每个 SM 只挂起 4.0 KiB，离平台很远，全卡读取负载轻，所以第 2 节的粗模型按接近空载的往返来估（`v1` 的单轮往返没有直接测）。至于怎样把每个 SM 的在途字节从 4.0 KiB 提到 64 KiB，那是第 3、4 章的事；挂起更多字节要占更多寄存器或片上存储，第 3 章算这笔账。

## 4. 能不能告诉 L2 哪些数据该留下？

**能。读取时给单次数据标先淘汰、给复用数据标后淘汰，能在会被挤出时保住复用数据；不会被挤出时只添开销。**

第 2 节说 16 KiB 的 $x$ 会留在 60 MiB 的 L2 里；可 $W$ 有 37.75 MB 只读一次的数据流过 L2，会不会把需要复用的数据挤出去？默认情况下，L2 硬件并不知道哪些数据待会儿还要再用、哪些数据读过一次就再也不用。当一大段只读一次的数据流过 L2 时，就可能把后面还要重读的数据换出 L2。

要改变这种默认行为，可以在读取时附带一个 **L2 留存提示**（cache hint；代码写法见附录 B）：对只读一次的流式数据标 `evict_first`（告诉 L2 要腾地方时先淘汰它），对要跨 CTA 反复重读的数据标 `evict_last`（告诉 L2 尽量留到最后）。

<!-- FIG ch02-l2-evict: 图 2-4 60 MiB L2 留存提示微基准解剖图：L2（60 个格子，每格约 1 MiB）先装入 32 MB 复用数据（一种颜色），再流过 64 MB 只读一次的数据（另一种颜色）；分两档对照“不加提示：按容量推断会被换出（未测）”与“加提示：复用数据留下（98.8%–100%）”。步骤卡：第 1 步 生成两种留存提示（写法见附录 B；2 条指令，只做一次）；第 2 步 读复用数据时附上 evict_last 提示（第 1 步生成的提示）；第 3 步 流过 64 MB 单次数据时附上 evict_first 提示（第 1 步生成的提示）；第 4 步 重读复用数据（命中 L2，代价：约 0.18 µs 往返）。总代价：每次读取多带一个留存提示，多几条指令。 -->

这件事在什么时候有用？看一个单独的微基准（图 2-4）：先读入 8–32 MB（图 2-4 以 32 MB 为例）需要复用的数据，接着流式读过 64 MB 只用一次的数据（超过了 60 MiB 的 L2 容量），然后再重读前面那批复用数据。实测显示，给两次读取分别标上 `evict_last` 和 `evict_first` 时，复用数据有 **98.8%–100%** 仍留在 L2 里；不加提示时，按容量推断，复用数据会被 64 MB 的流式数据挤出 L2（这一档的留存比例与相对增益没有测）。

L2 留存提示的取舍：

- **得到什么**：会被大流量挤出时，保住复用数据在 L2 里（数字见上面的微基准）。
- **付出什么**：每次读取都要多造并多传一个留存提示，代码更繁琐。
- **什么时候亏本**：当复用数据本来就不会被挤出时，多带的提示只添开销。在 `gemv` 上，因为 $x$ 只有 16 KiB、本来就不会被挤出，在后面第 8 节的 `v3` 之上加这两个提示试了一步（记作 `v4`），实测反而慢约 **1 µs**，所以不单独算一步；第 3 章第 8 节的 `v5` 仍带着这两个提示，它们在 `v5` 上的作用没有单独测。

## 5. 尾波只剩少数 CTA 时，怎样让更多 SM 一起算同一行？

**沿内积维把一行切几段分算再合并叫 Split-K；只把尾波的行对半切开叫 K-halves，每半行只走 32 轮。**

<!-- FIG ch02-splitk-wave: 图 2-5 gemv 尾波切分解剖图：三档对比“不切：192 个 CTA 各走 64 轮”、“K-halves：384 个半行 CTA 各走 32 轮”与“切得太碎（示意）：CTA 数超过 1 个 wave 容量，多出来的进下一个 wave，合并次数也变多”（第三档只画结构，不标耗时）。步骤卡：第 1 步 前半 CTA 算 $\sum_{k<4096}$（输入：W 半行 8 KiB 在 HBM、x 前半 8 KiB 在 L2；输出：部分和 FP32 4 B 写全局内存）；第 2 步 后半 CTA 同理；第 3 步 合并（交给第 6 节；代价：一次跨 SM 交接）。总代价：每行多写 2 个 4 B 部分和、多一次跨 SM 合并。 -->

第 1 节看到，尾波只有 192 个 CTA，但每个都要走完 64 轮读取，而尾波期间全卡约九成的位置空着。一行的内积本来就是 8,192 项相加，天然可以沿 $K$ 拆成前后两半：

$$y[\text{row}] = \underbrace{\sum_{k=0}^{4095} W[\text{row},k]\,x_k}_{\text{前半}} + \underbrace{\sum_{k=4096}^{8191} W[\text{row},k]\,x_k}_{\text{后半}}$$

前半和后半互不依赖，完全可以交给两个 CTA 在两个不同的 SM 上同时算，各自算完一个**部分和**，再加到一起。

只切尾波最划算的条件是：尾波余数 $r$ 不超过 1 个 wave 容量的一半（$r \le 2{,}112 / 2 = 1{,}056$）。这样把 $r$ 行切成 $2r$ 个半行 CTA 后，全部 $2r$ 个 CTA 都能塞进尾波那个 wave 原本空着的位置里，不会多出 1 个 wave。这种只把尾波的行对半切开的做法叫 **K-halves**（尾波对半切分）。在 `v1` 里，$r = 192$，对半切开后是 $2r = 384 \le 1{,}056$，正好满足条件。切开之后，每个半行 CTA 的串行链从 64 轮降到了 **32 轮**，而且尾波期间全卡同时在路上挂起的字节数也跟着翻倍（384 个 CTA 对 192 个 CTA，图 2-5 第二档）。

把这一做法推广到一般情形，就是 **Split-K**：当输出行数或输出分块太少、连 1 个 wave 容量都填不满时，把内积维 $K$ 切成 $S$ 段，让 $S$ 个 CTA 合算同一个输出，总 CTA 数就乘上 $S$（多词元矩阵乘上的 Split-K 见第 5 章第 6–7 节，演化链实测见第 6 章第 8 节）。

Split-K 与 K-halves 的取舍：

- **得到什么**：K-halves 让尾波每个 CTA 的串行链长减半（从 64 轮降到 32 轮），尾波期间全卡在途字节翻倍（实测收益见第 8 节）。
- **付出什么**：每个切开的行都要写出 2 个 4 B 的部分和（共 8 B），多做一次跨 SM 合并（第 6 节实测约 0.67 µs），而且 grid 的块编号映射更复杂。
- **什么时候亏本**：余数 $r$ 超过半个 wave，或者切得太碎、总 CTA 数越过 1 个 wave 时，就会亏本。在 `gemv` 上切 4 段没有测；在一个专家 kernel 上切 4 段实测比切 2 段更慢（见第 8 章第 3 节）。

## 6. 两个 SM 各算半行，怎样安全地加起来？

**两个半行写出部分和后各对 L2 计数器做原子加，拿到旧值 1 的后到者负责相加；两个 CTA 不必同时在片上。**

第一步先看为什么要经过 L2。每个 SM 的 L1（每个 SM 自己的一级缓存，第 3 章第 1 节细讲）是私有的，各个 SM 的 L1 之间硬件不会自动保持一致；第 2 节讲过，L2 是全卡唯一由所有 SM 共享的一层。因此用本章的全局内存访问，跨 SM 交换数据只能在中央 L2 汇合（另一条跨 SM 通路见第 7 章第 12 节）。

第二步解决“谁来相加”。这里用到**原子加**（atomic add）：把“读出旧值、加上新值、写回内存”三步合并成一次不可分割的操作，别的线程插不进来，并且返回加之前的旧值。两个半行算完后，各自对同一个初值为 0 的计数器（`int32`，4 B）做一次原子加 1：先到的那个（先到者）拿到旧值 0，直接退出；后到的那个（**last arriver**，后到者）拿到旧值 1，就知道对方已经来过了。

但光有原子加还不够。先到者在代码里虽然先写部分和 `part`、再对计数器加 1，可如果不加内存顺序约束，CUDA 的内存模型并不保证另一个 SM 先看到 `part` 的新值、再看到计数器的新值。硬件上，这可能表现为计数器比 `part` 先到 L2，或后到者读到本 SM L1 里的旧数据。

在看代码之前，先把三种内存顺序用白话定清楚：

- **relaxed**：只保证这一次原子操作本身不可分割，不约束它前后的其他读写顺序。
- **release**（释放）：本线程此前的读写都排在这次写之前；此前的写入对任何用 acquire 读到这次写的线程可见。
- **acquire**（获取）：本线程此后的读和写，不会排到这次读之前。

同时具备 release 和 acquire 叫作 `acq_rel`。因为各 SM 的 L1 之间不保持一致，GPU 上每次同步还必须指明作用范围（如 CTA 内、全卡 `device` 或整个系统）；这里两个半行 CTA 可能被派到全卡任意两个 SM 上，作用范围必须指定为 `device`（全卡范围，CUDA C++ 代码里写 `thread_scope_device`）。

<!-- FIG ch02-c: 图 2-6 上方画 SM A、SM B 各自的私有 L1 与中央共享的 L2（含计数器 cnt[i] 和两格 part）；下方两档时间线对比“只用 relaxed：后到者可能读到旧的部分和”与“acq_rel：release 把写推到 L2，acquire 作废本 SM 的 L1 后从 L2 读到新值”（硬件上的表现即 L1 作废是观察，不是规范保证）。步骤卡：第 1 步 SM A 写 part[2i]（FP32 4 B → 全局内存）；第 2 步 SM A fetch_add(acq_rel) 得 0，退出（代价：1,078 周期）；第 3 步 SM B 写 part[2i+1]，fetch_add 得 1；第 4 步 SM B 读两格相加写 y[row]（FP32 4 B），计数器复位（relaxed）。总代价：一次交接约 0.67 µs；L1 被作废后重读 x 变慢。 -->

GPU 在这里和常见的 CPU 不一样。x86 的 TSO 内存模型只允许一种重排：先写后读。一个核先写 A、后读 B 时，这次读可能在写 A 对别的核可见之前就完成；效果上像读排到了写前面。要禁止它，x86 要加 `MFENCE`。各核的缓存则由 MESI 一类协议自动保持一致。

GPU 的内存模型对不带同步的普通（weak）读写不给这些保证：读读、读写、写写、写读四种先后顺序都可能被打乱。普通弱读写与 `relaxed` 原子操作不同：`relaxed` 仍保证同一个地址上的修改顺序一致。要约束跨地址顺序，用 release / acquire，或者插入一条**内存栅栏**（fence，约束前后读写顺序的独立指令）。`acq_rel` 栅栏（`fence.acq_rel`）保证：此前的读写不会排到此后的写之后，此后的读写不会排到此前的读之前。它不禁止先写后读被打乱；这本书的算法不依赖这一点。

因此 x86 上直接能用的“先写数据、再写标志”，在 GPU 上必须写成带作用范围的 release / acquire。

```cuda
#include <cuda/atomic>
// tail_store（后到者合并）：0 号线程在块内归约之后执行（前面已有 __syncthreads()）
// i = 尾波里第几行（0..191），half = 0 表示前半、1 表示后半
part[2 * i + half] = sum;                                   // 写出本半行的部分和
cuda::atomic_ref<int, cuda::thread_scope_device> c(cnt[i]);
if (c.fetch_add(1, cuda::memory_order_acq_rel) == 1) {      // 拿到旧值 1：我是后到者
    y[row] = part[2 * i] + part[2 * i + 1];
    c.store(0, cuda::memory_order_relaxed);                 // 下一次启动才会再用
}
```

上面这段代码靠四个环节保证顺序：

1. **累积性**（cumulativity）：一个线程的 release 不只发布它自己的写入，也发布它在这次 release 之前已经通过 acquire 或块内屏障看到的别的线程的写入。因此同步链可以一环接一环传下去，而且**每一环的作用范围只要包含这一环自己的两个线程就够**。例如，线程 A 写入后，经 CTA 内的屏障交给线程 B。B 做 `device` 范围的 release，另一个 SM 上的 C 做成对的 `device` 范围 acquire，C 就看得到 A 的写入。如果 B→C 只用了 CTA 范围，链就在这一环断掉。
2. **块内到线程 0**：`tail_store` 里只有 0 号线程写 1 个标量 `part` 并做原子加。一个 CTA 的许多线程各自写出部分和时（如下面的 256 线程微基准与第 7 节），也不必每个线程都做原子加。先做一次 `__syncthreads()`（见导引三第 4 节），再由 0 号线程做一次 release，按第 1 条的累积性就能发布全块此前的写入。
3. **跨 SM 成对**：先到者的 release 和后到者的 acquire 作用在同一个计数器 `cnt[i]` 上。同一个计数器上的原子读改写链把先到者的 release 传给后到者的 acquire，两者**成对**生效，保证先到者写出的 `part` 对后到者一定可见。硬件上观察到的行为（不是规范保证）是：release 先把本 SM 的写入推到 L2，acquire 让本 SM 的 L1 作废，之后的读取回 L2 拉取。下面图表的后两档量的就是它。
4. **计数器复位**：后到者相加完写出 `y[row]` 后，把 `cnt[i]` 写回 0 只用 `relaxed` 就够了，因为下一次用到这个计数器是在下一次 kernel 启动里，中间已经隔着 kernel 结束这道流顺序边界（见第 1 章第 1 节）。

注意这套“谁后到谁合并”的写法**不需要两个 CTA 同时驻留在芯片上**：先到者做完原子加就立刻退出，不等待任何人；后到者到了就直接读取两半合并。所以不管两个半行 CTA 相隔多久被派发，都绝不会死锁。

作为对比，如果换一种写法，让一个 CTA 在循环里反复读取另一个 CTA 写的标志直到条件成立，这就叫**自旋等待**（spin-wait）。和操作系统线程不同，硬件不会为了同一次启动里还没派发的 CTA，把已经驻留的 CTA 换下 SM。自旋等待必须保证两个 CTA 同时在芯片上：因为 CUDA 规范不保证普通启动的派发顺序和同时驻留，一旦等待者在片上占满了位置不退出，写标志的那个 CTA 就永远拿不到 SM。

规范认可的无死锁办法有两种。第一种是把写标志的生产者放进前一个独立 kernel。第二种是使用 **cooperative launch**（协作启动），由驱动保证整个 grid 的所有 CTA 一次全部驻留在芯片上，放不下就直接拒绝启动（一个 SM 能放几个 CTA 见第 3 章第 1 节）。在普通启动下，靠第 1 节观察到的升序派发把生产者排在最前面的块编号也能跑通。**但驱动或硬件一改派发方式，它就可能挂死，而且不报错。**

最后算一下全卡范围同步的硬件代价。为什么全卡范围的 release / acquire 比 `relaxed` 贵得多？因为各 SM 的 L1 不保持一致，release 必须等本线程此前发出的写入都已经在 L2 落定，才能让别的 SM 看见；acquire 之后又不能再信任本 SM L1 里的旧数据。

后到者经 L2 合并的取舍：

- **得到什么**：不需要启动第二个归约 kernel 就能跨 SM 安全合并，也不要求两个 CTA 同时驻留。
- **付出什么**：每次合并要付一次约 0.67 µs 的跨 SM 交接，花在等此前的写落到 L2、原子操作往返与后到者读取上（见上面两张图）；本 SM 的 L1 被作废，后面重读变慢；还要多开一个计数器和一块暂存区。
- **什么时候亏本**：当要合并的部分和很大、很多时，让后到者那 1 个 CTA 独自把全部部分和读回来相加，它自己就会变成新的尾巴。

## 7. 部分和很多时，怎样不让最后一个 CTA 独自读完？

**两种改法：一是让 $S$ 个 CTA 各合并 $1/S$ 行；二是所有 CTA 直接对事先清零的输出做无返回值原子加。**

<!-- FIG ch02-l2-reduce-four: 图 2-7 跨 SM 合并大块部分和的两种做法与一个反例（时间轴只表示先后顺序）：模式 1 后到者串行读回全部部分和（红圈标出长读取链，后到者读 0.75 MiB 要多久未测）；模式 2 并行切片归约，每个 CTA 读 1/S；模式 3 直接原子加进清零的输出（无暂存区）；反例 BF16 标量原子加变成比较交换重试循环。步骤卡（模式 2）：第 1 步 写部分和到暂存区（输入：寄存器累加器 FP32；输出：全局内存）；第 2 步 0 号线程 acq_rel 领票 $t$ 并等齐 $S$ 张票；第 3 步 0 号线程等到后再做一次块内同步，块内其余线程读本 CTA 所属 1/S 行切片的 $S$ 份并相加写输出；代价：一次领票等待、读 1/S 的部分和。步骤卡（模式 3）：第 1 步 等清零可见；第 2 步 无返回值原子加；代价：无暂存区；结果下一个 kernel 才可见。 -->

第 6 节在 `gemv` 上只把尾波的每 1 行切成两半，一个计数器只管 1 行，后到者只需读回 2 个 4 B 的标量。如果把 `gemv` 的许多输出行合成一块、沿 $K$ 切成 $S$ 段，让一组 $S$ 个 CTA 共用一个计数器，后到者要独自读回的部分和就会成倍增长。多词元一起算时更大：例如 64 个词元、1,024 个输出列沿 $K$ 切给 $S = 4$ 个 CTA（见第 5 章第 6–7 节），4 份 FP32 部分和共有 $4 \times 64 \times 1{,}024 \times 4\ \text{B} = 1\ \text{MiB}$。如果还照第 6 节那样只让后到者那 1 个 CTA 把另外 3 份（0.75 MiB）串行读回来相加，这 1 个 CTA 的读取链就会变成一条新的长尾巴（图 2-7 模式 1）。

第一种改法是**并行切片归约**（图 2-7 模式 2）：不让先到的 $S - 1$ 个 CTA 直接退出，而是让 $S$ 个 CTA 平摊合并工作。具体分四步：

1. 每个 CTA 把自己的部分和写进全局暂存区，并在块内同步。
2. 每个 CTA 的 0 号线程对计数器做一次 `acq_rel` 原子加，领一张票号 $t$（原子加返回的旧值，从 0 起一直往上数；成对规则同第 6 节）。计数器从不复位。原因是：没有一个 CTA 知道其余 $S - 1$ 个 CTA 是否都已看到票数到齐、停止自旋；谁在这时把计数器写回 0，还在自旋的 CTA 就再也等不到票数到齐。所以每次调用都接着往上加 $S$ 张票。
3. 本组票号都领完时，计数器等于 $(\lfloor t / S \rfloor + 1) \cdot S$。0 号线程用 `acquire` 反复读计数器，直到它不小于这个值（最后一个领票者不用等），确认全部 $S$ 份部分和都已写出；0 号线程等到之后，再做一次 `__syncthreads()`，块内其余线程才去读。计数器回绕怎样处理，见第 5 章第 7 节。
4. 每个 CTA 按自己在 $K$ 方向上的序号，读回 $S$ 份部分和里对应的那 $1/S$ 行切片（$S = 4$ 时为 16 行），相加后写出。

因为先到的 CTA 要自旋等待后到的 CTA，第 6 节的同时驻留规则在这里直接适用：必须保证这 $S$ 个 CTA 同时驻留在芯片上（用第 6 节的协作启动；靠观察到的升序派发能跑通，但不受规范保证）。并行切片归约的取舍：

- **得到什么**：把合并读取平摊给 $S$ 个 CTA，消除了单 CTA 串行读回的长尾巴（实测见第 6 章第 8 节）。
- **付出什么**：仍需要部分和暂存区、一次领票与自旋等待，每个 CTA 多一段合并代码，且要求 $S$ 个 CTA 同时驻留。
- **什么时候亏本**：要合并的部分和很少时（例如第 6 节只有 2 个标量），平摊读取省下的时间可能抵不上自旋等待的开销；这个临界点没有测。

第二种改法是**直接原子加**（图 2-7 模式 3）：每个 CTA 算完自己的那一段内积后，所有线程直接对全局内存里的输出数组发出**不需要返回值的原子加**（只加不读，发出去就不等返回）。这样既不需要部分和暂存区，也不需要领票和计数器。

但它有三个前提：

1. **输出必须在第一次相加之前被清零**：规范安全的做法是在前一个独立 kernel 里清零；如果在同一个 kernel 里派专门的 CTA 清零并发布完成标志，就必须使用第 6 节的 release / acquire 成对同步，并且满足同时驻留要求（见第 6 节）。
2. **结果只对下一个 kernel 可见**：在当前 kernel 内部，没有任何一个 CTA 知道别的 CTA 什么时候加完；全部部分和加出来的最终结果，只有在当前 kernel 结束（或后继 kernel 跨过第 1 章第 4 节的等待调用）之后才对下一个 kernel 可见。
3. **输出不再逐比特固定（deterministic）**：因为浮点数加法不满足结合律，而各个 CTA 到达 L2 的先后顺序每次运行可能不同，累加出来的浮点数可能差最后几位。

直接原子加的取舍：

- **得到什么**：省掉部分和暂存区与计数器。
- **付出什么**：输出必须事先清零；结果不逐比特固定；很多 CTA 同时加同一个输出地址时，请求在 L2 排队（单请求注意力上的实测与解释见第 7 章第 12 节）。
- **什么时候亏本**：
  - 直接对 BF16 做标量原子加要靠比较交换重试：读出旧值、算出新值，只有内存里的值没被改过才写入，否则重来。实测更慢（见第 6 章第 8 节）。
  - 为了省独立清零而在同一个 kernel 的计算 CTA 入口边算边清零并发布标志，也会更慢（机理与实测见第 5 章第 7 节）。

## 8. `gemv` 演化 `v2 → v3`：用 K-halves 把尾波的 192 行对半切开

**`v3` 把最后 192 行拆成 384 个半行 CTA，尾波读取链从 64 轮降到 32 轮，实测快约 1.25 倍。**

在代码上，`v3` 让前 2,112 个 CTA（编号 `0..2111`）照旧每个算一整行；把编号 `2112..2495` 的 384 个 CTA 每两个分一行，各算 4,096 列，算完后用第 6 节那段计数器合并代码（`tail_store`）经中央 L2 合并写出 `y[row]`。半行 CTA 放在 grid 最后，是因为按第 1 节观察到的升序派发规律，编号最大的这批正好落在尾波：

```cuda
// v3：前 2,112 行每行 1 个 CTA，最后 192 行每行 2 个半行 CTA（grid = 2,496）
gemv_v3<<<2112 + 2 * 192, 128, 0, stream>>>(W, x, y, M, K, part, cnt);
```

改动之后，每个 SM 同时驻留的 CTA 数仍是 16 个（为什么不变，见第 3 章第 1 节）。按空载往返粗算，尾波链约缩短一半，估计约省 10 µs（算式见图 2-8 读数）。

`v3` 比 `v2` 快约 **1.25 倍**，省下的比简单尾波模型的估计略多，原因没有查明。这一步付出的代价是尾波的 192 行各做一次跨 SM 交接，并多开一块部分和暂存区与计数器（共 $192 \times 12\ \text{B} \approx 2.3\ \text{KB}$）；什么时候会亏本见第 5 节。

即便走完了 `v3`，`v3` 的耗时仍是下界的约 5.5 倍（下界只占 **18.1%**，含固定开销）。剩下的差距来自第 3 节指出的第二个原因：`v3` 每个 SM 同时挂起的在途字节仍然只有 4.0 KiB。

---

**带走一句话：** 一个 kernel 的耗时由最后结束的 CTA 决定，而 HBM 能不能跑满，看每个 SM 同时挂起多少字节。把尾波的行对半切开并经 L2 合并后，`gemv` 的耗时从 54.08 µs 降到了 43.34 µs。

**下一章的问题：** 跑满 HBM 需要每个 SM 挂起约 64 KiB（第 3 节），`v3` 每个 SM 只挂起 4.0 KiB。打开一个 SM：是什么限制了它能同时挂起多少字节，数据又怎样又快又不出错地到达寄存器和共享内存？
