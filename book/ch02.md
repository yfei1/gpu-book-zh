# 第 2 章 [第 1 级]：点开一个 kernel，整张 H200 芯片怎么接住它？

## 1. 132 个 SM 上的 wave、tail 与 K-halves

<!-- FIG ch02-a: 图 2-1 上方画 H200 芯片封装（两侧 HBM 堆叠［按 6144 位总线除以每堆叠 1024 位推得 6 个］、中间 GPU 裸片与中央 L2 缓存带，移动块对应 qkv_gate 的 W 行块依次流向各 SM），裸片上每个小方块代表 1 个 SM。下方画 2,304 个 CTA（按每 SM 1 个 CTA 的简化模型为 17 × 132 + 60）在 132 个 SM 上按波次推进的时间线。 -->

图 2-1 上方画出了 H200 芯片表面，裸片上的每个小方块是 1 个 SM（全卡共 132 个）。先假设每个 SM 一次只跑 1 个 CTA 来演示波次概念。第 3 章会算出 `v1 / v2` 实际每 SM 驻留 16 个 CTA（全卡一轮容量为 `132 × 16 = 2,112` 个，`2,304 = 2,112 + 192` 实际分两轮跑完）。全卡齐步跑完的一轮 CTA 称为一个 **wave**（波次）。在图 2-1 的单 CTA 模型中，启动 2,304 个 CTA 与启动 2,376 个 CTA 都要跑 `⌈2304 ÷ 132⌉ = 18` 个 wave。第 18 个 wave 无论有 60 个还是 132 个 SM 在算，整个 kernel 都要等这一波跑完才结束。

只要总 CTA 数不是单轮容量的整数倍，最后一个 wave 就只有余数 `r` 个块在算（图 2-1 中 `r = 60`）。其余 **`132 − r`**（72）个 SM 空等到终点线，这段空等就是 **tail**（尾波）。图 2-1 按每个 CTA 用时固定画出了尾波上界。受 HBM 带宽限制的 kernel 在尾波里在算的 SM 更少、排队更短，单个 CTA 会跑得略快，所以实际尾波损失小于图中的上界。当最后一波的余数 `r` 不超过单轮容量的一半（单 CTA 模型下 `2r ≤ 132`，即 `r ≤ 66`）时，可把队尾工作块沿 `K` 维对半切开。这一做法称为 **K-halves**（勾选图 2-1 的切半开关可见）。切开后的 `2r` 个半块刚好放进最后一轮的空闲位置里，两半结果经跨 SM 同步合并（见第 4 节）即可把尾波缩短约半个 wave。

## 2. PDL 提前进场时发生了什么：观察到的 CTA 派发顺序

按第 1 章的触发规则，PDL 后继 CTA 会落进图 2-1 最后一个 wave 里那些刚空闲出来的 SM 中。P2 的后继阶段采用了 **persistent kernel**（持久 kernel）。全卡每个 SM 启动 1 个 CTA，依次处理按 `blockIdx.x` 预先分给它的工作块。本来每个 CTA 分到的工作量相同，应该同时结束。但实测发现编号最大的 131 号 CTA 比编号小的 CTA 晚开始约 **2–3 µs**，在 decode 批量 16–32 的多数输入种子下成为最慢的 CTA。前序 kernel 的 SM 是一批批退场的，H200 的硬件派发器在交接处按 `blockIdx.x` 从小到大的顺序把新 CTA 依次派给刚退出的 SM。所以在代码里给编号大的 CTA 略微少分一点工作量，就能让各 CTA 的结束时间更接近。

## 3. 全卡内存层次与利特尔法则：为什么每个 SM 要挂起约 `64 KiB` 在途读取？

<!-- FIG ch02-b: 图 2-2 上方是算法带（1 个 16 KiB 在途单元对应 W 的 1 整行 8,192 × 2 B = 32 条 512 B 的 warp 读取，算出 y 的 1 个元素，标出已算完、在途、等待中的行），中间画每行从两侧 HBM 经中央 L2 流向 1 个 SM，下方画每行的往返时间线与全卡实测带宽随单 SM 在途 KiB（16 / 32 / 48 / 64 / 80 / 96 KiB）变化的曲线（横轴标出 v1–v10 的在途位置）。 -->

如图 2-2 所示，全卡 SM 读写全局指针 `W, x, y` 时，全部连向芯片中央共享的 **L2 cache**（L2 缓存，容量 60 MiB）。L2 未命中时再去芯片两侧的 HBM 读取。第 0 章算下界用的 4.8 TB/s 是手册标称峰值，而全卡用普通向量读取指令持续流式读 HBM 的实测可达上限约为 4.54 TB/s。平摊到每个 SM，目标带宽约为 `4.54 TB/s ÷ 132 ≈ 34 GB/s`。一条读取发出后、数据返回前，它请求的字节叫 **bytes in flight**（在途数据量）。图 2-2 把 `W` 的 1 整行（`16 KiB = 32` 条每次 512 字节的线程束读取，见第 3 章）画作 1 个在途单元。图 2-2 横轴用“▲”标出了 `v1–v10` 各版本的在途位置，其中 `v1–v4` 每线程只发 2 字节读取，每 SM 在途仅 4.0 KiB。根据 **Little's Law**（利特尔法则），要跑满单 SM 的目标带宽，SM 上同时保持的在途字节数必须覆盖往返延迟。

```text
所需在途数据量（Bytes in flight） = 单 SM 目标带宽 × 包含排队在内的往返延迟
```

先按空载延迟估算。当全卡只有 1 个请求在路上时（空载），读 HBM 往返约 0.33 µs，算出每 SM 只需挂起 `34 GB/s × 0.33 µs ≈ 11 KiB`。切换图 2-2 的档位。选“每个 SM 在途 16 KiB（同时读 1 行 W）”时，读数为“全卡 2.29 TB/s，是标称的 48%；一行往返约 0.94 µs”。再切到“每个 SM 在途 **64 KiB**（同时读 4 行 W）”。此时读数到达拐点“全卡 4.49 TB/s，是标称的 94%；一行往返约 1.92 µs”。满载往返约为空载延迟的 6 倍（可继续切到 80 与 96 KiB 档位查看读数）。超过约 64 KiB 后，增加在途字节只会拉长在 L2 与显存控制器前的排队时间，带宽停在约 4.54 TB/s。

## 4. 跨 SM 交换数据：为什么必须走 L2 同步？

<!-- FIG ch02-c: 图 2-3 上方画 SM A 与 SM B 各自独立的私有缓存及中央共享的 L2 cache（内含硬件原子加法器，移动块对应 K-halves 前半块 SM A 与后半块 SM B 写出部分和并经 L2 计数器交接合并的过程）。下方画通过 device 级 release 排空到 L2、再通过 acquire 失效本地旧缓存并从 L2 读到新值的交接时间线。 -->

同一 **cluster**（线程块集群）内的 CTA 可直接互读片上内存。但 K-halves 的两半与 P1 的各拆分块由任意空闲 SM 接手，不保证在同一 cluster 内。所以跨任意 SM 汇总必须走全卡唯一的一致点 L2。

在 P1 注意力中，各拆分块的部分和用无返回值的全局原子加法累加到同一个 FP32 工作区地址。L2 内部的硬件原子加法器把“读旧值、相加、写回”一步完成，发送方不用等旧值返回。

在 K-halves 中，两半各算完半行部分和后需要在 L2 汇合。x86 CPU 的 TSO（总存储序）内存模型保证同一核发出的写入按程序顺序对其他核可见。ARM 等弱序 CPU 不保证跨地址顺序，而硬件缓存一致性本身只保证同一地址的写入顺序。但在 GPU 上，各 SM 的私有缓存（见第 3 章的 L1 cache）之间硬件不自动保持一致。普通写入也不保证跨地址顺序：计数器的更新可能先于部分和到达 L2，后半块的普通读取也可能命中自己私有的旧缓存行。因此跨 SM 交接必须指定 **device**（全卡作用域）的 **release / acquire**（释放/获取）内存序。实战中把两步合成一个带 `acq_rel`（兼具 release 与 acquire）的原子计数。每个半块写完部分和后，对 L2 中的计数器执行一次 `fetch_add(1, memory_order_acq_rel)`。拿到旧值 `1` 的后到半块读取另一半的部分和并相加写回 `y[row]`，同时把计数器复位为 `0` 供下一次重放（后到者合并不必自旋等待）。

```cuda
#include <cuda/atomic>
// 每个半块块内归约后，0 号线程写出本半块部分和，并以 device 级 acq_rel 递增计数器
__syncthreads();
if (threadIdx.x == 0) {
    partial[half_id * M + row] = sum;
    cuda::atomic_ref<int, cuda::thread_scope_device> cnt(done_cnt[row]);
    if (cnt.fetch_add(1, cuda::memory_order_acq_rel) == 1) {
        y[row] = partial[row] + partial[M + row];
        cnt.store(0, cuda::memory_order_relaxed); // 复位供下一次 CUDA Graph 重放
    }
}
```

在图 2-3 的测试中，跨 SM 经 L2 交接一次的中位耗时约为 **0.67 µs**。这与第 1 章两个 kernel 之间的 PDL 交接（约 0.6 µs）同量级。所以能留在单 SM 内部完成的计算不跨 SM 交接。

## 5. gemv 演化（v2 → v3 → v4）：K-halves 切尾波与 L2 缓存留存提示

按第 3 章的驻留规则，**v2**（`<<<2304, 128>>>`）每 SM 驻留 16 个 CTA，全卡单轮容量为 2,112 个 CTA，第二轮留下 `r = 192` 个尾波 CTA。由于 `192 ≤ 2,112 ÷ 2` 满足第 1 节“余数不超过单轮容量一半”的切半条件，**v3**（在途 4.0 KiB/SM）把最后 192 行拆成 384 个半行 `K/2` 的 CTA（启动 2,496 个 CTA）。两半按第 4 节的 L2 `acq_rel` 原子计数由后到者合并写回。尾波里每个 CTA 只有 `128 × 2 B = 256` 字节在途，耗时由串行往返次数决定，切半 `K` 直接把尾波块的串行往返次数减半。H200 实测：`58.88 →` **48.26 µs**（`1.22×`），约为 7.9 µs 下界的 `16.3%`。

接着 **v4**（每 SM 16 个 CTA，在途 4.0 KiB/SM）用 `createpolicy` 为中央 L2 加上留存提示（`.L1::evict_first` 同时提示本 SM 的 L1 优先淘汰流式数据）。权重 `W` 每字节只读 1 次，标为 **`evict_first`**（读完优先淘汰）；向量 `x`（16 KiB）被重复读取，标为 **`evict_last`**（优先留在 L2）。

```cuda
// v4：用 createpolicy 生成 L2 策略描述符，W 标 evict_first，x 标 evict_last
asm volatile("createpolicy.fractional.L2::evict_first.b64 %0, 1.0;
"
             "ld.global.L1::evict_first.L2::cache_hint.b16 %1, [%2], %0;" : "=l"(pW), "=h"(w) : "l"(Wp));
asm volatile("createpolicy.fractional.L2::evict_last.b64 %0, 1.0;
"
             "ld.global.L2::cache_hint.b16 %1, [%2], %0;" : "=l"(pX), "=h"(xv) : "l"(xp));
```

测具在每次冷缓存计时前写入 512 MiB 清空 60 MiB 的 L2，H200 冷缓存实测：`48.26 →` **43.94 µs**（`1.10×`），约为 7.9 µs 下界的 `17.9%`。但在不清空 L2 的热缓存重复测试中，单层 `W`（37.7 MB）本可装进 60 MiB 的 L2。此时 `evict_first` 阻止了 `W` 留在 L2，使热缓存耗时反而从 `29.02 µs` 退化到 `42.88 µs`（真实多层推理中其他层本就会冲掉 `W`，冷缓存才是真实工作点）。

**带走一句话：** 普通读取指令需在每个 SM 上挂起约 64 KiB 在途字节（覆盖约 1.92 µs 满载排队往返）才能跑满 4.54 TB/s 的 HBM 带宽，而跨 SM 交接一次约需 0.67 µs。
