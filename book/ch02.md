# 第 2 章 [第 1 级]：整张 H200 芯片——132 个 SM 怎样铺平波次、喂饱 HBM 并在中央 L2 归约？

**本书地图：** 前言 → 第 0.0 章 → 第 0 章 → 第 0.5 章 → 第 1 章 [第 0 级] → **【第 2 章 [第 1 级]：整张 H200 芯片】** → 第 3 章 [第 2 级] → 第 4 章 [第 3 级] → 第 5 章 [第 4 级] → 第 6 章 [第 5 级] → 第 7–10 章

第 1 章在时间线上把单层的启动次数从约 17 次压到了 11 次，但末尾留了一个反常现象：`qkv_gemm g1a` 砍掉第二次归约启动后，在 `T = 256` 上反而比单核 cuBLAS 慢了 `10.50 µs`。这说明光看时间线上有几个条块还不够。把时间线上代表单个 kernel 的条块横向打开，里面是全卡 132 个 **SM**（Streaming Multiprocessor，流式多处理器，即执行指令的计算单元）、中央 60 MiB 的 **L2 cache**（二级缓存）以及两侧 4.8 TB/s 的 **HBM**（高带宽显存）。

一句话流过单层八个阶段（第 0 章）时，时间线上的每个阶段 kernel 都要派发到全卡 132 个 SM 上并行执行，包括阶段 1/3/4/5/7 的稠密投影（如 `qkv_gate` 2,304 行、`pooler` 4,096 行）、阶段 2 分页注意力拆分块和阶段 6 本地专家 CTA。因为 132 个 SM 共享中央 60 MiB 的 L2 缓存从 HBM 读权重，而且跨 SM 切开的半行或分片必须在 L2 汇合后才能把输出交给下一阶段，所以本章第 1 级管的是整张芯片上的四件事：整卡波次排布（第 1 节）、CTA 派发顺序（第 2 节）、单 SM 在途字节门槛（第 3 节），以及跨 SM 经中央 L2 归约的四种原语（第 4 节）。

---
## 1. 132 个 SM 上的 Wave（波次）、Tail（尾波）与非整除 Split-K 切分

为什么 2,304 行 `gemv` 的最后 192 个 CTA，或者 `qkv_gate` 在 `T = 128` 下的 72 个 CTA，会让 60 个 SM（45%）空闲等待？**因为一个 kernel 的耗时不是按所有 CTA 的平均进度算的，而是由最晚结束的那个 CTA 决定的。只要总 CTA 数不是全卡单轮驻留容量的整数倍，最后一轮里没分到块的那批 SM 就只能一直等到整个 kernel 结束。**

<!-- FIG ch02-a: 图 2-1 上方画 H200 芯片封装（两侧 HBM 堆叠［按 6144 位总线除以每堆叠 1024 位推得 6 个］、中间 GPU 裸片与中央 L2 缓存带，移动块对应 qkv_gate 的 W 行块依次流向各 SM），裸片上每个小方块代表 1 个 SM。下方画 2,304 个 CTA（按每 SM 1 个 CTA 的简化模型为 17 × 132 + 60）在 132 个 SM 上按波次推进的时间线。 -->

图 2-1 上方画的是 H200 芯片表面。中间裸片上的每个小方块是 1 个 SM，全卡一共 132 个；两侧是可用容量 141 GB 的 HBM3e 显存（按 6,144 位总线除以每堆叠 1,024 位推得 6 个堆叠，美光 H200 物理规格为每堆叠 24 GiB、8 层 DRAM，共 144 GiB 物理容量）。我们先按每个 SM 一次只跑 1 个 CTA 的简化模型来看波次（第 3 章会算出 `v1 / v2` 实际每 SM 驻留 16 个 CTA，全卡单轮容量为 `132 × 16 = 2,112` 个，`2,304 = 2,112 + 192` 实际分两轮跑完）。

全卡齐步跑完的一轮 CTA 叫一个 **wave**（波次）。在图 2-1 的单 CTA 模型里，启动 2,304 个 CTA（每块读 `W` 的 1 行 16 KiB）和启动 2,376 个 CTA，都要跑 `⌈2304 ÷ 132⌉ = 18` 个 wave。第 18 个 wave 不管是有 60 个还是 132 个 SM 在算，整个 kernel 都必须等这一波跑完才结束。

只要总 CTA 数不是单轮容量的整数倍，最后一个 wave 就只有余数 `r` 个块在算（图 2-1 里 `r = 60`）。其余 **`132 − r`**（72）个 SM 一直等到终点线，这段尾轮等待就是 **tail**（尾波）。当最后一波的余数 `r` 不超过单轮容量的一半（单 CTA 模型下 `2r ≤ 132`，即 `r ≤ 66`）时，可以把队尾每一行的 `K = 8,192` 列对半切开：前半块读前 4,096 列（8 KiB），后半块读后 4,096 列（8 KiB）。这就是 **K-halves**（尾波对半切分，勾选图 2-1 的切半开关可见）。切开后的 `2r` 个半块刚好放进最后一轮空闲的 SM 里，在该简化模型下能把尾波缩短约半个 wave。付出的代价是前半块要写出部分和，由后半块经第 4 节的 L2 同步读取相加。

把这个方法推广到更一般的情况：当输出矩阵的分块总数连全卡 132 个 SM 的单波次容量都填不满时，就要沿着内积求和维 `K` 切分成 `SPLIT` 段，称为 **Split-K**（沿内积维切分；阶段 2 注意力沿历史键值维切分见第 7 章第 2 节）。

<!-- FIG ch02-splitk-wave: 图 2-2 Split-K 切分数与 132-SM 波次权衡解剖图：上方对比阶段 6 下投影（M = 16）在 Split-K = 1（不满波）、Split-K = 2（铺满单波省 1.38 µs）与 Split-K = 4（跨波次加归约流量反慢 3.26 µs）下的 SM 占用，下方展示阶段 1 qkv_gate（T = 128/256）用非整除 Split-K = 3 将 36 个输出瓦片扩为 108 个 CTA（空闲 SM 从 60 个减至 24 个）的过程。 -->

拿阶段 6 路由专家的下投影矩阵乘（计算 `y = inter · W2^T`，内积维 `K = 4,096`，第 8 章详解）在 `decode 16`（`M = 16`）下的切分来做主例（图 2-2 上半部分）。当 `M = 16` 时，每个命中专家按列切出 64 个输出块。如果不切 `K`（图 2-2 模式 1），总块数 `A × 64` 填不满波次，SM 槽位空了一半。改成 `Split-K = 2`（`S = 2`，每段 `K_s = 2,048`）后，各分片 CTA 分别算出部分和平面 `y_part[s, tok, :] = inter[tok, s·2048:(s+1)·2048] · W2[:, s·2048:(s+1)·2048]^T`，再由后归一化核以单精度读取并求和 `y = y_part[0] + y_part[1]`，乘上每专家归一化与路由权重后写出 `m [16, 4096]`。切成 2 段让 CTA 总数翻倍铺满波次（图 2-2 模式 2），实测省下 **1.38 µs**（区间 `[-1.71, -1.18] µs`，5 个种子全胜）。代价是多写出 1 份部分和平面并由下游多读 1 次（最大绝对误差 `0.0078`，在容差内）。

但切分并不是越多越好。如果在同一 `decode 16` 上把切分数继续翻倍到 **`Split-K = 4`**（图 2-2 模式 3），CTA 数越过波次上限进入第 2 波，实测反而比 `Split-K = 2` 慢了 **+3.26 µs**（另一次 `+1.50 µs`）。而在 `decode 32`（`M = 32`）上尝试 `Split-K = 2` 时，虽池化均值快 `2.69 µs`，但因 1 个种子慢了 **+1.33 µs** 而被门控拦截。

用同样的波次算法，就能算出第 1 章末尾 `qkv_gemm g1a`（`T = 128 / 256`）变慢的原因（图 2-2 模式 4）。`W [2304, 8192]` 按列宽 64 切，只有 `2,304 ÷ 64 = 36` 个输出列块。`g1a` 用 `Split-K = 2` 只派出 `36 × 2 = 72` 个 CTA（每 SM 驻留 1 个 CTA），导致 `132 − 72 = 60` 个 SM（`45.5%`）闲置。要想再多切一段去填满 132 个 SM，`8,192 ÷ 64 = 128` 个 K 步又不能被 `3` 整除。这里的做法是引入**非整除 Split-K（uneven K parts）**：允许 `SPLIT = 3` 把 128 个 K 步拆成 `42 + 43 + 43` 步。在 `g1` 内核中，无论 `T = 128` 还是 `T = 256`（均只有 1 个行块），网格都扩成 `1 × 36 × 3 =` **108 个 CTA**，132 个 SM 里只剩 24 个空闲（后续第 5 章 `g4` 将列块扩为 128 宽配 7 段切分时会进一步达到 `18 × 7 = 126` 个 CTA）。实测 `g1a → g1` 在 `T = 128` 上省 **2.73 µs**，在 `T = 256` 上省 **7.94 µs**；配合第 4 节的票据并行切片归约，在 `verify 16 / 32` 单项评测中也省下 **2.78–2.86 µs** 与 **7.50–7.89 µs**。

除了上面专家的下投影矩阵乘在 `M = 16` 扩到 `Split-K = 4` 反慢 `+3.26 / +1.50 µs` 之外，Split-K 还有两处实测变慢或报错的边界。一处是在阶段 2 注意力的键值切分调参中（见第 7 章第 2 节），过多切分会因每 CTA `6.6 µs` 的固定开销与合并流量反而慢 `12.1 µs`。另一处是在不兼容的分块配置上开启 Split-K 路径：在阶段 1 / 阶段 5（`verify 16`，`T = 128`）上，曾尝试为 `BM = 128`、4 个线程束的分块内核开启 `SPLIT = 2 / 3` 切分路径，结果编译出的内核首次启动即触发硬件 `cudaErrorIllegalInstruction`（非法指令故障）并污染整个 CUDA 上下文，导致 30 个评测算例中的 10 个直接报错（即便按模型推算也会慢 `1–2 µs`），因此直接废弃。

## 2. PDL 提前进场时硬件按 `blockIdx.x` 顺序派发 CTA 的斜坡效应与死锁禁令

当后继 kernel 趁前序退场时逐个填进空出来的 SM，或者多个 CTA 在芯片上互相等待时，硬件是按什么顺序派发 CTA 的？**虽然编程手册没有明文保证派发顺序，但在 3 张不同 H200 上对内核做逐 CTA 时间戳统计证实：硬件派发器在启动 `grid` 时，实测严格按照程序块编号（`blockIdx` 展平后的线性序号）从小到大依次把 CTA 派给刚空出槽位的 SM。**

<!-- FIG ch02-e: 图 2-3 PDL 提前进场时，后继 kernel 的 CTA 按 blockIdx.x 顺序填进空出来的 SM；时间线显示最后一个 CTA 晚 2–3 µs 开始。 -->

依赖这条实测派发规律，我们在全卡层面导出三项设计：PDL 交接处的启动斜坡补偿、相邻块共享缓存行的排布，以及跨 CTA 自旋等待的防死锁编号规则。

先看 **PDL 交接处的启动斜坡（Ramp）与高编号块减负**（图 2-3）。按第 1 章第 3 节的拆法，阶段 6（路由专家）拆成阶段 A（算上投影与门控激活，每专家权重 18.9 MB，写出 `inter [M, 4096]`）和阶段 B（算下投影 `w2`，每专家权重 9.4 MB，写出 `y [M, 4096]`）。在小批量内核里，阶段 B 在全卡每个 SM 上启动 1 个常驻 CTA（`b = 0..131`；大批量持久队列见第 8 章第 3 节）。本来每个 CTA 分到的工作单元数相同，应该同时结束；但阶段 A 的 132 个 SM 是一批批退场的（结束跨度约 4–7 µs）。硬件派发器按 `blockIdx.x` 从小到大把阶段 B 的 `0..131` 号 CTA 依次填进刚空出的 SM，导致最后进场的 `131` 号 CTA 在 `decode 16`、`decode 32` 和 `verify 1`（`M = 8`）上，分别比前 100 个 CTA 晚 **2.0 µs、3.2 µs 和 0.9 µs** 到达第一个工作单元（每单元周期约 1.05 µs；图 2-3 三档读数与最慢种子占比见本节末表）。

因此在代码里从 100 号块起，按二次启动延迟项给编号大的 CTA 少分阶段 B 工作单元，在 `decode 16` 和 `decode 32` 上实测平均省下 **0.27 µs**（`[-0.41, -0.13]`）和 **0.31 µs**（`[-0.48, -0.15]`，`verify 1` 上为 `−0.02 µs`；二次延迟项本身的寄存器与指令代价未测，且必须仅在含有双分块段时开启，否则无该段时前序块过载会反慢 **+0.42 / +0.49 µs**，详见第 8 章第 3 节）。同理，利用“编号相邻的 CTA 在同一时刻被派上芯片”这一实测规律，阶段 2 注意力把同读一条 128 字节键值缓存行左右两半的两个 CTA 排在相邻 `blockIdx` 上同时启动，使后到者命中 L2，在 `verify 32 full` 上单项省下 **11.9 µs**（见第 7 章第 2 节）。

再看**跨 CTA 自旋等待的防死锁编号规则：当每个 SM 只能驻留 1 个 CTA 时，任何自旋等待的消费者 CTA 只准等待编号比自己更小的生产者 CTA**。我们用阶段 4 的 `router` 矩阵乘在 `verify 16 / 32`（`T = 128 / 256`）下的“清零 CTA + 单调标志归约”来说明（图 2-4）。

这一步把工作分成两类 CTA：4 个专职清零 CTA（Zero CTAs）先把输出矩阵 `scores [T, 256]`（FP32，每词 `1,024 B`）的 4 个分块写零，然后对单调递增的标志数组 `zero_flag[tile]` 执行释放加 1。其余沿 `K` 切分的计算 CTA（K-CTAs）读入激活 `h [T, 8192]` 和路由权重 `W_router [256, 8192]`（FP32，`8.4 MB`）各自算出部分和 `part`（FP32）。到了尾声，计算 CTA 自旋轮询 `ld.acquire.gpu(zero_flag[tile])` 直到清零完成，再用原子加把 `part` 累加进 `scores`，最后交给选择核挑出每词元最大的 8 个专家编号 `topk_ids [T, 8]` 与权重 `topk_weights [T, 8]`（见第 9 章第 1 节）。

为什么这 4 个清零 CTA 必须排在最前面？因为在 `T = 128` 的分块 `router` 内核里，每个 CTA 需要占用 **`196,640 B`（约 `192 KiB`）动态共享内存**，每个 SM 最多只能驻留 **1 个 CTA**，全卡同时驻留上限就是 132 个 CTA。如果把 4 个清零 CTA 的块编号排在计算 CTA 后面（`program_id 132 … 135`，图 2-4 模式 1，设计时按派发规则推演直接规避，未在线上触发该事故），硬件派发器会先把 `0..131` 号计算 CTA 派满全卡 132 个 SM。这 132 个计算 CTA 算完主循环后停在尾声自旋等待 `zero_flag` 翻转、永不退出，而排在队列后面的清零 CTA 因为没有 SM 空出来，**永远无法上片执行**，整张芯片就会陷入死锁。

把 4 个清零 CTA 硬性排在网格最前面的 **`program_id 0..3`**（图 2-4 模式 2），就能保证它们第一时间被硬件派上 SM，完成写零与标志释放并立刻退场让出 SM（同时将每线程寄存器从 72 个压至 64 个；其余代价与何时反输未测）。在 `router` 上，这一设计在 `T = 128` 省下 **1.22 µs**，在 `T = 256` 省下 **1.72 µs**（单调标志归约协议见第 4 节，阶段 4 全貌见第 9 章第 1 节）。

## 3. 全卡内存层次（HBM → 60 MiB L2 → 132 SM）与利特尔法则：为什么每 SM 需挂起约 64 KiB 在途读取？

第 0.5 章的 `v1` 已经把全卡 132 个 SM 都派满了，为什么实测带宽只有 `642 GB/s`（标称带宽为 `4.8 TB/s`）？**因为显存带宽能不能跑满，不看芯片上驻留了多少个线程，而看每个 SM 在路上同时挂起了多少还没返回的字节。当全卡 132 个 SM 一起读 HBM 时，排队会把往返延迟从空载的 `0.33 µs` 拉长到满载的 `1.92 µs`；每个 SM 必须在路上同时挂起约 `64 KiB` 的在途读取，才能跑满它分到的 `34 GB/s` 带宽。**

<!-- FIG ch02-mem: 图 2-5 H200 的存储层次：寄存器 → SMEM/L1 → L2 → HBM，每层的容量、延迟、带宽，以及 qkv_gate 的一个 W 元素和 x 走过哪些层。 -->

先看图 2-5 的 H200 四层存储结构（各层延迟独立测量，不直接相加）：

- **寄存器文件（最内层，每 SM 私有）**：每个 SM 有 `65,536` 个 32 位寄存器，依赖单精度乘加延迟约 `4.10` 个周期（第 3、4 章展开）。
- **SMEM 与 L1 cache（每 SM 私有，共 `256 KB` 片上池）**：切分为最多 `228 KiB` 的 **SMEM**（共享内存，无冲突读延迟 `23.06` 个周期，每 SM 峰值 `128 B/周期`，按 `1.7964 GHz` 持续张量时钟折合约 `229.9 GB/s`）和私有的 **L1 cache**（一级数据缓存，命中 `54.4` 个周期，见第 3 章）。
- **中央 L2 cache（全卡 132 个 SM 共享，容量 `60 MiB`）**：分近端与远端两个分区，近端命中 `327.8` 个周期、远端 `414.1` 个周期。在 528 个 CTA 重读 `32 MB` 留存工作集的微基准中，全卡重读带宽测得约 **7.33 TB/s**。
- **HBM（最外层，容量 `141 GB`）**：空载往返 `600.2` 个周期（按 `1.7964 GHz` 时钟折合约 `0.334 µs`），标称带宽 `4.8 TB/s`。

在 `qkv_gate`（`y = W · x`）中，权重 `W`（`37.7 MB`）每步只用 1 次，必须从最外层 HBM 经 L2 流进寄存器。而输入向量 `x`（`16 KiB`）被全部 `2,304` 个 CTA 重复读取，第一次读入后就能留在 L2 里就近返回（近端 `327.8` 个周期，约 `0.182 µs`）。切换图 2-5 的三档模式，就能对比不同读取方式在单 SM 在途量与整卡带宽上的差距（三档读数见本节末表）。

<!-- FIG ch02-b: 图 2-6 上方是算法带（1 个 16 KiB 在途单元对应 W 的 1 整行 8,192 × 2 B = 32 条 512 B 的 warp 读取，算出 y 的 1 个元素，标出已算完、在途、等待中的行），中间画每行从两侧 HBM 经中央 L2 流向 1 个 SM，下方画每行的往返时间线与全卡实测带宽随单 SM 在途 KiB（16 / 32 / 48 / 64 / 80 / 96 KiB）变化的曲线（横轴标出 v1–v10 的在途位置与单次启动实测点）。 -->

结合图 2-6 看清在途数据量与带宽的关系。全卡 132 个 SM 读写全局指针 `W, x, y` 时，全部连向芯片中央共享的 L2 cache，未命中时再去两侧 HBM 读取。第 0 章算下界用的 `4.8 TB/s` 是手册标称峰值，而全卡用普通 16 字节向量读取持续流式读 HBM 的实测稳态上限约为 **4.54 TB/s**（用下一章第 3 节的专用块拷贝硬件无缩放实测上限为 **4.51 TB/s**）。平摊到 132 个 SM，每个 SM 的目标带宽约为 `4.54 TB/s ÷ 132 ≈ 34 GB/s`。

一条读取发出后、数据返回前，它请求的字节叫 **bytes in flight**（在途数据量）。图 2-6 把 `W` 的 1 整行（`16 KiB`）画作 1 个在途单元，横轴用“▲”标出了各演进版本按机器指令数据流估算的在途位置，其中 `v1–v4` 每线程只发 2 字节读取，每 SM 在途估算仅 `4.0 KiB`。根据 **Little's Law**（利特尔法则），要跑满单 SM 的目标带宽，SM 上同时保持的在途字节数必须覆盖往返延迟：

```text
bytes in flight（所需在途数据量） = 单 SM 目标带宽 × 包含排队在内的往返延迟
```

如果只按空载延迟算，全卡只有 1 个请求在路上时，读 HBM 往返约 `0.33 µs`（`600.2` 个周期），每个 SM 似乎只需挂起 `34 GB/s × 0.33 µs ≈ 11 KiB`。但切到图 2-6 的“每个 SM 在途 16 KiB（同时读 1 行 W）”档位，全卡只有 `2.29 TB/s`（标称的 `48%`），一行往返已经涨到了约 `0.94 µs`。再切到“每个 SM 在途 **64 KiB**（同时读 4 行 W）”，读数才到达拐点：全卡 **4.49 TB/s**（标称的 `94%`），一行往返约 **1.92 µs**（下一章第 4 节的专用块拷贝流式读取则在每 SM 在途 **48 KiB** 处进入平台）。满载往返延迟是空载的约 6 倍，因为全卡并发请求在 L2 与显存控制器前拉长了排队时间。超过约 `64 KiB` 后，带宽就停在约 `4.54 TB/s`。

把图 2-6 的时间轴拖到最后一步，还能看清为什么单次 `37.7 MB` 启动的实测点（○，写 512 MiB 清缓存下第 4 章满在途版本单次启动为 `15.68 µs` 即 `2,409 GB/s`，读 512 MiB 干净清缓存下为 `14.27 µs` 即 `2,645 GB/s`）会落在稳态曲线下方。当在干净清缓存下把读取行数从 `2,304` 行扩到 `4,608` 行（`75.5 MB`）及以上时，H200 实测每多读 `37.7 MB` 的稳态斜率为 **4.54–4.61 TB/s**（线性拟合 `4.59 TB/s`，即图上 ◆），正好落在曲线上。单次 `37.7 MB` 启动的表观带宽偏低，是因为除了 `37.7 MB ÷ 4.59 TB/s ≈ 8.2 µs` 的稳态传输外，线性拟合截距显示每次启动还要付约 **6.4 µs** 的固定开销（`8.2 µs + 6.4 µs ≈ 14.6 µs`，实测 `14.27 µs`）：其中单 warp 空 kernel 启动加事件计时实测为 `3.81 µs`（约 `3.8 µs`，第 0.5 章首轮为 `3.68 µs`），其余约 `2.6 µs` 为拟合残差（片上硬件时钟记录的时间线显示 `2,304` 个 CTA 在 `0.16 µs` 内全部启动，但完成时间分布在 `7.7–12.6 µs` 之间，最后 `10%` 的线程束比前 `90%` 晚 `2.4 µs` 结束，推断收尾期在途字节下降使 HBM 未跑满）。

既然全卡读取都要经过中央 60 MiB（`62.9 MB`）的 L2，当几十兆字节的单次权重流经 L2 时，就可以用缓存留存提示来保护需要跨 CTA 复用的小数据（图 2-7）。独立微基准实测表明：把 `8–32 MB` 的复用数据标为 **`evict_last`**（优先留存），把 `64 MB` 的单次流式数据标为 **`evict_first`**（读完优先淘汰），可使复用数据在 `64 MB` 流式冲刷后仍保持 **98.8%–100%** 的 L2 留存率。`32 MB` 重读带宽可达 **7.33 TB/s**，而无提示默认策略会跌到 `4.19 TB/s`。

以阶段 6 路由专家在 `decode 1` 下的权重流 `evict_first` 提示为主例：在阶段 A（`h = x_2 · W13^T`）与阶段 B（`y = inter · W2^T`）中，命中专家的权重 `W13, W2`（`decode 1` 下平均约 `54.7 MB`，约占 `60 MiB` L2 容量的 `87%`）通过带 `evict_first` 提示的流式加载进片上缓冲。跨 CTA 复用的激活 `x_2`、中间激活 `inter`（各 `8,192 B`）与多趟复用的块则带 `.L2::cache_hint` 留存提示读取。这里需要把实测结果与模型推断分清：在 `decode 1` 单核内，`54.7 MB` 权重流约为 `60 MiB` L2 的 `87%`，单靠纯 LRU 模型并不能证明 `x_2` 一定被换出，且该核内的真实 L2 命中率与具体驱逐机理未测；这里有据可查的实测事实是阶段 A 去掉 `evict_first` 会变慢 **+2.44 µs**（详见第 8 章第 2 节）。付出的代价是：若在普通加载指令上使用 `createpolicy` 构造 64 位策略描述符，每条加载路径需多占 2 个 32 位寄存器（或直接传入 64 位字面量常数 `0x12F0000000000000` 省掉 `createpolicy`；且绝不可将 `createpolicy + L2::cache_hint` 强加在下一章第 3 节的逐线程异步拷贝指令上，否则会触发硬件非法指令故障）。

反过来，如果预取时机太早，预取进 L2 的数据会在用上之前被冲刷掉，反而变慢。在阶段 2 分页注意力（`decode 1/16/32 full`）中，曾尝试在 `griddepcontrol.wait`（PDL 等待点）之前由单线程提前发出异步块预取指令（机制见第 3 章第 3 节），试图把页表行预先拉进 `60 MiB` L2。结果 H200 实测不仅耗时变慢 **+0.03..+0.53 µs**，全卡 HBM 读取量还反常增加了 **+4.3 MB**（`decode 16 full`）与 **+8.5 MB**（`decode 32 full`）。原因在于过早预取进 L2 的页表缓存行在真正被消费前，就被中间流过的数 MB 键值缓存数据冲出了 L2，等到主循环真正使用时又不得不从 HBM 重读第二次（参见第 3 章第 4 节图 3-8 模式 2 的读数对比）。

## 4. 跨 SM 经中央 L2 交接部分和的四种原语：最后到达者 `acq_rel`、票据切片归约、零 CTA 单调标志与无返回值 `red.global.add.v4`

当 Split-K 的多个 CTA 在不同 SM 上算出了同一输出行的部分和，怎样不启动第二个 kernel 就把它们安全合并起来？**GPU 上各个 SM 的私有 L1 缓存之间硬件不会自动保持一致，普通写入也不保证跨地址到达顺序。因此跨任意 SM 合并部分和必须走全卡唯一的一致点（中央 60 MiB 的 L2 缓存）；而这四种原语的演进，就是在保证数据可见的前提下，一步步去掉最后 1 个 CTA 的串行读回、全局部分和工作区以及末尾的内存栅栏。**

同一个 **cluster**（线程块集群，即同一 GPC 内最多 8 个可移植或 16 个非可移植 CTA 组成的硬件编组）内的 CTA 可以直接互写片上共享内存（见第 7 章第 6 节）。但一般 Split-K 与 K-halves 的各切分块由任意空闲 SM 接手，不保证在同一个 cluster 内，因此跨任意 SM 汇总必须经过中央 **L2 cache**（所有 SM 看到同一份数据的位置）。本节集中讲透跨 SM 经中央 L2 归约的四种原语（硬件二维块原子加见第 5 章第 4 节，注意力专属的按指数重缩放合并见第 7 章第 6 节）。

**原语一：最后到达者 `acq_rel` 串行归约（适用于标量或小分片，如图 2-8 的 K-halves）**。

前半块（SM A，列 `0..4095`，读 `8 KiB` `W` 与 `8 KiB` `x`）和后半块（SM B，列 `4096..8191`）各自在寄存器里算出标量部分和 `sum`（FP32，`4 B`）。每个半块先把 `partial[half_id * M + row] = sum` 写到全局内存，再对 L2 里的计数器 `done_cnt[row]`（`int32`，`4 B`）执行原子加 1。拿到旧值 `1` 的后到者负责算出 `y[row] = partial[row] + partial[M + row]` 写回 HBM 交给阶段 2 注意力，最后把 `done_cnt[row]` 复位为 `0`。

为什么计数器必须指定 **device**（全卡作用域）的 **release / acquire**（释放/获取）内存序，不能只用 `relaxed`？因为各 SM 的私有 L1 缓存之间不自动同步，普通写入也不保证跨地址顺序：计数器 `done_cnt[row]` 的更新可能比 `partial` 先到达 L2，后到半块的普通读取也可能命中本 SM 私有的旧缓存行。因此跨 SM 交接必须合成一个带 `acq_rel` 的原子加法：

```cuda
#include <cuda/atomic>
// 每个半块块内归约后，0 号线程写出本半块部分和，并以 device 级 acq_rel 递增计数器
__syncthreads();
if (threadIdx.x == 0) {
    partial[half_id * M + row] = sum;
    cuda::atomic_ref<int, cuda::thread_scope_device> cnt(done_cnt[row]);
    if (cnt.fetch_add(1, cuda::memory_order_acq_rel) == 1) {
        y[row] = partial[row] + partial[M + row];
        cnt.store(0, cuda::memory_order_relaxed); // 复位供下一次 CUDA Graph 重放
    }
}
```

图 2-8 画出了最坏到达顺序下的交接时间线。如果选“只用 relaxed（不指定内存序）”，没有栅栏等待，B 侧交接链是 `506（H200 实测）+ 54.4 = 560.4` 个周期，在最坏到达顺序下 B 会读到旧的部分和，导致 `y[r]` 算错（实际硬件上不加内存序出错的频率未测）。切到“device 级 acq_rel”（读数为：`acq_rel：每次原子加 5 条 SASS（含 MEMBAR.ALL.GPU、CCTL.IVALL）`，反汇编观察到与 `atom.acq_rel.gpu` 一致的 5 条指令序列），其中 `MEMBAR.ALL.GPU` 把当前线程此前的写入排空到 L2 并等确认（全卡栅栏 `fence.acq_rel.gpu` 空载实测 `269.0` 个周期，带 1 条未决写入时升至 `475` 个周期）；`CCTL.IVALL` 则在获取后将本 SM 的私有 L1 整块置为无效（指令本身仅多约 3 个周期，但后续重读原本驻留在 L1 的 `16 KiB` `x` 会退化为从 L2 重填，耗时从 `319.8` 个周期涨到 `596.6` 个周期，多付约 277 个周期）。按 `1.98 GHz` SM 自旋时钟换算，B 侧带未决写入的 `acq_rel` 原子加（`1,078` 个周期，约 `0.54 µs`）加上从 L2 近端命中读取 `partial[row]`（`327.8` 个周期，约 `0.166–0.182 µs`），合计 **1,405.8 个周期**（约 **0.71–0.78 µs**），与独立测得的 256 次写入加 `release / acquire` 跨 SM 交接中位数（**0.67 µs**）同量级。

**原语二：票据并行切片归约（Ticket Parallel Slice Reduction）**。

第一种原语在标量或小分片上很直接（`gemv v3` 省 **10.62 µs**，阶段 6 `M = 1` 上/下投影省 **1.12 / 0.86 µs**，见图 2-9 模式 1）。但到了大瓦片下就会遇到单 CTA 串行读回瓶颈：比如第 1 章末尾的 `g1a` 里，`qkv_gate` 在 `T = 128 / 256` 下全卡部分和总计约 `1 MB`，由最后到达的 **1 个 CTA 独自串行读回 1 MB 部分和**（单 CTA 串行读 `1 MB` 的单独耗时未测）。

票据并行切片归约（图 2-9 模式 2）的做法是不让前 `SPLIT - 1` 个到达的 CTA 直接退场。每个切分块 CTA 先把自己算出的瓦片部分和 `part[s, :, :]` 写入全局工作区，通过原子票据登记到达次序 `t`。随后每个 CTA 只负责归约该输出瓦片的第 `t` 个 **`1 / SPLIT` 行切片** `Y[rows_t, cols] = Σ_{s=0..SPLIT-1} part[s, rows_t, cols]`（`SPLIT = 3` 时，每个 CTA 只归约读取 `1 / 3` 即约 `0.33 MB`）。把归约读取分摊给全部 `SPLIT` 个 CTA 之后，配合第 1 节的网格扩充，在 `qkv_gate` `T = 128 / 256` 上省下了 **2.78–2.86 µs** 与 **7.50–7.89 µs**（其中归约并行化本身贡献约 `0.8–1.6 µs`）。

**原语三与原语四：清零 CTA + 永不复位单调标志 + 无返回值向量原子加 `red.global.add`**。

票据切片归约还是要先写部分和工作区、发 `MEMBAR.ALL.GPU` 排空、取 `acq_rel` 票据读回相加、最后把计数器清零。这一整套串行收尾步骤要花 `1.05–1.15 µs`（其中票据栅栏占 `0.71–0.82 µs`，读写与清零占 `0.23–0.33 µs`）。能不能连部分和工作区和末尾 `MEMBAR` 也省掉？

这就是第三种与第四种原语（图 2-9 模式 3）。以阶段 4 的 `router` 矩阵乘（`T = 8 / 16 / 32`，及第 2 节的 `T = 128 / 256`）为主例，它分三步走：

1. **清零 CTA 写零并释放单调标志**：专职清零 CTA（按第 2 节规则排在 `program_id 0..3`）先把输出瓦片 `out [T, 256]`（FP32）清零，再对 L2 里**永不复位**的单调计数器 `flag[tile]`（`uint32`，`4 B`）执行一次 `red.release.gpu.add.u32(+1)`。
2. **主循环前预领轮次票据**：每个计算 CTA 在**进入 K 主循环之前**，先用 `atom.relaxed.gpu.add` 领一张单调递增的调用轮次票据 `epoch = ticket / SPLIT + 1`，让原子往返与主循环重叠。
3. **尾声单次获取并直发无返回值原子加**：主循环算出寄存器累加器 `acc`（FP32）后，只需执行 1 次 `ld.acquire.gpu(flag[tile]) == epoch` 确认输出瓦片已由清零 CTA 写零，随后直接向中央 L2 硬件原子加法器发出**无返回值的全局原子加** `red.global.add.f32 / .v4.f32`，把 `acc` 原地加进 `out`。

因为 `red.global.add` 不等返回值，也不需要部分和工作区、计数器复位或末尾 `MEMBAR`，它直接砍掉了那 `1.05–1.15 µs` 的归约尾，在 `router` 的 `T = 8 / 16 / 32` 上分别省下 **0.88 / 1.07 / 0.98 µs**，在 `T = 128 / 256` 上分别省下 **1.22 / 1.72 µs**。同理，阶段 2 注意力在 `verify 16/32 full` 下用 4 个单精度打包发 1 条无返回值向量原子加 `red.global.add.v4.f32` 直写 L2、核尾按行协作归一，删掉独立合并核后省下 **1.68–2.98 µs**（`red.v4` 比 `red.v2` 快 `1.2–2.6 µs`；见第 7 章第 6 节）。代价是需额外派发 4 个专职清零 CTA（必须排在网格最前防死锁），且 `red.global.add` 在 L2 内的跨 CTA 累加顺序不固定（在 `router` 上何时反输未测；而在阶段 2 单请求 `decode 1` 下，256 个 CTA 争写单行会反慢 **+2.96 µs**，假说为 L2 原子串行化）。

用中央 L2 原子操作与写零时，有三个实测变慢的反例需要避开：

1. **对 BF16 输出直接发标量原子加（图 2-9 模式 4）**：在阶段 1 与阶段 5（`decode T = 1..32` 的 12 位 Split-K 内核）中，曾尝试省掉 FP32 输出转换，直接对 BF16 输出张量执行标量原子加 `atom.add.noftz.bf16`。反汇编显示，编译器（见第 6 章第 1 节）在底层将其降级为 **17 处比较并交换重试循环（`ATOMG.E.CAS.STRONG.GPU`）**，全核产生 `18,634` 次原子请求、`77,582` 个扇区，使 DRAM 利用率从 `46.7%` 降至 **`16.3%`**。结果 `qkv_gate` 在 `T = 16 / 32` 上从 `11.36 / 12.03 µs` 升至 **`24.10 / 35.87 µs`（慢 `+12.74 / +23.84 µs`）**，`pooler` 在 `T = 16 / 32` 上从 `16.51 / 17.02 µs` 升至 **`29.63 / 41.38 µs`（慢 `+13.12 / +24.36 µs`；`pooler` 在 `T = 1 / 8` 上也从 `15.71 / 16.35 µs` 慢至 `17.68 / 21.25 µs`）**。因此向 L2 发浮点数原子加，必须使用 32 位/128 位 `red.global.add.f32 / .v4.f32`、`red.add.noftz.bf16x2` 成对打包指令，或第 5 章第 4 节的硬件二维块原子加。
2. **不用独立清零 CTA，改在计算 CTA 入口、第 0 分片或生产者 warp 里发全局写零**：在 `qkv_gate` 与 `pooler`（`verify 16 / 32`，`T = 128 / 256`）上，曾尝试省掉专职清零 CTA，改由第 0 号切分块（或拆散到各块入口、或由生产者 warp）在内核入口先把输出瓦片写零。实测证明，在入口发出的全局写零（`SM → L2`）会抢在第一批权重读取请求之前塞进显存队列，把每个 CTA 的启动斜坡拉长 `0.25 µs`（8 KB）、`0.55–0.66 µs`（16 KB）至 `1.03 µs`（64 KB），推迟首块权重到达时间并让负责写零的 CTA 停顿 `2–3 µs`（把写零平摊给多个 CTA 也只是移动了排队成本），在 `qkv_gate` 与 `pooler`（`T = 128`）上实测反慢 **+0.42..+0.69 µs** 与 **+0.38..+0.69 µs** 被否决。
3. **全 CTA 512 个线程同时向同一计数器发 `red.release.gpu`（见第 8 章第 4 节）**：即便使用无返回值的 `red.release.gpu`，如果每个 CTA 的全部 512 个线程（而非每线程束选 1 个代表线程或单通道释放）同时向 L2 计数器发射原子释放，在阶段 6 大批量专家核（`verify 32`）上实测会因 L2 原子串行化造成 **+93.3 µs** 的严重停顿。

## 5. `qkv_gate` 双轨演化（第 1 级）：`gemv`（v2 → v3 → v4）与 `qkv_gemm`（g1a → g1，108 CTA + 票据归约）

把本章第 1 级的波次切分和 L2 归约放回 `qkv_gate` 的两条演化轨道上：**在 `T = 1` 的 `gemv` 轨道上，用 K-halves 把第二轮尾波的 192 行对半切开，省掉 `10.62 µs` 的尾波等待；在 `T = 128 / 256` 的 `qkv_gemm` 轨道上，用 108 个 CTA 的非整除 Split-K 加上票据并行切片归约，把第 1 章末尾 `g1a` 因 60 个 SM 闲置和单 CTA 串行读回丢掉的 `2.73 / 7.94 µs` 拿了回来。**

### 轨道一（`T = 1`）：`gemv v2 → v3 → v4`（K-halves 切尾波与 L2 缓存留存提示）

按第 3 章的驻留规则，**v2**（`<<<2304, 128>>>`）每 SM 驻留 16 个 CTA，全卡单轮容量为 2,112 个 CTA，第二轮留下 `r = 192` 个尾波 CTA。由于 `192 ≤ 2,112 ÷ 2` 满足第 1 节“余数不超过单轮容量一半”的切半条件，**v3** 把最后 192 行拆成 384 个半行 `K/2` 的 CTA（共启动 `2,112 + 384 = 2,496` 个 CTA，每线程寄存器从 22 增至 23 个，每 CTA 仍占 512 B SMEM，每 SM 驻留 16 个 CTA）。两半按第 4 节的原语一（L2 `acq_rel` 原子计数）由后到者合并写回。

图 2-10 用单个尾波 CTA 的串行往返链来估算切半收益。每个尾波 CTA 只有 `128 × 2 B = 256` 字节在途，算完一整行要走 `8,192 ÷ 128 = 64` 次串行往返。按空载单次 `0.334 µs`（`600.2` 个周期 ÷ `1.7964 GHz`）估算，不切半时一个 CTA 走 64 轮约 `21.4 µs`；切半后两个 CTA 各走 32 轮加 L2 合并（图 2-10 模型按两次 L2 近端命中每次 `0.182 µs` 加 `0.15 µs` 错开估算）约 `11.2 µs`，单 CTA 链模型估算省约 `10.2 µs`。整个 kernel 的实测耗时从 `v1` 的 `58.88 µs` 降到 `v3` 的 **48.26 µs**（`1.22×`，约为 `7.86 µs` 下界的 `16.3%`）。实测节省的 **10.62 µs** 大于简单按半轮波次比例的预测（整个 kernel 层面的精确拆解未单独测量），与图 2-10 的单 CTA 串行往返模型同量级。

接着 **v4** 用 `createpolicy` 为中央 L2 加上留存提示（`.L1::evict_first` 与 `.L1::evict_last` 同时提示本 SM 的 L1，每线程寄存器从 23 增至 27 个，全核执行指令从 `7.41 M` 增至 `11.12 M`）。权重 `W` 每字节只读 1 次，标为 **`evict_first`**（读完优先淘汰）；向量 `x`（16 KiB）被重复读取，标为 **`evict_last`**（优先留在缓存）。

```cuda
// v4：用 createpolicy 生成 L2 策略描述符，W 标 evict_first，x 标 evict_last
asm volatile("createpolicy.fractional.L2::evict_first.b64 %0, 1.0;\n"
             "ld.global.L1::evict_first.L2::cache_hint.b16 %1, [%2], %0;" : "=&l"(pW), "=h"(w) : "l"(Wp));
asm volatile("createpolicy.fractional.L2::evict_last.b64 %0, 1.0;\n"
             "ld.global.L1::evict_last.L2::cache_hint.b16 %1, [%2], %0;" : "=&l"(pX), "=h"(xv) : "l"(xp));
```

在写 512 MiB 清空 L2 的冷缓存测试下，H200 实测 `v3 → v4` 从 `48.26 µs` 变为 **43.94 µs**（`1.10×`，约为 `7.86 µs` 下界的 `17.9%`）。但对照实验表明，这一 `1.10×` 并非来自 `x` 的命中率提升（有无提示下 `x` 在 L2 均为 100% 命中，且在途量仍为 `4.0 KiB/SM`），而是**在该测试中由写 512 MiB 脏行清缓存带来的测法假象**。当改用**读取** 512 MiB 干净清空 L2 时，`v3` 为 `42.88 µs`、`v4` 为 `43.49 µs`，提速消失（推断原因是未加 `evict_first` 的 `W` 挤出 L2 脏行时触发了回写竞争，这一脏冲刷假象同样把普通读取的 v0–v3 冷缓存耗时相对 v4+ 垫高了约 `4–6 µs`；在真实多层推理中前序 kernel 写出的脏 L2 下该提示是否有益，本实验未测量）。而在不清空缓存的热缓存重复测试中，`W`（37.7 MB）本可装进 60 MiB L2，`v3 → v4` 的热缓存耗时从 `29.02 µs` 退化到 `42.88 µs`（推断原因是 `evict_first` 阻止了 `W` 在跨迭代间留存于 L2）。

### 轨道二（`T = 8..256`）：`qkv_gemm g1a → g1`（非整除 Split-K 扩至 108 CTA + 票据切片并行归约）

在第 1 章末尾，单核化的 **g1a** 在 `T = 128 / 256` 上因为只启动了 `36 × 2 = 72` 个 CTA（让 132 个 SM 中的 60 个闲置），而且由最后到达的 1 个 CTA 串行读回 `1 MB` 部分和，导致在 `T = 128` 上跑出 `21.57 µs`、在 `T = 256` 上慢至 `33.39 µs`（比 cuBLAS 的 `22.90 µs` 慢了 `10.50 µs`）。

本章第 1 级的 **g1** 将第 1 节的**非整除 Split-K（`SPLIT = 3`）**与第 4 节的原语二（**票据并行切片归约**）同时合入 `T = 128`（分块 `128 × 64`）与 `T = 256`（分块 `256 × 64`）。两档网格均从 72 个 CTA 扩为 `1 × 36 × 3 =` **108 个 CTA**（空闲 SM 从 60 个压至 24 个），并让每个到达的切分 CTA 各认领 `1 / 3` 的瓦片行并行归约（`T = 8 / 32` 保持与 `g1a` 相同的内核）。H200 实测对照如下：

小结一下第 1 级整卡视角：每个 SM 需要在路上同时挂起约 64 KiB 的普通在途读取，才能跑满 4.54 TB/s 的 HBM 稳态带宽。把波次切分和 L2 同步原语落到 `qkv_gate` 的两条演化轨道上，`gemv v3` 用 K-halves 把耗时从 `58.88 µs` 压到 **48.26 µs**，`qkv_gemm g1` 用 108-CTA 非整除 Split-K 加票据并行归约在 `T = 128 / 256` 上追回了 **2.73 / 7.94 µs**（`T = 128` 反超 cuBLAS，而 `T = 256` 仍比 cuBLAS 慢 `2.56 µs`）。接下来我们把图 2-1 里的 1 个 SM 小方块拆开，进入第 3 章的第 2 级（单个 SM）：看看它的四项固定容量上限怎样决定驻留与寄存器分配，全局向量读取与二维矩阵分块又各自通过什么硬件通路搬进片上环形缓冲与 32 个存储体。
