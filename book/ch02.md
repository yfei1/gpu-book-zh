# 第 2 章 [第 2 级]：整张 H200 芯片——2,304 个 CTA 派满了 132 个 SM，时间还花在哪里？

**本书地图：** 前言 → 导引一 → 导引二 → 导引三 → 第 1 章 [第 1 级] → **【第 2 章 [第 2 级]】** → 第 3 章 [第 3 级] → 第 4 章 [第 4 级] → 第 5 章 [第 5 级] → 第 6 章 [第 6 级] → 第 7–9 章 → 第 10 章 → 附录

在第 1 章里，我们压掉了 kernel 之间的空隙，但单个 `gemv_kernel` 自己的耗时一点没变。现在我们点开这个 kernel，把视野放大到第 2 级：整张 H200 芯片。

**`v1` 的 2,304 个 CTA 明明已经派满了全部 132 个 SM，`gemv` 却要跑 54.08 µs，而从显存读一遍 $W$ 的下界只需 7.86 µs——站在整张芯片这一级看，多出来的时间到底花在了哪里？**

这一章我们顺着 `v1 / v2` 的 `gemv_kernel` 往下查：权重是 $\shape{W}{2304,\ 8192}{BF16}$，输入是 $\shape{x}{8192}{BF16}$，输出是 $\shape{y}{2304}{FP32}$，启动配置为 `<<<2304, 128>>>`。

## 1. CTA 怎样分到 132 个 SM 上？最后一批为什么拖住整个 kernel？

**整张卡一次最多只能同时装下 2,112 个 CTA；多出来的 192 个 CTA 必须等空位腾出来，再从头走完 64 轮串行读取。**

<!-- FIG ch02-a: 图 2-1 上方芯片画 132 个 SM（每个 SM 方块含 16 个驻留位置）、中央 L2 带与两侧 HBM；算法带画 W 的行块按观察到的 blockIdx.x 升序派发推断流向 SM，最后 192 行标成尾波颜色；下方时间线画每个 CTA 一条 64 格的串行读取链，第 1 个 wave 2,112 个位置全满，第 2 个 wave 只有 192 个位置在算（r = 192）。读数：wave 容量 2,112、尾波 192、在用比例约 9%。步骤卡：第 1 步 派发 2,112 个 CTA（每个 CTA：$y[\text{row}] = \sum_k W[\text{row},k]x_k$，输入 W 一行 16 KiB 在 HBM、x 16 KiB；代价：每 CTA 64 轮往返）；第 2 步 第一批退出、尾波 192 个派上 SM；第 3 步 尾波走完 64 轮（代价：全卡约 9% 的位置在用）。 -->

GPU 硬件以 CTA 为单位把活派到 132 个 SM 上（见导引三第 1 节）。但每个 SM 同时能驻留的 CTA 数是有上限的，在 `v1` 里这个上限是 16 个（为什么是 16 个，我们留到第 3 章第 1 节再算）。把全卡 132 个 SM 加起来，整张卡同一时刻最多只能驻留 $132 \times 16 = 2{,}112$ 个 CTA。

我们把**全卡一次能同时驻留的 CTA 数**称作 1 个 **wave**（波次）。不过要注意，wave 指的是同一时刻片上能装下的容量，而不是“上一批必须齐步跑完才换下一批”：只要某一个 CTA 跑完退出，它腾出来的位置马上就会由下一个排队待派的 CTA 补上。

现在把 `v1` 的 2,304 个 CTA 往 2,112 的全卡容量里装，刚好是 $2{,}304 = 2{,}112 + 192$。第一批 2,112 个 CTA 一起进场开跑；因为 `v1` 里每个 CTA 的工作量一模一样，这 2,112 个 CTA 几乎在同一时刻跑完退出；多出来的 192 个 CTA 这时候才补进空位开始算。最后这一小撮不满 1 个 wave 的 CTA 就叫 **tail**（尾波），余数记作 $r = 192$（图 2-1）。

为什么尾波这区区 192 个 CTA 会把整个 kernel 的耗时拉长将近一倍？我们拆开单个 CTA 的内部循环来看：128 个线程每轮各读 1 个 $W$ 元素，扫完一行 8,192 列一共要走 $8{,}192 / 128 = 64$ 轮。关键在于，每一轮都必须死等上一轮读的数据回来，才能迈进下一轮。这是因为单个线程的指令是按顺序发射的：在 `v1` 编译出来的循环里，下一轮的读取指令排在这一轮的乘加指令后面，而乘加指令又必须等这一轮的数据从显存回来才能执行。结果每个线程同一时刻在路上只有 1 个 $W$ 读取（指令按顺序发射的机制见第 4 章第 2 节）。

CPU 核遇到这种等待时，会靠乱序执行和硬件预取把它藏起来。但 GPU 的每个 warp 严格按顺序发射，不会越过卡住的指令去提前发后面的读取；一个 warp 在等数据时，SM 就切去发别的 warp 的读取。至于 H200 有没有硬件预取，我们没有测。我们要让每个 SM 同时挂起更多读取，靠的是直接改代码：要么在 SM 上多驻留线程（见第 3 章），要么让每个线程一次连发好几条读取（见第 4 章）。

这样退回整张芯片一看，`v1` 的总耗时就像两条首尾相接的 64 轮串行读取链：第 1 个 wave 的 2,112 个 CTA 先走完第一条 64 轮的链，尾波那 192 个 CTA 紧接着又得从头走一条一模一样的 64 轮链。整个尾波期间，全卡 2,112 个驻留位置里只用上了 192 个（约 **9%**），剩下九成位置全在空转，可整个 kernel 偏偏得等这最后 192 个 CTA 走完 64 轮才能收工。

那到底是哪 192 个 CTA 留在了尾波里？CUDA 规范本身不规定 CTA 的派发先后。但在 H200 上，我们给第 8 章一个由 PDL 衔接的 132-CTA kernel 打上全局纳秒时间戳后观察到：编号最大的 131 号 CTA 比前 100 号（编号小于 100）晚约 2.0–3.2 µs 才进场，走势与按 `blockIdx.x` 从小到大依次派发一致。照此往 `v1` 外推，留在尾波里的就是编号最大的那 192 个 CTA（这一点我们没有直接测过）。不过 `v3` 的计算结果对错并不仰仗这一派发顺序，顺序只影响它能快多少。

## 2. 一次读取从 HBM 回到 SM 要多久？$x$ 为什么不用从 HBM 读 2,304 遍？

**空载读一趟 HBM 往返约 0.33 µs，命中全卡共用的二级缓存约 0.18–0.23 µs；$W$ 每次从 HBM 流式读入，$x$ 则留在缓存里反复复用。**

<!-- FIG ch02-mem: 图 2-2 H200 四层存储位置关系图：片外 HBM（标称 4.8 TB/s，空载往返 0.33 µs）→ 全卡共享的 L2（60 MiB，近的一半命中往返约 0.18 µs，远的一半约 0.23 µs）→ SM 内的 L1 / 共享内存与寄存器（容量见第 3 章）。动画标出：W 元素从 HBM 经 L2 到 SM（红圈①），x 第一次从 HBM 进 L2（②），之后各 CTA 读 x 在本 SM 的 L1 或 L2 命中（③）。步骤卡：第 1 步 读 W[row,k]（输入：BF16，2 B，在 HBM；代价：约 0.33 µs 往返）；第 2 步 读 x[k]（第一次来自 HBM，以后来自 L1 或 L2；L2 近半命中约 0.18 µs）；第 3 步 乘加进寄存器 acc（输出 FP32，留在寄存器，交给块内归约）。总代价：每轮约一次 HBM 往返。 -->

图 2-2 画出了数据从片外一路进到计算单元的存储通路。最外层是片外的 HBM（高带宽显存，标称带宽 4.8 TB/s，见导引一第 4 节），往芯片里面走一步是 132 个 SM 共用的片上 **L2 cache**（二级缓存，总容量 60 MiB），再进到每个 SM 内部，则是 **L1 cache**（每个 SM 私有的一级缓存）、共享内存与寄存器（它们的容量和细节留到第 3 章第 1 节再展开）。

一条默认的全局内存读取指令发出去后，会先查本 SM 的 L1；L1 里没有，再去查全卡共用的 L2。如果数据已经在 L2 里（叫作**命中**），L2 就直接把数据交回 SM；如果连 L2 里也没有（叫作**未命中**），请求才会出片去 HBM 把数据取回来，穿过 L2 送进 SM。这一节我们先盯住最外面的 L2 和 HBM 两层；记住 L2 是整张 GPU 上唯一由所有 SM 共用的缓存，第 6 节做跨 SM 合并时还会靠它牵线。

要量出从发出读取到数据回到寄存器的**往返**时间，我们先定一个硬件时间单位：**周期**（clock cycle），也就是 SM 时钟跳一拍的时间。在空载情况下，从 HBM 读一趟往返大约要 600 个周期；如果在 L2 命中，数据在离本 SM 近的那一半 L2 时约 328 个周期，在远的那一半时约 414 个周期。我们统一按约 1.8 GHz（1 个周期约 0.56 ns）把周期折算成时间，对应大约 **0.33 µs** 和 **0.18 µs**（远半边 L2 约 0.23 µs，见下图）。


有了这组数字，导引三留下的两个问题就迎刃而解了。第一，在单次 kernel 执行中，权重矩阵 $W$（37.75 MB）的每个元素只由一个 CTA 读取一次，因此在 L2 中不会命中。而在真实推理时，下一次再读同一份 $W$ 要到下一趟前向传播；两趟之间会有约 9.0 GB 的固定权重（见导引一第 4 节）流经 60 MiB 的 L2，老早便将上一趟留下的 $W$ 冲刷出去，因此计时前先冲刷片上缓存正好贴合真实运行（见导引三第 5 节）。

第二，输入向量 $x$ 只有 16 KiB，跟 60 MiB 的 L2 比起来连零头都不到。光按容量就能推断：第一批 CTA 第一次读 $x$ 时把它从 HBM 拉进 L2 之后，同一个 SM 上的后续 CTA 再读 $x$ 时多半直接在本 SM 的 L1 命中，就算没命中 L1 也会在 L2 命中（我们在 `v1` 上没有实测 L1 和 L2 的命中率）。

现在把这笔延迟账代回第 1 节的串行读取链。在 `v1` 的每一轮循环里，每个线程同时发出一条 $W$ 读取（去 HBM）和一条 $x$ 读取（在 L1 或 L2 命中），因此每一轮等数据的时间基本就等于一次 HBM 往返。按 0.33 µs 的空载往返粗算，跑完一条 64 轮的串行读取链大约要花 $64 \times 0.33 \approx 21\ \mu\text{s}$，第 8 节估算尾波时长时就会拿这个数当参照。前后两条链加起来约 42 µs，再算上 4.6 µs 固定开销就是约 47 µs，比 `v1` 实测的 54.08 µs 少约 7 µs。这个粗模型只用来抓数量级，剩下的差值来自哪里我们没有拆开测。

## 3. 每个 SM 要同时挂起多少字节，才能跑满 HBM？

**全卡一起读时，往返时间会随在途字节增加而拉长；每个 SM 至少要挂起约 64 KiB 才能摸到带宽平台，而 `v1` 只挂起了 4.0 KiB。**

<!-- FIG ch02-b: 图 2-3 上方算法带把微基准里 1 个 CTA 挂起的 16 KiB（等于 W 的 1 行）作为 1 个在途单元，标出已完成、在途与等待中的单元；中间画每个 16 KiB 单元从 HBM 经 L2 流向 1 个 SM；下方画往返时间线与全卡实测带宽随每 SM 在途字节变化的曲线，曲线上标出 v1（4.0 KiB/SM）与拐点 64 KiB。读数：每 SM 在途 KiB、全卡带宽、往返时间。步骤卡：第 1 步 一个 SM 放 1 个 CTA（在途 16 KiB；代价：往返约 0.94 µs，单 CTA 读时约 0.82 µs）；第 2 步 放 4 个 CTA（64 KiB；往返约 1.9 µs；全卡约 4.49 TB/s）；第 3 步 v1：4.0 KiB（代价：HBM 大部分时间空闲）。 -->

SM 已经发出读取请求、但数据还在路上没回来的字节数，叫作 **bytes in flight**（在途字节）。在途字节、带宽与往返时间三者的关系，可以用 **Little's Law**（利特尔法则）写出：

$$\text{在途字节} = \text{带宽} \times \text{往返时间}$$

换句话说，要想让一个 SM 吃满它分到的那份显存带宽，它在路上同时挂起的字节数就必须足以填满一趟往返时间。

我们先算算目标有多高。当全卡 132 个 SM 一起持续流式读取 HBM 时，实测能摸到的**带宽平台**（再往路上塞更多在途字节、带宽也不再往上涨的平坦区）约为 **4.54 TB/s**，平摊到每个 SM 大约是 **34 GB/s**。如果直接拿第 2 节测出的 0.33 µs 空载往返往公式里代，看起来每个 SM 只要在路上挂起 $34\ \text{GB/s} \times 0.33\ \mu\text{s} \approx 11\ \text{KiB}$ 就够了。

可真全卡一起读起来并不是这么回事。我们专门跑了一个带宽扫描微基准（不是 `gemv`）：让 132 个 SM 持续读 HBM，每个 SM 上放 1–6 个 CTA，每个 CTA 用 16 B 读取（见第 3 章第 8 节）始终在路上挂着 16 KiB（正好等于 1 行 $W$ 的字节数），也就是每个 SM 同时挂起 16–96 KiB。结果每个 SM 只挂 16 KiB 时，全卡实测带宽离平台还差一大截（见下图），按利特尔法则反推出来的平均往返已经到了约 0.94 µs，比空载的 0.33 µs 长得多。哪怕全卡只放 1 个 CTA 读，往返也要约 0.82 µs；多出来的这段时间花在了哪里，我们没有测。

顺着图表往右看：直到每个 SM 同时挂起 **64 KiB**（4 个 CTA，相当于 4 行 $W$ 的字节数），全卡带宽才真正爬到拐点，再往右就稳在约 4.54 TB/s 的平台上了。**64 KiB 就是实测出来的拐点**；上了平台之后再多挂在途字节，带宽不会再涨，按 $\text{往返时间} = \text{在途字节} \div \text{带宽}$ 算出来的往返时间只会白白变长。就在 64 KiB 这个拐点上，按利特尔法则算出的平均往返已经涨到了约 **1.9 µs**，足足是空载时的约 6 倍。多出来的时间花在通路的哪一段我们没有测，常见的解释是请求在路上排队。

拿这个 64 KiB 的拐点一对照，`v1` 跑得慢的第二个病根就彻底暴露了。在 `v1` 里，每个线程每一轮只有 1 个 2 B 的 $W$ 读取在路上，1 个 CTA（128 个线程）加起来在途只有 $128 \times 2\ \text{B} = 256\ \text{B}$，就算把 1 个 SM 上的 16 个 CTA 全算上，一共也才 **4.0 KiB**（图 2-3）。这点在途量连图表最左边的 16 KiB 那一档都没够着，离 64 KiB 的拐点更是差了整整 16 倍。

把第 1 节和这一节放在一起看：第 1 节算的是串行读取链有多长，这一节算的是每一轮到底能让 HBM 忙起来多少。因为 `v1` 每个 SM 只挂起 4.0 KiB，离带宽平台远得很，全卡的显存读取负载其实很轻，所以第 2 节的粗模型才能直接拿接近空载的往返时间来估（`v1` 每一轮的实际往返时间我们没有直接测）。至于怎么把每个 SM 的在途字节从 4.0 KiB 一路推到 64 KiB，那是第 3、4 章要干的事；而在路上挂起更多字节就得拿更多寄存器或片上存储去接，第 3 章马上就来算这笔资源账。

## 4. 能不能告诉 L2 哪些数据该留下？

**能。读取时给单次数据标先淘汰、给复用数据标后淘汰，能在会被挤出时保住复用数据；不会被挤出时只添开销。**

我们在第 2 节按容量推断，16 KiB 的 $x$ 会稳稳留在 60 MiB 的 L2 里；但在 `gemv` 运行期间，还有 37.75 MB 只读一次的权重 $W$ 也要浩浩荡荡流过 L2——这股流式数据会不会把我们要复用的数据挤出去？如果不做任何干预，L2 硬件自己是没法预知哪些数据待会儿还要重读、哪些数据用过一次就扔的。一旦有大块只用一次的数据流过 L2，它就可能把后面 CTA 还要重读的热数据给顶出 L2。

要想改变这种默认行为，我们可以在发读取指令时附带一个 **L2 留存提示**（cache hint，代码写法见附录 B）：给只读一次的流式数据打上 `evict_first` 标签（告诉 L2 空间不够时先拿它开刀），给要跨 CTA 反复重读的数据打上 `evict_last` 标签（告诉 L2 尽量把它留到最后）。

这招在什么情况下管用？我们看一个专门设计的独立微基准（图 2-4）：先读入 8–32 MB 需要复用的数据（图 2-4 以 32 MB 为例），接着流式读过 64 MB 只用一次的数据——这已经超过了 L2 的 60 MiB 总容量——最后再去重读第一步那批复用数据。实测下来，如果给这两类读取分别标上 `evict_last` 和 `evict_first`，重读复用数据的带宽能达到 5.70–7.33 TB/s，相当于中间没有流式读取干扰时的 **98.8%–100%**（从这一带宽比例可以推断，要复用的数据基本都保在了 L2 里），约为冷读 HBM 的 1.7–1.9 倍。反之，若不加提示（两批读取都走默认淘汰优先级），重读带宽就会跌到 3.36–4.19 TB/s，仅比冷读 HBM（3.16–3.91 TB/s）高出 5%–7%，可见要复用的数据大都已被挤出了 L2。

算一下 L2 留存提示这笔账：

- **得到什么**：当大流量单次数据会把复用数据冲出 L2 时，帮你在 L2 里保住复用数据（实测数字见上面的微基准）。
- **付出什么**：要先构造两个留存提示（只做一次），之后每一条读取都得带上其中一个，代码写起来更繁琐。
- **什么时候亏本**：如果复用数据本来就不会被挤出 L2，多带的提示就纯属添乱。在我们的 `gemv` 上，$x$ 只有 16 KiB，本来就不会被挤出去；我们在第 8 节的 `v3` 之上试着加上这两个提示（记作 `v4`；`v4` 同时给 L1 也标了先淘汰 / 后淘汰，只加 L2 提示的变体同样变慢），实测反而慢了约 **1 µs**，所以我们不把它单独算作一步。第 3 章第 8 节的 `v5` 代码里仍带着这组提示，它们在 `v5` 里的单独作用我们没有拆开测。

## 5. 尾波只剩少数 CTA 时，怎样让更多 SM 一起算同一行？

**沿内积维把一行切几段分算再合并叫 Split-K；只把尾波的行对半切开叫 K-halves，每半行只走 32 轮。**

<!-- FIG ch02-splitk-wave: 图 2-5 gemv 尾波切分解剖图：三档对比“不切：192 个 CTA 各走 64 轮”、“K-halves：384 个半行 CTA 各走 32 轮”与“切得太碎（示意）：CTA 数超过 1 个 wave 容量，多出来的进下一个 wave，合并次数也变多”（第三档只画结构，不标耗时）。步骤卡：第 1 步 前半 CTA 算 $\sum_{k<4096}$（输入：W 半行 8 KiB 在 HBM、x 前半 8 KiB 在 L1 或 L2；输出：部分和 FP32 4 B 写全局内存）；第 2 步 后半 CTA 同理；第 3 步 合并（交给第 6 节；代价：一次跨 SM 交接）。总代价：每行多写 2 个 4 B 部分和、多一次跨 SM 合并。 -->

回到第 1 节那个痛点：尾波只剩 192 个 CTA，每个却还要老老实实走完 64 轮串行读取，而这期间全卡约九成的驻留位置都在闲着。既然一行的内积本来就是 8,192 项相加，我们完全可以顺着内积维 $K$ 把它一刀切成前后两半：

$$y[\text{row}] = \underbrace{\sum_{k=0}^{4095} W[\text{row},k]\,x_k}_{\text{前半}} + \underbrace{\sum_{k=4096}^{8191} W[\text{row},k]\,x_k}_{\text{后半}}$$

前半段和后半段互不依赖，直接派给两个 CTA 在两个不同的 SM 上同时算就行：各自算出一个**部分和**，最后再把两半加到一起。

只切尾波什么时候最划算？条件很明确：尾波余数 $r$ 不超过 1 个 wave 容量的一半（$r \le 2{,}112 / 2 = 1{,}056$）。只要满足这个条件，把 $r$ 行拆成 $2r$ 个半行 CTA 之后，这 $2r$ 个 CTA 全都能塞进尾波原本空着的位置里，绝对不会多溢出 1 个 wave。这种只把尾波的行对半切开的做法，我们叫它 **K-halves**（尾波对半切分）。在 `v1` 里，$r = 192$，对半切开后是 $2r = 384 \le 1{,}056$，正好落在甜点区。这一刀下去，每个半行 CTA 的串行读取链直接从 64 轮砍半到 **32 轮**，而且尾波期间全卡同时在路上挂起的字节数也跟着翻了一倍（从 192 个 CTA 变成 384 个 CTA，见图 2-5 第二档）。

把这个思路推广到整个 grid，就是通用的 **Split-K**：当输出行数或输出分块太少、连 1 个 wave 的容量都填不满时，干脆把内积维 $K$ 切成 $S$ 段，让 $S$ 个 CTA 合伙算同一个输出，把总 CTA 数一口气乘上 $S$（多词元矩阵乘上的 Split-K 见第 5 章第 6–7 节，演化链上的实测见第 6 章第 8 节）。

算一下 Split-K 与 K-halves 的账：

- **得到什么**：K-halves 把尾波每个 CTA 的串行链长直接砍半（从 64 轮降到 32 轮），同时让尾波期间全卡的在途字节翻倍（实测收益见第 8 节）。
- **付出什么**：每个切开的行都要写出 2 个 4 B 的部分和（共 8 B），多做一次跨 SM 合并，而且 grid 的块编号映射更复杂。在第 6 节的微基准里，一次跨 SM 交接约 0.67 µs；`v3` 里这种不等待的合并我们没有单独测。
- **什么时候亏本**：当尾波余数 $r$ 超过半个 wave，或者切得太碎、让总 CTA 数翻出 1 个 wave 容量之外时，就会亏本。我们在 `gemv` 上没有测切 4 段；但在第 8 章第 3 节的一个专家 kernel 上，切 4 段实测比切 2 段更慢。

## 6. 两个 SM 各算半行，怎样安全地加起来？

**两个半行写出部分和后各对 L2 计数器做原子加，拿到旧值 1 的后到者负责相加；两个 CTA 不必同时在片上。**

先看第一步：为什么两个 SM 交接数据非得走 L2？因为每个 SM 的 L1 缓存是它自己私有的，不同 SM 的 L1 之间硬件并不会自动保持一致；我们在第 2 节见过，L2 是整张芯片上唯一由所有 SM 共用的缓存。所以只要走这一章的全局内存访问，跨 SM 交换数据就只能在中央 L2 碰头（另一条跨 SM 通路见第 7 章第 12 节）。

第二步要解决“由谁来把两半加起来”。这里靠的是**原子加**（atomic add）：硬件把“读出旧值、加上新值、写回内存”三步捆成一次不可分割的操作，别的线程绝对插不进来，同时把加之前的旧值返回给你。两个半行 CTA 算完各自的部分和之后，分别对同一个初值为 0 的计数器（`int32`，4 B）做一次原子加 1：先到的那个（先到者）拿到旧值 0，拍拍手直接退出；后到的那个（**last arriver**，后到者）拿到旧值 1，由此得知同伴已经走完这步，于是接手把两半部分和加起来。

但只有原子加还不够。先到者在代码里明明是先写部分和 `part`、再对计数器加 1，可如果不加内存顺序约束，CUDA 内存模型根本不保证另一个 SM 会先看到 `part` 的新值、后看到计数器的新值。落在硬件上，完全可能是计数器的更新比 `part` 先一步到了 L2，或者后到者直接从自己 SM 的 L1 里读到了过期的旧数据。

在看代码之前，我们先用大白话把三种内存顺序定清楚：

- **relaxed**：只保证这一次原子操作本身不可分割，完全不管它前后的其他读写按什么顺序发生。
- **release**（释放）：把本线程此前的读写全部排在这次写之前；只要作用范围（见下文）盖住收发双方，此前的写入对任何通过 acquire 读到这次写的线程都必定可见。
- **acquire**（获取）：保证本线程此后的读和写，绝不会跑到这次读之前去执行。

把 release 和 acquire 合二为一，就叫 `acq_rel`。此外，GPU 上的每一次同步还必须带一个**作用范围**（scope，比如 CTA 内部、全卡 `device` 或整个系统）。作用范围越小硬件代价越低，所以我们通常只写刚好盖住通信双方的最小范围（如果不写，CUDA C++ 的原子类型默认是整个系统范围）。在这里，两个半行 CTA 可能被派到全卡任意两个 SM 上，因此作用范围至少要是 `device`（全卡范围，在 CUDA C++ 里写作 `thread_scope_device`）。

<!-- FIG ch02-c: 图 2-6 上方画 SM A、SM B 各自的私有 L1 与中央共享的 L2（含计数器 cnt[i] 和两格 part）；下方两档时间线对比“只用 relaxed：后到者可能读到旧的部分和”与“acq_rel：release 把写推到 L2，acquire 作废本 SM 的 L1 后从 L2 读到新值”（硬件上的表现即 L1 作废是观察，不是规范保证）。步骤卡：第 1 步 SM A 写 part[2i]（FP32 4 B → 全局内存）；第 2 步 SM A fetch_add(acq_rel) 得 0，退出（代价：1,078 周期）；第 3 步 SM B 写 part[2i+1]，fetch_add 得 1；第 4 步 SM B 读两格相加写 y[row]（FP32 4 B），计数器复位（relaxed）。总代价：两次 acq_rel 原子加（带等待的交接微基准约 0.67 µs）；L1 被作废后重读 x 变慢（在一条 acq_rel 栅栏之后测）。 -->

这一点上，GPU 和我们熟悉的 CPU 脾气完全不同。x86 的 TSO 内存模型只允许一种乱序：先写后读。当一个核先写 A、紧接着读 B 时，这笔读可能会在写 A 对其他核可见之前就先完成，效果上就像读排到了写前面；要想禁止它，x86 只需插一条 `MFENCE`，而各个核之间的缓存则由 MESI 这类硬件协议自动保持一致。

GPU 的内存模型对不带同步的普通（weak）读写则完全不给这些兜底：读读、读写、写写、写读四种顺序全都可能被打乱。注意普通弱读写和 `relaxed` 原子操作还不一样，`relaxed` 至少保证同一个地址上的修改顺序一致。要想在 GPU 上约束跨地址的读写顺序，你就得用 release / acquire，或者显式插一条**内存栅栏**（fence，专门用来约束前后读写顺序的独立指令）。一条 `acq_rel` 栅栏（`fence.acq_rel`）保证：栅栏之前的读写不会排到栅栏之后的写后面，栅栏之后的读写也不会排到栅栏之前的读前面。它并不禁止“先写后读”被打乱，不过我们书里的算法也不依赖这一点。

所以，在 x86 上顺手就能写的“先写数据、再写标志”，搬到 GPU 上就必须老老实实写成带作用范围的 release / acquire。

```cuda
#include <cuda/atomic>
// tail_store（后到者合并）：0 号线程在块内归约之后执行（前面已有 __syncthreads()）
// i = 尾波里第几行（0..191），half = 0 表示前半、1 表示后半
part[2 * i + half] = sum;                                   // 写出本半行的部分和
cuda::atomic_ref<int, cuda::thread_scope_device> c(cnt[i]);
if (c.fetch_add(1, cuda::memory_order_acq_rel) == 1) {      // 拿到旧值 1：我是后到者
    y[row] = part[2 * i] + part[2 * i + 1];
    c.store(0, cuda::memory_order_relaxed);                 // 下一次启动才会再用
}
```

上面这几行代码靠四个环环相扣的步骤锁死顺序：

1. **累积性**（cumulativity）：一个线程做 release 时，发布的不只是它自己写的数据，还包括它在这次 release 之前已经通过 acquire 或块内屏障看到的别的线程的写入。靠这个性质，同步链可以一棒接一棒传下去，而且**每一棒的作用范围只需要盖住交接这一棒的两个线程就够了**。比如线程 A 写完数据，先通过 CTA 内的屏障交给同块的线程 B；接着 B 做一次 `device` 范围的 release，另一个 SM 上的线程 C 做一次配对的 `device` 范围 acquire，C 就一定能看见 A 的写入。反过来，如果 B→C 这一棒只写了 CTA 范围，同步链就会在这一棒断掉。
2. **块内归拢到 0 号线程**：在 `tail_store` 里，只有 0 号线程写出 1 个标量 `part` 并做原子加。就算遇到一个 CTA 里有许多线程各自写出部分和的情况（比如第 7 节），也完全不需要每个线程都去做原子加：先在块内做一次 `__syncthreads()`（见导引三第 4 节），再让 0 号线程独自做一次 release，按第 1 条的累积性，整个 CTA 此前的所有写入就一次性全发布出去了。
3. **跨 SM 成对同步**：先到者的 release 和后到者的 acquire 落在同一个计数器 `cnt[i]` 上。这同一个计数器上的原子读改写链，把先到者的 release 直接传给了后到者的 acquire，两者**成对**生效，保证先到者写出的 `part` 对后到者一定可见。我们在硬件上观察到的具体表现（注意这只是实测观察，不是规范保证）是：release 会先把本 SM 的写入推到 L2，而 acquire 会把本 SM 的 L1 作废，逼着后面的读取去 L2 拉新数据。下面第一张图表的后两根柱子量的就是这笔开销。
4. **计数器复位**：后到者把两半加完写出 `y[row]` 之后，把 `cnt[i]` 清回 0 只用最轻量的 `relaxed` 就够了——因为下一次再碰这个计数器已经是下一次 kernel 启动的事了，两次启动之间本来就隔着 kernel 结束这道天然的流顺序边界（见第 1 章第 1 节）。

特别要注意，这套“谁后到谁合并”的写法**根本不需要两个 CTA 同时驻留在芯片上**：先到者做完原子加就拍拍屁股退出了，谁也不等；后到者一到场，直接读出两半加起来完事。所以不管两个半行 CTA 被派发的时间差了多久，都绝不可能死锁。

反过来，如果你换成另一种写法，让一个 CTA 在循环里不停地读另一个 CTA 写的标志，直到条件成立才往下走，这就叫**自旋等待**（spin-wait）。跟操作系统里的 CPU 线程不同，GPU 硬件不会为了同一次启动里还没排上号的 CTA，把已经驻留在 SM 上的 CTA 先换下来。因此一旦用了自旋等待，你就必须保证互相等的 CTA 同时在芯片上：因为 CUDA 规范既不保证普通启动的派发顺序，也不保证同时驻留；万一在片上空转等待的 CTA 把全卡位置占满了还不退出，那个负责写标志的 CTA 就永远拿不到 SM，整张卡直接死锁。

如果你确实需要让一个 CTA 等另一个 CTA，CUDA 规范认可的无死锁办法有三种。第一种是把写标志的生产者放到前一个独立的 kernel 里。第二种是用 **cooperative launch**（协作启动），由驱动保证整个 grid 的所有 CTA 一次性全部驻留在芯片上，只要放不下就干脆拒绝启动（一个 SM 能放几个 CTA 见第 3 章第 1 节）。第三种适用于只有少数几个 CTA 互相等的情形：Hopper 支持把这几个 CTA 声明成一组，由规范保证同组的 CTA 同时被调度到 SM 上并发运行（见第 7 章第 12 节）。虽然在普通启动下，靠第 1 节观察到的升序派发规律把生产者排在最前面的块编号也能跑通，**但只要驱动或硬件一改派发顺序，程序就可能悄无声息地挂死，连错都不会报。**

最后我们来算一笔全卡范围同步的硬件账。为什么全卡范围的 release / acquire 会比 `relaxed` 贵那么多？原因就在缓存一致性上：因为各个 SM 的 L1 互不同步，release 必须死等本线程此前发出的写入全都在中央 L2 落定，才能让别的 SM 看见；而 acquire 之后，本 SM 又不能再相信自己 L1 里的旧数据。

我们还另外跑了一个跨 SM 交接微基准：先让一个 CTA 写出 256 个数，通过 `__syncthreads()` 和一次 release 原子加，把数据交接给另一个 SM 上反复用 acquire 读取轮询（每次轮询之间短暂休眠）的 CTA。测下来，完成一次完整的跨 SM 交接，中位数耗时约为 **0.67 µs**。

算一下后到者经 L2 合并这笔账：

- **得到什么**：不用再单独启动第二个归约 kernel 就能跨 SM 安全合并，而且完全不要求两个 CTA 同时驻留在芯片上。
- **付出什么**：每次合并都要付一次全卡范围的 `acq_rel` 原子加（单线程约 1,078 个周期）外加后到者的读取开销。我们在 `v3` 里没有单独拆测这项代价；作为参照，上面带自旋等待的跨 SM 交接微基准约为 0.67 µs。此外，本 SM 的 L1 被作废会让后面的重读变慢，还得额外开一个计数器数组和一块部分和暂存区。
- **什么时候亏本**：如果要合并的部分和体积很大、份数很多，还让后到者那 1 个 CTA 独自把所有部分和串行读回来相加，这最后 1 个 CTA 自己就会拖出一条新的长尾巴。

## 7. 部分和很多时，怎样不让最后一个 CTA 独自读完？

**两种改法：一是让 $S$ 个 CTA 各合并 $1/S$ 行；二是所有 CTA 直接对事先清零的输出做无返回值原子加。**

<!-- FIG ch02-l2-reduce-four: 图 2-7 跨 SM 合并大块部分和的两种做法与一个反例（时间轴只表示先后顺序）：模式 1 后到者串行读回全部部分和（红圈标出长读取链，后到者读 192 KiB 要多久没有测）；模式 2 并行切片归约，每个 CTA 读 1/S；模式 3 直接原子加进清零的输出（无暂存区）；反例（第 6 章第 8 节的写法）：编译器把 BF16 标量原子加编成比较交换重试循环。步骤卡（模式 2）：第 1 步 写部分和到暂存区（输入：寄存器累加器 FP32；输出：全局内存）；第 2 步 0 号线程 acq_rel 领票 $t$ 并等齐 $S$ 张票；第 3 步 0 号线程等到后再做一次块内同步，块内其余线程读本 CTA 所属 1/S 行切片的 $S$ 份并相加写输出；代价：一次领票等待、读 1/S 的部分和。步骤卡（模式 3）：第 1 步 等清零可见；第 2 步 无返回值原子加；代价：无暂存区；结果下一个 kernel 才可见。 -->

在第 6 节的 `gemv` 里，我们只把尾波的每一行切成两半，一个计数器只管 1 行，后到者只需要读回 2 个 4 B 的标量，轻轻松松就能算完。可如果我们把 `gemv` 的许多输出行打包成一块、沿 $K$ 切成 $S$ 段，让一组 $S$ 个 CTA 共用一个计数器，后到者得独自读回的部分和就会成倍膨胀。到了多词元一起算的矩阵乘里，这个体积还会大得多：比如把一个 64 个词元、256 个输出列的分块沿 $K$ 切给 $S = 4$ 个 CTA（分块矩阵乘见第 5 章第 6–7 节），4 份 FP32 部分和加起来就有 $4 \times 64 \times 256 \times 4\ \text{B} = 256\ \text{KiB}$。如果还照搬第 6 节的做法，让最后到的那 1 个 CTA 独自把另外 3 份（192 KiB）串行读回来相加，这 1 个 CTA 的读取链立马又会拖出一条长尾巴（图 2-7 模式 1）。

第一种改法叫**并行切片归约**（图 2-7 模式 2）：别让先到的 $S - 1$ 个 CTA 拍拍手直接走人，而是把 $S$ 个 CTA 全留下来平摊合并工作。具体分四步走：

1. 每个 CTA 把自己算出的部分和写进全局暂存区，再在块内做一次同步。
2. 每个 CTA 的 0 号线程对计数器做一次 `acq_rel` 原子加，领走一张票号 $t$（也就是原子加返回的旧值，从 0 开始一直往上累加；成对同步规则和第 6 节一样）。注意这个计数器永远不复位。道理很简单：没有任何一个 CTA 知道其余 $S - 1$ 个 CTA 是不是都已经看到票数到齐、退出了自旋；万一谁在这时候把计数器清回 0，还在自旋的 CTA 就永远等不到票数达标了。所以后续每次调用都直接接着往上加 $S$ 张票。
3. 当本组的票全部被领完时，计数器的值正好达到 $(\lfloor t / S \rfloor + 1) \cdot S$。0 号线程用 `acquire` 反复读取计数器，直到它不小于这个目标值（最后一个领到票的天然不用等），由此确认全部 $S$ 份部分和都已经落定；0 号线程等齐之后，再做一次 `__syncthreads()`，块内其余线程才动手去读（计数器加满回绕怎么处理见第 5 章第 7 节）。
4. 每个 CTA 按自己在 $K$ 方向上的段序号，从全部 $S$ 份部分和里只读回归自己管的那 $1/S$ 行切片（$S = 4$ 时就是各读 16 行），加起来写出最终结果。

因为先到的 CTA 现在要自旋等待后到的 CTA，第 6 节讲的同时驻留铁律在这里立刻生效：你必须保证这 $S$ 个 CTA 同时驻留在芯片上。规范安全的做法是用第 6 节的协作启动，或者把这 $S$ 个 CTA 声明成同时驻留的一组（见第 7 章第 12 节）；靠观察到的升序派发规律虽然也能跑通，但并不受规范保护。算一下并行切片归约的账：

- **得到什么**：把合并阶段的读取量平摊给 $S$ 个 CTA，砍掉了单个后到者串行读回全部部分和的长尾巴（实测收益见第 6 章第 8 节）。
- **付出什么**：依然要开部分和暂存区，要做一次领票和自旋等待，每个 CTA 都得多跑一段合并代码，并且要求 $S$ 个 CTA 同时驻留。
- **什么时候亏本**：当要合并的部分和本来就很少时（比如第 6 节只有 2 个标量），平摊读取省下的那点时间可能还抵不上自旋等待的开销；这个盈亏临界点我们没有测。

第二种改法更干脆，叫**直接原子加**（图 2-7 模式 3）：每个 CTA 算完自己那一段内积之后，所有线程直接往全局内存的输出数组发**不需要返回值的原子加**——只管往上加、不读回旧值，指令发出去根本不用等返回。这样一来，连部分和暂存区、领票和计数器全都省掉了。

不过想用这招，必须先满足三个前提：

1. **输出数组在第一次累加前必须先清零**：规范安全的做法是在前一个独立 kernel 里先把输出清零；如果想在同一个 kernel 里派专门的 CTA 清零并发布完成标志，那就必须用第 6 节的 release / acquire 成对同步，并且满足同时驻留要求（见第 6 节）。
2. **最终结果只对下一个 kernel 可见**：在当前 kernel 内部，没有任何一个 CTA 知道别的 CTA 什么时候加完；所有部分和累加出来的最终结果，必须等当前 kernel 完全结束（或者后继 kernel 跨过第 1 章第 4 节的等待调用）之后，才对下一个 kernel 可见。
3. **输出不再逐比特固定（deterministic）**：因为浮点数加法不满足结合律，而每次运行时各个 CTA 到达 L2 的先后顺序可能微调，累加出来的浮点数在最后几个比特上可能会有出入。

算一下直接原子加的账：

- **得到什么**：一口气省掉了部分和暂存区与计数器。
- **付出什么**：输出必须提前清零；结果不再逐比特固定；而且当很多 CTA 同时往同一个输出地址做原子加时，请求会在 L2 排队（单请求注意力上的实测与分析见第 7 章第 12 节）。
- **什么时候亏本**：
  - 按第 6 章第 8 节那个 kernel 的写法，BF16 标量原子加会被编译器编成比较交换重试循环：先读旧值、算出新值，仅当该内存位置期间未被改写时才写入，否则从头重试，实测反而变慢（见第 6 章第 8 节；将两个相邻 BF16 打包在一起的 `BF16x2` 成对原子加见第 5 章第 7 节）。
  - 把清零合进同一个 kernel 时，要是负责清零的计算 CTA 刚写完零就马上立就绪标志，实测同样会变慢（原因与实测见第 5 章第 7 节）。

## 8. `gemv` 演化 `v2 → v3`：用 K-halves 把尾波的 192 行对半切开

**`v3` 把最后 192 行拆成 384 个半行 CTA，尾波读取链从 64 轮降到 32 轮，实测快约 1.25 倍。**

<!-- FIG ch02-d: 图 2-8 K-halves 尾波切半解剖图：上方画一行切成两半、两个 SM 各算一半，中央 L2 存有计数器 cnt[i] 与两格 part；下方时间线对比“切半前：一条 64 轮的链”与“切半后：两条 32 轮的链 + 一次合并”。读数：估计 21.4 µs 对 11.4 µs（按 1.8 GHz 折算）；实测整个 kernel 54.19 → 43.34 µs。步骤卡：第 1 步 前半 CTA 32 轮（输入 W 半行 8 KiB、x 前半；代价：32 次往返）；第 2 步 后半 CTA 32 轮；第 3 步 两个 fetch_add(acq_rel)（代价：两次 acq_rel 原子加，单线程约 1,078 个周期；按交接微基准 0.67 µs 估算）；第 4 步 后到者写 y[row]。总代价：384 个半行 × 一次交接，暂存区 192 × 2 × 4 B + 计数器 192 × 4 B。 -->

落到代码上，`v3` 的改法非常直接：前 2,112 个 CTA（编号 `0..2111`）照旧每个包揽一整行；后面编号 `2112..2495` 的 384 个 CTA 则每两个合算一行，各自只扫 4,096 列，算完后直接调第 6 节那段计数器合并代码（`tail_store`）经中央 L2 合并写出 `y[row]`。之所以把这批半行 CTA 排在 grid 的最后面，正是因为按第 1 节观察到的升序派发规律，编号最大的这一批刚好落进尾波：

```cuda
// v3：前 2,112 行每行 1 个 CTA，最后 192 行每行 2 个半行 CTA（grid = 2,496）
gemv_v3<<<2112 + 2 * 192, 128, 0, stream>>>(W, x, y, M, K, part, cnt);
```

这么改完之后，每个 SM 同时能驻留的 CTA 数依然是 16 个（为什么没变，见第 3 章第 1 节）。用空载往返做粗算，尾波那条串行读取链缩短约一半，预计可省下约 10 µs（算式见图 2-8 读数）。

实测下来，`v3` 比 `v2` 快了约 **1.25 倍**，省下的时间比简单尾波模型估出来的还要略多一点，具体原因没有查明。相应的代价是尾波的 192 行每行要多走一次跨 SM 交接，并且要额外分配一块部分和暂存区与计数器数组（合计 $192 \times 12\ \text{B} \approx 2.3\ \text{KB}$；何时反而不划算见第 5 节）。

不过就算走到了 `v3`，43.34 µs 的耗时依然是 7.86 µs 带宽下界的约 5.5 倍（带宽下界只占总耗时的 **18.1%**，含固定开销）。剩下的这大截差距，正是第 3 节揪出来的第二个病根：`v3` 在每个 SM 上同时挂起的在途字节，依然只有可怜的 4.0 KiB。

---

**带走一句话：** 一个 kernel 跑多久由最后退出的 CTA 决定，而 HBM 能不能喂饱，看的是每个 SM 同时在路上挂起多少字节。把尾波的行对半切开并经 L2 合并之后，`gemv` 的耗时从 54.19 µs（`v2`）降到了 43.34 µs（`v3`）。

**下一章的问题：** 喂饱 HBM 需要每个 SM 同时挂起约 64 KiB（第 3 节），可 `v3` 在每个 SM 上只挂起了 4.0 KiB。现在拆开一个 SM：到底是什么卡住了它能同时挂起的字节数，数据进片之后又怎样才能又快又不出错地送到寄存器和共享内存？
