# 第 4 章 [第 3 级]：点开 1 个 SMSP，调度器每个周期怎么选 warp 并发射指令？

**本书地图：** 前言 → 第 0.0 章 → 第 0 章 → 第 0.5 章 → 第 1 章 [第 0 级] → 第 2 章 [第 1 级] → 第 3 章 [第 2 级] → **【第 4 章 [第 3 级]：单个 SMSP】** → 第 5 章 [第 4 级] → 第 6 章 [第 5 级] → 第 7–9 章

承接第 3 章末尾的问题（第 3 级：单个 SMSP）：第 3 章算出每个 SM 最多驻留 64 个 warp，平摊到 4 个 SMSP 后每个 SMSP 最多分到 16 个驻留 warp。单个 SMSP 的调度器每周期怎样选 warp 发射指令，需要多少驻留 warp 才能掩盖读取延迟，什么会让同 warp 的线程无法齐步执行？

在一句话穿过单层八个阶段（第 0 章）时，每个 SM 的 4 个 SMSP 各管 1 个调度器和 16,384 个 32 位寄存器。阶段 2（P1 分页注意力）需要从 `seq_lens` 查 `page_table` 再发起 `cp.async`，阶段 1/3/4/5/7 的 `T = 1` 投影需要每线程挂起多条 `16 B` 向量读取，最后还要把同 warp 32 个线程寄存器里的 `acc`（FP32，每线程 4 B）归约成单行结果 `y[row]`（或在线 Softmax 的行最大值与分母）。因此第 3 级决定了单 warp 指令如何跨过记分牌停顿，以及同 warp 线程如何在寄存器间直接交接数据。

## 1. 每个周期选 1 个就绪 warp，以及什么是 no eligible

<!-- FIG ch04-a: 图 4-1 上方画单个 SMSP（调度器、16 个按 warp 着色的槽位，以及发射时亮起的 LSU 与 FMA/ALU），下方画按周期展开的时间线，每行是一个 warp（CTA r 的 warp 读 W 的第 r 行，算 y[r]），标出读发射、算术发射、就绪未选中与等待数据返回（按 600 周期读延迟、每次读取配 6 条指令建模）。 -->

一个 **clock cycle**（时钟周期，简称周期）是硬件调度的最小时间步。如图 4-1 所示，每个周期，SMSP 的 **warp scheduler**（线程束调度器）扫描本分区的驻留 warp。下一条指令的操作数和执行单元都已就绪的 warp 叫 **eligible**（就绪）。调度器每周期只有一个 **issue slot**（发射槽，即每周期从 1 个选中的 warp 发出指令的机会），所以它从中挑 1 个发射。其余就绪 warp 在 profiler 里显示为 **not selected**（未选中）。因此一个周期里即便有 15 个驻留 warp 处于 not selected，发射槽利用率仍是 **100%**。只有一个 eligible 都没有时，这个周期才叫 **no eligible**（无就绪周期），发射槽空置并拉长总耗时。每个驻留 warp 的私有寄存器在 CTA 启动时就已固定分配在本 SMSP 的寄存器文件里（见第 3 章）。所以切换 warp 不需要保存或恢复上下文，耗时为 0 个周期。

## 2. 顺序发射、scoreboard（记分牌）与掩盖延迟的两个条件

<!-- FIG ch04-b: 图 4-2 上方画 1 个 warp 按程序顺序发出内存读取（如读取 W[row * K + k] 或 smem[i]）并在 scoreboard 上登记目标寄存器的过程。下方对比串行依赖链与多 warp 轮流发射的时间线。 -->

与乱序执行的 CPU 核心不同，GPU 的每个 warp 按程序顺序发射指令。当 warp 发出一条内存读取（如 `W[row * K + k]` 或 `smem[i]`）时，请求本身不阻塞该 warp。硬件只是在 **scoreboard**（记分牌，记录每个寄存器是否还在等数据返回的硬件表）上把目标寄存器标为“未就绪”。该 warp 可继续发射后续不读该寄存器的独立指令。直到遇到第一条使用该目标寄存器的指令时，它才被挂起，由调度器换另一个 eligible warp 上场。按每周期发射 1 条指令计算，让 SMSP 发射槽不空所需的驻留 warp 数为：

```text
所需驻留 warp 数 ≈ ⌈ 读取返回延迟（周期） ÷ 从发出读取到首次使用前本 warp 能发出的指令数 n ⌉
```

第一个条件是让 SMSP 发射槽不空（掩盖片上 SMEM 短延迟）。从 SMEM 无冲突读取数据返回实测为 `23.06` 个周期（图 4-2 模型取整为 23 个周期，第三行读数写着 `LDS 延迟取 H200 实测 23.06 个周期（模型取整 23）`）。若每个 warp 发出 1 条读取后紧跟 3 条独立指令（共 `n = 4` 条），单个 SMSP 只需驻留 `⌈23 ÷ 4⌉ =` **6** 个 warp。这 6 个 warp 轮流发射，就能实现 0 个 no eligible 空周期（图 4-2 下行）。如图 4-2 所示，选“6 个 warp，n = 4”，读数为：`6 个 warp，n = 4`；`发射槽忙 100% · no eligible 0 个周期 · 前 72 个周期内读取返回 12 次`。若像阶段 2（P1 分页注意力）那样写成 `idx = len[i]; p = table[idx]; v = data[p];` 后一步地址依赖前一步结果的串行链，每步 `n = 1`（3 次串行读取共需 `3 × 23.06 = 69.2` 个周期）。此时单个 warp 会连续停在记分牌上，必须提前预取下一轮地址表以增大 `n`。选“串行依赖链：1 个 warp，每步 n = 1”，读数为：`串行依赖链：1 个 warp，每步 n = 1`；`发射槽忙 7% · no eligible 67 个周期 · 前 72 个周期内读取返回 3 次`。

第二个条件是让 HBM 带宽跑满，它与发射槽不空是两个独立条件。第 2 章约 0.33 µs 的空载单请求 HBM 读取折合约 600 个周期（按 H200 约 1.8 GHz 的 SM 时钟换算，满载排队时更长）。若想靠条件一的轮流发射来掩盖 HBM 延迟，每个 warp 每次只挂 1 条读取（`n = 4`）时，`600 ÷ 4` 需要 150 个 warp，远超单 SMSP 的 16 个上限。这说明靠 warp 轮流发射掩盖不了 HBM 长延迟，必须靠第 2 章的在途字节数（见第 2 章第 3 节）。程序要么让每个线程同时挂起多条独立的 16 字节向量读取，要么像第 3 章那样用 TMA 环形缓冲把在途字节装进 SMEM。

回头看第 0.5 章的 `gemv_kernel`（v1）。每个线程每轮只从 HBM 挂起 1 条 2 字节的 `W` 读取（`x` 仅 16 KiB，被所有 CTA 重复读取时命中缓存）。即使单 SM 驻留满 16 个 CTA（每个 128 线程），不展开循环时全 SM 同时在途的 HBM 读取也只有 `16 × 128 × 2 B = 4.0 KiB`。要凑够第 2 章图 2-2 普通读取约 64 KiB 的拐点，每个线程须同时挂起 `64 ÷ 4 = 16` 轮 2 字节读取。在图 4-1 中选 v1，读数为：`发射槽忙 17% 的周期 · no eligible（没有可发射的 warp） 83% · 本 SMSP 最多同时在途 1.0 KiB`。再选第 4 节的 v7（图 4-1 按每 SMSP 4 个 warp 建模）。此时读数变为：`发射槽忙 19% 的周期 · no eligible（没有可发射的 warp） 81% · 本 SMSP 最多同时在途 16 KiB`。此时 4 个 SMSP 合计最多同时在途 **64 KiB**（实际 v7 的在途量见第 4 节），到达图 2-2 的 64 KiB 拐点。两种配置下调度器都有超过八成的周期处于 no eligible 空闲，但 v7 的峰值在途字节是 v1 的 16 倍。只要满足条件二把 HBM 喂饱，即使发射槽有大量 no eligible 空周期也不会损失显存吞吐。

## 3. 条件掩码、branch divergence（分支分化）与锁步屏障规则

<!-- FIG ch04-c: 图 4-3 上方画 1 个 warp 的 32 条线程通道与共用指令流（对应 gemv_kernel 末尾 if (tid == 0) 归约步与条件分支）。下方对比谓词执行、单侧分支 if (tid == 0) 掩码等待与双侧长 if/else 分支分化的时间线。 -->

同一个 warp 的 32 个 thread 按 **SIMT**（单指令多线程）方式运行。warp 每次为走同一路径的活跃线程发一条指令，其余线程被掩码关闭。同一路径上的线程齐步执行，叫 **lockstep**（锁步）。因为每个 thread 有自己的程序位置（**Independent Thread Scheduling**，独立线程调度），非结构化分支分开的线程在显式同步前不保证回到锁步。

对后续还有指令的简短条件（如 `if (tid == 0) y[row] = sum;`），编译器常将其改写为 **predication**（谓词执行，共 5 条机器指令：1 条比较 `ISETP` 加 3 条带谓词地址指令与 1 条 `@!P0 STG.E`），整个 warp 1 遍走完。若该 `if (tid == 0)` 位于 kernel 最末尾且后面无其他工作（如第 0.5 章的归约尾步），编译器直接生成 `@P0 EXIT` 让其余 31 个线程立刻退出。此时只留 0 号线程执行合并为 4 元素一组的 32 条 `LDS.128` 与 128 条 `FADD`（常数循环展开后共 **166** 条指令，用 `blockDim.x` 时动态执行 231 条）。若 `if` 和 `else` 两支都很长且同 warp 内不同 thread 走向不同分支，就会发生 **branch divergence**（分支分化，图 4-3）。此时调度器必须先跑完 `if` 子集再跑 `else` 子集（共 **329** 条指令），耗时为两支之和。

如图 4-3 所示，先选“谓词执行（短条件）”，三行读数为：`谓词执行：if (tid == 0) y[row] = sum;（1 遍走完）`；`5 条 warp 指令 · 活跃 lane 占比 23%`；`谓词执行，无分支，无 BSSY/BSYNC`。再选“单侧分支 if (tid == 0)”，读数为：`单侧分支：if (tid == 0) { 128 次加法 }（v1 的写法）`；`166 条 warp 指令（blockDim.x 写法动态 231 条） · 活跃 lane 占比 4%`；`尾部 if 变成 @P0 EXIT；__syncwarp() 为 0 条 SASS`。最后选“双侧分支 if / else”，读数为：`双侧分支：if / else 两支都长（示意代码）`；`329 条 warp 指令 · 活跃 lane 占比 51%`；`BSSY/BSYNC 汇合；__syncwarp() 为 0 条 SASS`。对结构化 `if / else`，编译器已自动插入 `BSSY / BSYNC` 汇合指令，紧跟其后的 **`__syncwarp()`** 编译为 **0** 条机器指令。但在非结构化分支后或 warp 内交换寄存器前，仍须调用带掩码的同步原语保证汇合。而 `__syncthreads()` 要求本 CTA 内的所有 thread 满足相同的分支条件全员到达。若只有部分 thread 进入含 `__syncthreads()` 的分支，程序极易死锁或产生错误结果。

## 4. gemv 演化（v6 → v7 → v8）：每线程挂起 8 条向量读取与 warp 洗牌归约

在 **v6**（见第 3 章，在途仅 8.7 KiB/SM）基础上，本章的 **v7** 让每个线程在首次乘加前先连发 8 条独立的 `uint4` 读取（单线程在途 `8 × 16 = 128` 字节）。v7 编译占 83 个寄存器（按 8 的倍数分配 88 个），寄存器池限制每 SM 最多放 `⌊65,536 ÷ (32 × 88)⌋ = 23` 个 CTA。每 SM 实际只需驻留 17.45 个（低于 23），因此全部 2,304 行仍在一轮内同时驻留。全 SM 在途 `W` 字节跃升至 `17.45 × 32 × 128 B ≈` **69.8 KiB/SM**，达到了图 2-2 的 64 KiB 拐点。H200 实测：`21.86 →` **15.68 µs**（`1.39×`，约为 7.9 µs 下界的 `50.2%`）。它比 **cuBLAS**（NVIDIA 官方线性代数库，PyTorch 的 `torch.mv` 内部将其转为 `cublasGemmEx` 调用，实测 `21.12 µs`）快 5.4 µs。如第 2 章第 3 节（图 2-2 最后一步）实测所示，v7 的稳态传输率确为 **4.54–4.61 TB/s**（读 37.7 MB 稳态仅需 `8.2 µs`）。单次启动的表观带宽为 `2,409 GB/s`，是因为单次 37.7 MB 启动还包含 `6.4 µs` 固定开销（`3.8 µs` 事件计时加约 `2.6 µs` 核内收尾斜坡，干净清 L2 实测 `14.27 µs`，写脏行清 L2 实测 `15.68 µs`）。

<!-- FIG ch04-d: 图 4-4 把一行的部分和加成一个数：对比写法 1（v1 经 SMEM 屏障加 0 号线程 128 次串行加法）与写法 2（v8 单 warp 内 5 层 shuffle 树形折半归约），逐步展示每一步的周期与 SMEM 代价。 -->

接着 **v8** 引入图 4-4 所示的 **warp shuffle**（线程束洗牌：同一 warp 的 32 个线程直接交换各自的 `acc` 寄存器，经 `offset = 16, 8, 4, 2, 1` 共 5 层树形折半把 32 个 FP32 值归约为 1 个总和）。在 H200 上实测，128 线程的 `__syncthreads()` 在 4 个 warp 同时到达时耗时 `20.4` 个周期（单 SM 1 个 CTA；4 个 CTA/SM 时平均 8 个周期）。连同屏障前的 `STS` 写入与屏障后的首次 `LDS` 读取合计实测 **50.3 个周期**。再加上 0 号线程的 128 次串行依赖加法（`128 × 4 = 512` 个周期）与写出 1 个周期，总计至少约 **563 个周期**。在图 4-4 中选写法 1（v1），读数为：`写法 1：128 次串行加法 + 1 次屏障（H200 实测 20.4 个周期）`；`写 + 屏障 + 读合计实测 50.3 · 至少约 563 个周期 · 用到 SMEM`。再选写法 2（v8），读数变为：`写法 2：5 层 shuffle`；`至少约 141 个周期 · 不用 SMEM`（5 层各约 24 个周期 shuffle 加 4 个周期加法，另加写出 1 个周期）。

```cuda
// v7：每线程连发 8 条独立 uint4 读取（128 B 在途），随后再做乘加
uint4 w0 = W_vec[k + 0], w1 = W_vec[k + 32], ..., w7 = W_vec[k + 224];
// v8：单 warp 内用 __shfl_down_sync 5 步折半归约，无需 smem 与 __syncthreads()
for (int offset = 16; offset > 0; offset >>= 1) acc += __shfl_down_sync(0xffffffff, acc, offset);
```

编译器在 v8 中保持每线程 7 条而非 8 条读取同时在途，全 SM 在途略降为 `17.45 × 32 × 112 B ≈ 61.1 KiB/SM`。H200 实测：`15.68 →` **15.62 µs**（`1.00×`，约为 7.9 µs 下界的 `50.4%`）。因为在途数据量几乎未变，洗牌归约省下的四百多个周期被藏在了显存等待里。

**带走一句话：** v7 靠每线程连发 8 条 16 字节读取把全 SM 在途量从 8.7 KiB 推到 69.8 KiB（稳态带宽达 4.54–4.61 TB/s），将单次启动实测耗时从 21.86 µs 压到 15.68 µs（v8 改用 5 层洗牌归约保持 15.62 µs）。
