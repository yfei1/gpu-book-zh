# 第 0.0 章（导引）：一句话怎样穿过 62 层大模型变成下一个词？

**本书地图：** 前言 → **【第 0.0 章：一句话穿过 62 层模型】** → 第 0 章 → 第 0.5 章 → 第 1 章 [第 0 级] → 第 2 章 [第 1 级] → 第 3 章 [第 2 级] → 第 4 章 [第 3 级] → 第 5 章 [第 4 级] → 第 6 章 [第 5 级] → 第 7–10 章

承接前言的问题：一句话输入大模型后，中间经历了哪几步计算，张量的形状和数据类型怎么变？上一层算完怎么把结果交给下一层？推理又为什么会分成 **prefill**（预填充）、**decode**（逐词解码）和 **verify**（投机解码检验）三种走法？

## 1. 入站（步骤 1–2）：从一句话到第 0 层的双轨入口

<!-- FIG ch00_0-a: 图 0.0-1 一句话穿过 Muse Spark Open：分词 → 嵌入 → 62 层 → lm_head → 采样，以及 prefill / decode / verify 三种走法。 -->

用户发过来的是一串文本，但 GPU 的算术单元只会算固定宽度的数字数组。所以在进入第 0 层之前，入站阶段只做一件事：**先把文本切成词元、换成词表里的整数行号，再按行号从显存的词嵌入表里抽出对应的向量，整理成第 0 层能直接相乘的入口矩阵。**

如图 0.0-1 的步骤 1 和步骤 2 所示，这个转换分两步走完。

步骤 1 是分词与取词编号（`Tokenize`）。主机端的分词器把输入文本切成 `L` 个基本词元（**token**，图 0.0-1 示例取 `L = 5`）。词表一共有 `202,048` 个词项，每个词元对应里面的一个整数编号（具体分词算法与编号字节位宽未公开）。这 `L` 个编号拼成序列 `ids`（形状 `[L]`），拷进 GPU 的高带宽主显存（**HBM**）交给步骤 2。到了后面自回归生成的后续步，就不用再分词了，直接拿上一步选出的词元编号当输入。

步骤 2 是词表嵌入查表（`Embedding Lookup`）。HBM 里存着一张词嵌入表 `W_embed`，形状是 `[202048, 8192]`。按模型默认的 16 位脑浮点（**BF16**，每元素 2 字节）推算，整张表占 `202,048 × 8,192 × 2 B =` **3.31 GB**（8 卡部署下词表是否切分未知，图 0.0-1 按单卡持有完整词表示意）。虽然这张表有 3.31 GB，但查表不是矩阵乘法，GPU 不用把整张表读一遍。程序只拿 `ids` 里的 `L` 个编号当行号，从 HBM 取出对应的 `L` 行向量 `e = W_embed[ids, :]`（BF16，`[L, 8192]`）。

取出的这 `L` 行向量接着分成两条轨道，生成第 0 层的两个入口张量。第一条轨道对 `e` 做一次无权重的均方根归一化（**RMSNorm**），再转为 32 位单精度浮点（**FP32**，每元素 4 字节），得到主干残差流（**residual stream**）`stream_0`（形状 `[L, 8192]`，每词占 `32 KiB`）。这里的均方根归一化按向量各元素平方均值的平方根做缩放，用来把数值幅度控制在稳定范围内，因此残差流从起点开始就是归一化过的向量。第二条轨道在 `stream_0` 上做第 0 层的入口归一化，乘上以 `1.0` 为中心的逐维缩放权重 `(1 + gamma_0)`，再转回 BF16 得到第 0 层注意力入口激活 `x_0`（形状 `[L, 8192]`，每词占 `16 KiB`）。当 `gamma_0` 为 0 时，缩放系数为 `1.0`，保持原幅度不变。

两条张量写回 HBM 后，通过 HBM 全局指针把 `(x_0, stream_0)` 交给步骤 3 的第 0 层（`layers.0`）。算下来，步骤 2 每个词只需从 HBM 读 `16 KiB`，写出 `32 + 16 = 48 KiB`。当 `L = 5` 时，一共读 `80 KiB`、写 `240 KiB`。两步的公式与规格汇总如下表：

| 步骤 | 公式 | 输入（形状 / 类型 / 位置） | 输出（形状 / 类型 / 位置） | 交给下一步 | 本步硬件代价 |
|---|---|---|---|---|---|
| 步骤 1：`Tokenize`（分词与取词编号） | `ids = Tokenizer(text)` | 用户文本字符串（自回归后续步直接取上一步选出的词元编号） | 词元编号序列 `ids`（`[L]`，HBM） | `ids [L]` 交给步骤 2 | 主机端分词并拷入 `L` 个整数编号至 HBM（字节数极小，图 0.0-1 未计入显存带宽耗时） |
| 步骤 2：`Embedding Lookup`（词表嵌入查表） | `e = W_embed[ids, :]`；`stream_0 = Float32(RMSNorm(e))`；`x_0 = BF16(RMSNorm(stream_0) * (1 + gamma_0))` | `ids`（`[L]`，HBM）；`W_embed`（`[202048, 8192]`，BF16，占 `3.31 GB`，HBM） | `stream_0`（`[L, 8192]`，FP32，每词 `32 KiB`，HBM）；`x_0`（`[L, 8192]`，BF16，每词 `16 KiB`，HBM） | `(x_0, stream_0)` 经 HBM 指针交给步骤 3 的第 0 层（`layers.0`） | 无需读整张 `3.31 GB` 表，仅按行号收集 `L` 行：每词读 `16 KiB`、写 `32 + 16 = 48 KiB`（`L = 5` 时共读 `80 KiB`、写 `240 KiB`） |

## 2. 穿过 62 层（步骤 3）：纵向跨层交接与横向 KV 缓存留存

拿到初始的 `(x_0, stream_0)` 之后，数据要依次走过 **62 层**解码器层（`layers.0` 到 `layers.61`）。要理清这 62 层的运转方式，只需分清两个正交的数据流向：**每一层算完的激活和残差流沿着网络深度纵向传给下一层；每一层算出来的键值（`K, V`）则留在当前层自己的显存里，横向留给后续时间步读取。**

在图 0.0-1 的步骤 3 中点开任意第 `l` 层（`l = 0 .. 61`），可以看到所有 62 层的进出接口形状都一样。每一层从 HBM 读入本层入口激活 `x_l`（BF16）与本层残差流 `stream_l`（FP32），并访问第 `l` 层专属的键值缓存（**KV cache**）`K_cache[l], V_cache[l]`。键值缓存采用 8 位浮点 **FP8** `E4M3` 格式（每元素 1 字节，位于 HBM，具体编码见第 6 章、分页结构见第 7 章）。在 8 卡切分下，单张 H200 负责 2 个键值头、每头宽 64（见第 0 章第 1 节）。因此每个词在每一层的缓存格大小固定为 `2 (K与V) × 2 (头) × 64 (宽) × 1 B =` **256 字节**。

本层算完后，输出的张量分两条正交的路径往外送：

第一条是纵向跨层交接（`Layer l → Layer l + 1`）。对 `l = 0 .. 60`，第 `l` 层向第 `l + 1` 层传出更新后的残差流 `stream_{l+1}`（FP32，每词 `32 KiB`）和一并为下一层算好的预归一化激活 `x_{l+1}`（BF16，每词 `16 KiB`）。到了最后一层 `l = 61`，层尾不再计算下一层预归一化，只把 `stream_62` 交给步骤 4 的最终归一化。为什么要把第 `l + 1` 层的入口归一化挪到第 `l` 层末尾一起算？因为第 `l` 层末尾刚算出 `stream_{l+1}`，此时直接算出 `x_{l+1}`，第 `l + 1` 层开头只读 `x_{l+1}` 即可，省去了在下一层开头再从 HBM 读一次 `stream_{l+1}`。这样做的代价是第 `l` 层末尾要多读一次下一层的归一化权重向量并写出 `x_{l+1}`。公开参考实现固定采用这种交接格式，拆为独立步骤的耗时差未测（合并做法见第 9 章第 3 节）。

第二条是横向跨时间步留存（留在 `Layer l` 原地）。第 `l` 层算出的新键值 `K_new, V_new`（每新词 `256 B`，FP8 `E4M3`）原地写进 HBM 的 `K_cache[l], V_cache[l]`，不传给第 `l + 1` 层。它留在第 `l` 层自己的显存里，等后续生成第 `t + 1, t + 2, ...` 个新词再次路过第 `l` 层时，作为历史上下文被第 `l` 层的注意力直接读取。

虽然 62 层的接口相同，但各层内部在注意力视野与专家权重格式上有两处规律性的排布（单层内部结构见第 0 章）：

第一处是 **46 个滑窗层**与 **16 个全长层**交替排布。全长层位于下标 `1, 5, 9, ..., 61`，也就是满足 `l % 4 == 1` 的层。在 16 个全长注意力层上，每个词回顾从第 0 个位置到当前位置的全部历史上下文（上限 `1,048,576` 个位置），且不施加旋转位置编码（**RoPE**）。其余 46 层是滑动窗口注意力层，每个词只回顾最近 `2,048` 个位置（当前词加前 `2,047` 个词），并在注意力计算前对查询与键施加 `RoPE`。`RoPE` 给查询与键乘上随位置变化的旋转角度，用来标记词与词之间的相对距离（见第 0 章第 2 节与第 7 章）。

第二处是 **60 个 4 位浮点专家层**与 **2 个首尾 BF16 专家层**。全部 62 层都包含一个混合专家（**MoE**）半区：每层备有 256 个专家子网络，每个词只挑其中 8 个来算（无共享专家，见第 0 章第 1 节）。中间 60 层（`layers.1` 至 `layers.60`）的专家权重采用 4 位浮点格式（**NVFP4**，平均每权重 `0.5625` 字节，单专家占 `28.3 MB`，见第 0 章第 1 节与第 6 章）。首尾的第 0 层与第 61 层不参与 4 位量化，专家权重保持 **BF16**。

把单卡在步骤 3 的稠密权重读取量与运算量加起来：当单趟词数 `L ≤ 8` 时，单张 H200 上单层 5 个稠密投影矩阵必读权重为 `37.7 + 16.8 + 67.1 + 8.4 + 8.4 =` **138.4 MB**。62 层稠密权重合计 `62 × 138.4 MB = 8,580.8 MB =` **8.58 GB**（不含专家；每个被激活的本地 4 位专家另加 `28.3 MB`）。单层稠密投影每词运算 `2 × 67,108,864 = 0.1342 GFLOP`（约 **0.134 GFLOP**），62 层每词合计 `8.32 GFLOP`。单层接口契约与 62 层排布规格汇总如下表：

| 项目 | 内容与规格 |
|---|---|
| 单层公式（`l = 0 .. 60`） | `(x_{l+1}, stream_{l+1}, K_cache[l], V_cache[l]) = Layer_l(x_l, stream_l, K_cache[l], V_cache[l], pos)`；`x_{l+1} = RMSNorm(stream_{l+1}) * (1 + w_next_pre_attn)` |
| 末层边界（`l = 61`） | 层尾不计算下一层预归一化，返回 `(stream_62, None)`，只向步骤 4 输出 `stream_62` |
| 注意力视野排布（46 滑窗 + 16 全长） | 全长层位于下标 `1, 5, 9, ..., 61`（`l % 4 == 1`），回顾 `0` 到当前位置全部历史（上限 `1,048,576`），不加 `RoPE`；其余 46 层为滑窗层，回顾最近 `2,048` 位置（当前词 + 前 `2,047` 词），对查询与键施加 `RoPE` |
| 专家权重格式排布（60 层 NVFP4 + 2 层 BF16） | 全部 62 层均含 256 选 8（无共享专家）MoE 半区；中间 60 层（`layers.1..60`）为 `NVFP4`（`0.5625 B/权重`，单专家 `28.3 MB`），首尾 `layers.0` 与 `layers.61` 保持 BF16 |
| 本层输入（均位于 HBM） | `x_l`（`[L, 8192]`，BF16）；`stream_l`（`[L, 8192]`，FP32）；本层专属 `K_cache[l], V_cache[l]`（FP8 `E4M3`，每元素 1 B，每词每层 `2 × 2 × 64 × 1 B = 256 B`） |
| 本层输出（均位于 HBM） | 纵向传给下一层：`stream_{l+1}`（`[L, 8192]`，FP32，每词 `32 KiB`）与 `x_{l+1}`（`[L, 8192]`，BF16，每词 `16 KiB`，仅 `l = 0 .. 60`）；横向留存本层：原地写入 `K_new, V_new`（每新词 `256 B`，FP8） |
| 单卡稠密权重与运算量（`L ≤ 8`，不含专家） | 单层必读权重 `37.7 + 16.8 + 67.1 + 8.4 + 8.4 = 138.4 MB`，62 层合计 `62 × 138.4 MB = 8,580.8 MB = 8.58 GB`（每激活一个本地 4 位专家另加 `28.3 MB`）；单层每词运算 `2 × 67,108,864 = 0.1342 GFLOP`（约 `0.134 GFLOP`），62 层合计：1 词 `8.32 GFLOP`，5 词 `41.6 GFLOP`，8 词 `66.6 GFLOP` |

## 3. 出站与回流（步骤 4–8）：最终归一化、词表投影、软上限与采样闭环

数据穿完第 61 层输出 `stream_62` 时，结果还是 `8,192` 维的浮点向量，而推理最终要产出的是下一个词。图 0.0-1 右侧的步骤 4 至步骤 8 做的是入站的逆过程：**挑出需要预测的 `R` 个位置，把 `8,192` 维向量投影到全部 `202,048` 个词表候选项上打分，选出下一个词的编号，再送回步骤 2 启动下一趟前向计算。**

在这五步里，耗时占大头的是步骤 5 的 `lm_head` 词表投影。入站查 `W_embed` 只需按行号取 `L` 行，出站算 `lm_head` 则要拿每个待预测位置的特征与词表里全部 `202,048` 行做内积，必须把整张 `3.31 GB` 的输出词表矩阵完整读出一遍。

因此在进 `lm_head` 之前，步骤 4（最终归一化，`Final Norm`）会先把不需要预测的行裁掉。只预测单个新词时，只取最后一个位置（下标 `L - 1`，即 `R = 1` 行）；投机解码检验 8 个词时，才取全部 `R = 8` 行。程序从 HBM 读入 `stream_62` 的这 `R` 行（每行 `32 KiB`），先转为 BF16 再做最终均方根归一化。和层内各处乘 `1 + gamma` 的归一化不同，最终归一化直接乘上权重向量 `w_norm` 本身（核内按 BF16 读取，检查点存储位宽未知），写出归一化特征 `h`（每行 `16 KiB`）。

步骤 5（词表线性投影，`lm_head`）接过 `h [R, 8192]`，乘上独立的输出词表矩阵 `W_lm_head`（形状 `[202048, 8192]`，BF16，占 `3.31 GB`，不与 `W_embed` 共享权重），以单精度累加得到 `202,048` 个候选词的原始打分 `z`（**FP32**，每行约 `808.2 KB`）。词表并行切分宽度取决于部署启动参数，8 卡下是否切分未知。按图 0.0-1 单张 GPU 读取完整 3.31 GB 权重计算，在 H200 的 `4.8 TB/s` 峰值带宽下，光读完 `W_lm_head` 至少就要 **0.69 ms**。每行执行 `2 × 202,048 × 8,192 =` **3.31 GFLOP** 乘加运算，算术强度只有 `R FLOP/B`。

算出原始打分 `z` 后，步骤 6 到步骤 8 把打分限幅、选出新词，再送回步骤 2 启动下一趟。步骤 6（输出缩放与对数几率软上限，`Logit Scale & Softcapping`）先把 `z` 乘上输出缩放常数 `0.1767767`（即 `1 / sqrt(32)`），再用软上限常数 `20.0` 通过双曲正切 `20.0 * tanh((0.1767767 * z) / 20.0)` 把打分平滑限制在 `(-20, +20)` 区间内。步骤 7（采样选词，`Sample`）扫描每行的 `202,048` 个候选打分，选出新词编号 `next_id`（具体采样规则、温度参数与 `next_id` 字节位宽未公开，常见做法是取最高分下标或按概率分布采样）。最后，步骤 8（自回归回流，`Feedback`）令 `ids_next = [next_id]`，把位置游标推进 `pos ← pos + 1`，再将编号指针拉回步骤 2 作为下一趟查 `W_embed` 的行号。步骤 4 至步骤 8 的公式与规格汇总如下表：

| 步骤 | 公式 | 输入（形状 / 类型 / 位置） | 输出（形状 / 类型 / 位置） | 交给下一步 | 本步硬件代价 |
|---|---|---|---|---|---|
| 步骤 4：`Final Norm`（最终归一化） | `h = BF16(RMSNorm(BF16(stream_62[rows, :])) * w_norm)` | `stream_62` 目标行（`[R, 8192]`，FP32，每行 `32 KiB`，HBM）；`w_norm`（`[8192]`，BF16，HBM） | `h`（`[R, 8192]`，BF16，每行 `16 KiB`，写回 HBM） | `h [R, 8192]` 交给步骤 5 的 `lm_head` | 从 HBM 读 `R × 32 KiB`（`R = 1` 时 `32 KiB`，`R = 8` 时 `256 KiB`），写 `R × 16 KiB`（`16 KiB` 或 `128 KiB`） |
| 步骤 5：`lm_head`（词表线性投影） | `z = Float32(h @ W_lm_head.T)` | `h`（`[R, 8192]`，BF16，HBM）；`W_lm_head`（`[202048, 8192]`，BF16，占 `202,048 × 8,192 × 2 B = 3.31 GB`，HBM） | 原始词表打分 `z`（`[R, 202048]`，FP32，每行约 `808.2 KB`，写回 HBM） | `z [R, 202048]` 交给步骤 6 | 单卡读完整 `3.31 GB` 权重按 `4.8 TB/s` 至少需 **0.69 ms**；每行 `2 × 202,048 × 8,192 =` **3.31 GFLOP**（算术强度仅 `R FLOP/B`） |
| 步骤 6：`Logit Scale & Softcapping`（输出缩放与软上限） | `logits = 20.0 * tanh((0.1767767 * z) / 20.0)` | 原始打分 `z`（`[R, 202048]`，FP32，HBM） | 限幅后的打分 `logits`（`[R, 202048]`，FP32，HBM） | `logits [R, 202048]` 交给步骤 7 | 对 `R × 202,048` 个 FP32 元素执行缩放与双曲正切（常与步骤 5 合并写出，图 0.0-1 未单独计入带宽下界） |
| 步骤 7：`Sample`（采样选词） | 取最大值下标或按概率分布采样 | `logits`（`[R, 202048]`，FP32，HBM） | 新词编号 `next_id`（`[R]`，HBM） | `next_id` 交给步骤 8 回流 | 归约扫描 `R × 202,048` 个候选分数并写出 `R` 个编号 |
| 步骤 8：`Feedback`（自回归回流） | `ids_next = [next_id]`；位置游标 `pos ← pos + 1` | `next_id`（`[R]`，HBM） | 下一趟入口编号 `ids_next`（单步生成时形状为 `[1]`，HBM） | 拉回步骤 2 作为下一趟查 `W_embed` 的行号 | 仅更新位置游标并传递编号指针，单步搬运字节可忽略 |

## 4. 同一个模型，为什么会有 prefill、decode、verify 三种走法？

同一个 62 层的模型，权重是同一份，前向传播的算子也是同一套，为什么在推理服务里要分成 **prefill**（预填充）、**decode**（逐词解码）和 **verify**（投机解码检验）三种走法？你可以先切换图 0.0-1 顶部的三个模式按钮，对照看一眼顶部读数的变化。

分出这三种走法，直接原因在于：**一趟前向计算开始之前，已知的输入词有几个。**

在看具体怎么跑之前，先算一下每跑一趟都必须读取的权重量。这个模型 62 层的稠密权重是 `8.58 GB`，末尾的 `lm_head` 是 `3.31 GB`，加起来一共 **11.89 GB**（这里还没算专家权重）。只要模型往前跑一趟，GPU 就得把这 `11.89 GB` 的权重从 HBM 里读出来一遍。按 H200 的 `4.8 TB/s` 显存带宽上限来算，光把这批权重读进芯片，至少就要 **2.48 ms**。

这 `11.89 GB` 的权重读取量是按“趟”计算的，不是按“词”计算的。一趟只输入 1 个词，要读 `11.89 GB`；一趟并排输入 5 个词或 8 个词，读的仍是这 `11.89 GB`。三种走法的性能差异，就来自每次读出的 `11.89 GB` 权重能由几个词共同分摊。

先看第一阶段 **prefill**（预填充）：输入词全部已知，一趟并排算完。用户刚提交整句提示词时（图 0.0-1 示例取 `L = 5`），这 `L` 个词在计算前已经全部知道了。既然都知道，就没必要一个一个往里送，而是直接把它们叠成一个 `[L, 8192]` 的矩阵，让这 5 个词一次性并排流过全部 62 层。在每一层内部，因果注意力只让第 `j` 个词看它自己和排在它前面的词。算出来的 `L` 格新键值写进这一层的 KV 缓存（每层写 5 格，62 层全网共写 `62 × 5 × 256 B = 79,360 B`），留给后续生成新词时直接读取。流完 62 层之后，前 4 个位置的下一个词本来就是提示词里已知的，只需取最后一行（`R = 1`）送进 `lm_head`，就能产出第 6 个词。

加一下这一趟的运算量和权重读取量：稠密部分 `41.6 GFLOP` 加上 `lm_head` `3.31 GFLOP`，一共做了 `44.92 GFLOP` 的运算（不含专家与注意力），从 HBM 读了 **11.89 GB** 权重。因为 5 个词共享了同一次权重读取，平均每个词分摊下来的权重读取量就只有 **2.38 GB**。

在线上运行 prefill 时，还会遇到两个实际问题：

第一个问题是**提示词太长怎么办**。如果提示词长达数万词，把几万行的激活张量一次全展开，单次激活显存就会不够用。所以服务会采用**分块预填充**（Chunked Prefill）。例如首轮按 `L = 16,384` 个新词为一块依次推进，在已有 `0`、`32,768` 或 `65,536` 个缓存词后每次追加 `16,384` 个词；或者在多轮对话已有的 `80,000` 个缓存词上追加 `L = 753` 个新词。这样每一趟查询 `Q` 的行数就只是本块新增的 `L`（`753` 或 `16,384`）。键 `K` 与值 `V` 的可见总长度则是“历史缓存加本块新词”，在全长层下达 `80,753` 或 `81,920`，在滑窗层下为 `2,048` 窗口。

分块预填充的好处是控住了单次激活显存占用。相应的代价是后续分块在全长层上需要把前序已缓存的 KV 重新读一遍。另外，分块也不能切得过小，否则权重复用率会下降：在 `L = 753` 时，每个本地专家平均只分到约 24 个词，还没跨过算力平衡点；要到 `L = 16,384`、每个专家平均分到 512 个词时，才转为矩阵运算算力受限（见第 0 章第 3 节；不同分块大小的对比耗时未测）。

第二个问题是**不同请求开头都一样怎么办**。因果注意力里，前序位置的键和值只依赖它自己及更早的词，不依赖后面的词。当多个并发请求的提示词开头共享同一段固定系统前缀时，这段前缀在各层里的 `K` 和 `V` 算一次就够了，这叫**跨请求公共前缀 KV 复用**。在一个 36 层稠密排序模型的整网预填充评测中，260 个词的公共前缀占了平均 792.7 词总输入长度的 **32.8%**。把这 260 个公共前缀词的 `K, V` 只算一次并拷入各请求的 KV 缓存位置，让预填充只算剩余后缀，22 个预填充算例的实测耗时比中位数降到了 **`0.843×`**（即中位数省 **16%** 时间，范围 `0.650–0.938×`）。输出与全量重算一致，且后缀越短、公共前缀占比越高，收益越明显。相应的代价是显存里要常驻维护公共前缀的 KV 缓冲区，并在请求入站时做一次前缀 KV 拷贝（额外显存占用字节数未测）。如果不同请求的提示词开头互不相同（公共前缀长度为 0），那就省不下任何词元计算，反而增加了前缀管理与拷贝开销（反例耗时未测）。

再看第二阶段 **decode**（逐词解码）：下一个词还没算出来，只能一次跑 1 个词。一旦第 6 个词在步骤 7 被选出来，接下来要去生成第 7 个词、第 8 个词时，计算条件就变了。自回归生成里，第 8 个词依赖第 7 个词的结果；在算完第 7 个词之前，第 8 个词还不存在。于是从这一刻起，每一趟前向计算的输入退化为只有刚产出的第 6 个词这 **1 个词**（`L = 1`）。前 5 个词的键值已经在预填充时留在了各层的 KV 缓存里。本趟每层只需写入第 6 个词的 **1 格** KV（`256 B`），再连同已缓存的 5 格一起读出 **6 格** KV（每层 `1,536 B`，62 层共读 `95,232 B`、写 `15,872 B`），产出第 7 个词。

把 decode 和 prefill 摆在一起比，就能看出单请求 decode 慢在哪儿。因为输入只有 1 个词，稠密加 `lm_head` 的运算量降到了约 `8.32 + 3.31 = 11.63 GFLOP`（图 0.0-1 显示 `8.3 + 3.31 GFLOP`，不含专家与注意力）。计算量砍掉了将近四分之三，但为了算这 1 个词，GPU 还是得把那 **11.89 GB** 的全部稠密与 `lm_head` 权重从 HBM 重读一遍。整整 `11.89 GB` 的权重只算 1 个词，算术强度只有约 `1 FLOP/B`，远低于 H200 的算力与带宽平衡点（`206 FLOP/B`，见第 0 章第 3 节）。GPU 的计算单元大部分时间都在等显存搬权重，单趟耗时被 **2.48 ms** 的带宽下界卡住。

最后看第三阶段 **verify**（投机解码检验）：单趟 `11.89 GB` 的权重既然每次都得读，那就先让草稿模型猜出几个词并排送进去一起验。为了改变单请求 decode 下读一次权重只算 1 个词的低复用率，公开参考实现默认打开投机解码。它先由轻量草稿机制提出 **8 个候选词**（`L = 8`），再把这 8 个词拼成 `[8, 8192]` 一次性送进 62 层大模型同时检验（块内带下三角因果掩码）。在图 0.0-1 的 5 词缓存示意场景中，为保持 `L = 8` 档位，图上把预填充刚产出的第 6 个已知词与位置 `7..13` 的 7 个草稿词合为 8 个输入词，接在 5 格已缓存词之后。这一趟每层写入 8 格 KV，连同原有 5 格共读出 `5 + 8 =` **13 格**（`3,328 B`）KV（62 层共读 `206,336 B`、写 `126,976 B`），到末尾取全部 `R = 8` 行送入 `lm_head` 检验猜对了几个。

对比 verify 的运算量和权重读取量，就能看出它的得失。8 个词让稠密部分（约 `66.6 GFLOP`）加 `lm_head`（`26.48 GFLOP`）的运算量升到了 `93.05 GFLOP`，但同样只读一次 62 层稠密与 `lm_head` 权重（**11.89 GB**，下界 **2.48 ms**）。8 个词一起分摊，平均每词分摊的稠密权重读取量直接砍到原来的 1/8（缩小了 8 倍），降到 **1.49 GB**。只要前几个草稿词检验通过，就能用跑一趟前向的时间产出多个词。相应的代价是要额外运行草稿机制生成候选词，每层注意力多读写 8 个位置的 KV，且在阶段 6 会激活更多本地专家（见第 0 章第 2 节；草稿生成与接受规则耗时未测）。如果候选词在靠前位置就被拒绝，后面位置的检验计算就会作废而变成亏本（具体盈亏接受率阈值未测）。三种走法在图 0.0-1 下的读数与数值汇总如下表：

| 模式 | 图 0.0-1 顶部读数 | 本趟词数 `L` 与 `lm_head` 行数 `R` | 每层与 62 层全网 KV 读写 | 稠密 + `lm_head` 运算（不含专家与注意力） | 读权重（不含专家）与每词分摊 | 带宽下界（`4.8 TB/s`） |
|---|---|---|---|---|---|---|
| **prefill**（预填充） | `本趟 5 个词同时流过 62 层 · 每层写入 KV 5 格 · 产出第 6 个词`；`读权重 11.89 GB（不含专家）· 平均每个词摊 2.38 GB · 带宽下界 2.48 ms` | `L = 5`，`R = 1` | 每层写 5 格；全网写 `62 × 5 × 256 B = 79,360 B` | `41.6 + 3.31 = 44.92 GFLOP` | 读 **11.89 GB**（`8.58 + 3.31`），每词分摊 **2.38 GB** | **2.48 ms** |
| **decode**（逐词解码） | `本趟 1 个词流过 62 层 · 每层读 KV 6 格、写 1 格 · 产出第 7 个词`；`读权重 11.89 GB（不含专家）· 平均每个词摊 11.89 GB · 带宽下界 2.48 ms` | `L = 1`，`R = 1` | 每层读 6 格（`1,536 B`）、写 1 格（`256 B`）；全网读 `95,232 B`、写 `15,872 B` | 约 `8.32 + 3.31 = 11.63 GFLOP`（图显 `8.3 + 3.31 GFLOP`） | 读 **11.89 GB**，每词分摊 **11.89 GB** | **2.48 ms** |
| **verify**（投机解码检验） | `本趟 8 个词（第 6 个已知 + 7 个草稿）一次流过 62 层 · 每层读 KV 13 格、写 8 格`；`读权重 11.89 GB（不含专家）· 平均每个词摊 1.49 GB · 带宽下界 2.48 ms` | `L = 8`（第 6 个已知 + `7..13` 共 7 个草稿），`R = 8` | 每层读 `5 + 8 = 13` 格（`3,328 B`）、写 8 格；全网读 `206,336 B`、写 `126,976 B` | 约 `66.6 + 26.48 = 93.05 GFLOP` | 读 **11.89 GB**，每词分摊 **1.49 GB** | **2.48 ms** |

看完 62 层模型在三种走法下的读写量和耗时下界，就能看出来为什么接下来的章节可以只盯住其中的 **1 层**。除开最前面的词表嵌入、末尾的 `lm_head` 以及跨卡集合通信，整张网的主体计算就是把接口契约一致的单层结构重复跑 62 遍。每一层都从 HBM 接过上一层留下的 `(x_l BF16 [T, 8192], stream_l FP32 [T, 8192])`，读写本层自己的 FP8 KV 缓存，再把更新后的状态交给下一层。只要把这 1 层在不同词数 `T` 下的计算和访存拆透，整个 62 层模型在 GPU 上是怎么跑的也就全通了。

**带走一句话：** 一句话穿过 `Muse Spark Open` 的 62 层时，纵向靠 `(x_l BF16, stream_l FP32)` 跨层传递激活与残差流，横向靠留在各层原地的 `256 B/词` FP8 KV 缓存跨时间步复用；而一趟 `11.89 GB` 的权重读取由几个词分摊，把推理分成了 `prefill`（已知词并排共享）、`decode`（未知生成词逐个重读）与 `verify`（草稿词成批并行检验）三种走法。
