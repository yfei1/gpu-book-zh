# 第 0.0 章（导引）：一句话怎样穿过 62 层大模型变成下一个词？

**本书地图：** 前言 → **【第 0.0 章：一句话穿过 62 层模型】** → 第 0 章 → 第 0.5 章 → 第 1 章 [第 0 级] → 第 2 章 [第 1 级] → 第 3 章 [第 2 级] → 第 4 章 [第 3 级] → 第 5 章 [第 4 级] → 第 6 章 [第 5 级] → 第 7–9 章

承接前言的问题（从整网闭环到单层入口）：当用户输入一句话时，大模型经历了哪几步计算、张量形状与数据类型怎样变化、每一层算完如何把结果交给下一层，又为什么必然分裂成 **prefill**（预填充）、**decode**（逐词解码）与 **verify**（投机解码检验）三种工作模式？

---

## 1. 入站（步骤 1–2）：从一句话到词元编号，再查表变成 8,192 维向量

<!-- FIG ch00_0-a: 图 0.0-1 一句话穿过 Muse Spark Open：分词 → 嵌入 → 62 层 → lm_head → 采样，以及 prefill / decode / verify 三种走法。 -->

GPU 的算术单元只处理固定宽度的数字数组，不直接处理原始文本。如图 0.0-1 的步骤 1 与步骤 2 所示，一句话进入 `Muse Spark Open` 后，先经历两步入站转换，把文本变成第 0 层能直接相乘的浮点数矩阵。本书五个计时赛题只截取第 0 层至第 61 层的单层计算，入站与出站步骤按模型配置与图 0.0-1 示意闭合全流程。
- 步骤 1（分词与取词编号，`Tokenize`）。分词器把用户输入的文本切成 `L` 个基本词元（称为 **token**，图 0.0-1 示例提示词取 `L = 5`）。每个词元对应词表（共 `202,048` 个词项）里的一个整数编号（分词算法与编号的字节位宽不在赛题文件中规定）。
  - 公式：`ids = Tokenizer(text)`。
  - 输入：用户文本字符串（在自回归循环的后续步中，直接取上一步已选出的词元编号）。
  - 输出：长度为 `L` 的词元编号序列 `ids`（形状 `[L]`），送入 GPU 的 **HBM**（高带宽显存）。
  - 交给下一步：`ids [L]` 交给步骤 2 的词表嵌入查表。
- 步骤 2（词表嵌入查表，`Embedding Lookup`）。模型权重索引包含词嵌入表 `W_embed`（`model.language_model.embed_tokens.weight`）。程序拿 `ids` 里的 `L` 个编号当作行号，从 `W_embed` 中取出对应的 `L` 行向量，形成第 0 层的两个入口数组。
  - 公式：从 `W_embed[ids[t], :]` 取出第 `t` 个词的向量转为单精度初始残差流 `stream_0[t, :]`（转换细节未公开）。进入第 0 层前，按单层参考实现做无权重的均方根归一化得到 `x_0 = RMSNorm(stream_0)`（首层前是否另带归一化权重未知）。
  - 输入：词元编号 `ids`（`[L]`，位于 HBM）与词嵌入表 `W_embed`（完整形状 `[202048, 8192]`）。按模型默认 **BF16**（脑浮点，每元素 2 字节）推算，整张表占 `202,048 × 8,192 × 2 B =` **3.31 GB**（位于 HBM）。词表是否跨 8 卡切分未知，图 0.0-1 按单卡持有完整词表示意。
  - 输出：进入第 0 层的两条初始张量。第一条是高精度主干 **residual stream**（残差流）`stream_0`（形状 `[L, 8192]`）。它的类型为 **FP32**（单精度浮点，每元素 4 字节，每词占 `32 KiB`，写回 HBM）。第二条是第 0 层注意力入口激活 `x_0`（形状 `[L, 8192]`），类型为 BF16（每词占 `16 KiB`，写回 HBM）。
  - 交给下一步：`(x_0, stream_0)` 通过 HBM 全局指针交给步骤 3 的第 0 层（`layers.0`）。
  - 本步硬件代价：GPU 无需读取整张 3.31 GB 的 `W_embed`，只需按行号从 HBM 收集 `L` 行。每词读取 `16 KiB`、写出 `32 + 16 = 48 KiB`（当 `L = 5` 时共读 `80 KiB`、写 `240 KiB`）。

## 2. 穿过躯干（步骤 3）：62 层堆叠的纵向跨层交接与横向 KV 缓存留存

拿到初始的 `(x_0, stream_0)` 后，数据流要依次穿过模型躯干的 **62 层**解码器层（`layers.0` 到 `layers.61`）。这 62 层的接口形状完全相同，但在注意力视野与专家量化精度上有两处规律性的排布。
- 第一处是 **46 个滑窗层**与 **16 个全长层**按 `3 : 1` 交替排布。下标为 `1, 5, 9, ..., 61`（即每 4 层中的最后 1 层，`l % 4 == 1`）的 16 层是全长注意力层。在这些层上，每个词要回顾从第 0 个位置到当前位置的全部历史上下文（上限 `1,048,576` 个位置），且不施加旋转位置编码（`RoPE`）。其余 46 层是滑动窗口注意力层，每个词只回顾最近 `2,048` 个位置，并在注意力前对查询与键施加 `RoPE`。
- 第二处是 **60 个 NVFP4 量化专家层**与 **2 个首尾非 NVFP4 层**。全部 62 层都包含一个 256 选 8 的混合专家（MoE）半区。中间 60 层（`layers.1` 至 `layers.60`）的专家权重压缩为 4 位浮点 **NVFP4**（平均每权重 `0.5625` 字节，单专家 `28.3 MB`）。首尾第 0 层与第 61 层则被排除在 NVFP4 量化之外（这两层的具体权重格式未知）。

在图 0.0-1 的步骤 3 中，点开任意第 `l` 层（`l = 0 .. 61`），它与前后层及未来时间步之间的契约都可以精确写为以下四项。
- 公式：`(x_{l+1}, stream_{l+1}, K_cache[l], V_cache[l]) = Layer_l(x_l, stream_l, K_cache[l], V_cache[l], pos)`（其中第 61 层只向步骤 4 输出 `stream_62`，是否同时算出 `x_62` 未知）。
- 输入：本层入口激活 `x_l`（`[L, 8192]`，BF16，HBM）与本层残差流 `stream_l`（`[L, 8192]`，FP32，HBM）。第三个输入是第 `l` 层专属的分页 **KV cache**（键值缓存）`K_cache[l], V_cache[l]`，类型为 **FP8**（`E4M3`，每元素 1 字节，位于 HBM）。在 8 卡张量并行（TP8）下，单张 H200 负责 2 个键值头、每头宽 64，因此每个词在每一层的缓存格大小固定为 `2 (K与V) × 2 (头) × 64 (宽) × 1 B =` **256 字节**。
- 输出：更新后的残差流 `stream_{l+1}`（`[L, 8192]`，FP32，每词 `32 KiB`，HBM），对 `l = 0 .. 60` 还输出顺手为下一层算好的预归一化激活 `x_{l+1} = RMSNorm(stream_{l+1}) * (1 + w_next_pre_attn)`（`[L, 8192]`，BF16，每词 `16 KiB`，HBM）。同时输出原地写入第 `l` 层缓存页的新键值 `K_new, V_new`（每新词 `256 B`，FP8 `E4M3`，HBM）。
- 交给下一步（两条正交的交接路径）：
  1. 纵向跨层交接（`Layer l → Layer l + 1`）。对 `l = 0 .. 60`，只有 `(x_{l+1}, stream_{l+1})` 沿网络深度传给第 `l + 1` 层。因为第 `l` 层的收尾操作已经把第 `l + 1` 层的入口归一化算好写进 `x_{l+1}`，第 `l + 1` 层一进场就能直接启动矩阵乘，省去了一次独立的跨层归一化读写。到了最后一层 `l = 61`，其输出的 `stream_62` 交给步骤 4 的最终归一化。
  2. 横向跨时间步留存（留在 `Layer l` 原地）。第 `l` 层写入 HBM 的 `K_cache[l], V_cache[l]` **绝不传给第 `l + 1` 层**。它留在第 `l` 层自己的显存页里，专门等后续生成第 `t + 1, t + 2, ...` 个新词再次路过第 `l` 层时，作为历史上下文被第 `l` 层的注意力直接读取。
- 本步单卡单层与 62 层总代价：在单张 TP8/EP8 H200 上，当单趟词数 `L ≤ 8` 时，单层 5 个稠密投影矩阵必读权重为 `37.7 + 16.8 + 67.1 + 8.4 + 8.4 =` **138.4 MB**。62 层稠密权重合计 `62 × 138.4 MB = 8,580.8 MB =` **8.58 GB**（不含专家；每个被激活的本地 NVFP4 专家另加 `28.3 MB`）。单层稠密投影每词运算 `2 × 67,108,864 = 0.1342 GFLOP`（约 **0.134 GFLOP**；62 层每词合计 `8.32 GFLOP`，5 词合计 `41.6 GFLOP`，8 词合计 `66.6 GFLOP`）。

## 3. 出站与回流（步骤 4–8）：最终归一化、词表投影、软上限与采样闭环

当数据穿完第 61 层（吐出 `stream_62`）后，完整推理还要走完图 0.0-1 右侧的步骤 4 至步骤 8。这五步把 8,192 维向量还原成下一个词的编号并送回第 0 层。这五步位于单层赛题 P1–P5 之外，以下按模型配置与图 0.0-1 示意说明其数据流。
- 步骤 4（最终归一化，`Final Norm`）。模型权重索引包含最终归一化向量 `model.language_model.norm.weight`（具体权重形式与公式未知）。按常见做法，生成单个新词时只取最后一个位置（下标 `L - 1`，即 `R = 1` 行）的残差流；投机检验 8 个词时则取全部 `R = 8` 行。
  - 公式：`h = RMSNorm(stream_62[rows, :])`（权重形式未知）。
  - 输入：`stream_62` 的目标行（`[R, 8192]`，FP32，每行 `32 KiB`，HBM）。
  - 输出：归一化后的特征 `h`（`[R, 8192]`，BF16，每行 `16 KiB`，写回 HBM），交给步骤 5。
- 步骤 5（词表线性投影，`lm_head`）。把 8,192 维特征乘上独立的输出词表矩阵 `W_lm_head`（配置文件中 `tie_word_embeddings = false`，即不与 `W_embed` 共享权重，且排除在量化之外），为词表里的 `202,048` 个候选词逐一打分。
  - 公式：`z = h @ W_lm_head.T`。
  - 输入：`h`（`[R, 8192]`，BF16，HBM）与 `W_lm_head`（完整形状 `[202048, 8192]`，按默认 BF16 推算占 `202,048 × 8,192 × 2 B =` **3.31 GB**，位于 HBM）。词表是否跨 8 卡切分未知，图 0.0-1 设单张 GPU 读取完整 3.31 GB。
  - 输出：原始词表打分 `z`（形状 `[R, 202048]`，写回 HBM），交给步骤 6。
  - 本步代价：若单卡读取完整 **3.31 GB** 权重，按 H200 的 `4.8 TB/s` 峰值带宽计算，单是读完 `W_lm_head` 至少就要 **0.69 ms**。每行执行 `2 × 202,048 × 8,192 =` **3.31 GFLOP** 乘加运算（算术强度仅 `R FLOP/B`）。
- 步骤 6（对数几率软上限，`Logit Softcapping`）。模型配置文件设有 `final_logit_softcapping = 20.0`（五个单层赛题均不执行此步）。
  - 公式：按常见定义记为 `logits = 20.0 * tanh(z / 20.0)`。
  - 输入与输出：输入 `z [R, 202048]`，输出限幅后的 `logits [R, 202048]`（HBM），交给步骤 7。
- 步骤 7（采样选词，`Sample`）。根据 `202,048` 个候选词的打分选出下一个词的编号（具体采样规则与温度参数未知）。
  - 输入与输出：输入 `logits [R, 202048]`，输出选出的词元编号 `next_id`（交给步骤 8）。
- 步骤 8（自回归回流，`Feedback`）。
  - 公式：`ids_next = [next_id]`，位置游标 `pos ← pos + 1`。
  - 交接闭环：刚刚选出的单个 `next_id` 拉回步骤 2 的入口，作为下一趟前向计算的输入词元去查 `W_embed`，从而启动生成下一个词的循环。

## 4. 为什么必然分裂成 Prefill、Decode 与 Verify 三种走法？

切换图 0.0-1 顶部的三个模式按钮，观察同一个 62 层模型在三种走法下的顶部读数。这三种工作模式不是人为规定的软件分支，而是自回归因果律作用在 HBM 带宽上的必然结果。
- 第一阶段：**prefill**（预填充，对应本书赛题 P5）。用户刚提交整句提示词时（图 0.0-1 示例取 `L = 5`；真实服务首轮按 `L = 16,384` 分块，或多轮在 `80,000` 历史词上追加 `L = 753`），这 `L` 个词在计算前全部已知。因此它们可以叠成 `[L, 8192]` 矩阵，一次性并排流过全部 62 层（每层注意力用下三角因果掩码保证第 `j` 个词只看自己及之前的词）。这一趟顺手把每层的 `L` 格新键值写进 KV 缓存，最后按常见做法只取最后一行（`R = 1`）送入 `lm_head` 产出第 6 个词。图 0.0-1 在该模式下的读数为：`本趟 5 个词同时流过 62 层 · 每层写入 KV 5 格 · 产出第 6 个词`；`读权重 11.89 GB（不含专家）· 平均每个词摊 2.38 GB · 带宽下界 2.48 ms`。
  算清这笔总账：62 层稠密权重（`8.58 GB`）加上完整 `lm_head`（`3.31 GB`）共需从 HBM 读取 **11.89 GB**（不含专家）。按 H200 的 `4.8 TB/s` 带宽上限，光读完这 11.89 GB 至少需要 **2.48 ms**（全网写 KV 共 `62 × 5 × 256 B = 79,360 B`，稠密部分约 `41.6 GFLOP` 加 `lm_head` `3.31 GFLOP` 共 `44.92 GFLOP`，不含专家与注意力）。因为 5 个词共享同一次权重读取，平均每个词只分摊 **2.38 GB**。在多轮对话追加 `L = 753` 个词时，每个本地专家平均分到约 24 个词，尚未跨过算力平衡点。而当首轮分块达到 `L = 16,384` 个词（每专家平均 512 个词）时，瓶颈就从 HBM 读权重彻底翻转为 Tensor Core 算力。
- 第二阶段：**decode**（逐词解码，对应赛题 P1–P4 的单词档）。一旦第 6 个词在步骤 7 被选出来，要去生成第 7 个词、第 8 个词时，处境就彻底变了。因为第 8 个词依赖第 7 个词的结果，在算完第 7 个词之前，第 8 个词根本不存在。于是从这一刻起，每一趟前向计算的输入被迫退化为只有刚产出的第 6 个词这 **1 个词**（`L = 1`）。前 5 个词的键值已经在预填充时留在了各层的 KV 缓存里。本趟每层只需写入第 6 个词的 **1 格** KV（`256 B`），并连同已缓存的 5 格一起读出 **6 格** KV（每层 `1,536 B`，62 层共读 `95,232 B`、写 `15,872 B`）。图 0.0-1 在该模式下的读数为：`本趟 1 个词流过 62 层 · 每层读 KV 6 格、写 1 格 · 产出第 7 个词`；`读权重 11.89 GB（不含专家）· 平均每个词摊 11.89 GB · 带宽下界 2.48 ms`。
  对比两行读数就能看到单请求 decode 的根本痛点。虽然稠密加 `lm_head` 运算降到了约 `8.32 + 3.31 = 11.63 GFLOP`（图 0.0-1 显示 `8.3 + 3.31 GFLOP`，不含专家与注意力）。但为算这 1 个词，GPU 仍要把 **11.89 GB** 权重从 HBM 重读一遍（带宽下界仍是 **2.48 ms**）。结果每个词都独自背负全部 11.89 GB 的权重读取，算术强度仅约 `1 FLOP/B`，远低于 H200 的 `206 FLOP/B` 平衡点。
- 第三阶段：**verify**（投机解码检验，对应赛题 P1–P4 的 8 词档）。既然在 decode 下花 2.48 ms 读一遍权重只算 1 个词让算力严重闲置，SGLang 默认打开投机解码。它把预填充刚产出的第 6 个已知词，连同位置 `7..13` 的 **7 个草稿词**合在一起，凑成 **8 个输入词**（`L = 8`，保持在 `T ≤ 8` 档位）。这 8 个词拼成 `[8, 8192]` 一次性送进 62 层同时检验（块内带因果掩码，草稿来源与接受规则不展开）。在图 0.0-1 中，这 8 个词（位置 `6..13`）接在 5 格已缓存词之后。每层写入 8 格 KV，并连同原有 5 格共读出 `5 + 8 =` **13 格**（`3,328 B`）KV（62 层共读 `206,336 B`、写 `126,976 B`，末尾取全部 `R = 8` 行送入 `lm_head`）。图 0.0-1 在该模式下的读数为：`本趟 8 个词（第 6 个已知 + 7 个草稿）一次流过 62 层 · 每层读 KV 13 格、写 8 格`；`读权重 11.89 GB（不含专家）· 平均每个词摊 1.49 GB · 带宽下界 2.48 ms`。
  这一趟同样读取 **11.89 GB** 稠密与 `lm_head` 权重（不含专家的带宽下界同为 **2.48 ms**，稠密部分约 `66.6 GFLOP` 加 `lm_head` `26.48 GFLOP` 共 `93.05 GFLOP`）。8 个词把平均每词分摊的稠密权重读取压低了 8 倍至 **1.49 GB**，只要草稿猜中前几个词，就能用一趟前向的时间产出多个词。

看清了整座 62 层大模型的全貌后，为什么本书接下来的所有章节都只拆开其中 **1 层**？因为这 62 层具有完全一致的接口契约。每一层都从 HBM 接过上一层留下的 `(x_l BF16 [T, 8192], stream_l FP32 [T, 8192])`，读写本层自己的 FP8 KV 缓存，再把更新后的状态交给下一层。只要把这 **1 层**内部的全部计算与硬件交接压到物理极限，就能把重复 62 次的主体解码器推到极限（整网耗时还包含词表嵌入、`lm_head` 及线上 8 卡通信）。

---

**带走一句话：** 一句话穿过 `Muse Spark Open` 的 62 层时，纵向靠 `(x_l BF16, stream_l FP32)` 跨层交接、横向靠留在各层原地的 `256 B/词` FP8 KV 缓存跨时间步复用，而“已知提示词可并排共享 `11.89 GB` 权重、未知生成词只能逐个重读权重”的因果差异，把推理必然劈成了 `prefill`、`decode` 与 `verify` 三种模式。

**下一章要回答的问题：** 点开图 0.0-1 步骤 3 里的任意 **1 层**（`Layer_l`），它在单张 H200 上究竟包含哪 8 个具体计算阶段、各阶段之间怎么交接，为什么同一层在单请求 `decode` 下全卡在 HBM 带宽（滑窗层下界 40.0 µs、全长层下界 44.2 µs），而在首轮 16,384 词分块 `prefill` 下全卡在 Tensor Core 算力（单层下界 5.5–9.8 ms）？→ 进入 第 0 章：拆开一层模型——它在 Decode 与 Prefill 下算什么、最快能跑多快？
