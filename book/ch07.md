## 1. 起点 `a0`：阶段 2 算什么，为什么要把 8 个查询头叠成矩阵乘的行？

<!-- FIG ch07-gqa: 图 7-1 画阶段 2 分页 GQA 注意力起点（a0）的数据流解剖：上方对比标量逐查询头独立读取历史 KV 缓存与 GQA 8:1 分组将同一 KV 头的 8 个查询头叠成 Tensor Core 矩阵乘的 M 行（共享 1 次 256 B/词元 FP8 键值读取）；下方展示将按头均方根归一化、滑窗层 RoPE 与新键值 FP8 写入缓存合并为单次序言启动的算法步。 -->

分组查询注意力（GQA `8:1`）里，8 个查询头对应同一个 KV 头。如果让每个查询头各自去读历史 KV 缓存，同一份键值数据就得从显存里读 8 遍；把这 8 个查询头叠成一个矩阵的行，读一次键值就能同时算完 8 个头。

在看具体优化之前，先把阶段 2 的输入、输出和五步计算理清楚。8 卡张量并行下，单张 H200 负责 16 个查询头和 2 个 KV 头（每头宽 64 维，见第 0 章第 1 节）。阶段 2 接收阶段 1 留在 HBM 或 L2 里的 `qkv`（形状 `[B, L, 2304]`，`BF16`），同时从 HBM 读取序列长度 `seq_lens`（`[B]`，`int32`）、每页存 1 个词元的分页页表 `page_table`（`[B, max_pages]`，`int32`），以及 1 字节浮点的分页缓存 `K_cache, V_cache`（`[pages, 1, 2, 64]`，`FP8 E4M3`，单卡每个历史词元每层占 `2 × 2 × 64 × 1 B =` **256 B**）。五步计算依次如下：

1. **按头均方根归一化（RMSNorm）**：把 `qkv` 切分成查询 `q_in [B, L, 16, 64]`、键 `k_in [B, L, 2, 64]`、值 `v_in [B, L, 2, 64]` 和门控 `gate [B, L, 16, 64]`。对查询和键各自按 64 维的头在 `FP32` 里做无权重均方根归一化以稳定向量范数，再舍入回 `BF16`；值 `v_in` 不做归一化。
2. **旋转位置编码（RoPE，只在 46 个滑窗层执行，16 个全长层直接跳过）**：把 `q_norm` 和 `k_norm` 按相邻偶数与奇数维配对 `(2i, 2i+1)`，在 `FP32` 中按词元的绝对位置旋转一个角度，把位置信息编进查询与键的夹角里，结果再舍入回 `BF16`。
3. **转成 `FP8` 并原地写进分页缓存**：为了把键值缓存体积和带宽需求压到 `BF16` 的一半、并直接送进吞吐翻倍的原生 `FP8` Tensor Core，把查询直接转为 `q_fp8`（`FP8 E4M3`），把新算出的 `k` 和原始 `v_in` 夹断在 `±448` 内饱和转为 `FP8 E4M3`，按物理页槽索引 `cache_loc [T]` 原地写进 `K_cache, V_cache` 供后续步骤读取。
4. **`8:1` 分组查询注意力**：本卡 16 个查询头均分成 2 组，每组 **8 个查询头共享 1 个 KV 头**。对请求 `b` 位置在 `p = seq + j` 的第 `j` 个新词元，全长层读 `0..p` 的全部可见键，滑窗层只读最近 `max(0, p - 2047)..p` 的可见键（块内 `L` 个新词元之间满足下三角因果掩码），将查询缩放因子 `5.473` 与 `1 / √64 = 1/8` 合并后算出注意力权重 `P = softmax((q_fp8 @ K_visible.T) * (5.473 / 8))` 和 `o_raw = P @ V_visible`。
5. **门控输出归一化**：每个查询头的输出独立做一次无权重均方根归一化再乘门控激活，得到 `o_attn = rmsnorm(o_raw) * sigmoid(gate)`（形状 `[T, 1024]`，`BF16`），写回 HBM 或 L2 交给阶段 3 的 `o` 输出投影。

同样是这五步计算，当每个请求的新词数 `L` 从 1 变到 8、再变到 753 与 16,384 时，每读一页历史 KV 能分摊给多少行查询跟着变，算子依次跨过第 5 章第 2 节的三个区间，硬件瓶颈也随之转移：

- **逐词解码（`L = 1, T = B`，对应区间 I）**：每个请求只有 1 个新词。滑窗层只看最近 `2,048` 个词的键值，数据量极小，耗时卡在内核启动与归约延迟上；全长层在 `80,000` 词历史上下文下每请求要读 `20.5 MB` 键值，单请求算术强度只有 **`16 FLOP/B`**（带宽下界 **`4.3 µs`**），`B = 32` 时全卡带宽下界为 **`126.4 µs`**，属于 HBM 带宽与分页寻址延迟受限。
- **8 词投机检验（`L = 8, T = 8B`，对应区间 II）**：同一个请求里的 8 个候选词共享同一批历史键值页，全长层算术强度涨了 8 倍，升到 **`127.5 FLOP/B`**（`B = 32, T = 256` 时带宽下界 **`126.8 µs`**，算力下界 **`78.5 µs`**）。对 CUDA core 来说，理想算力平衡点只有约 `14 FLOP/B`（见第 5 章第 2 节），`127.5 FLOP/B` 早已让标量管线彻底算力受限；而且每个 KV 头对应的 8 个查询头乘 8 个检验词刚好凑齐 **`64` 行**，计算必须切进 `wgmma` Tensor Core 管线。
- **长分块预填充（`L = 753` 或 `16,384`，对应区间 III）**：同一页历史 KV 被成百上千行查询复用。在已有 `65,536` 个缓存词后面追加 `L = 16,384` 个新词的全长层分块上，运算量达到 **`4,948 GFLOP`**（算力下界约 **`5.00 ms`**），而读一遍 `65,536` 个历史词元的键值缓存只有 `16.8 MB`（按 `4.8 TB/s` 算只需 **`3.5 µs`**）。到这里，瓶颈彻底转成了 Tensor Core、特殊函数管线（SFU）与指令发射槽受限。

未融合的基线把这五步拆成 5 个独立内核依次启动：按头归一化、写缓存、查询转 `FP8`、分页注意力主核和门控输出归一化。起点内核 **`a0`** 在基线上改了两处（图 7-1）：

第一处是按 KV 头组织 CTA，把同一 KV 头的 8 个查询头直接排作矩阵乘左矩阵 `Q` 的行（`L = 1` 时为 8 行，`L = 8` 时 `8 × 8 = 64` 行刚好填满 `wgmma` 的 `M = 64` 行），并把 `Q` 直接量化成 `FP8 E4M3`，让第一段矩阵乘 `Q · K^T` 直接跑在吞吐翻倍的原生 `FP8` Tensor Core 上，省去对 `K` 的解包指令（见第 5 章第 4 节）。每页键值搬进片上后当场与 8 个查询头相乘，相比标量逐头独立读取的设计，历史 KV 的读取量降到了**八分之一**。代价是在单词解码（`L = 1`）时，8 个查询头只填满 `mma.sync` 16 行的一半，剩下 8 行是无用填充；但因为 `L = 1` 时瓶颈在读 KV 的显存带宽而不在 Tensor Core 算力，这 8 行空填充不会拖慢关键路径（亏本边界未测）。

第二处是把主核前后的序言和尾声合起来，省去中间读写显存的往返（见第 1 章第 1 节与第 4 章第 2 节）。主核前面的按头归一化、`RoPE`、查询转 `FP8` 与新键值写缓存合为一次序言启动，方差归约留在寄存器里。在预填充 `T = 16,384`（及 4 个请求各追加 753 个词的 `T = 3,012`）下，按每词元 1 个 CTA 组织的融合序言核把耗时从 `52.75 µs` 压到 **`31.0 µs`**（`T = 3,012` 从 `10.75 µs` 压到 **`6.9 µs`**）。预填充注意力主核则在尾声直接算完 `rmsnorm(o_raw) * sigmoid(gate)`，省掉独立的输出归一化启动，换上这套带融合尾声的预填充注意力核后，整层预填充耗时从 `233.07 ms` 降到 **`231.36 ms`**。代价是序言、尾声与主核代码耦合在一起，单项额外的寄存器与共享内存占用未测。

合入 GQA `8:1` 矩阵化读取、原生 `FP8 Q · K^T` 与序言/尾声融合后，就得到了阶段 2 的起点 **`a0`**。但 `a0` 给每个 `(请求, KV 头)` 只派 1 个 CTA：单请求解码（`B = 1`，仅 2 个 KV 头）时全卡只有 2 个 CTA，130 个 SM 空着；多请求并发时，请求长短不一又会让长请求在波次末尾拖出尾巴。下一步就得沿键值维做切分，把全卡 132 个 SM 的波次排平（`a0 → a1`）。

## 2. `a0 → a1`：在线 Softmax 原理，以及并发不够或请求长短不齐时 KV 该切几段？

<!-- FIG ch07-split: 图 7-2 画阶段 2 注意力从 a0 到 a1 的四项波次与切分决策：上方对比解码 16/32 请求全长下过度切分（128/64 段产生 3.88 轮波次、每 CTA 6.6 µs 固定开销累加）与收拢为 32/16 段（省 12.10 / 9.74 µs）的权衡；中间展示 verify 32 请求全长调整网格顺序让读取同一 128 B 键值行两半的 CTA 相邻启动以命中 L2（省 11.90 µs）；下方展示空分片写 lse = -inf 跳过零输出写出与按形状查表分派最优内核的算法步。 -->

把长序列的历史 KV 缓存切成多段并行算（Split-KV），或者在单个 CTA 里分块流式读取键值，首先会撞上一个算法问题：Softmax 的分母需要所有键的指数和，键值还没读完时，怎么边读边算？

答案是 **Online Softmax（在线 Softmax）**。常规做法要先扫第一遍全部键算出整行最大值 `m = max_k s_k` 和指数和分母 `l = sum_k 2^(s_k - m)`，第二遍才能拿 `2^(s_k - m) / l` 去乘值向量 `V`（这里底数取 `2` 而不是 `e`，是因为 GPU 的硬件超越函数指令 `ex2` 直接算 `2^x`，只需把注意力缩放系数预先乘上 `log2(e) ≈ 1.4427`，就和以 `e` 为底完全等价）。在线 Softmax 把两遍扫描压成了一遍边读边修正的递推：每流进一块新键值，先算出本块的行最大值 `m_tile`，把运行期行最大值从旧基准 `m_old` 更新为 `m_new = max(m_old, m_tile)`。因为之前累加在寄存器里的分母 `l_old` 和未归一化输出 `O_old` 都是按旧基准 `m_old` 缩放的（存的是 `sum 2^(s - m_old)`），当基准抬高到 `m_new` 时，只需给旧的 `l_old` 和 `O_old` 都乘上同一个重缩放因子 `alpha = 2^(m_old - m_new)`，就能把历史累加值原地折算到新基准下，再加上本块的 `sum 2^(s - m_new)` 与 `sum 2^(s - m_new) * V`。等全部键值块流完，最后做一次除法 `o = O / l`，就得到完整的注意力输出。

理解了块内的换底递推，也就看懂了 **为什么 Split-KV 跨 CTA 合并是精确的**。把一个请求的可见历史键区间 `[0, N_b)` 切成 `S` 段交给 `S` 个分片 CTA 后，第 `i` 个 CTA 各自用在线 Softmax 算出本段的行最大值 `m_i`、局部指数和 `l_i` 以及按本段分母归一化的局部输出 `o_i = O_i / l_i`，并把对数分母 `lse_i = m_i + log2(l_i)` 与 `o_i` 写进全局工作区。注意 `2^lse_i = 2^m_i * l_i` 正是以 `0` 为基准的本段真实分母，因此全体键的总对数分母就是 `lse_total = log2(sum_i 2^lse_i)`。合并核（或第 7 节的核内归约）按 `o = sum_i 2^(lse_i - lse_total) * o_i` 把各段加起来：乘上 `2^(lse_i - lse_total)` 恰好把每段自己的分母 `l_i` 消掉、换成了全体键的总分母，加起来的结果与不切分时分毫不差。

有了精确切分与合并的数学保证，接下来算硬件账。每个分片 CTA 除了流式处理 64-key 分块（每块约 `2.04 µs`），还要独立执行一遍序言（读页表、装查询 `Q`）和尾声（写回局部 `o_i` 与 `lse_i`）；这套每个分片 CTA 都要付一次的固定工作约占 **`6.6 µs`** 的 SM 时间，和第 1 章讲的内核启动空隙是两回事。一旦分片 CTA 总数超出全卡一轮波次的驻留容量、叠成多轮波次，每一轮都要多付一遍这 `6.6 µs`，合并核也要多读一份局部结果。所以切分原则很直接：**并发不够时切细，把 132 个 SM 填满；并发够了就少切，省下每段 `6.6 µs` 的固定开销，再按实际键数均分工作量，别让长请求在波次末尾拖出尾巴。**

顺着这笔账，**`a0 → a1`** 做了五处改动（前四项对应图 7-2 的四个模式，第二项的虚拟键等分与图 7-10 模式 1 对应）：

第一处是让切分段数 `S` 与并发请求数 `B` 反比调节。解码全长分片核每个 SM 可驻留 8 个 CTA，全卡 132 个 SM 一轮波次容量为 `132 × 8 = 1,056` 个 CTA。单请求解码（`B = 1`）时，128 段切分（2 个 KV 头共 256 个 CTA）只占 `0.24` 轮波次；把 `S` 翻倍到 `256` 段能增加在途读取字节，使主核耗时从 `15.52 µs` 降到 **`13.82 µs`**（端到端省 **`1.07 µs`**），代价是合并核要读 256 份局部结果。到了 `B = 16 / 32` 解码全长，保持 `128 / 64` 段会产生 `4,096` 个 CTA（`3.88` 轮波次）；把 `S` 收拢到 `32 / 16` 段（`1,024` 个 CTA = `0.97` 轮），虽然每个 CTA 处理的键值分块数变为 4 倍，但省掉了多轮 `6.6 µs` 的每 CTA 固定开销、并把局部结果份数砍到四分之一，在解码 16 和 32 请求全长上分别省下 **`12.10 µs` 和 `9.74 µs`**。同理，在 8 词 `verify 16 / 32 请求全长`上把切分从 `32` 段减到 `16` 段，合并核耗时从 `12.58 µs` 压到 `7.58 µs`（32 请求），端到端分别省下 **`2.54 µs` 和 `7.74 µs`**；但若继续砍到 `8` 段，全卡只剩 `0.48` 轮波次，SM 填不满反而**慢了 `101 µs`**。而在单请求滑窗检验（`B = 1, T = 8`）中，改为启动 `33` 个各算 1 块的单分块 CTA，并把流水级数设为 1 级（只算 1 块时 2 级环没有任何可重叠的下一块，只会白跑填充拷贝），端到端省下 **`1.10 µs`**。

第二处是按实际键数比例切分，抹平长短请求之间的尾波（见第 2 章第 1 节）。在多轮智能体对话（`agentic`）负载下，各请求的历史长度在均值 `±7.5%` 内均匀分布，最长约为最短的 `1.16` 倍；若给每个请求机械分配相同段数，长请求 CTA 会比短请求慢约 **`15%`**。在 **`verify 32 请求全长（T = 256）`** 上，双头 verify 核每线程占 80 个寄存器、每 SM 驻留 2 个 CTA，全卡一轮波次容量正好是 `132 × 2 =` **`264` 个 CTA**。`a1` 直接启动满额的 `264` 个 CTA（凑满 `1.00` 轮波次，补齐原 `256` 个 CTA 只占 `0.97` 轮留下的 4 个空闲 SM），把 32 个请求的虚拟键值空间拼成一条连续带（每个请求边界预留 5 个虚拟分块）交给 264 个 CTA 等分，使每个 SM 最少活跃时间占比从 `63.8%` 升到 `94.9%`，端到端净省 **`3.90 µs`**（整层解码/检验上同机制省 **`9.5 µs`**；代价是跨请求边界的分片让合并核多花 `1.50 µs`）。同理，在预填充 `T = 16,384` 全长层上，原网格 `1,366` 个 CTA 跑完 10 轮波次后还余 46 个尾部块；把最轻的 40 个查询块各沿键值维拆成 4 个子块（扩为 `1,606` 个 CTA）去填满尾波，在 `ctx = 32K` 和 `65K` 全长核上分别省下 **`210 µs` 和 `345 µs`**。

第三处是重排网格维度顺序，让读同一条 128 B 键值行的两个 CTA 相邻启动。在分页缓存 `K_cache, V_cache`（`[pages, 1, 2, 64]`，`FP8 E4M3`）里，同一个历史词元的两个 KV 头紧挨着存放在同一条 128 B 缓存行里，每个头占 64 B 半行。在每个 CTA 处理单个 KV 头的 verify 全长核里，如果两个 KV 头的 CTA 启动时间隔得远，前一个 CTA 读进 60 MiB L2 的 128 B 缓存行等不到后一个 CTA 就被后续键值流冲掉了，同一行大概率要从 HBM 读两次。CUDA 规范并不保证网格内 CTA 的派发顺序，但 H200 硬件块调度器实测按网格索引递增派发；把网格维度顺序排成 `(HKV, batch, splits)`、让 `HKV` 成为变化最快的第一维后，读取同一随机 128 B 行前半段和后半段的两个 CTA 会紧挨着先后启动，第二个 CTA 直接命中还留在 L2 里的那半行（这一做法只用来提高 L2 命中率，即使硬件派发顺序改变也绝不影响正确性；若需规范保证的跨 CTA 片上协同，则应使用第 3 章的线程块集群）。这一步不占任何额外寄存器和共享内存，在 **`verify 32 请求全长`**上实测省下 **`11.90 µs`**（在 `verify 16 全长`上为中性）。

第四处是跳过空分片与无效掩码区。切分数固定时，短序列或滑窗边界处会出现 `start_i >= end_i` 的空分片；`a1` 让空分片只写 `lse_i = -inf`，不写全零的局部输出缓冲，合并核看到 `lse_i == -inf` 直接跳过读取（单项收益未测）。预填充里则按每 8 个查询词一块先算出紧致的可见键起止范围，跳过落在因果与滑窗掩码之外的键值块。

第五处是按 `(batch, q_len, window)` 静态查表分派最优内核。没有任何单一内核或切分参数能在全部负载下都最快。为 12 个解码与检验形状（6 个负载 × 滑窗层权重 46 与全长层权重 16）分别绑定实测最快的内核与切分参数（包括在 `verify 16 滑窗`上把每集群 CTA 数从 8 缩为 7 消除 16 个 3-CTA SM 争抢、省下 **`1.31 µs`**，见第 3 章第 1 节），使 12 个形状的几何平均耗时从 `3,473.0 µs` 降到 **`3,193.4 µs`**（快 **`8.05%`**）。

反之，如果试图省去静态比例计算、改用全局原子计数器让同组 CTA 动态认领（steal）键值分块，在注意力里一定会亏本。因为单个 64-key 分块的计算只需 `0.87–2.04 µs`，动态认领在每块上带来的块内屏障同步（`bar.sync`）与元数据交接开销直接让单块成本涨了 `10%` 并打断页表预取，在 `verify 32` 和 `16 请求全长`上反而**慢了 `22.6 µs` 和 `10.0 µs`**（在分块区入口用原子 `CAS` 动态挑槽位，推断因每次切换排空了 `cp.async` 环形缓冲，在 `verify 32 全长`上也**慢了 `18.90 µs`**）。

`a1` 把 132 个 SM 的波次排平之后，剖析器指向了单个 CTA 内部：每读一页历史 KV 都要先走三跳指针追踪（`a1 → a2`）。

## 3. `a1 → a2`：每读一页 KV 都要走三跳指针追踪，怎么藏住 640 ns 的页表往返？

<!-- FIG ch08-a1: 图 7-3 画阶段 2 分页注意力打破三跳指针追踪链的数据流（对应入口“读 seq_lens（600 ns）→ 读 page_table（640 ns）→ 首条 cp.async 落地（1,150 ns）”三跳串行长记分牌等待、单请求满长投机并发与跨轮提前流水化）。 -->

<!-- FIG ch07-d: 图 7-4 画阶段 2 注意力在 PDL 等待前由单线程发出 cp.async.bulk.prefetch.L2 页表预取被 KV 流冲出导致 DRAM 读 2 次的实测反例数据流与时间线（同图模式 1 的多播反例见第 3 章第 4 节）。 -->

为什么常规的 `cp.async` 环形缓冲藏不住分页 KV 缓存的读取延迟？因为当每页只存 1 个词元（`page_size = 1`）时，读一页历史键值必须先串行走完三跳指针追踪（图 7-3 模式 1）。第 1 跳从全局内存读序列长度 `seq_lens[b]`（约 `600 ns`）；第 2 跳用算出的逻辑页号去读离散页表 `page_table[b, page]`（约 `640 ns`）；等物理页号写回寄存器之后，第 3 跳才能用宽整数乘加指令（`IMAD.WIDE`）算出显存地址 `addr = base + phys_page * 128`，发出首条 `cp.async` 把键值搬进共享内存（约 `1,150 ns`）。三跳串行加起来，在 **`verify 1 请求全长（T = 8）`** 上从启动到首块数据落地实测要等 **`2,400 ns`**（约 `2.4 µs`）。

先看单次收集是怎么做的。Hopper 的硬件 TMA 不支持按索引列表收集离散的 64 字节或 128 字节行，注意力内核只能用 16 B 的 `cp.async` 逐行收集。第 2 节的单头核每次只取 64 B 半行，随机行带宽只有 `2.6–3.1 TB/s`；解码核改为把同一个词元两个 KV 头拼成的 128 B 整行一次收进共享内存并配 128 B 异或交错（见第 3 章第 2、5 节），把随机行带宽推到 **`4.0–4.1 TB/s`**，解码 32 请求全长核耗时从 `200.4 µs` 降到 `183.9 µs`，端到端省下 **`15.58 µs`**（滑窗省 **`2.11 µs`**），同时给页表加载打上 `evict_last` 留存提示（见第 2 章第 3 节）。即便如此，在第一次使用物理页号计算显存地址的 `IMAD.WIDE` 指令处，依然有 **37%–42%** 的停顿卡在长记分牌上。

问题就出在那 `640 ns` 的第 2 跳页表往返还留在每轮 `cp.async` 的发射路径上。**`a1 → a2`** 用两处改动拆开这条三跳串行链（图 7-3）：

第一处是把页表读取跨 4 个分块提前流水化（`tile j + 4`，图 7-3 模式 3）。在进入主循环等待之前，内核先把第 `0..3` 分块的页表项读进寄存器（并在 16 / 32 请求解码滑窗上把 `cp.async` 环设为 3 级）。进入第 `j` 轮主循环后，线程一面用已经在寄存器里就绪的物理页号 `phys_page_{j+1}` 发出下一块的键值 `cp.async`，一面提前向 `page_table` 发出第 `j + 4` 分块的页表读取，把在途的 `phys_page_{j+2..j+4}` 保存在寄存器里（跨 4 块是平衡 `640 ns` 页表往返与寄存器占用的实测最优跨度）。这样等循环走到第 `j + 4` 轮时，物理页号早已就绪，在解码 16 请求全长上端到端最高省下 **`1.58 µs`**（额外寄存器增量未测）。此外，在进入 PDL 等待点之前先算好与上游无关的门控激活 `sigmoid(gate)` 和分块边界在 `verify 16 全长`上省下 **`1.05 µs`**，只让持有新词元行的分片 CTA 执行块内屏障在解码 16 滑窗上省下 **`0.61 µs`**（见第 1 章第 2 节与第 3 章第 3 节）。

第二处是在单请求解码上做投机并发读取（图 7-3 模式 2）。分页页表 `page_table` 的列跨度等于当前批次分配的最大页数；当批次里只有 1 个请求（`B = 1`）时，这个最大页数恰好就是该请求的历史词数加上本步新词数。所以在 **解码 1 请求全长（`T = 1`）** 入口处，内核不等第 1 跳 `seq_lens[0]`（`600 ns`）返回，先假设该请求占满整行页表，把前 4 块的页表读取与 `seq_lens[0]` **同时发出去**，在 PDL 等待点之前再拿刚回来的真实长度核对（猜错就回退，实测全猜错代价为 `0.00 µs`）。这把入口的三跳串行等待压成了两跳，在解码 1 请求全长上实测省下 **`0.26 µs`**（移植到整层解码 16 / 32 全长也提速 **`0.53% / 0.45%`**）。不过在 8 词 `verify 1 全长（T = 8）`上，生产者从第 3 块起就要等消费者腾出环形缓冲槽位，入口抢先的一点时间到第 3 块就被槽位等待吞掉了，没有端到端收益。

预取并不是越早、越远越好。一旦越过**寄存器配额、显存队列或 L2 留存窗口**这三条边界，预取就会变成亏本：

第一条边界是**寄存器配额**。当生产者只有 32 个寄存器预算时（见第 4 节双头 verify 核），把页表读取的领先距离从 82 条指令拉大到 152 条指令，在途页号多占寄存器直接触发了 `28 B` 写出与 `56 B` 读入的局部内存溢出，在 `verify 32 全长`上反而**慢了 `2.6%`**（做删除实验把页表加载直接删掉测上限，最多也只能快 `1%–2%`，见第 10 章；阶段 6 专家核因预取过远掉驻留的同类反例见第 8 章）。

第二条边界是**显存队列与无效预载**。在解码全长核里把主循环提前 `1.0–2.1 µs` 启动，提前发出的请求排在第 0 分块前面堵住了显存队列，把第 0 分块的等待时间等量拉长，整个循环结束的时刻没有提前，在解码 16 / 32 全长上反而**慢了 `0.13–0.56 µs`**。而在合并核检查对数分母掩码（`lse == -inf`）之前无条件预载局部输出缓冲，会多读一倍合并字节，在 `verify 16 全长`上**慢了 `0.80 µs`**。

第三条边界是 **L2 留存窗口**（图 7-4 模式 2）。如果在 PDL 等待点之前发出 `cp.async.bulk.prefetch.L2` 预取页表，预取行在用到之前就被流经 L2 的键值数据冲掉了，同一批页表行得从 DRAM 读两次，耗时反而**慢了 `0.03–0.53 µs`**（见第 2 章第 3 节与第 3 章第 4 节）。

`a2` 把页表往返藏进流水线之后，当词元数涨到 `T = 128..16,384`、大量查询行进入 `wgmma` 主循环时，瓶颈搬进了 CTA 内部的分工与发射槽（`a2 → a3`）。

## 4. `a2 → a3`：多词注意力进入 `wgmma` 后，寄存器怎么分、多余指令怎么删？

<!-- FIG ch08-a2: 图 7-5 画阶段 2 预填充全长注意力将全 warp 相同的环槽号、相位位与矩阵描述符从私有向量寄存器 R 移入统一寄存器 UR 并改按 warp 到达 mbarrier 的数据流。 -->

<!-- FIG ch07-vw2: 图 7-6 画阶段 2 注意力从 a2 到 a3 的双头分工与指令瘦身解剖：上方展示 verify 全长双头内核由 1 个生产者收集整条 256 B 双头键值行同时喂给 2 个消费者 warpgroup，并将生产者设为默认分区以消除跨 setmaxnreg 的 8 B 寄存器溢出（省 15.78 µs）；中间展示两个消费者 warpgroup 通过命名屏障 4/5 交替执行 [QK(0)] 与 [PV(j), QK(j+1)] 窗口的乒乓调度（省 2.32 µs）；下方展示消费者循环拆为无掩码内部段与有掩码边界段（省 3.38 µs）及解码 6 分块 pg_a/pg_b 寄存器轮换的算法步。 -->

当注意力进入 8 词 verify（`T = 128 / 256`）和长序列预填充（`T = 753..16,384`）时，每个分块的矩阵乘切进了 4 个 warp 协同的 `wgmma`（见第 5 章第 3 节）。此时瓶颈已经不在显存，而在 CTA 内部：**生产者与消费者怎么分寄存器才不会溢出到局部内存，两个消费者组怎么错开使用硬件管线，以及怎么把占着发射槽的重复标量指令删掉。**

先看单个 CTA 内部是怎么分工的。在 **`verify 32 与 16 请求全长（T = 256 / 128）`** 里，本卡的 2 个 KV 头共享同一个请求的历史页表。因此 `a3` 把这 2 个 KV 头合进同一个**双头 verify 注意力核**：每个 CTA 包含 3 个 warpgroup（384 线程），即 1 个生产者组和 2 个 4-warp 消费者组（分别算 KV 头 `h = 0, 1`）；编译时按每线程 80 个寄存器分配，每个 SM 驻留 2 个 CTA，运行期再用第 3 章第 1 节的 `setmaxnreg` 把生产者压到 32 个寄存器，把腾出来的寄存器留给两个消费者组。本请求两个 KV 头的查询块 `Q_0, Q_1`（各 `[64, 64]`，`FP8 E4M3`）常驻共享内存；生产者每次按词元从 HBM 读入双头共 `256 B` 的 `K, V` 整行填入环形缓冲，同时喂给两个消费者组，在各自的寄存器里累加局部注意力输出 `O_0, O_1`。仅把两个 KV 头合进同一 CTA 收集这一步，在 `verify 32 全长`上就省下 **`4.80 µs`**（将 `verify 16 全长`也切入该双头核后，核耗时从 `133.06 µs` 降到 `129.02 µs`，端到端省 **`2.24 µs`**）。代价是每线程占 80 个寄存器、每 SM 限驻 2 个 CTA，且单个 CTA 包揽两个 KV 头会让全卡的总 CTA 数减半。

在此基础上，**`a2 → a3`** 在核内改了四处（图 7-5 与图 7-6）：

第一处是把生产者放在主分支（默认分区），消除跨越 `setmaxnreg` 缩配额点的 8 字节寄存器溢出（图 7-6 模式 1）。在写生产者与消费者的角色分支时，排在主分支上的角色会直接继承分支前准备好的局部变量；而跳去支线的角色在执行 `setmaxnreg` 缩减寄存器配额时，任何跨过分支点还存活的变量都可能因为缩配额后装不下而被编译器溢出到局部内存。原先把消费者放在主分支、让生产者跳去支线并把配额压到 32 个寄存器，编译器把生产者的一个键值行变量提到了分支点之前，跨过 `setmaxnreg` 时直接触发了 **8 字节局部内存溢出（Spill）**。反过来把**生产者设为默认主分支**并配合下文的无掩码循环剥离后，8 字节溢出直接归零，长记分牌停顿少了 `18%`，剖析器测得的核耗时从 `248.90 µs` 降到 **`229.44 µs`**，在 `verify 32 全长`上端到端省下 **`15.78 µs`**（快 **`6.8%`**）。

第二处是用命名屏障 4 和 5 让两个消费者 warpgroup 乒乓交错（图 7-6 模式 2）。命名屏障是带编号（`0..15`）的硬件屏障指令 `bar.sync id, N`，只让指定的 `N` 个线程互相等，同一 CTA 里的生产者不受影响。在双头 verify 核里，如果两个消费者组同时去抢 Tensor Core 发射 `wgmma`，接着又同时停下来做两段矩阵乘之间的逐元素计算（见第 5、6 节），矩阵管线和算术管线（FMA/SFU）就会轮流空转。`a3` 用两条 256 线程的命名屏障（`bar.sync 4, 256` 与 `bar.sync 5, 256`）让两个消费者组错开半拍，轮流进入开头的 `[QK(0)]` 和随后的 `[PV(j), QK(j+1)]` 矩阵乘窗口（见图 7-6 模式 2 的时间线）。代价是每轮多一次 256 线程屏障同步、串行化两组的矩阵发射窗口，但两条硬件管线都能连续运转，在 `verify 32 全长`上省下 **`2.32 µs`**。

第三处是把无掩码的内部循环和带掩码的边界循环拆开（图 7-6 模式 3）。在 8 词 verify 与长序列预填充里，前面绝大多数历史键值分块都完整落在因果与滑窗视野内部，根本不需要掩码；只有最后几个边界分块才需要按词元位置判断掩码。前 `nu` 个完整分块直接走不含掩码分支的紧凑主循环，把掩码判断留给最后的边界循环，在 **`verify 16 请求全长（T = 128）`** 上省下 **`3.38 µs`**（快 **`2.74%`**；在 `verify 1 全长`上为中性）。

第四处是把整个 warp 相同的标量移进统一寄存器 `UR`，并清理主循环里的冗余指令（图 7-5 模式 2 与图 7-6 模式 3）。在**预填充全长注意力核**（1 个生产者 warpgroup 加 3 个消费者 warpgroup，共 512 线程）里，环槽号 `slot`、相位位 `phase` 和 `wgmma` 的 64 位矩阵描述符在同一个 warp 的 32 个线程里完全一样，原先却在向量寄存器里反复重建。把这几个标量放进每个 warp 共用的统一寄存器（`UR`，见第 4 章）后，每个 warp 每轮只算一次；同时把每块一次的 128 线程屏障改成每个消费者 warp 在 `wgmma.wait_group<0>` 后各自独立向空槽 `mbarrier` 报到，使每分块静态指令从 `304` 条降到 **`284` 条**，净省 **20 条**指令。在解码与滑窗内核里，则按 6 个分块展开循环、用奇偶两组页号寄存器 `pg_a / pg_b` 轮换消除 `if` 汇合点的假记分牌拷贝停顿（解码 32 全长省 **`0.86 µs`**），把查询准备辅助函数强制内联以消除局部内存栈帧、把 64 位有符号除法换成 32 位无符号除法（`verify 32 全长`省 **`0.40 µs`**），并在单请求滑窗核里用硬件转置加载指令 `ldmatrix.trans`（从共享内存加载 `8×8` 半精度子块时顺带在硬件里完成行列转置）读取 `V^T`（提速 **`1.2%–2.6%`**）。

这几项改动有两处会亏本：

第一处是**不能把双头共驻单 CTA 的做法照搬到单词解码（`L = 1`）**。在 8 词 verify 下，单个 KV 头已经有 64 行查询，双头合进 1 个 CTA 能省 `4.80 µs`。但在 `L = 1` 解码下，把两个 KV 头塞进同一个 CTA，实测观察到解码 16 和 32 请求全长的速度退化到 **`0.54×` 和 `0.50×`（慢了约一倍）**；推断是因为 `L = 1` 时单头只有 8 行查询，合并双头既填不满 `wgmma`，又让全卡的 CTA 总数直接减半、并发严重不足。

第二处是**乒乓屏障锁住的窗口不能过碎**。在双头 verify 核里，如果只锁住单次 `[QK(j)]` 窗口而不把 `[PV(j), QK(j+1)]` 合在一个窗口里交替，每轮多出来的屏障等待会让 `verify 32 全长`反而**慢 `4.5 µs`**（至于在阶段 6 专家核里为凑乒乓压浅环形缓冲槽数导致亏本的反例，见第 8 章）。

`a3` 理顺了 CTA 内部的分工与指令流之后，剖析器指向了夹在两段矩阵乘之间的在线 Softmax：在 64-key 循环里它占了 `58%` 的指令，在预填充 128-key 循环里它把 4 通道 SFU 的占用率推高到了 `77.3%`（`a3 → a4`）。

## 5. `a3 → a4`：4 通道 SFU 忙到 77.3% 时，怎么把指数和行求和挪去别的管线？

<!-- FIG ch08-b1: 图 7-7 画阶段 2 在线 Softmax 惰性重缩放与空闲 Tensor Core 行求和的数据流（对应主循环给指数留出 2^τ 余量跳过未超阈值的 SFU exp2f 与 FMA 历史修正、以及用 wgmma 乘全 1.0 矩阵替代 FADD 加 SHFL 求 64 行之和的算法步）。 -->

<!-- FIG ch08-d: 图 7-8 画阶段 2 注意力中 ex2.approx.f16x2 的编译真相与 ALU/FMA 直接生成 E4M3 指数编码的管线对比（对应单行半精度打包指数 PTX 被 ptxas 拆成两条串行发往 4 通道 SFU 的 MUFU.EX2.F16 加一条 PRMT、对比惰性重缩放与在 ALU/FMA 上按 8(y+7) 直接算出 FP8 权重字节将 MUFU.EX2 从 66 条压到 2 条的算法步）。 -->

为什么夹在两段矩阵乘中间的在线 Softmax 会把整个消费者循环卡住？第 2 节算过它的递推步：每流进一块新键值，消费者都要对整个分数块求指数 `2^(s_k - m_new)`，并用 `alpha = 2^(m_old - m_new)` 重缩放历史累加器 `O`。对照第 5 章第 1 节的硬件通道数就能看出瓶颈所在：每个 SMSP 的特殊函数管线（SFU）只有 **4 条通道**，发射间隔（8 周期）是 32 通道 FMA 管线（1 周期）的 **8 倍**。在 8 词 verify 的 64-key 分块循环（共 `288` 条 SASS 指令）里，在线 Softmax 一项就占了 **58%** 的指令；而在预填充全长核的 128-key 分块循环里，每个消费者 warp 每分块要发 **`66` 条超越函数指令 `MUFU.EX2`**，把 4 通道 SFU 的占用率推高到 **77.3%**（3 个消费者 warpgroup 争用同一个 SM 的 SFU，仅排完这批指数指令就要耗去每分块 `1,548` 个周期）。

为了把工作从拥挤的 SFU 和发射槽上挪开，它接收第一段矩阵乘留在寄存器里的分数块 `S` 和历史参考最大值 `m_ref`，直接产出打包好的 1 字节权重片段 `P_fp8`（`FP8 E4M3`，每 4 个字节装进 1 个 32 位寄存器）与更新后的行分母 `l`（`FP32`）。围绕这一步，**`a3 → a4`** 做了三项跨管线改造（图 7-7 与图 7-8）：

第一项是用固定参考常数或 `__any_sync` 投票做**惰性重缩放（Lazy Rescaling，图 7-7 模式 1）**，省掉非必要的历史 `O` 重缩放链。标准在线 Softmax 每见到更大的行最大值就去重缩放历史累加器，只是为了防止 `2^(s - m)` 上溢。第 1 节对查询和键做过 64 维均方根归一化，两者的向量范数都稳定在 `√64 = 8` 附近；计入有限分位数波动后，点积乘缩放系数再转成以 2 为底的对数分数满足 `|s| ≤ 71.3`：
- 当权重 `P` 存为 `BF16`（与 `FP32` 同样有 8 位指数，正数上界约 `2^128`）时，`2^71.3` 根本不会溢出。直接拿固定常数 **`72`** 当参考基数去算 `p = 2^min(s, 72)`，每块连行最大值归约、`alpha` 因子和历史 `O` 的重缩放乘法都可以省掉，在 **`verify 32 与 16 请求全长`**上分别省下 **`6.69 µs` 和 `2.77 µs`**。
- 当第 6 节把权重 `P` 压成量程较窄的 1 字节 `FP8 E4M3`（最大正规数为 `448`，接近 `2^8 = 256`）时，就不能再用固定常数 `72` 了。此时改为保留第 0 块的参考行最大值 `m_ref`，平时把权重缩放成 `P' = 2^(8 - τ) * 2^(s - m_ref)`，特意在指数上留出 `2^τ` 的增长余量（这里用 `τ` 表示惰性重缩放的对数阈值）。只要新分块的行最大值 `m_tile ≤ m_ref + τ`，就有 `P' ≤ 2^(8 - τ) * 2^τ = 256 < 448`，既不会撑爆 `E4M3` 上界，也无需改动 `m_ref` 和重缩放历史累加器 `O, l`。每轮算出 `m_tile` 后，全 warp 只跑一条硬件投票指令 `__any_sync(0xffffffff, m_tile > m_ref + τ)`；只有当某一行突破阈值 `τ` 时，才更新 `m_ref` 并乘上 `alpha = 2^(m_old - m_new)`。在双头 verify 核里，`τ = 4` 时每块触发率只有 `7%–18%`；把阈值放宽到 **`τ = 6`** 在 `verify 32 全长`上再省 **`1.42 µs`**（滑窗 verify 核设 `τ = 8` 省 **`0.83 µs`**），代价只是每轮多 1 条投票指令并占用 `2^τ` 的指数余量。

第二项是把指数从 4 通道 SFU 挪到 32 通道 FMA 和 16 通道 ALU，并把行求和 `P × 1` 挪到空闲的 Tensor Core（图 7-8 模式 3 与图 7-7 模式 2）。

先看指数怎么挪下 SFU。无符号 `FP8 E4M3` 字节由 1 位符号 `0`、4 位指数（偏置为 `7`）和 3 位尾数组成。把偏移后的对数分数写成整数与小数部分 `y = n + f`（`0 ≤ f < 1`），要把 `2^y = 2^n * 2^f` 编码成 `E4M3` 字节，4 位指数左移 3 位填入 `8(n + 7)`，3 位尾数按分段线性近似 `2^f ≈ 1 + f` 填入 `≈ 8f`；合起来，`2^y` 的 `E4M3` 无符号字节码正好近似等于线性函数 **`8(y + 7)`**。既然是线性函数，就没必要去排 4 通道的 SFU：直接在空闲的 FMA 与 ALU 管线上用饱和乘加（`FFMA.SAT`）、打包半精度乘加和字节提取指令 `PRMT`，就能算出 `E4M3` 权重字节；同时行分母 `l` 也拿同一批 `P` 字节去乘全 `1` 矩阵，保证分子与分母自洽。这一步把每分块的 `MUFU.EX2` 从 `66` 条压到了 **`2` 条**（只留给行最大值重缩放），SFU 占用率从 `77.3%` 降到 **`0.58%`**，使预填充 `ctx = 65K` 全长注意力核耗时从 `6,651.9 µs` 降到 **`5,471.4 µs`**（单核省 **`1,180.5 µs`**），预填充整层全长与滑窗分别提速 **`2.33%` 和 `0.55%`**。代价是每 4 个权重占用的发射槽从 4 条涨到了约 9–10 条，且带分段线性近似偏差。

再看行求和 `P × 1` 怎么搬上 Tensor Core（图 7-7 模式 2）。按行累加 `64 × 64` 的权重块 `P`，原本要在算术管线上发 `38` 条浮点加法（`FADD`）加 `4` 条洗牌指令（`SHFL`，共 `42` 条）。在发射槽受限而 Tensor Core 还有空闲周期的内核里，在共享内存里放一块 `2,048 B` 全为 `1.0` 的常数矩阵 `1_{64×8}`，改发 **4 条 `wgmma.m64n8k16`** 计算 `l_tile = P_tile @ 1_{64×8}`，每分块净省 **38 条**指令，在整层 `verify 16 / 32 全长`上缩短 **`3.9 µs` 和 `3.4 µs`**（在独立注意力的双头 verify 核上用上这一步后，总指令也减少 `13%`、耗时缩短 **`1.6%–2.6%`**）。反过来，在 Tensor Core 周期已经满载的单头全长和单头滑窗 verify 核上，多发 4 条 `wgmma` 反而会拖慢矩阵管线，把这一步**删掉**反而在 `verify 32 滑窗`上省下 **`0.26 µs`**。同一个做法在两个内核里一正一负，分界线就在于哪条硬件管线先到上限。

第三项是用半精度非规格化数舍入打包和三输入最大值指令 `VHMNMX` 把发射槽省回来。把指数搬到 ALU/FMA 之后，做删除实验测上限（见第 10 章）可以看到：字节打包链占了 `ctx = 65K` 全长注意力核耗时的 **24.5%**，而且每分块还有 `138` 条单精度最大值比较指令（`FMNMX`）。`a4` 接着从这两处省回指令：
- 第一处是用**半精度非规格化数（Subnormal）舍入打包**。半精度浮点数最小的那一段（非规格化区间）是等间距排列的，相邻两个可表示数的最小步长恰好是 `2^-24`。我们在乘加阶段直接把线性编码 `n = 8(y + 7)` 额外乘上 `2^-24` 放进这个区间（即把系数 `8 × 2^-24 = 2^-21` 折进 `FFMA.SAT`），随后调用一条浮点转半精度指令 `cvt.rn.f16x2.f32`——硬件在做类型转换时按“向最近偶数舍入”，就顺带把 `n` 直接取整放进了半精度尾数最低位，省掉了单独的取整乘加。这让每 4 个值省掉 2 条半精度乘加（`HFMA2`）和 2 条搬运指令（全长核每块省 64 条、滑窗核省 96 条 `HFMA2`），在 `ctx = 65K` 全长核上省下 **`78.3 µs`**（整层预填充提速 **`0.96%`**）。
- 第二处是用**三输入最大值指令 `VHMNMX`** 压短行最大值归约。把行最大值归约和 `E4M3` 线性编码合并成打包的 `f16x2` 指令后，`ptxas` 会融合成一条指令取三个数最大值的 `VHMNMX` 加 1 条 `f16x2` 乘加，把每分块的 `FMNMX` 从 `138` 条压到 **`14` 条**，抵消新增指令后每块净省 **28 条**指令，预填充整层再提速 **`0.60%`**（在整层 `verify 16 / 32 全长`上，利用正数范围内 `BF16` 位模式单调保序的性质，用 16 条打包 `min.bf16x2` 替代 32 条 `FMNMX` 也净省 16 条指令，提速 **`0.74%` 和 `0.54%`**）。

在这个阶段，也有三类看似合理但实测亏本的做法：

第一类是**指望 `ex2.approx.f16x2` 半精度打包指数省一半 SFU 周期**（图 7-8 模式 1）。Hopper 的 4 通道 SFU 是纯标量硬件，`ptxas` 会把一条 `ex2.approx.f16x2` 拆成 **2 条串行的 `MUFU.EX2.F16` 加 1 条字节重排指令 `PRMT`**，SFU 时间一分未省还多占 1 条 ALU 指令，实测为 0 收益。

第二类是**用通用 FMA 多项式模拟 `exp2`，或未触发 `VHMNMX` 融合导致指令膨胀**。用多项式在 FMA 上模拟 `exp2`，每替掉 1 条 `MUFU.EX2` 要多发 **7.5 条指令**，在发射槽受限下反而变慢；没有触发三输入 `VHMNMX` 融合的 `f16x2` 最大值写法整层只快 `0.14%`，比融合版的 `0.60%` 少拿 **`0.46%`**；而在 SFU 已经 `52%` 忙碌的整层 verify 核里把 ALU 指数退回精确 `MUFU.EX2`，在 `verify 16 / 32 全长`上会**慢 `0.86%` 和 `0.78%`**。

第三类是**把惰性重缩放阈值 `τ` 推过 `FP8` 的下溢边界**。在双头 verify 核里把阈值从 `τ = 6` 推到 `τ = 8`，虽然能快 `3.74 µs`，但留给权重的缩放余量只剩 `2^(8-8) = 1`，小权重大量下溢成 0，导致输出相对误差突破精度上限（上限为 FP8 查询参考自身误差的 2.5 倍加 1.5%）。

`a4` 把在线 Softmax 从 4 通道 SFU 上挪开之后，注意力的主循环和内核边界还剩最后两处开销：循环内部第二段矩阵乘 `P · V` 还在把 `V` 解包成半精度，循环外部还多一次独立的合并核启动（`a4 → a5 → a6`）。

## 6. `a4 → a5`：主循环收官——怎样把 `P · V` 搬上原生 FP8 `QGMMA`，并把 `V` 转置藏进异步窗口？

<!-- FIG ch08-b2: 图 7-9 画阶段 2 原生 FP8 QGMMA 及跨管线异步重叠时间线（对应在发出 Q·K^T 的 wgmma 后、wait_group<0> 之前利用 1 条 LDSM + 8 条 PRMT + 8 条 STS 并行完成 V 分块转置，以及在 verify 16 请求全长上让 P·V 的 FP8 QGMMA 跨入下一轮 wait_group<1> 重叠的算法步）。 -->

把在线 Softmax 从 SFU 上挪开之后，注意力的主循环里还剩一处明显浪费：分页缓存里的 `V` 本来就是 1 字节的 `FP8 E4M3`，早期的过渡写法却先在共享内存环里把 `V` 解包成 2 字节的半精度 `FP16`，既多花了类型转换指令，又多占了一倍共享内存；而且还要等第一段矩阵乘 `Q · K^T` 算完，才串行去重排 `V` 的字节顺序。**`a4 → a5`** 在主循环内部做了两处改动（图 7-9）：

第一处是直接用原生 FP8 Tensor Core 指令 **`QGMMA`** 计算 `P · V`，并在预填充无掩码分块上用半精度 `F16` 累加 `Q · K^T`。既然第 5 节已经把在线 Softmax 产出的注意力权重直接编码成了寄存器里的 1 字节 `FP8 E4M3` 片段 `P_fp8`（开启这一步时双头核先设惰性阈值 `τ = 4`，配合第 5 节放宽到 `τ = 6`），`a5` 就直接调用吞吐翻倍的原生 FP8 指令 `wgmma.m64n64k32.f32.e4m3.e4m3`（`QGMMA`，见第 5 章第 4 节）计算 `O += P_fp8 @ V_trans`。这一步省掉了每分块对 `V` 的解包转换，还省下了 `8–16 KiB` 共享内存；双头 verify 核在 **`verify 32 请求全长`**上的核耗时从 `198.22 µs` 降到 **`190.11 µs`**，端到端省下 **`8.77 µs`**（`verify 16 全长`省 **`3.04 µs`**；滑窗 verify 核省 **`0.74 µs`**；整层 `verify 16 / 32 全长`分别提速 **`1.51%` 和 `2.13%`**）。与此同时，在预填充全长核的无掩码完整分块上，第一段矩阵乘 `Q · K^T` 直接改用半精度 `F16` 累加器，每分块省掉 34 条 `f32 → f16x2` 转换指令并释放 32 个寄存器，使 `ctx = 65K` 全长注意力核耗时下降 **`14.5%–16.8%`**、整层预填充提速 **`1.79%`**（原理与上界推导见第 5 章第 4 节）。

第二处是把 17 条 `V` 字节转置指令藏进 `Q · K^T` 的异步执行窗口，并在寄存器有余量时启用**跨轮在途 `P · V`（`wait_group<1>`）**。原生 FP8 `QGMMA` 要求右矩阵 `V_trans` 按内积维（即同一个特征维不同键位置的字节紧挨着存放，称为 `K`-主序）排列，而缓存页里的 `V` 是按特征维连续存放的，因此必须先在共享内存里做一次字节转置。每个分块的转置由 1 条共享内存矩阵加载指令 `ldmatrix`（SASS 助记符 `LDSM`）、8 条字节重排指令 `PRMT` 和 8 条共享内存写入指令 `STS` 组成，一共 17 条指令。因为 `wgmma` 提交之后是在后台异步执行的，`a5` 把这 17 条转置指令直接插进 `Q · K^T` 的提交点（`commit_group`）与等待点（`wait_group<0>`）之间并发执行（图 7-9 模式 1），在 `verify 32 全长`上省下 **`1.79 µs`**。而在寄存器还没用满的 **`verify 16 请求全长`**上，`a5` 进一步启用跨轮在途 `P · V`（图 7-9 模式 2）：删掉分块末尾的等待，让本轮 `P · V` 跨过循环回边与下一轮的 `Q · K^T` 保持在途重叠（`wait_group<1>`），两项加起来省下 **`1.71 µs`**（代价是跨循环回边要多保持一套在途寄存器片段）。

在主循环里做跨管线重叠有两条亏本边界：
- **寄存器满载时不能开跨轮在途 `P · V`**：在 `verify 32 全长`的 `264`-CTA 虚拟键等分核里，每线程已经用满 80 个寄存器，跨循环回边多保有一轮 `P · V` 的输入片段会直接触发 **20 字节寄存器溢出**，因此该核必须关闭跨轮在途 `P · V`，只保留把 17 条 `V` 转置藏进 `Q · K^T` 的异步窗口。
- **预填充全长核不能强行把 Softmax 与 `P · V` 做二级流水或切碎子块**：在预填充 128-key 循环里尝试把 Softmax 和 `P · V` 做二级流水或乒乓重叠时，`ptxas` 会把 66 条超越函数指令下沉到末尾的 `wait` 之后，静态指令还多了 `10.9%`，实测整层反而**慢了 `0.51%` 和 `2.72%`**；在 128-key 块内再拆 64-key 子块做流水虽然减少了 `64%` 的 `wgmma` 等待，却让每块指令增加了 `18%`，净收益归零。

`a5` 把主循环内部的矩阵乘和转置压紧之后，只剩内核首尾的序言启动与耗时 `3.7–7.2 µs` 的独立合并核启动（`a5 → a6`）。

## 7. `a5 → a6`：核首尾收官——怎样把序言和跨分片归约并进注意力主核？

<!-- FIG ch07-b1: 图 7-10 画阶段 2 整卡波次均衡与 L2 免启动归约数据流（对应按实际历史键数比例分配 Split-KV 切分块消除 15% 长尾波，以及经中央 L2 最后到达者原地重缩放合并或 red.global.v4.f32 向量原子加的算法步）。 -->

<!-- FIG ch07-b2: 图 7-11 画同 GPC 集群 DSMEM 跨 SM 直写归约的数据流（对应阶段 2 注意力中同 GPC 内多个 SM 组成 cluster 通过片上 DSMEM 直接汇总分块结果绕开中央 L2）。 -->

主循环跑顺之后，注意力算子一头一尾还留着两次独立内核启动：入口处的序言核，以及出口处耗时 `3.7–7.2 µs` 的 Split-KV 合并核（当保留独立合并核时，把全局工作区的局部输出从 `FP32` 压成 `BF16` 可减半合并读写字节，与参考实现的最大绝对偏差仅 `0.00332`）。**`a5 → a6`** 把这两头一并收进注意力主核（图 7-10 与图 7-11）：

在入口处，解码与单请求 verify 直接把序言并进每个分片 CTA（见第 1 章第 1 节）：每个分片 CTA 直接从 `qkv` 就地重算自己要用的那几行 `q`，只让负责最新位置的那 1 个分片 CTA 把新 `K, V` 写进缓存页，省掉独立的序言启动和一条 PDL 依赖边，在解码全长（1 / 16 / 32 请求）和 `verify 1 全长`上省下 **`0.58–1.76 µs`**（其中解码 1 请求全长省 **`1.76 µs`**）。

在出口处，为了彻底省掉独立合并核，需要在注意力主核末尾直接把所有分片的局部结果加起来，并结合 `gate` 算出 `o_attn = rmsnorm(O_total) * sigmoid(gate)` 交给阶段 3。这里有一个初看很容易卡住的问题：第 2 节的合并公式需要全体分片的总对数分母 `lse_total`，可是在最后一个分片算完之前，谁都不知道 `lse_total` 是多少，那先算完的分片怎么提前把结果加进工作区？

答案就藏在第 5 节的分数上界里：因为归一化后的对数分数满足 `|m_i| ≤ 71.3 < 126`，`2^m_i` 根本不会溢出单精度 `FP32`（上界约 `2^128`）。每个分片 CTA 算完本段后，不需要除以本段分母 `l_i`，而是直接乘上 `2^m_i`，把按本段基准 `m_i` 缩放的未归一化输出 `O_i` 和分母 `l_i` 换算回**以 `0` 为统一基准的真实分子 `O_i * 2^m_i` 与真实分母 `l_i * 2^m_i`**。既然所有分片都对齐到了同一个固定基准 `0`，各分片就能随时把自己的分子和分母直接累加进全局工作区，等所有分片加完再做最后一次除法 `O_total / l_total`。围绕这一思路，**`a6`** 按网格规模分了三条免启动核内归约通路（见第 2 章第 4 节与第 3 章第 4 节）：

第一条通路是 **L2 无返回值向量原子加（`red.global.add.v4.f32`）加核尾按行协作归一**（图 7-10 模式 2，用于 `verify 16 / 32 请求全长`）。各个分片 CTA 的消费者线程先向位于 L2 的单精度工作区发出 `red.global.add.v4.f32` 累加分子、发出 `red.global.add.f32` 累加分母，并在等待期间预先从 `qkv` 读出门控向量算好 `sigmoid(gate)`。为了让所有 CTA 知道全局累加何时完成，必须走一条完整的因果同步链：
1. 本 CTA 全部消费者线程发完 `red.global.add` 后，先执行一次块内屏障（`bar.sync`），保证本块所有线程的原子加指令都已发出；
2. 随后由本 CTA 的 1 个代表线程对全局到达计数器执行一次设备级 `atom.acq_rel.gpu` 原子加，并循环用 `ld.acquire.gpu` 轮询该计数器，直到全部 264 个 CTA 都已到达（规范认可的通用全网格同步做法是使用协作启动 `cudaLaunchCooperativeKernel`；此处因为 `264 = 2 × 132` 个 CTA 恰好占满 1 轮波次、全部同时驻留在 132 个 SM 上，无协作启动的自旋等待实测同样成立）；
3. 代表线程观察到全员到达后，再执行一次块内屏障（`bar.sync`），把 `acquire` 读建立的可见性传递给本 CTA 的所有线程；随后 264 个 CTA 按行分工读出汇总好的分子与分母相除，做完均方根归一化、乘上 `sigmoid(gate)` 写出最终结果，顺手把工作区清零留给下一轮图重放。

这一步虽然让主注意力核自身变长了 `2.1–2.8 µs`，但删掉了耗时 `5.2 µs` 与 `7.2 µs` 的独立合并核及核间空隙，在 **`verify 16 与 32 请求全长`**上端到端净省 **`1.73 µs` 和 `2.98 µs`**。代价有两条：一是网格必须能在一轮波次内全部同时驻留；二是跨 CTA 的浮点原子加顺序随硬件调度微幅波动，输出最后几个尾数比特具有非确定性（相对误差在 `3e-5` 以内，完全在精度容差内；若改用两元向量原子加 `red.v2`，因原子事务翻倍会比 `v4` 慢 `1.2–2.6 µs`）。

第二条通路是 **L2 `acq_rel` 票据加最后到达者原地合并**（图 7-10 模式 2，用于整层解码 `T = 16 / 32`）。在分片数较少或网格跨波次的解码注意力里，不让先算完的 CTA 原地自旋。每个分片按 `f = 2^min(m_i, 126)`（`126` 防止极端输入下 `2^m_i` 溢出 `FP32`）把分子分母用 `red.global.add.v4.f32` 加进工作区，紧接着执行一次块内屏障 `__syncthreads()`，再由 0 号线程对当前 `(请求, 头)` 的计数器执行 `atom.acq_rel.gpu` 原子加 1 领票（见第 2 章第 4 节；块内屏障不可省略，否则 0 号线程的 `release` 票据无法覆盖同块其他线程的 `red` 写入）。先到的 CTA 领完票直接退出；只有看到自己拿到最后一张票的那个 CTA 留下，经块内屏障后从 L2 读出完整行完成除法归一与门控，在整层解码 16 请求全长上提速 **`1.35%`**。

第三条通路是**同 GPC 集群 `DSMEM` 的 `st.async + mbarrier` 直写合并**（图 7-11 模式 1，用于滑窗与小批量 verify）。当同一个请求的分片数在 `2–16` 之间时，把这些分片 CTA 声明成一个线程块集群（同一集群的 CTA 同时驻留在同一个 **GPC（图形处理簇）** 内，可通过 **DSMEM（分布式共享内存）** 直接读写同伴 CTA 的共享内存，定义见第 3 章第 1、3 节）。各个分片算完局部结果后，直接用异步跨块写指令 `st.async` 把结果推进接收方 CTA 的共享内存并触发硬件事务屏障 `mbarrier`，全程绕开中央 L2，在整层 6 个 verify 算例上省下 **`0.95–3.65 µs`**。在单请求滑窗（`B = 1`，解码 `T = 1` 与检验 `T = 8`）上，更把序言、分片和 16-CTA 集群 `DSMEM` 合并压进单个内核，3 次启动合为 1 次，分别省下 **`0.86 µs` 和 `1.57 µs`**。同样，在整层集群边界归一化核里，用 `st.async + mbarrier` 点对点完成计数替代会触发全局内存栅栏（`MEMBAR.ALL.GPU + ERRBAR`，换前占未发射采样的 `36%–46%`）的集群屏障，每次启动也省下 **`0.86–0.99 µs`**（整层提速 **`0.46%`**）。

核内归约也有三条在注意力算子里必须避开的亏本边界：
- **不能把核内协作收尾函数直接内联进 `K` 循环所在的函数**：在双头 verify 全长核里直接内联收尾代码会干扰 `ptxas` 对主循环的寄存器与指令排布，在 `verify 16 / 32 全长`上反而**慢了 `1.50–3.39 µs` 和 `0.35–0.64 µs`**，必须将收尾函数与主循环隔离。
- **单请求全长（`B = 1`）不能照搬核内 `red.global.add` 原子合并**：在解码 1 请求全长和 `verify 1 全长`上，核内归约尾步耗时达 `5.3–6.2 µs`，远慢于原本 `2.5 µs` 的独立合并核，端到端反而**慢了 `2.96 µs` 和 `0.62 µs`**；推断是因为单请求下多达 256 个分片 CTA 同时争写同一行输出地址，在 L2 原子单元上发生了串行排队。
- **集群 `DSMEM` 归约受单 GPC 驻留容量约束，不能超配单块资源**：如第 3 章第 1 节所测，在 `verify 32 滑窗`上如果把每个 CTA 扩为 2 个消费者组（384 线程）或加大共享内存、把每 SM 驻留压到 2 个 CTA，全卡最后 2 个集群就会掉进第 2 轮波次，完成时间推迟 **`11.7 µs`**（至于把集群 `DSMEM` 归约套到阶段 4 路由投影 `router` 上因跨波次与存储体冲突变慢的反例，见第 9 章第 1 节）。
