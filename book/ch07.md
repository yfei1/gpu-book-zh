## 1. 第 0 级（时间线）：算子融合、PDL 预读与合写大核的边界

<!-- FIG ch07-a: 图 7-1 画 P1–P5 在第 0 级时间线上的三项实战改造数据流：上方对比 P5 独立 pre_expert 归一化 kernel（多一次 HBM 读写往返）与融合进 pooler 尾声的时间线；中间画 P3 后继 kernel 在 PDL 等待前预读静态权重 W 的流水线；下方对比全层合写协作大 kernel（受最慢阶段寄存器限制并卡在全网格栅栏）与按阶段拆开用 PDL 串联的时间线。 -->

在 P5（预填充整层）基线中，profiler 时间线显示 `pooler` 投影与专家矩阵乘之间夹着一个独立的归一化小 kernel（见第 1 章第 1 节）。它不读大矩阵权重，却把全批中间激活写回 HBM 再重新读出。该向量只被 `pooler` 写出一次，又只被紧随其后的专家阶段读取一次。因此改造方案将均方根求逆融进 `pooler` 写出尾声，并把归一化权重乘法折入专家第一层矩阵乘的尾声缩放中。这消掉了整个独立 kernel 及其 HBM 往返，在 H200 上使 P5 整层实测提速 **0.60%–1.35%**。

相邻两个阶段若因并行维度不同而无法合成一个 kernel（如 P1 注意力与后续投影），瓶颈就落在第 1 章第 2 节的节点切换空隙与收尾期。与开源 FlashInfer 和 CUTLASS 的流水线做法一致，P3 在同一条 `stream` 上开启 PDL。后继 kernel 把 `cudaGridDependencySynchronize()` 放在静态权重预读指令之后。后继 CTA 趁前序最后一个波次收尾的空档提前进场，先把不依赖前序结果的静态权重分块搬进片上。直到要读前序激活时它才停下等待，在 P3 上实测将交接段重叠掉 **5–11 µs**（整层提速 `0.80%`）。

减少启动次数能省空隙，但把更多阶段合写进同一个协作启动（`cudaLaunchCooperativeKernel`，见第 1 章第 3 节）的大 kernel 并不总是更快。在 P2（小批量专家）中，把 `w13` 与 `w2` 拆成两个由 PDL 串联的 kernel，反而比带全网格栅栏的单一大 kernel 净快 `0.70–0.82 µs`。而在 P3 中尝试把多个不同形状的阶段塞进同一个全层协作大 kernel 时，端到端实测反而变慢 **5–8 µs**。全网格同步栅栏不仅本身耗时约 1.4 µs，还强迫整个大 kernel 按寄存器需求最高的那一个阶段统一分配寄存器（见第 3 章第 1 节）。这要求所有 CTA 同时驻留，锁死了各阶段独立调整波次与在途字节的空间。开源界对全层虚拟机的复盘同样证实，当跨阶段全卡同步开销占优时，按阶段拆开并用 PDL 预读权重反而快于单一大核。

## 2. 第 1 级（整张芯片）：132 个 SM 上的波次均衡、Split-KV 与 L2 归约

<!-- FIG ch07-b: 图 7-2 画第 1 级整卡上的三项工作切分与 L2 归约数据流：上方对比不均匀序列长度下按请求切分（长序列 CTA 拖出长尾波）与按实际历史键数切分（132 个 SM 齐平收尾）的时间线；中间对比 Split-KV 单独启动合并 kernel 与最后到达者在 L2 原地合并的过程；下方画 P4 使用 TMA 异步二维块原子加（cp.reduce.async.bulk）直接向 L2 累加分块的通路。 -->

在 P1（分页注意力）和 P3 中，当并发请求数很少或各请求历史长度相差悬殊时，只按“请求 × 注意力头”派发 CTA 会导致严重失衡。要么总 CTA 数填不满 132 个 SM，要么长序列的 CTA 比短序列慢几倍，在时间线上拖出长尾波（见第 2 章第 1 节）。开源 FlashAttention-3 与 FlashInfer 采用 **Split-KV**（又叫 Flash-Decoding）。它把长历史序列沿键值维切成多段并行计算，再合并各段的局部加权和与对数分母。但若给每个请求分配相同数量的切分块，长请求分到的块依然很大，尾波仍在。P1 与 P3 改为按每个请求的实际历史 token 数比例分配切分块，使各 CTA 分到的键值页数均匀对齐。这把全卡收尾拉平为整齐的波次，在 P1 上实测缩短 `3.90 µs`，在 P3 全长注意力上缩短 **9.5 µs**。

切开历史序列或求和维 `K`（如 K-halves 与开源 CUTLASS 的 **Stream-K**）后，多个 SM 的部分和必须汇总。为省掉第二个合并 kernel 的切换空隙，P1–P4 在中央 L2 上采用了三种免启动归约方案。
- 方案一（L2 原子计数加最后到达者原地合并）。在 P1 与 P3 的 Split-KV 中，每个切分块 CTA 写出局部结果后，对 L2 计数器执行一次带 `acq_rel` 的原子加（见第 2 章第 4 节）。拿到最后序号的 CTA 直接从 L2 读出同组局部结果并完成重缩放合并，在 P1 上实测省下 **1.73–2.98 µs**（P3 提速 `1.35%`）。
- 方案二（无返回值的向量化全局原子加）。当部分和可直接相加时，线程直接发出不要求返回旧值的向量原子加指令，由 L2 内部的硬件原子加法器一步完成（P1 实测比单独合并省 `1.82–3.61 µs`）。
- 方案三（TMA 异步二维块原子加）。在 P4 批量 `T = 128 / 256` 的 `qkv_gate` 拆分矩阵乘中，每个 CTA 算完一块 SMEM 输出分块后，调用第 3 章的 TMA 引擎发起异步二维块原子加（`cp.reduce.async.bulk.tensor.2d...add`）。硬件把整个片上分块直接送往 L2 原子累加，实测比逐线程原子归约快 **1.84–2.66 µs**。

在 P2 与 P3 的多专家计算中，相邻 SM 经常需要交换数据。若它们同属一个物理 GPC（见第 2 章第 4 节），就可把 2 到 16 个 CTA 声明为一个 cluster。它们直接通过 GPC 内部的 DSMEM 互写片上存储，绕开中央 L2，在 P3 上实测省下 **0.95–3.65 µs**。同时，为消除持久 kernel 跨轮重放时清零全局同步数组的开销，P2 采用奇偶交替的双账本（每本 1,024 个字）。本轮调用使用偶账本同步时，后台单个 warp 顺带把奇账本清零供下一轮 CUDA Graph 重放使用，实现了零额外启动的跨轮复用。

## 3. 第 2 级（单个 SM）：生产者-消费者分工、动态寄存器配额与环形缓冲

<!-- FIG ch07-c: 图 7-3 画第 2 级单个 SM 内部的四项实战改造数据流：上方画 1 个生产者 warpgroup（调用 setmaxnreg.dec 退还至 40 个寄存器）专职发 TMA 填 3 槽环形缓冲、消费者 warpgroup（调用 setmaxnreg.inc 扩至 232 个寄存器）专职跑 Tensor Core 的分工；下方对比 P3 路由直方图在 32 字行宽下的 32 路 Bank 冲突与 33 字填充后的零冲突并行读取。 -->

在 P2（大批量专家）和 P5 中，单个 CTA 同时包含发 TMA 的线程与跑 `wgmma` 的线程，65,536 寄存器池立刻成为瓶颈。跑矩阵乘的消费者线程需要上百个寄存器存放累加器，而发 TMA 的生产者线程只需二三十个寄存器。若按统一的每线程最大数分配，整个 CTA 就会超出上限并触发溢出。P2 与 P5 采用了 **warp specialization**（线程束分工）。这一设计与开源 FlashAttention-3、CUTLASS 和 DeepGEMM 同构。它们在同一 CTA 内把不同 warpgroup 按角色切开。生产者 warpgroup 在入口调用 `setmaxnreg.dec 40` 把每线程寄存器退还到 40 个。消费者 warpgroup 调用 `setmaxnreg.inc 232` 把寄存器扩充到每线程 **232** 个（合计 `64,512 ≤ 65,536` 个），在零溢出的前提下跑满 Tensor Core。

在片上环形缓冲（见第 3 章第 4 节）设计上，缓冲槽数 `N` 必须与单分块大小及在途字节目标精确匹配。
- 在 P4 的 `pooler`（`T = 32`）中，每个权重分块仅 16 KiB，6 槽环只能保持 5 个槽（80 KiB）在途，在双向模式下仍未完全覆盖满载往返延迟。将其从 6 槽扩到 **7** 槽（SMEM 从 144 KiB 增至 168 KiB，仍低于 228 KiB 上限）后，H200 实测耗时立即下降。
- 反之，在 P2 大批量专家 kernel 中，单个分块已达 36 KiB，3 槽环（保持 72 KiB 在途）已跨过 TMA 的 48 KiB 平台。若为追求两组消费者交替算尾声的乒乓调度而把双倍分块塞进 SMEM，环形缓冲就会退化为 2 槽。此时在途量只剩 36 KiB（跌破 48 KiB 平台），实测反而变慢 **1.2–1.6 µs**。因此 P2 采用 4 个消费者 warpgroup 协同共算同一分块、共享同一个 3 槽环的方案。

在消除 SMEM 的 32 个 bank 冲突（见第 3 章第 5 节）上，所有 TMA 矩阵分块都打开了 128 字节 `XOR Swizzle`。开源 DeepGEMM 同样靠给输出分块补齐 Swizzle，将吞吐从 1,212 推到了 1,270 TFLOP/s。同时，手写小数组的冲突也会卡住关键路径。在 P3 的专家路由准备阶段，各线程要在 SMEM 中构建一个 32 列的本地专家计数表。原始 32 字行宽使不同行同一专家的计数全部撞在同一号 bank 上。把每行末尾填充 1 个空白字改为 33 字行宽后，在 P3 的四个 verify 形状上实测省下 **0.95–7.49 µs**（提速 `0.6%–2.1%`）。

## 4. 第 1 级与第 2 级的两个实测反例：为什么“省带宽”的特性反而更慢？

<!-- FIG ch07-d: 图 7-4 画第 1–2 级的两个实测反例数据流与时间线：上方对比 pooler128 在热 L2（8.8–10.1 TB/s）下各 SM 独立发 TMA 读取与开启 cluster 多播（受跨 SM 远端 mbarrier 握手拖累反而慢 2.1 倍）的时间线；下方画 P1 页表 L2 预取行在间隔过长时被中间的 KV 数据流冲出 L2、导致 DRAM 重复读取多花 4.3–8.5 MB 的过程。 -->

硬件手册里的加速特性都有各自的物理前提。当工作负载不满足前提时，照搬特性反而会制造新的瓶颈，下面是第 1 级和第 2 级实测到的两个典型反例。
- 反例一（在热 L2 下开启 TMA 集群多播，实测反而慢 **2.1 倍**）。Hopper 的 TMA 支持集群多播（`.multicast::cluster`）：同一 cluster 的多个 SM 需要同一块权重时，由 L2 读一次同时广播写进各 SM 的 SMEM。但在 `pooler`（批量 128）微基准实测中，开启 TMA 多播反而比各 SM 独立发单播 TMA 慢了 2.1 倍。原因是当该权重块已被读进中央 L2 时，热 L2 本身就能提供 8.8–10.1 TB/s 的读取带宽，远超单 SM 所需。此时开启多播省不下任何 HBM 流量。相反，它逼着同一 cluster 的所有 SM 在每轮释放槽位时都通过跨 SM 远端 mbarrier 互等，最慢的 SM 把全集群拖慢了一倍以上。
- 反例二（过早发出页表 L2 预取，实测反而多读 **4.3–8.5 MB** 显存）。在 P1 分页注意力中，为掩盖读取离散页表项的延迟，曾尝试在循环前提前很多步发出全局 L2 预取指令（`prefetch.global.L2`）。然而 H200 实测不仅耗时变慢 `0.03–0.53 µs`，全卡 HBM 读取量还反常增加了 4.3–8.5 MB。由于注意力主循环每步都在流式搬运数兆字节的 KV cache，预取进 L2 的页表行在消费前就被庞大的 KV 数据流冲出了 L2。等到真正使用时又得从 HBM 重读第二次（同理，P2 尝试重排任务顺序复用 L2 激活也多产生 2–4 MB 显存流量且零收益）。因此，任何 L2 预取都必须先核算从预取到消费之间流过 L2 的字节数是否小于 60 MiB 容量。

---

**带走一句话：** 在第 0 级至第 2 级上，按实际键数切分与 L2 原地归约消除了最高 9.5 µs 的尾波与合并开销，而脱离热 L2 握手代价与 60 MiB 容量边界的盲目多播或预取反而会使耗时倒退 2.1 倍。
