# 第 9 章：性能诊断法：给你一个慢 kernel，怎样按第 0 级到第 5 级找出真瓶颈？

**本书地图：** 第 0 章 → 第 0.5 章 → 第 1 章 [第 0 级] → 第 2 章 [第 1 级] → 第 3 章 [第 2 级] → 第 4 章 [第 3 级] → 第 5 章 [第 4 级] → 第 6 章 [第 5 级] → 第 7–8 章 → **【第 9 章：性能诊断法】**

承接第 8 章末尾的问题（第三部分：性能诊断闭环）：前八章拆解了第 0 级到第 5 级的硬件机制与实战案例。拿到一个全新的慢 kernel 时，怎样不靠猜测、顺着这六级放大顺序用剖析器定位它的真实瓶颈？

## 1. 诊断前的测量纪律：为什么不能直接拿剖析器耗时做对比？

动手改代码之前，必须先建立不受缓存、频率与剖析器干扰的计时基准。**Nsight Compute**（简称 NCU，内核级性能剖析器）报告的 `gpu__time_duration.sum` 不能当成真实端到端耗时。NCU 默认把 SM 频率锁在 1.25–1.53 GHz 的基准频率，低于约 1.8 GHz 的满载持续频率（见第 4 章）。同时它会把同一个 kernel 重放多遍，用来收集不同的硬件计数器。在 `gemv` 演化的 v7 中，事件计时的冷缓存中位数是 15.68 µs，而 NCU 报告的内核耗时是 12.54 µs（两者相差 3.14 µs）。同一测试台单次空 kernel 的事件计时约为 3.68 µs，但因 NCU 锁定频率与清缓存方式不同，两者不能直接相减。所以正确分工是：用 CUDA Graph 配事件计时测量真实微秒数，用 NCU 读取利用率百分比、停顿原因占比与指令条数。

真实计时必须守住下面三条基线规则，否则测出的加速比会被系统噪声淹没。
- 每次迭代前清空 60 MiB 的 L2（见第 2 章第 5 节）。单层 `qkv_gate` 权重为 37.7 MB，若紧挨着重复调用同一个 kernel，权重会留在 60 MiB 的 L2 里。在 v3 中，不清空 L2 的热缓存耗时仅 29.02 µs。每次调用前写入 512 MiB 缓冲区冲空 L2 后，真实冷缓存耗时是 48.26 µs。
- 使用非零随机权重保持功耗一致。H200 的热设计功耗上限最高可配置至 700 W。测试矩阵乘时应使用真实分布的非零随机张量，避免全零输入带来的测量偏差（公开的 H800 FP16 `wgmma` 微基准显示全零与非零随机输入下的实测吞吐相差约 3.4%）。
- 用 **ABBA**（交替配对评测）抵消温度漂移。ABBA 在同一进程对同一批输入按 A、B、B、A 顺序交替运行候选版与基线版。同时要把两份完全相同的基线代码当作 A1 与 A2 跑一次对照，测出系统自身的本底噪声带。在 P4 的 14 轮 ABBA 中，本底偏差上限约为 **0.13 µs**。只有当候选版相对基线版的节省跨过这道噪声门槛（如超过 0.15 µs）时，改动才算真正生效。

## 2. 外三层诊断（第 0 级 → 第 2 级）：时间线空隙、全卡下界与单 SM 驻留

<!-- FIG ch09-a: 图 9-1 上方画出从第 0 级时间线到第 5 级单条指令的六步诊断决策树（移动块对应待诊断的 qkv_gate 或 P2 专家 kernel 顺着六级关卡逐层筛查的过程），下方联动展示每一级对应的剖析器面板读数与修复动作。 -->

拿到一个慢 kernel 后，按图 9-1 从外向内逐级排查，不在外层没看清时盲目改内层指令。外三层回答“芯片有没有在干活、全卡带宽有没有跑满、单个 SM 的资源够不够”。
- 第 0 级（时间线上的 kernel，见第 1 章）。打开 **Nsight Systems**（系统级时间线剖析器）观察相邻 kernel 之间的时间空隙。第 1 章的三步链由 CPU 逐步下发时耗时 73.02 µs，录进单张 CUDA Graph 重放后降至 36.19 µs。若 GPU 时间线上出现这类微秒级空白，说明主机下发跟不上 GPU，应先录进 CUDA Graph 并把层间小操作融进相邻矩阵乘。若相邻图节点切换处仍有收尾与切换空隙（例如 v2 三节点链录进图后比连续入队省下 2.1 µs 冷缓存耗时），就启用 PDL 让后继在前序收尾期提前进场预读静态权重。后继可选择把权重预取至 L2 或装入 SMEM，直到调用 `cudaGridDependencySynchronize()` 时才阻塞等待前序网格完成并刷回显存。
- 第 1 级（整张 H200 芯片，见第 2 章）。先按第 0 章算式算出理论下界 `floor`。再读 NCU **Speed Of Light**（简称 SOL，光速上限面板）的 `gpu__dram_throughput.avg.pct_of_peak_sustained_elapsed`（显存带宽占峰值百分比）与 `dram__bytes_read.sum`（HBM 实读字节数）。若实读字节远超算法必读字节，说明读取未合并或缓存被冲刷。若实读字节已贴近下界且显存带宽占比超过 80%（如 P2 专家在批量 32 下实测达 **83.6%**），说明已触及 HBM 物理上限。此时只能靠压窄权重位宽（见第 6 章）或用 `evict_last` 留存共享输入。若显存与算力利用率双低，就在 kernel 起止处读取特殊寄存器 `%globaltimer` 与 `%smid` 打点。一旦发现最后一批 CTA 拖出长 tail（或 P2 拆分内核第二阶段的 131 号 CTA 比首波晚启动 2.0–3.2 µs），就用 K-halves 切半尾波或按编号削减队尾分块。
- 第 2 级（单个 SM，见第 3 章）。结合编译输出 `ptxas -v` 与 NCU 的 **Launch Statistics**（启动统计面板：查 `launch__grid_size`、`launch__block_size`）、**Occupancy**（占用率面板）和 **Memory Workload Analysis**（内存工作负载面板）。第一步查 `ptxas -v` 的寄存器溢出（`spill stores / loads`）是否为 0（例如 P2 主内核用 139–144 个寄存器保持 0 溢出，该步未单独采集 NCU 占用率读数）。第二步算单 SM 在途字节。在 `gemv` 从 v5 到 v6 的演进中，单 CTA 缩为 1 个 warp（32 线程，每 SM 上限 32 个 CTA）。全卡 2,304 个 CTA 虽能一次驻留，但平均每 SM 仅分到 `2,304 ÷ 132 = 17.45` 个活跃 warp（活跃占用率从 79.3% 跌至 25.8%）。单 SM 在途量随即从 32.0 KiB 骤降近四倍至 8.7 KiB，连带显存吞吐从 49.5% 跌至 38.6%。第三步查每个读取请求搬回的扇区数与 SMEM 的 bank conflict，用 16 字节 `uint4` 合并加载与 XOR Swizzle 消除无效字节和存储体冲突。

## 3. 内三层诊断（第 3 级 → 第 5 级）：调度停顿、执行管线与 SASS 指令

当外三层确认全卡负载均衡、单 SM 驻留与扇区合并都正常，但耗时仍远高于理论下界时，继续沿图 9-1 点开 SMSP 调度器、物理执行管线与底层 SASS 指令。
- 第 3 级（单个 SMSP 调度器，见第 4 章）。读取 NCU **Scheduler Statistics**（调度器统计面板）的 `smsp__issue_active.avg.pct_of_peak_sustained_active`（发射槽活跃周期占比）与无就绪周期占比（no eligible）。同时加 `-lineinfo` 编译，在 **Source Counters**（源码计数器页面）查看停顿采样 `smsp__pcsamp_warps_issue_stalled_*`。若 `issue_active` 高且首要状态是 not selected（如 P2 在 decode 批量 16 下 `issue_active` 达 75.8%、`not_selected` 占 33.6%），说明每周期都有就绪 warp 可发，应直接进入第 4 级。反之若 no eligible 高且显存未饱和，就在 Source 页面定位消费者 warp 的首要停顿。卡在 **long_scoreboard**（长记分牌停顿，等待全局内存 `LDG` 返回，如 `gemv` 的首要停顿比值从 v1 的 44.7 降到 v7 的 8.1），说明 HBM 预取深度不够或存在串行地址链。卡在 **mio_throttle**（MIO 队列节流停顿，如 P5 注意力基线占 22.7%）或 **short_scoreboard**（短记分牌停顿，等待 SMEM 读取或 SFU 返回），说明片上读取与使用贴得太近或 SFU 队列排满。卡在 **barrier** 或 **wait**（屏障或等待停顿，如 P5 注意力长序列基线占 46.7%，重排流水后降至 13.7%），说明生产者供数慢于消费者，或 `wait_group<0>` 把异步矩阵乘卡成了串行等待。
- 第 4 级（执行管线与 Tensor Core，见第 5 章）。读取 NCU **Compute Workload Analysis**（计算工作负载面板）的各管线利用率（如 `sm__inst_executed_pipe_tensor_op_hmma`、`alu`、`fma`、`xu`、`lsu`）与总指令数 `inst_executed`。若单条管线独高，就把指令分流到空闲管线。例如 P5 专家尾声原本把标量转换 `F2F` 与超越函数 `MUFU` 都塞给 4 通道的 SFU 管线。改用走 ALU 管线的双值打包转换 `F2FP` 后，`sm__inst_executed_pipe_xu` 从 **5.74%** 降到 **3.08%**。第 6 章用 FMA 重型子管线的 `IMAD.SHL` 分担 ALU 移位、并用 `wait_group<1>` 让算术管线与 Tensor Core 重叠也是同一原理。若所有管线都不满但发射槽已忙（如 P2 专家尾声 4 个 warp 需 932 个发射周期，大于 SFU 的 768 个周期），说明卡在每周期 1 条的发射槽上限。此时必须靠代数合并常数与双元素打包指令直接削减总指令数。
- 第 5 级（单条指令与比特，见第 6 章）。运行 `cuobjdump --dump-sass` 检查 128 位 SASS 反汇编。第一查 `ptxas` 是否因在 `wgmma` 流水阶段起止之间由非 `wgmma` 指令定义了累加器寄存器（报出 `C7515` 告警）或在分化路径上依赖编译器插入的同步（报出 `C7520` 告警），从而在每条 `HGMMA` 后强插 `WARPGROUP.DEPBAR.LE 0`。在 P4 批量 `T = 128` 的 `qkv_gate` 中，这会使主循环从 8.84 µs 涨到 **20.74 µs**。第二查 `ptxas` 是否把本该在 `griddepcontrol.wait`（`ACQBULK`）之前发出的只读预取 `ld.global.nc` 下沉到了等待之后（P2 用 `asm volatile` 锁住顺序省下 0.45–0.67 µs）。同时查内层循环是否重复解包计算循环不变量（P2 用空内联汇编锁住寄存器减少 483 条指令，省 0.21–0.30 µs）。第三查消费者向 `empty[s]` 报到前是否还有未落定的 `LDS`，防止片上 WAR 覆写（见第 3 章第 4 节）。

## 4. 微扰删除实验：怎样区分真瓶颈与被异步掩盖的假忙碌？

<!-- FIG ch09-b: 图 9-2 上方画异步重叠的两条并行硬件轨道（HBM/TMA 或 Tensor Core 主轨道与待测算术/归约支路，移动块对应 P2 专家尾声的 MUFU.TANH 步与 P4 pooler 的 split-K 归约尾步），下方对比“删掉后总耗时不变（被主轨道掩盖）”与“删掉后总耗时下降（真关键路径上界）”的时间线。 -->

在异步执行的 GPU 上，NCU 里计数高或停顿多的代码行不一定是真瓶颈。TMA 搬运、异步 `wgmma` 与多 warp 轮流发射会让多条硬件轨道同时推进。只要较短的算术支路完全藏在更慢的 HBM 或 Tensor Core 主轨道阴影里，把支路优化到零周期也不会缩短总耗时。在投入精力重写代码前，最高效的判据是做图 9-2 所示的 **perturbation test**（微扰删除实验）。实验保持非零随机输入，用 1 行条件或空操作临时旁路待测代码段，直接测量配对 ABBA 的耗时差。
- 删掉后耗时不变（假瓶颈，已被主轨道掩盖）。在 P2 专家计算的激活尾声中，临时删掉 `MUFU.TANH` 指令后实测耗时变化为 **0.0%**。这证明 SFU 管线已被主循环掩盖，改用多项式展开近似反而因多占发射槽慢了 0.4%。同理，在第 4、5 章的 `gemv` 演进中，v8 用洗牌归约替掉 SMEM 屏障（`15.68 → 15.62 µs`），v9 用 ALU 拆包把总指令数削减 24%（`2.67 M → 2.02 M`，耗时 `15.62 → 15.58 µs`）。两步的端到端耗时都几乎不变，因为单 token decode 的主轨道一直在等 HBM 返回权重。
- 删掉后耗时下降（真关键路径，下降量即收益上界）。在 P4 批量 `T = 256` 的 `pooler` 矩阵乘中，临时删掉末尾的跨块归约尾步（让各分片直接写出局部和退出），内核耗时从 28.99 µs 降到 24.10 µs。这证明归约尾步在关键路径上暴露了 **4.9 µs** 的最大可省空间。随后改用 L2 硬件执行的 TMA 原子归约（`UTMAREDG.2D.ADD`），打点实测将归约尾步压到 2.06 µs（图 9-2 第三行显示 `24.10 + 2.06 = 26.16 µs`），在独立配对 ABBA 评测中端到端净省 2.66 µs（`28.99 - 2.66 = 26.33 µs`）。在 P5 全长注意力最大算例（`L = 16,384`，历史 `65,536`）中，微扰删除实验测出 FP8 字节打包链占了该算例注意力核耗时的 **24.5%**。利用非规格化数舍入省掉多余打包指令后，该算例注意力的单核实测耗时直接缩短 78 µs（后续版本进一步将其合入半精度打包指令中）。

## 5. gemv 演化诊断复盘（v0 → v10）：六级计数器如何一步步指向 15.49 µs？

把贯穿全书的 `qkv_gate`（`v0 → v10`）放回图 9-1 的六级诊断树，每一次耗时跳变都对应唯一一级的计数器信号。
- 从 v0（675.71 µs）到 v1（58.88 µs）再到 v4（43.94 µs）：第 0 级与第 1 级诊断。v0 的 NCU 活跃占用率仅 6.2%、显存带宽占比仅 0.9%，因为 18 个 CTA 只用上了 132 个 SM 中的 18 个，且跨行读取每扇区只有 6% 字节有用。v1 派出 2,304 个 CTA 并让相邻线程读相邻元素后，占用率升至 73.3%、显存带宽占比升至 14.2%，耗时降到 58.88 µs。随后在第 0 级用 v2 的 CUDA Graph 消除主机下发空隙，三步链热缓存从 73.02 µs 压到 36.19 µs（冷缓存省 2.1 µs）。接着在第 1 级用 v3 的 K-halves 切平 192 个尾波 CTA（48.26 µs）。至于 v4 的 L2 留存提示（在写入 512 MiB 脏缓存冲刷下从 48.26 µs 降到 43.94 µs），对照实验测出该 1.10 倍差异来自脏缓存冲刷本身。推断原因是未标 `evict_first` 的权重读取挤出脏缓存行触发了写回竞争；若改用干净的只读 512 MiB 冲刷，v3（42.88 µs）与 v4（43.49 µs）耗时基本一致。
- 从 v4（43.94 µs）到 v5（17.76 µs）再到 v6（21.86 µs）：第 2 级与第 3 级诊断。v4 的首要停顿是 `long_scoreboard`（比值 28.1），因为每线程每次只发 2 字节读取，单 SM 在途仅 4.0 KiB。v5 改用第 2 级的 16 字节 `uint4` 合并加载后，总指令数从 11.12 M 降到 4.49 M。单 SM 在途升至 32.0 KiB，显存带宽占比跃升至 49.5%，耗时压到 17.76 µs。而 v6 改为每 CTA 32 线程（每 SM 理论上限 32 个 CTA，全卡容量 4,224 远大于 2,304）虽消除了尾波，但 2,304 个单 warp CTA 平摊到 132 个 SM 上平均每 SM 只有 17.45 个活跃 warp。这使第 2 级活跃占用率从 79.3% 跌到 25.8%，单 SM 在途量从 32.0 KiB 骤降近四倍至 8.7 KiB，耗时退化到 21.86 µs。
- 从 v6（21.86 µs）到 v7（15.68 µs）再到 v10（15.49 µs）：第 3 级到第 5 级收官。v7 在第 3 级让每线程连发 8 条 `uint4` 读取，把单 SM 在途推到 69.8 KiB（跨过图 2-2 的 64 KiB 拐点）。`long_scoreboard` 比值从 12.9 降到 8.1，显存带宽占比升至 63.2%，在同一脏冲刷基准下耗时压到 15.68 µs，反超 PyTorch `torch.mv` 经 `cublasGemmEx` 调用的 21.12 µs（在干净只读冲刷下 v7 为 14.27 µs）。扩大行数的专项实测表明，v7 的稳态流式带宽已达 `4.54–4.61 TB/s`；单次 37.7 MB 调用由约 8.2 µs 稳态传输加约 6.4 µs 固定开销（含约 3.8 µs 事件计时与约 2.6 µs 核内拟合残差）组成。此后第 3 级的 v8 洗牌归约（在途 61.1 KiB 紧贴拐点，耗时 15.62 µs）与第 4 级的 v9 ALU 拆包（在途 61.1 KiB，指令数再减 24% 至 2.02 M，显存带宽占比达 65.0%，耗时 15.58 µs）都印证了第 4 节的规律。当读取深度已喂饱 HBM 时，片上归约与算术指令已被显存等待掩盖。最后第 5 级的 v10 改从源头削减必读字节，用 12 位 C12 无损打包把权重从 37.7 MB 压到 28.4 MB（理论下界从 7.9 µs 移至 5.9 µs），将实测耗时推到 **15.49 µs**（相对 v0 提速 **44 倍**）。

---

**带走一句话：** 按第 0 级到第 5 级依次核对冷 L2 带宽占比与微扰删除实验，就能过滤掉被显存等待掩盖的假忙碌，把 `qkv_gate` 从 675.71 µs 推进到 15.49 µs。
