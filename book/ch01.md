# 第 1 章 [第 0 级]：时间线上的 Kernel 序列——阶段之间怎样消除启动空隙并提前重叠？

**本书地图：** 前言 → 第 0.0 章 → 第 0 章 → 第 0.5 章 → **【第 1 章 [第 0 级]：时间线上的 Kernel 序列】** → 第 2 章 [第 1 级] → 第 3 章 [第 2 级] → 第 4 章 [第 3 级] → 第 5 章 [第 4 级] → 第 6 章 [第 5 级] → 第 7–10 章

第 0.5 章写出了阶段 1 `qkv_gate` 的第一个可用 kernel（`v1`，单核实测 `54.08 µs`）。但回到第 0 章的单层全景，一句话流过一层模型并不是只跑这一个 kernel，而是要把八个阶段连同前后的归一化、路由和残差粘合操作排成一列，顺着同一条 `stream` 依次启动。当每个小 kernel 只跑几微秒到几十微秒时，相邻 kernel 之间的时间空隙是从哪里来的，又该怎么压到最低？

<!-- FIG part1-map: 图 I-1 全书硬件放大总图：第 0 级时间线 → 第 1 级芯片 → 第 2 级 SM → 第 3 级 SMSP → 第 4 级管线 → 第 5 级指令与比特，每级标出它决定单层的哪几步。 -->

在进入具体机制之前，可以先看一眼图 I-1 的推进顺序。本书第一部分按从外到内做六级硬件放大，每一章只拆开上一章刚看到的那个硬件部件：

- **第 0 级（时间线，第 1 章）**：看一条 `stream` 上的 kernel 序列，解决算子启动、计算图切换与相邻 kernel 之间的交接重叠。
- **第 1 级（整张芯片，第 2 章）**：点开时间线上的单个 kernel，看全卡 132 个 SM、共享的中央 **L2 cache**（二级缓存，132 个 SM 共用的片上缓存）和两侧 HBM 怎样分工配合。
- **第 2 级（单个 SM，第 3 章）**：点开 1 个 SM，看它内部的片上存储容量怎样决定能同时驻留多少个 CTA，以及数据怎样从显存搬进片上。
- **第 3 级（SM 内部调度器，第 4 章）**：看 1 个 SM 里的指令调度器怎样在等待数据返回时切换线程组，以及同一组线程内部怎样直接交换数据。
- **第 4 级（执行管线，第 5 章）**：看算术管线与专用矩阵运算单元怎样并行跑满算力。
- **第 5 级（指令与比特，第 6 章）**：一直放大到编译器生成的机器指令和 32 位寄存器里的比特排布。

本章先停留在最外层的第 0 级时间线。一句话流过 62 层模型的每一层时，第 0 章的八个阶段要依次在 `stream` 上执行，并在阶段之间经 HBM 或中央 L2 缓存交接中间激活，每一次跨核交接都会带来启动空隙和额外的显存读写。本章顺着时间线依次解决三个问题：第 1 节消除主机下发空隙和多余的小 kernel 启动，第 2 节让后一个 kernel 在前一个收尾时提前进场预读权重，第 3 节判断相连两阶段该合写成一个大 kernel 还是拆成两个串联 kernel。

## 1. 队列排空、算子融合与 CUDA Graph 整图重放

当单个小算子在 GPU 上只跑几微秒时，决定耗时的往往不是算子本身算了多少，而是算子之间怎么交接。**这里有三个拖慢执行的原因：第一，CPU 准备下发命令比 GPU 跑完小算子还慢；第二，中间结果跨算子在显存里多走了一趟读写；第三，后一个算子必须等前一个算子的全部线程块退出才能启动。**

<!-- FIG ch01-a: 图 1-1 画同一条 x = 时间 (µs) 轴上的三行单层时间线对比（移动块对应单层 decode 依次执行的 rmsnorm -> qkv_gate -> attention -> o 等阶段 kernel 条块）。读数显示：逐个流启动（空 kernel 流启动含事件计时约 5 µs）、CUDA Graph 重放、以及算子融合加提前启动。 -->

先看图 1-1 第一行的“逐个流启动”。单个小 kernel 在 GPU 上几微秒就跑完了。如果 CPU 准备下一次启动的时间比 GPU 执行还长，`stream` 队列（见第 0.5 章）就会排空，GPU 只能停下来等 CPU。在单 CTA 空 kernel 的独立微基准里，逐次从流上启动并做事件计时的读数约为 `4.7 µs`（若流队列已预先排满，单次事件计时底座为第 0.5 章的 `4.6 µs`）。图 1-1 第一行按每次独立启动约 `4.7 µs` 的量级画出 17 次启动的示意总宽（约 `80 µs`），用来和整层 `40.0 µs` 的滑窗计算下界对照：如果让 CPU 逐个现发小算子，花在启动和等待上的时间比算子本身还长。

要省去 CPU 每次逐个下发的准备时间，可以把整层录进 **CUDA Graph**（计算图录制与重放）。预热时用 `cudaStreamBeginCapture` 和 `cudaStreamEndCapture` 把整层的调用顺序和固定显存地址录成一张静态图并完成实例化；到了运行时，CPU 只调一次 `cudaGraphLaunch`，剩下的节点切换就交给 GPU 片上的硬件派发器自己按图重放。代价是预热期要多做一次图录制与实例化，且图内算子读写的显存地址必须固定。

不过切到图 1-1 第二行的“CUDA Graph 重放”就会看到，就算 CPU 只调一次，基线里还是留着两处损耗。

第一处是显存往返。按头归一化、旋转位置编码（RoPE）、写 KV 缓存、残差归一化、路由选择等层间粘合小操作，如果各自写成独立 kernel，每一步都得把中间结果写回 HBM 再重新读出来。在 SGLang 的单请求 decode 剖析里，这些未融合的小操作占了整步耗时的约四分之一。

第二处是图节点切换本身的空隙。同一条 `stream` 里，后一个图节点必须等前一个节点的所有 CTA 退出、全局内存写入全部可见后才能开始。这道隐式边界在相邻节点切换时留下约 **1.0 µs**（实测中位数 `1.024 µs`）的硬件切换空隙，17 个图节点加起来仍有约 `17 × 1.0 ≈ 17 µs`。

解决这两处损耗的办法很直接：**与其把中间结果写回显存再启动下一个小 kernel 读回来，不如在主计算 kernel 的序言或尾声里直接算完。** 这就是 **kernel fusion**（算子融合）。单请求 decode（`T = 1`）做完各阶段内部与跨边界融合后，整层从基线估算的约 17 个 kernel 压到了 **11** 个（若再配合下一节的提前启动把每条串行边压到约 `0.64 µs`，图 1-1 第三行 11 个节点的示意切换总宽就降到了约 `7 µs`）。

<!-- FIG ch01-fuse-m1: 图 1-2 单请求专家（T = 1）算子融合解剖图：上方对比未融合时“独立路由核 → 上投影核 → 独立归约 → 下投影核 → 独立归约”的多次启动与全局往返，下方展示删去独立路由核并由上、下投影最后到达 CTA 在核内原地完成部分和归约的时间线。 -->

图 1-2 用阶段 6 路由专家在单请求 decode（`T = 1`）下的三次连续融合，展示了怎么一步步砍掉多余的启动边界。在 `T = 1` 下，每个命中的本地专家只处理 1 个词元的输入 `p [1, 4096]`（来自阶段 5 `pooler`），但一行权重有 4,096 列；为了让全卡 132 个 SM 都有活干，主核会把每一行的内积求和拆给多个 CTA 各算一段部分和（为什么这样拆见第 2 章第 1 节）。在未融合基线（图 1-2 模式 1）里，算完这一阶段要连发 5 个 kernel：路由核、上投影核、上投影归约核、下投影核、下投影归约核，中间隔着 4 道切换边。

我们分三步把多余的启动拿掉：

1. **上投影尾声核内归约（图 1-2 模式 2）**：上投影各分片算完部分和之后，不再写回显存等独立归约核来收，而是改由最后到达的那个 CTA 在核内原地汇总，接着算出门控激活 `inter = silu(h_gate) ⊙ h_up`，直接把中间激活 `inter` 写进中央 L2 缓存。这一步把流程减为 4 个 kernel、3 道切换边，实测省下 **1.12 µs**。
2. **删掉独立路由核（图 1-2 模式 3）**：不再单独启动一个路由 kernel 生成重排表，而是让矩阵乘 CTA 直接读取阶段 4 产出的路由索引 `topk_ids [1, 8]` 定位命中的本地专家。流程减为 3 个 kernel、2 道切换边，本步再省 **1.42 µs**。
3. **下投影尾声核内归约（图 1-2 模式 4）**：下投影同样改由最后到达的 CTA 在核内原地累加部分和，直接算出各命中专家的输出并完成专家后归一化与加权求和，写出 `m [1, 4096]` 送往阶段 7 `unpooler`。整段压到 2 个 kernel、1 道切换边，本步再省 **0.86 µs**。

三步合起来一共省下 **3.40 µs**。同样的思路也用在阶段 2 注意力上：把入口的按头归一化、位置编码与写 KV 缓存合进单次启动，并在预填充注意力核尾声直接融合门控输出归一化（`233.07 → 230.23 ms`，详见第 7 章）。这样做的代价，是主 kernel 需要在序言或尾声多承担一步计算与同步（例如上、下投影尾声要维护原子到达计数器并由最后到达者归约，跨 SM 归约的代价见第 2 章第 4 节）。

反过来，如果拆得太碎或者合并不当，就会直接亏本。第一种反例是反方向把算子拆碎：在预填充（`T = 3,012`）的阶段 6 专家路由中，曾尝试把路由对齐拆成计数核和独立的散射重排核两步，结果独立的散射核每线程占了 **205 个寄存器**、单核耗时高达 **90 µs**，整层实测反而变慢 **1.4%**。第二种反例是把原本能趁前序收尾空档提前进场的小 kernel 强行并进前序大核的串行尾声（见下一节与第 9 章第 4 节）：在整层多词检验（`T = 128 / 256`）的 7 项尾部强行融合尝试中全部实测变慢（例如 32 请求滑窗检验慢了 `+6.75 µs`；阶段 6 小批量与预填充的同类强行融合也让耗时分别增加 `+1.18..+8.34 µs` 与约 `+145..+340 µs`）。

## 2. 用 PDL（编程依赖启动）让前序收尾与后继读静态权重重叠

两个相邻阶段如果并行切分方式不同、没法融合成一个 kernel，是不是就只能等前一个 kernel 全部退场再启动后一个？不一定。**一个 kernel 的所有 CTA 不会在同一时刻结束。当最后几个 CTA 还在收尾写回时，大部分 SM 已经空出来了；而后继 kernel 进场做的第一件事往往只是从 HBM 读它自己的静态权重，并不依赖前一个 kernel 还没写完的激活。**

<!-- FIG ch01-pdl: 图 1-3 画 PDL 四步交接流程与时间线：第 1 步主机端声明编程依赖属性；第 2 步前序 CTA 算完主体后调用触发函数；第 3 步后继 CTA 趁前序收尾期从 HBM 预读静态权重 W；第 4 步后继在读取前序激活前调同步等待函数等前序写入落定（对比触发点放在函数开头导致后继空占 CTA 槽位慢近 2 µs 的反例）。 -->

**Hopper**（H200 架构代号 `sm_90a`）的 **PDL**（Programmatic Dependent Launch，编程依赖启动）就是用来拆开这两个时间点的。它把“允许后继 kernel 派发上 SM”和“前序 kernel 的全局内存写入全部可见”分成两步控制。结合图 1-1 第三行与图 1-3，拿第 0 章讲过的阶段 2 → 阶段 3 边界（注意力写完 `o_attn [T, 1024]` 交给输出投影 `o` 计算 `a = o_attn · W_o^T`）以及阶段 2 内部的分页注意力链（`prologue → attention → merge`）来看，PDL 的交接分四步走：

1. **声明编程依赖边**：主机端在启动后继 kernel 时挂上 `cudaLaunchAttributeProgrammaticStreamSerialization` 属性。
2. **前序触发放行**：前序每个 CTA 在算完主体循环、进入收尾写出之前，调用 `cudaTriggerProgrammaticLaunchCompletion()`（底层 PTX 指令为 `griddepcontrol.launch_dependents`，机器指令见第 6 章第 1 节）。一旦所有前序 CTA 都已触发或退出，硬件派发器就可以把后继 kernel 的 CTA 派上空闲 SM，不等前序把收尾写回全部做完。
3. **后继提前预读静态权重**：后继 CTA 进场后，先不去读前序尚未写完的激活（如 `o_attn` 或注意力分片部分和），而是趁前序收尾的空档，先把只依赖模型权重的静态数据（如阶段 3 的 `W_o`，`16.8 MB`）从 HBM 预读进缓存或片上内存。
4. **后继等待前序写入可见**：在真正读取前序输出之前，后继调用 `cudaGridDependencySynchronize()`（底层 PTX 指令为 `griddepcontrol.wait`）阻塞等待。直到前序整个 `grid` 执行完毕且所有全局内存写入刷新可见，后继才跨过等待点开始计算（单 CTA 入口等待的实测串行边为 **0.64 µs**）。

在图 1-3 里对比“无 PDL：等前序全部退出”和“PDL：触发在主体循环之后”两档，就能直接看到把静态权重预读塞进前序收尾期的收益。在阶段 2 单请求全长层 decode（`T = 1`）的 `attention → merge` 双核边界上，关掉 PDL 会慢 **0.93 / 0.88 µs**（正反序配对，图 1-3 对照读数显示 `+0.93 µs`；单请求全长层检验开启三核 PDL 链省 **0.45–0.90 µs**，全部 7 个带独立归约核的算例关掉 PDL 慢 **0.11–1.60 µs**）。同样的做法用在阶段 6 专家上：给路由到上投影、上投影到下投影挂上 PDL 并在等待前预取静态权重与缩放因子，分别省下 **0.63 µs** 和 **1.66 µs**；专家主核向后归一化核挂 PDL 在 `T = 1..256` 各档也省下 **0.31–0.93 µs**（详见第 8 章第 2 节）。

使用 PDL 的代价，是后继 kernel 必须在首次读取前序数据前插入 `cudaGridDependencySynchronize()` 等待点（在被测的分页注意力核上寄存器占用没有增加，其余算子的寄存器与共享内存变化未测）。

但这并不意味着触发点放得越早越好。触发函数只负责放行派发，不代表前序数据已经写完。切到图 1-3 的“PDL：触发在函数开头（反例）”可以看到：在阶段 2 全长注意力测试中，如果把触发调用提前到主循环开头（函数入口），过早进场的后继归约核从进场到跑完被拉长到了 **9.86 µs**（其中自身归约工作仅约 `2.4 µs`，绝大部分时间都停在等待点上干等），最后一次触发后仍留有 `1.5–1.9 µs` 的入口间隙。结果全部 7 个带归约核的算例正序实测反而慢了 **+0.48..+1.95 µs**（单请求全长层 decode 正反序慢 **+1.95 / +1.84 µs**，前序注意力核自身也延长了 `+0.07..+1.65 µs`）。我们推测这是因为前序和后继的 CTA 可以同驻一个 SM，过早触发让后继 CTA 提早占住了 SM 槽位空等（确切微架构机理未单独验证）。同样地，如果触发点放进本身很快跑完的滑窗注意力核（`T = 32` decode），或者在整层阶段 3–8 上盲目移动触发与等待位置，也会在小批量滑窗 decode（`T = 16`）上实测倒退约 **1%**。

## 3. 什么时候该合写成一个协作大核，什么时候该拆成两个 PDL 串联核？

把相邻的两个计算阶段写进同一个**持久 kernel**（persistent kernel，即只启动刚好铺满全卡的 132 个 CTA，每个 CTA 在循环里连续认领多份子任务直到全部做完）、中间用一道全网格同步栅栏隔开，一定比拆成两个 kernel 更快吗？不一定。**如果相连的两步之间存在全对全的数据依赖，合写进一个协作大核就必须让全卡 132 个 SM 在栅栏处等最慢的那一个块跑完；反过来，拆成两个用 PDL 串联的 kernel，先算完第一步的 CTA 一退场，第二步的 CTA 就能立刻填进空出的 SM，趁等待前序数据落定的时间先把第二步的静态权重预读上片。**

<!-- FIG ch01-b: 图 1-4 上方画专家计算的两个相连矩阵乘阶段（移动块对应专家先算上投影 w13 写出中间激活、再算下投影 w2 读该激活的算法步）。下方对比合写单一大 kernel 与拆成两个 PDL 串联 kernel 的时间线。 -->

看第 0 章阶段 6 的路由专家计算（图 1-4）。阶段 A 读入某专家分到的 $n$ 个词元输入 `p_e [n, 4096]`（来自阶段 5 `pooler` 的输出 `p`，BF16）与上投影权重 `W13`（每专家共 **18.9 MB**，位于 HBM；4 位打包格式见第 6 章），先算上投影 `h = p_e · W13^T`，再经门控激活 `inter = silu(h[:, :4096]) ⊙ h[:, 4096:]` 写出中间激活 `inter [n, 4096]`（BF16，经中央 L2 缓存交接）。阶段 B 读入 `inter` 与下投影权重 `W2`（每专家共 **9.4 MB**，位于 HBM），接着算下投影 `y = inter · W2^T` 写出 `y [n, 4096]`，最后经每专家归一化与路由权重加权求和，产出 `m [T, 4096]` 送往阶段 7 `unpooler`。因为下投影权重 `W2` 的每一行都要读完 `inter` 的全部 4,096 列，而这 4,096 列是由许多 CTA 在阶段 A 分别算出来的，所以阶段 A 和阶段 B 之间是全对全的数据依赖。

如果用 **cooperative launch**（协作启动，`cudaLaunchCooperativeKernel`）把阶段 A 和阶段 B 合写进一个持久大 kernel（全卡 132 个 CTA），两步之间就必须插一道 **grid barrier**（全网格同步栅栏）。协作启动要求所有 CTA 同时驻留在芯片上（超出同时驻留容量时驱动会直接拒绝启动），因为只要有一个 CTA 还没派上芯片，已经驻留的 CTA 在栅栏处永远等不到它，就会死锁。切到图 1-4 的“合写成一个协作大 kernel”，这道全网格栅栏在 132 个 CTA 下实测耗时 **1.42 µs**（`1,419.3 ns`；264 个 CTA 下为 `1,521.5 ns`）。在这个合写核里，全卡 132 个 SM 都得停在栅栏前面，等阶段 A 最慢的那一个区域跑完，才一起进入阶段 B 去读权重 `W2`。

切到图 1-4 的“拆成两个 PDL 串联 kernel”，做法就变了。我们把阶段 A 和阶段 B 拆成两个由 PDL 串联的 kernel（阶段 A 也通过 PDL 接在路由核后面）。这样不僅省掉了那道 `1.42 µs` 的全网格栅栏（PDL 串行边为 `0.64 µs`），而且先算完阶段 A 的 CTA 一退场，阶段 B 的 CTA 就能立刻填进刚空出来的 SM，在 `cudaGridDependencySynchronize()` 等待阶段 A 全部写完之前，先把 `W2`（每专家 **9.4 MB**）的权重分块预读上片（栅栏省时与预读各自占多少比例属于推断，未单独拆分测量；在合写协作核里能否在栅栏前同样预取 `W2` 也未单独测）。

在批量 decode 的 `T = 16` 和 `T = 32` 上，拆成两个 PDL 串联核比单一协作大核实测净快 **0.70 µs** 和 **0.82 µs**；在单请求 verify（`T = 8`）上，拆核并配合权重预取共省下 **0.37 µs**（首版省 `0.21 µs`）。不过到了单请求 decode（`T = 1`），拆核与合写的实测差只有 `+0.03 µs`（没有收益），所以 `T = 1` 保持单核协作启动。

拆成两个 kernel 的代价，是多出 1 个 CUDA Graph 节点。同时，因为阶段 A 与阶段 B 的每个 CTA 都占用了大块片上共享内存（见第 3 章），两个 CTA 合起来超出了单个 SM `228 KiB` 的共享内存总容量（单 CTA 上限 `227 KiB`），阶段 B 的 CTA 无法与阶段 A 同 SM 共驻，只能随阶段 A 退场按 `blockIdx.x` 顺序逐个进场（由此带来的高编号 CTA 晚启动斜坡会在第 2 章第 2 节解决）。

往单一大核方向强行合并还有两个反例。第一个是在已被 PDL 重叠的预填充专家（`T > 1,024`）上合写单一持久上、下投影大核：此时上投影与下投影的交接边界已经被块完成信号和 PDL 压得很窄，所能省下的边界时间占整层耗时的比例估算不到 **0.3%**（实际可兑现估算仅约 `0.1%–0.16%`），却会丢掉下投影把各专家分块交由硬件动态调度的能力（见第 8 章第 5 节）。第二个是跨整层把不同形状的阶段硬塞进单一全层协作大核（见第 9 章第 4 节）：如果把整层多个不同矩阵形状、不同寄存器需求的阶段塞进同一个持久协作大核，全核驻留会被寄存器需求最高的那一阶段卡住上限，而且每道阶段边界都要付全网格同步代价（单层结构性损耗估算达 `+8.3 µs`，整层实测比按阶段拆开再用 PDL 串联显著变慢）。

## 4. `gemv` 演化（`v1 → v2`）：把三步调用链录进单张 CUDA Graph 重放

回到贯穿本书第一部分的阶段 1 `qkv_gate`（权重 `W [2304, 8192]` BF16，`37.7 MB`）。把本章第 0 级的做法落到单请求 `T = 1` 的 `gemv` 演化链上，这一步要解决的就是**主机下发与跨核切换空隙**。

为了看清 `gemv_kernel`（**v1**，见第 0.5 章）放在前后算子调用链里的启动开销，计时程序构造了一条三步链：入口归一化核（1 个 CTA）、`gemv_kernel` 矩阵-向量乘核（2,304 个 CTA）和后处理核（9 个 CTA）。如果主机端从 Python 逐个往流里发这三步，相邻 kernel 之间就会暴露出下发与切换空隙。本章的 **v2** 不改 `gemv_kernel` 本身（单核冷缓存耗时仍是 `54.08 µs`），只在预热期把这条三步链录进同一张 CUDA Graph 并完成实例化，运行时一次提交整张图重放（多词 `T = 8..256` 下用尾声核内归约消去独立归约核启动的 `qkv_gemm` 演化，见第 6 章第 4 节）。

```cuda
// v1：主机端在 stream 上逐个下发 [入口归一化核, gemv_kernel, 后处理核] 三步 kernel
gemv_kernel<<<2304, 128, 0, stream>>>(W, x, y, K);
// v2：预热期录制三步链并实例化为 graph_exec，运行时单次提交整张图
cudaGraphLaunch(graph_exec, stream);
```

在全书统一的冷缓存测法下（每次重放前先读 `512 MiB` 清空 L2），单次重放这张三步 CUDA Graph 的实测中位数是 **`60.0 µs`**。拿它和同一冷缓存下的两种流启动对比：如果流队列没有预先排满、由 CPU 逐个往流里下发这三步，耗时要 **`102.6 µs`**，整图重放直接省下约 **`42.6 µs`**（**`1.71×`**）的主机下发空隙；就算流队列已经预先排满、CPU 下发延迟被队列掩盖，三步流启动仍要 **`61.6 µs`**，整图重放在两道跨核交接边界上还能再省约 **`1.5 µs`**（**`1.03×`**，平均每道边界省约 `0.8 µs`）。

这样做的代价是预热期需要录制并实例化静态计算图，且图内算子读写的显存指针必须固定；只要调用序列和缓冲地址固定，整图重放始终优于逐个流启动。

---

**带走一句话：** 算子之间的时间花在主机下发、显存往返和切换等待上；用 CUDA Graph 重放、算子融合和 PDL 提前启动可以把跨核空隙压到微秒以内，但它们不改变单个 kernel 内部的执行耗时。
