## 1. 队列排空、算子融合与 CUDA Graph 整图重放

<!-- FIG ch01-a: 图 1-1 画同一条 x = 时间 (µs) 轴上的三行单层时间线对比（移动块对应单层 decode 依次执行的 rmsnorm -> qkv_gate -> attention -> o 等阶段 kernel 条块）。读数显示：逐个流启动（空 kernel 流启动含事件计时约 5 µs）、CUDA Graph 重放、以及算子融合加 PDL。 -->

如图 1-1 所示，在模式选项里选“逐个流启动”，读数写着“17 次启动 · 每次准备约 4.7 µs（空 kernel，含事件计时）”与“合计约 17 × 4.7 ≈ 80 µs，而单层下界是 40 µs（滑窗层）”。图 1-1 第一行里，GPU 有一段时间停下空等。单个小 kernel 在 GPU 上只跑几微秒，而逐个流启动的准备时间比它还长。由于 CPU 跟不上 GPU，`stream` 队列（见第 0.5 章）就会排空。所以在线推理服务默认启用 **CUDA Graph**（计算图录制与重放），SGLang 的 decode 基线也是这样。预热时，`cudaStreamBeginCapture` 与 `cudaStreamEndCapture` 把整层调用顺序和固定显存地址录成静态图并实例化。运行时 CPU 只调一次 `cudaGraphLaunch`，由片上硬件派发器（从 `stream` 读命令并派发 CTA 的硬件，NVIDIA 未公开其内部结构）自主重放整张图。

但图 1-1 第二行显示，开启 CUDA Graph 后基线仍有两处损耗。第一，未融合的层间小操作各自把中间向量写回 HBM 再读出来，占了单请求 decode 单层耗时的约四分之一。第二，同一 `stream` 里后一个图节点必须等前一个节点的所有 CTA 退出、写入全部可见后才能开始。这道隐式栅栏在相邻图节点切换时留下约 1 µs 的硬件切换空隙。选“CUDA Graph 重放”，读数写着“17 个图节点 · 每次节点切换约 1.0 µs（中位数 1.024 µs）”与“合计约 17 × 1.0 ≈ 17 µs · CPU 只调 1 次”。因此第 0 级的第一步优化是做 **kernel fusion**（算子融合），把层间小操作融进相邻的矩阵乘与注意力 kernel 中。每少一次启动就省掉一次切换空隙和一次 HBM 往返，这把单请求 decode（`T = 1`）的单层启动从 SGLang 基线估计的约 17 次压到 **11** 次。选“算子融合 + PDL”，读数写着“11 个 kernel · 每条 PDL 串行边 0.64 µs”与“合计约 11 × 0.64 ≈ 7 µs · 预读权重与前序收尾重叠”。

## 2. 用 PDL（编程依赖启动）让前序收尾与后继读权重重叠

<!-- FIG ch01-pdl: 图 1-2 画 PDL 四步交接流程与时间线：第 1 步主机端声明编程依赖属性；第 2 步前序 CTA 算完主体后调用触发函数；第 3 步后继 CTA 趁前序收尾期从 HBM 预读静态权重 W；第 4 步后继在读取前序激活前调同步等待函数等前序写入落定（对比触发点放在函数开头导致后继空占 CTA 槽位慢近 2 µs 的反例）。 -->

如图 1-1 第三行与图 1-2 所示，每个 kernel 末尾都不是同时停下的。大部分 CTA 已结束时，仍有少数 CTA 在收尾。收尾期大部分计算单元已经空出，且后继预读静态权重不依赖前序刚算出的激活。所以 Hopper 的 **PDL**（Programmatic Dependent Launch，编程依赖启动）允许后继在前序收尾时提前进场。PDL 按下面四步工作。
- 声明编程依赖边。主机端启动后继时挂上属性 `cudaLaunchAttributeProgrammaticStreamSerialization`。
- 前序触发。前序每个 CTA 在算完主体循环、进入收尾期前调用 `cudaTriggerProgrammaticLaunchCompletion()`。所有前序 CTA 都已触发或退出时，硬件派发器即可启动后继 kernel。
- 后继预读静态权重。后继 kernel（如 `o` 或 `pooler`）进场后先不读前序尚未写完的激活向量，而是先从 HBM 预读自己最先要用的几块静态权重分块。
- 后继等待前序数据可见。读取前序激活之前，后继调用 `cudaGridDependencySynchronize()` 停下等待，等前序显存写入全部落定后再继续执行。

在 P1 全长层 decode（`T = 1`）测试中，把触发点放在前序函数开头反而比放在主体循环之后慢了近 **2 µs**。触发调用并不代表前序数据已写完。过早进场的后继 CTA 只能停在等待函数上，空占芯片上的 CTA 位置（见第 3 章）。在图 1-2 中先选“PDL：触发在主体循环之后”，读数写着“PDL，触发在主体循环之后：串行边 0.64 µs”。再选“PDL：触发在函数开头（反例）”，读数写着“PDL，触发在函数开头：比 ② 慢 +1.95 µs（decode 1）”与“后继 CTA 停在等待函数上 9.86 µs，空占 SM 槽位”。

## 3. 合写成一个协作大 kernel 还是拆成两个 PDL 串联 kernel？

<!-- FIG ch01-b: 图 1-3 上方画专家计算的两个相连矩阵乘阶段（移动块对应 P2 专家先算上投影 w13 写出中间激活、再算下投影 w2 读该激活的算法步）。下方对比合写单一大 kernel 与拆成两个 PDL 串联 kernel 的时间线。 -->

第 0 章的专家计算（P2）里，每个专家先乘 `w13`，再乘 `w2`。`w2` 的每一行都要读 `w13` 的全部输出，而这些输出由许多 CTA 分别写出。若用协作启动（`cudaLaunchCooperativeKernel`）把两步合写进一个大 kernel，两步之间就必须插一道全网格同步栅栏。协作启动要求所有 CTA 同时驻留在芯片上，否则没上芯片的 CTA 永远到不了栅栏就会死锁。而芯片一次能同时驻留的 CTA 数量有限（见第 3 章）。图 1-3 的 P2（decode 批量 16–32）对比中，拆成两个 PDL 串联 kernel 的写法反而净快约 **0.7–0.8 µs**。可能的原因是全网格栅栏本身耗时约 1.4 µs，且全卡 CTA 都要空等最慢的那个算完 `w13`。拆开后两个 kernel 之间的 PDL 交接只需约 0.6 µs，而且先算完 `w13` 的 CTA 一退场，`w2` 的 CTA 就能进场预读权重分块。在图 1-3 中先选“合写成一个协作大 kernel”，读数写着“合写成一个协作 kernel：全网格栅栏 1.42 µs”。再选“拆成两个 PDL 串联 kernel”，读数写着“拆成两个 PDL 串联 kernel：交接边 0.64 µs”与“先算完的 SM 立即预读 w2 · 实测净快 0.70 / 0.82 µs（decode 16 / 32）”。

## 4. gemv 演化（v1 → v2）：把流启动链录进单张 CUDA Graph 重放

单层里 **v1**（见第 0.5 章）的 `gemv_kernel` 前后紧跟归一化（`rmsnorm`）与写缓存后处理（`rope_kv`）。若主机端从 Python 逐个流启动 `[rmsnorm, gemv_kernel, rope_kv]`，相邻 kernel 之间会暴露下发空隙。本章的 **v2** 在预热期把三步调用链录进同一张 CUDA Graph 并实例化，运行时单次重放。

```cuda
// v1：主机端在 stream 上逐个下发三步 kernel
gemv_kernel<<<2304, 128, 0, stream>>>(W, x, y, K);
// v2：预热期录制三步链并实例化为 graph_exec，运行时单次提交整张图
cudaGraphLaunch(graph_exec, stream);
```

整图重放由片上硬件派发器自主启动，消除了 CPU 逐个下发的排空等待。三步链的 H200 实测：由 CPU 逐步流启动（热缓存）耗时 73.02 µs，改为单张 CUDA Graph 重放后降至 36.19 µs（省去 36.8 µs 下发空隙）。在冷缓存且流队列预先排满时，整图重放也从流启动的 `67.23 µs` 降至 **65.15 µs**（2 个节点边界共省约 2.1 µs，平均每个边界省约 1 µs）。

**带走一句话：** 算子融合把单请求 decode 的单层启动从约 17 次压到 11 次，每次节点切换仍留约 1 µs 空隙。
