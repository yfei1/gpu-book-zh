## 1. 队列排空、算子融合与 CUDA Graph 整图重放

<!-- FIG ch01-a: 图 1-1 画同一条 x = 时间 (µs) 轴上的三行单层时间线对比（移动块对应单层 decode 依次执行的 rmsnorm -> qkv_gate -> attention -> o 等阶段 kernel 条块）。读数显示：逐个流启动（空 kernel 流启动含事件计时约 5 µs）、CUDA Graph 重放、以及算子融合加 PDL。 -->

如图 1-1 所示，在模式选项里选“逐个流启动”。读数为：`17 次启动 · 每次准备约 4.7 µs（空 kernel，含事件计时）`；`合计约 17 × 4.7 ≈ 80 µs，而单层下界是 40 µs（滑窗层）`（这里的 4.7 µs 是单 CTA 空 kernel 单次流启动含事件计时的独立微基准，用来展示逐个启动的量级，不同于第 0.5 章 `gemv` 计时程序在预排满队列下测得的 3.68 µs）。图 1-1 第一行里，GPU 有一段时间停下空等。单个小 kernel 在 GPU 上只跑几微秒，当 CPU 逐个下发的准备时间比它还长时，`stream` 队列（见第 0.5 章）就会排空。所以评测程序将整层录成 **CUDA Graph**（计算图录制与重放）重放计时。预热时，`cudaStreamBeginCapture` 与 `cudaStreamEndCapture` 把整层调用顺序和固定显存地址录成静态图并实例化。运行时 CPU 只调一次 `cudaGraphLaunch`。随后由片上硬件派发器（从 `stream` 读命令并派发 CTA 的硬件，内部结构未公开）自主重放整张图。

但图 1-1 第二行显示，开启 CUDA Graph 后基线仍有两处损耗。第一，未融合的层间粘合小操作（归一化、门控残差与路由）各自读写 HBM 并启动 kernel，在 SGLang 的单请求 decode 剖析中占了整步耗时的约四分之一。第二，同一 `stream` 里后一个图节点必须等前一个节点的所有 CTA 退出、写入全部可见后才能开始。这道隐式栅栏在相邻图节点切换时留下约 **1.0 µs** 的硬件切换空隙。选“CUDA Graph 重放”，读数为：`17 个图节点 · 每次节点切换约 1.0 µs（中位数 1.024 µs）`；`合计约 17 × 1.0 ≈ 17 µs · CPU 只调 1 次`。因此第 0 级还要做 **kernel fusion**（算子融合，第 7 章展开），把层间小操作融进相邻矩阵乘与注意力的片上内存直接交接。每少一次启动就省掉一次切换空隙和一次 HBM 往返，把单请求 decode（`T = 1`）的单层启动从按 SGLang 基线模块表推算的约 17 次压到 **11** 次。选“算子融合 + PDL”，读数为：`11 个 kernel · 每条 PDL 串行边 0.64 µs`（单 CTA 实测量级）；`合计约 11 × 0.64 ≈ 7 µs · 预读权重与前序收尾重叠`。

## 2. 用 PDL（编程依赖启动）让前序收尾与后继读权重重叠

<!-- FIG ch01-pdl: 图 1-2 画 PDL 四步交接流程与时间线：第 1 步主机端声明编程依赖属性；第 2 步前序 CTA 算完主体后调用触发函数；第 3 步后继 CTA 趁前序收尾期从 HBM 预读静态权重 W；第 4 步后继在读取前序激活前调同步等待函数等前序写入落定（对比触发点放在函数开头导致后继空占 CTA 槽位慢近 2 µs 的反例）。 -->

如图 1-1 第三行与图 1-2 所示，每个 kernel 末尾都不是同时停下的。大部分 CTA 已结束时，仍有少数 CTA 在收尾。图 1-2 以单层阶段 2（`attention`）向阶段 3（`o` 投影，算 `a = y · W_o^T`）交接示意。`o` 的输入是 `attention` 写出的激活 `y`（即 `o_attn`，BF16 `[1, 1024]`，2,048 B，位于 L2/HBM）与静态权重 `W_o`（BF16 `[8192, 1024]`，16.8 MB，位于 HBM）。`o` 的输出是 `a`（BF16 `[1, 8192]`，16,384 B，写回 HBM 交给门控残差 1）。因为收尾期大部分 SM 已经空出，且 `o` 预读静态权重 `W_o` 不依赖前序尚未写完的 `y`，所以 **Hopper**（H200 架构代号 `sm_90a`）的 **PDL**（Programmatic Dependent Launch，编程依赖启动）允许后继在前序收尾时提前进场。PDL 按下面四步工作。
- 声明编程依赖边。主机端启动后继 `o` 时挂上属性 `cudaLaunchAttributeProgrammaticStreamSerialization`（传入 `W_o`、`y`、`a` 三个 8 B 指针）。
- 前序触发。前序每个 CTA 在算完主体循环、进入收尾前调用 `cudaTriggerProgrammaticLaunchCompletion()`（编译为机器指令 `PREEXIT`）。所有前序 CTA 都已触发或退出时，硬件派发器即可启动后继 kernel。
- 后继预读静态权重。后继 `o`（或阶段 5 的 `pooler`）进场后先不读前序尚未写完的激活 `y`。它按自身代码先把 `W_o` 的前几块静态权重从 HBM 预读进 L2 或片上共享内存（落点由后继代码自己决定，PDL 本身不规定）。
- 后继等待前序数据可见。读取前序激活 `y` 之前，后继调用 `cudaGridDependencySynchronize()`（编译为 `ACQBULK`）阻塞等待。直到前序整个 `grid` 执行完毕且所有全局内存写入已刷新可见，后继才读入 `y` 计算 `a = y · W_o^T`。

在图 1-2 中先选“无 PDL：等前序全部退出”，读数为：`无 PDL：后继在前序全部退出后才启动`；`对照：关 PDL 比开 PDL 慢 +0.93 µs（decode 1，全层）`（该微秒数测自 P1 单请求 `decode 1` 全长注意力层的 `attention → _o_merge_gate` 边界，正反序配对实测为 `+0.93 / +0.88 µs`）。再选“PDL：触发在主体循环之后”，读数为：`PDL，触发在主体循环之后：串行边 0.64 µs`；`权重预读藏在前序收尾里 · 这是保留的写法`。但触发调用只放行派发，并不代表前序数据已写完。在同一 P1 全长注意力层 `decode 1` 边界测试中，把触发点放在前序函数开头反而比放在主体循环后慢了 **1.95 / 1.84 µs**（正反序配对）。这是因为过早进场的后继归约 CTA 只能停在等待函数上 9.86 µs，空占 SM 槽位（见第 3 章）并拖慢前序收尾。选“PDL：触发在函数开头（反例）”，读数为：`PDL，触发在函数开头：比 ② 慢 +1.95 µs（decode 1）`；`后继 CTA 停在等待函数上 9.86 µs，空占 SM 槽位`。

## 3. 合写成一个协作大 kernel 还是拆成两个 PDL 串联 kernel？

<!-- FIG ch01-b: 图 1-3 上方画专家计算的两个相连矩阵乘阶段（移动块对应 P2 专家先算上投影 w13 写出中间激活、再算下投影 w2 读该激活的算法步）。下方对比合写单一大 kernel 与拆成两个 PDL 串联 kernel 的时间线。 -->

在第 0 章阶段 6 的专家计算（P2）里，设某专家分到 `n` 个词的输入 `x_2`（BF16 `[n, 4096]`，位于 HBM/L2）。第一阶段读取上投影权重 `W13`（`uint8 [8192, 2048]` 加块缩放 `FP8 [8192, 256]`，共 **18.9 MB**，位于 HBM）。它算出 `h = x_2 · W13^T`，经门控激活 `inter = silu(h[:, :4096]) ⊙ h[:, 4096:]` 写出中间激活 `inter`（参考实现为 BF16 `[n, 4096]`，图 1-3 按经 L2 交接示意）。第二阶段读取 `inter` 与下投影权重 `W2`（`uint8 [4096, 2048]` 加块缩放 `FP8 [4096, 256]`，共 **9.4 MB**，位于 HBM）。它算出 `y = inter · W2^T`（BF16 `[n, 4096]`），交给每专家独立归一化与路由加权求和产出 `m [M, 4096]`。因为 `W2` 的每一行都要读完 `inter` 的全部 4,096 列，而这 4,096 列由许多 CTA 在第一阶段分别写出，两阶段之间有全对全依赖。

若用 **cooperative launch**（协作启动，`cudaLaunchCooperativeKernel`）把两步合写进一个大 kernel（全卡 132 个 CTA），两步之间必须插一道 **grid barrier**（全网格同步栅栏）。协作启动要求所有 CTA 同时驻留在芯片上（超出同时驻留容量时驱动直接拒绝启动），因为若有 CTA 没上芯片，已驻留的 CTA 在栅栏处永远等不到它就会死锁。在图 1-3 中选“合写成一个协作大 kernel”，读数为：`合写成一个协作 kernel：全网格栅栏 1.42 µs`；`132 个 CTA 必须同时驻留 · 全卡等最慢的一区`。这道全网格栅栏在 132 个 CTA 下实测耗时 **1.42 µs**，且全卡 132 个 CTA 都要等最慢的一区算完第一阶段才能开始第二阶段。拆成两个由 PDL 串联的 kernel 后，串行交接边为 **0.64 µs**，且先算完第一阶段的 CTA 一退场，第二阶段的 CTA 就能进场预读 `W2` 分块（栅栏省时与预读各自占多少比例属于推断，未单独拆分测量）。选“拆成两个 PDL 串联 kernel”，读数为：`拆成两个 PDL 串联 kernel：交接边 0.64 µs`；`先算完的 SM 立即预读 w2 · 实测净快 0.70 / 0.82 µs（decode 16 / 32）`。因此在 P2 的 decode 批量 16 与 32 对比中，拆成两个 PDL 串联 kernel 比单一大 kernel 实测净快 **0.70 / 0.82 µs**。

## 4. gemv 演化（v1 → v2）：把流启动链录进单张 CUDA Graph 重放

为测量 `gemv_kernel`（**v1**，见第 0.5 章）在多层调用链中的启动开销，计时程序构造了三步链 `[nb_rmsnorm (1 CTA), gemv_kernel (2,304 CTAs), nb_post (9 CTAs)]`（入口归一化、矩阵乘向量与 9 个 CTA 的后处理）。若主机端从 Python 逐个流启动这三步，相邻 kernel 之间会暴露下发空隙。本章的 **v2**（不改 `gemv_kernel` 本身，单 kernel 冷缓存耗时仍为 58.88 µs）在预热期把三步链录进同一张 CUDA Graph 并实例化，运行时单次重放。

```cuda
// v1：主机端在 stream 上逐个下发 [nb_rmsnorm, gemv_kernel, nb_post] 三步 kernel
gemv_kernel<<<2304, 128, 0, stream>>>(W, x, y, K);
// v2：预热期录制三步链并实例化为 graph_exec，运行时单次提交整张图
cudaGraphLaunch(graph_exec, stream);
```

在热缓存（不清空缓存，37.7 MB 的 `W` 留在片上缓存里）且由 Python 按步下发时，单个 kernel 跑得比 CPU 下发准备更快，导致 `stream` 队列排空。改用单张 CUDA Graph 重放后，H200 实测三步链耗时从逐个流启动的 73.02 µs 降至 **36.19 µs**，省去 **36.8 µs** 的队列排空等待。而在冷缓存且流队列预先排满时，CPU 下发已被队列掩盖，整图重放仍从流启动的 `67.23 µs`（热缓存预排满为 `37.89 µs`）降至 **65.15 µs**（2 个节点边界共省约 2.1 µs，平均每道边界比预先排满的流启动省约 1 µs）。

**带走一句话：** 算子融合把单请求 decode 的单层启动从约 17 次压到 11 次（无 PDL 时相邻图节点切换留约 1.0 µs 空隙，PDL 串行边约 0.64 µs），而 v2 用 CUDA Graph 重放将三步链耗时从 73.02 µs 压到 36.19 µs（队列预先排满时每道边界仍比流启动省约 1 µs）。
