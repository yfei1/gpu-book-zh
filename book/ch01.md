# 第 1 章 [第 0 级]：时间线上的 Kernel 序列——阶段之间怎样消除启动空隙并提前重叠？

**本书地图：** 前言 → 第 0.0 章 → 第 0 章 → 第 0.5 章 → **【第 1 章 [第 0 级]：时间线上的 Kernel 序列】** → 第 2 章 [第 1 级] → 第 3 章 [第 2 级] → 第 4 章 [第 3 级] → 第 5 章 [第 4 级] → 第 6 章 [第 5 级] → 第 7–10 章

先看第 0.5 章末尾留下的那组数字。按第 0 章算出的下界，单请求滑窗层把计算做完只需要约 40 µs。但在实际运行时，词元数 `T = 8..128` 下光是库函数算一次矩阵乘，就会在 `stream` 上连续启动两个独立 kernel（到 `T = 256` 才是单核）。当单层的算子排成一列放进 `stream` 时，相邻 kernel 之间那些微秒级的空隙是从哪里来的，又该怎么压到最低？

<!-- FIG part1-map: 图 I-1 全书硬件放大总图：第 0 级时间线 → 第 1 级芯片 → 第 2 级 SM → 第 3 级 SMSP → 第 4 级管线 → 第 5 级指令与比特，每级标出它决定单层的哪几步。 -->

在进入具体机制之前，可以先点开图 I-1 看一眼全书第一部分的推进顺序。第一部分按从外到内做六级硬件放大，每一章只拆开上一章刚看到的那个硬件部件。

- **第 0 级（时间线，第 1 章）**：看一条 `stream` 上的 kernel 序列，管算子启动、图节点切换（约 `1.0 µs`）与跨核交接，在 `40.0 µs` 的单层下界前把单层从原来约 17 个 kernel 压到 11 个。
- **第 1 级（整张芯片，第 2 章）**：拆开单个 kernel，看全卡 132 个 SM 怎样铺平波次、挂起在途读取用满 HBM 带宽，并在中央 L2 缓存汇总部分和。
- **第 2 级（单个 SM，第 3 章）**：拆开 1 个 SM，看片上资源容量怎样决定驻留，以及数据怎样搬进片上内存。
- **第 3 级（单个调度分区，第 4 章）**：看硬件调度器怎样跨过数据等待停顿，并在单个线程束内做归约。
- **第 4 级（执行管线，第 5 章）**：看算术管线与矩阵运算单元怎样并行重叠。
- **第 5 级（指令与比特，第 6 章）**：一直放大到 128 位机器指令字，以及 32 位寄存器里的浮点数比特位（`FP32 = 1 + 8 + 23` 位，`BF16 = 1 + 8 + 7` 位）。

本章先停留在最外层的第 0 级时间线。一句话流过 62 层模型（第 0.0 章）的每一层时，第 0 章的八个阶段要依次在 `stream` 上执行，并在阶段之间经 HBM 或 L2 交接中间激活，最后把更新后的隐藏状态和残差流交给下一层。每一次跨核交接都会带来启动空隙和额外的 HBM 读写。本章顺着时间线依次解决三个问题：第 1 节消除主机下发空隙和多余的小 kernel 启动，第 2 节让后一个 kernel 在前一个收尾时提前进场预读权重，第 3 节判断相连两阶段该合写成一个大 kernel 还是拆成两个串联 kernel。

## 1. 队列排空、算子融合与 CUDA Graph 整图重放

当单个小算子在 GPU 上只跑几微秒时，决定耗时的往往不是算子本身算了多少，而是算子之间怎么交接。**这里有三个拖慢执行的原因：CPU 准备下发命令比 GPU 跑完小算子还慢，中间结果跨算子在显存里多走了一趟读写，后一个算子又必须等前一个算子的全部线程块退出才能启动。**

<!-- FIG ch01-a: 图 1-1 画同一条 x = 时间 (µs) 轴上的三行单层时间线对比（移动块对应单层 decode 依次执行的 rmsnorm -> qkv_gate -> attention -> o 等阶段 kernel 条块）。读数显示：逐个流启动（空 kernel 流启动含事件计时约 5 µs）、CUDA Graph 重放、以及算子融合加提前启动。 -->

先看图 1-1 第一行的“逐个流启动”。单个小 kernel 在 GPU 上几微秒就跑完了。如果 CPU 准备下一次启动的时间比 GPU 执行还长，`stream` 队列（见第 0.5 章）就会排空，GPU 只能停下来等 CPU。按单 CTA 空 kernel 单次流启动含事件计时的独立微基准，每次启动准备大约要 `4.7 µs`（这里测的是逐个启动的量级；第 0.5 章在预排满队列下测得的单 CTA 空 kernel 事件开销是 `3.68 µs`）。单层如果分 17 次启动，光准备下发就要花掉约 `17 × 4.7 ≈ 80 µs`，而滑窗层的单层计算下界只有 `40 µs`。

要省去 CPU 每次逐个启动的准备时间，评测程序把整层录进 **CUDA Graph**（计算图录制与重放）。预热时用 `cudaStreamBeginCapture` 和 `cudaStreamEndCapture` 把整层的调用顺序和固定显存地址录成一张静态图并完成实例化。到了运行时，CPU 只调一次 `cudaGraphLaunch`，剩下的节点切换就交给 GPU 片上的硬件派发器（从 `stream` 读命令并派发 CTA 的硬件，内部结构未公开）自己按图重放。

不过切到图 1-1 第二行的“CUDA Graph 重放”就会看到，就算 CPU 只调一次，基线里还是留着两处损耗。

第一处是显存往返。按头归一化、旋转位置编码、写分页缓存、门控输出归一化、残差归一化、路由与 top-8 选择、以及专家前后归一化这些层间粘合小操作，如果各自写成独立 kernel，每一步都得把中间结果写回 HBM 再重新读出来。在 SGLang 的单请求 decode 剖析里，这些未融合的小操作占了整步耗时的约四分之一。

第二处是图节点切换本身的空隙。同一条 `stream` 里，后一个图节点必须等前一个节点的所有 CTA 退出、全局内存写入全部可见后才能开始。这道隐式栅栏在相邻节点切换时留下约 **1.0 µs**（中位数 `1.024 µs`）的硬件切换空隙，17 个图节点加起来仍有约 `17 × 1.0 ≈ 17 µs`。

解决这两处损耗的办法很直接：**与其把中间结果写回显存再启动下一个小 kernel 读回来，不如在主计算 kernel 的序言或尾声里直接算完。** 这就是 **kernel fusion**（算子融合）。对比按 SGLang 基线模块列表估算的约 17 次启动，单请求 decode（`T = 1`）做完各阶段内部融合，再把专家前归一化跨阶段折入前后算子（见第 9 章第 3 节，将整层从 12 次启动减为 11 次），整层就压到了 **11** 个 kernel。如果再配合下一节的编程依赖启动（PDL，让后继在前序收尾期提前进场预读权重），切到图 1-1 第三行“算子融合 + PDL”，每条 PDL 串行边降到 `0.64 µs`（单 CTA 入口等待的实测量级），11 个 kernel 按单边量级乘算的示意对比值合计约 `11 × 0.64 ≈ 7 µs`。

<!-- FIG ch01-fuse-m1: 图 1-2 单请求专家（T = 1）算子融合解剖图：上方对比未融合时“独立路由核 → 上投影核 → 独立归约 → 下投影核 → 独立归约”的多次启动与全局往返，下方展示删去独立路由核并由上、下投影最后到达 CTA 在核内原地完成部分和归约的时间线。 -->

图 1-2 用阶段 6 路由专家在单请求解码（`T = 1`，即 `M = 1`）下的三次连续融合，展示了怎么一步步减少启动边界和归约趟数。在未融合基线（图 1-2 模式 1）里，跑完这一步要连发 5 个 kernel：路由、上投影、归约、下投影、归约各启动一次，中间隔着 4 条串行边（每条约 `0.64 µs`）。

我们分三步把多余的启动拿掉：

1. **上投影核内归约（图 1-2 模式 2）**：上投影 `h_part[s, :] = x_2 @ dequant(W13_s[e]).T` 沿求和维切分算完部分和之后，不再写回全局内存等独立归约核来收。它改由最后到达的那个 CTA 在核内原地汇总 `h = Σ_s h_part[s, :]`，接着算出门控激活 `inter = silu(h_gate) ⊙ h_up`，直接把中间激活 `inter` 写进 L2。这一步把流程减为 4 个 kernel、3 条串行边，实测省下 **1.12 µs**。
2. **删掉独立路由核（图 1-2 模式 3）**：不再单独启动一个路由 kernel 生成重排表，而是让矩阵乘 CTA 直接读取路由索引 `topk_ids [1, 8]` 定位命中的本地专家 `e`。流程减为 3 个 kernel、2 条串行边，本步再省 **1.42 µs**（区间 `[-1.60, -1.28]`，累计 `-2.54 µs`）。
3. **下投影核内归约（图 1-2 模式 4）**：下投影 `y_part[s, :] = inter @ dequant(W2_s[e]).T` 同样改由最后到达的 CTA 在核内原地累加 `y = Σ_s y_part[s, :]`，直接写出各命中专家的输出 `y`，再交给专家后归一化与加权求和写出 `m [1, 4096]` 送往阶段 7 的 `unpooler`。整段压到 2 个 kernel、1 条串行边，本步再省 **0.86 µs**。

三步合起来一共省下 **3.40 µs**（`-3.40 µs`，5/5 种子全胜，输出比特等价）。这样做的代价，是主矩阵乘 CTA 需要在尾声维护原子到达计数器，并由最后到达者多做一步求和；具体的寄存器与共享内存变化以及什么时候会反输，没有单独测。除了在单个 kernel 的序言和尾声里融合，利用矩阵乘的行线性性质把跨阶段的 `pre_expert_norm` 拆入前后两核尾声（第 9 章第 3 节）以及整层跨分支融合（第 9 章第 4 节），也是同一思路的延伸。

反过来，如果拆得太碎或者合并不当，反而会变慢。第一种反例是反方向把算子拆碎。在预填充 `T = 3,012` 的阶段 6 专家路由中，曾尝试把路由对齐拆成两个 kernel，先跑计数、再跑独立的散射重排核。结果独立的散射 kernel 每线程占用 **205 个寄存器**（每个线程的片上私有暂存槽，见第 3 章）、单核耗时高达 **90 µs**，导致第 4 轮整层实测倒退 **-1.4%** 被否决。第二种反例是把原本能被前序退场期掩盖的小 kernel 并进大核串行尾声（见第 9 章第 4 节）。如果后继小 kernel 本来可以趁前序大核收尾的空档提前进场重叠执行（下一节详解），强行把它融进前序大核尾声反而会拉长关键路径。在整层检验批量（`verify T = 128 / 256`）的 7 项尾部强行融合尝试中全部实测变慢，其中 `verify 32 sliding` 最慢倒退 `+6.75 µs`；阶段 6 小批量与预填充的同类强行融合也分别慢了 `+1.18..+8.34 µs` 与 `+145..+340 µs`。

## 2. 用 PDL（编程依赖启动）让前序收尾与后继读静态权重重叠（含触发点过早反例）

两个阶段如果并行维度不同、没法融合成一个 kernel，是不是就只能等前一个 kernel 全部退场再启动后一个？不一定。**一个 kernel 的所有 CTA 不会在同一时刻结束。当最后几个 CTA 还在收尾写回时，大部分 SM 已经空出来了，而后继 kernel 进场做的第一件事往往只是从 HBM 读它自己的静态权重，并不依赖前一个 kernel 还没写完的激活。**

<!-- FIG ch01-pdl: 图 1-3 画 PDL 四步交接流程与时间线：第 1 步主机端声明编程依赖属性；第 2 步前序 CTA 算完主体后调用触发函数；第 3 步后继 CTA 趁前序收尾期从 HBM 预读静态权重 W；第 4 步后继在读取前序激活前调同步等待函数等前序写入落定（对比触发点放在函数开头导致后继空占 CTA 槽位慢近 2 µs 的反例）。 -->

**Hopper**（H200 架构代号 `sm_90a`）的 **PDL**（Programmatic Dependent Launch，编程依赖启动）就是用来拆开这两个时间点的。它把“允许后继 kernel 派发上 SM”和“前序 kernel 的全局内存写入全部可见”分成两步控制。结合图 1-1 第三行与图 1-3，我们看阶段 2 内部的分页注意力链（`prologue → attention → merge`，由归约核合并输出 `y = rmsnorm(Σ_s exp2(lse_s - lse) · o_s) ⊙ sigmoid(gate)`）以及阶段 2→3 边界（`attention → o` 输出投影，计算 `a = y · W_o^T`，最后把 `a` 交给门控残差 1）是怎么分四步交接重叠起来的：

1. **声明编程依赖边**：主机端在启动后继 kernel 时挂上 `cudaLaunchAttributeProgrammaticStreamSerialization` 属性（传入 `W_o`、`y`、`a` 三个 8 B 指针）。
2. **前序触发**：前序每个 CTA 在算完主体循环、进入收尾写出之前，调用 `cudaTriggerProgrammaticLaunchCompletion()`（底层是 `griddepcontrol.launch_dependents`，对应机器指令 `PREEXIT`，即通知硬件可提前派发后继，编译链路见第 6 章第 1 节）。当所有前序 CTA 都已经触发或退出时，硬件派发器就可以启动后继 kernel。
3. **后继预读静态权重与无关准备**：后继 CTA 进场后，先不去读前序尚未写完的激活（如阶段 2 内部的 `q_fp8`、`partial_o`，或阶段 2→3 边界的 `y`），而是先把 `W_o`（`16.8 MB`）的前几块静态权重从 HBM 预读进 L2 或片上共享内存（落点由后继代码自己决定，PDL 本身不规定）。
4. **后继等待前序数据可见**：在真正读取前序输出之前，后继调用 `cudaGridDependencySynchronize()`（底层是 `griddepcontrol.wait`，对应机器指令 `ACQBULK`，即等待前序批量写入落定）阻塞等待。直到前序整个 `grid` 执行完毕且所有全局内存写入刷新可见，后继才跨过等待点开始计算（单 CTA 入口等待的实测串行边为 **0.64 µs**）。

在图 1-3 里对比“无 PDL：等前序全部退出”和“PDL：触发在主体循环之后”两档，就能直接看到把权重预读放进前序收尾期的收益。在阶段 2 单请求 `decode 1 full`（全长注意力层）的 `attention + merge` 双核图边界上，正反序配对关掉 PDL 会慢 **+0.93 / +0.88 µs**（图 1-3 对照读数显示 `+0.93 µs`）。在 `verify 1 full` 上开启 `prologue → attention → merge` PDL 链，4 次运行省下 **0.45–0.90 µs**。在全部 7 个带独立合并核的算例上，关掉 PDL 慢 **+0.11..+1.60 µs**（除 `verify 32 full` 的 `+0.11 / +0.51 µs` 落在噪声带内外，其余 6 个算例均慢 **+0.54..+1.60 µs**，正序中位数为 `+0.64..+1.60 µs`）。

这样做的代价，是后继核必须在首次读取前序数据前插入 `ACQBULK` 同步等待点，寄存器与共享内存无额外代价；此外在阶段 6 的双节点 CUDA Graph 结构分解测量中，空图底座 `3.39 µs` 由评测框架扣除后，第 1 个核节点固定图结构成本为 `+1.87 µs`、第 2 个挂有 PDL 属性的核节点固定图结构成本为 `+1.15 µs`，协作启动属性本身占 `0.00–0.09 µs`。整层 11 个 kernel 的同流 PDL 串联、共驻掩码与借空闲 SM 提前执行将在第 9 章第 4 节展开。

但这并不意味着触发点放得越早越好。触发函数只负责放行派发，不代表前序数据已经写完。如果前序和后继的 CTA 能够同时驻留在同一个 SM 上，过早触发反而会让后继 CTA 提早进场占住 SM 槽位空等。切到图 1-3 的“PDL：触发在函数开头（反例）”就能看到这个现象：在阶段 2 全长注意力测试中，把 `griddepcontrol.launch_dependents` 提前到 `K` 循环开头（函数入口），过早进场的后继归约 CTA 在 `ACQBULK` 等待点上空停了 **9.86 µs**，最后一次触发后仍留下 `1.5–1.9 µs` 的入口间隙。全部 7 个合并算例正序实测慢了 **+0.48..+1.95 µs**（反序最小慢 `+0.51 µs`，`decode 1 full` 正反序慢 **+1.95 / +1.84 µs**；前序注意力核自身仅延长 `+0.07..+0.64 µs`，导致整体变慢的确切微架构机理未测）。另外，在阶段 3–8 整层流水线中尝试另外 4 种 PDL 触发与等待位置变体时，虽然大批量 `verify 16/32 full` 微涨 `+0.2%..+0.5%`，但小批量 `decode 16 sliding` 实测倒退约 **-1%**（超出同任务 A/A 噪声带，原因未测），因此整包被否决。

## 3. 什么时候该合写成一个协作大核，什么时候该拆成两个 PDL 串联核？

把相邻的两个阶段写进同一个持久大 kernel、中间用一道全网格同步栅栏隔开，一定比拆成两个 kernel 更快吗？不一定。**如果相连的两步之间存在全对全的数据依赖，合写进一个协作大核就必须让全卡 132 个 SM 在栅栏处等最慢的那一个块跑完。反过来，拆成两个用 PDL 串联的 kernel，先算完第一步的 CTA 一退场，第二步的 CTA 就能立刻填进空出的 SM，趁等待前序数据落定的时间先把第二步的静态权重预读上片。**

<!-- FIG ch01-b: 图 1-4 上方画专家计算的两个相连矩阵乘阶段（移动块对应专家先算上投影 w13 写出中间激活、再算下投影 w2 读该激活的算法步）。下方对比合写单一大 kernel 与拆成两个 PDL 串联 kernel 的时间线。 -->

看第 0 章阶段 6 的路由专家计算（图 1-4）。阶段 A 读入某专家分到的 $n$ 个词元输入 `x_2 [n, 4096]`（BF16，位于 HBM/L2）与上投影权重 `W13`（`uint8 [8192, 2048]` 加块缩放 `[8192, 256]`，每专家共 **18.9 MB**，位于 HBM），先算上投影 `h = x_2 · W13^T`，再经门控激活 `inter = silu(h[:, :4096]) ⊙ h[:, 4096:]` 写出中间激活 `inter [n, 4096]`（BF16，经 L2 交接）。阶段 B 读入 `inter` 与下投影权重 `W2`（`uint8 [4096, 2048]` 加块缩放 `[4096, 256]`，每专家共 **9.4 MB**，位于 HBM），接着算下投影 `y = inter · W2^T` 写出 `y [n, 4096]`，最后交给每专家独立均方根归一化与路由权重加权求和，产出 `m [M, 4096]` 送往阶段 7 的 `unpooler`。因为下投影权重 `W2` 的每一行都要读完 `inter` 的全部 4,096 列，而这 4,096 列是由许多 CTA 在阶段 A 分别算出来的，所以阶段 A 和阶段 B 之间是全对全的数据依赖。

如果用 **cooperative launch**（协作启动，`cudaLaunchCooperativeKernel`）把阶段 A 和阶段 B 合写进一个持久大 kernel（全卡 132 个 CTA），两步之间就必须插一道 **grid barrier**（全网格同步栅栏）。协作启动要求所有 CTA 同时驻留在芯片上（超出同时驻留容量时驱动会直接拒绝启动），因为只要有一个 CTA 还没派上芯片，已经驻留的 CTA 在栅栏处永远等不到它，就会死锁。切到图 1-4 的“合写成一个协作大 kernel”，这道全网格栅栏在 132 个 CTA 下实测耗时 **1.42 µs**（`1,419.3 ns`；264 个 CTA 下为 `1,521.5 ns`）。而且全卡 132 个 SM 都得停在栅栏前面，等阶段 A 最慢的那一个区域跑完，才能开始去读阶段 B 的权重 `W2`。

切到图 1-4 的“拆成两个 PDL 串联 kernel”，做法就变了。我们把阶段 A 和阶段 B 拆成两个由 PDL 串联的 kernel（阶段 A 也通过 PDL 接在路由核后面）。这样串行交接边降到了 **0.64 µs**。更重要的是，先算完阶段 A 的 CTA 一退场，阶段 B 的 CTA 就能立刻填进刚空出来的 SM，在 `griddepcontrol.wait` 之前先把 `W2`（每专家 **9.4 MB**）的权重分块预读上片（栅栏省时与预读各自占多少比例属于推断，未单独拆分测量）。

在 `decode 16`（`M = 16`）和 `decode 32`（`M = 32`）上，拆成两个 PDL 串联核比单一协作大核实测净快 **0.70 µs**（`[-0.80, -0.60] µs`）和 **0.82 µs**（`[-0.91, -0.73] µs`，160 次配对，比特级等价）。在 `verify 1`（`M = 8`）上，首版省下 `0.21 µs`，进一步将相位拆分配合编译器版本门控的权重环栅栏推广到 `M = 8` 后，`verify 1` 的总节省达到 **0.37 µs**（`[-0.52, -0.22] µs`）。不过到了单请求 `decode 1`（`M = 1`），拆核对照差为 `+0.03 µs`，没有拆核收益，所以 `M = 1` 保持单核协作启动。

拆成两个 kernel 的代价，是多出 1 个 CUDA Graph 节点。同时，因为阶段 A 与阶段 B 每个 CTA 各占约 `132 KB` 共享内存（CTA 片上共享暂存，见第 3 章），两个 CTA 合起来要 `2 × 132 KB ≈ 264 KB > 227 KB`（超出单 SM 可用共享内存上限），阶段 B 的 CTA 无法与阶段 A 同 SM 共驻，只能按 `blockIdx.x` 顺序随阶段 A 退场逐个进场（由此带来的高编号 CTA 晚启动斜坡会在第 2 章第 2 节解决）。

往单一大核方向强行合并还有两个反例。第一个是在已被 PDL 重叠的预填充专家上合写单一持久上、下投影大核。在预填充 `T > 1,024`（阶段 6 专家）中，线上版本已经通过块完成信号和 PDL 把上投影与下投影的交接边界压得很窄。如果强行把两步合写进单个持久大核，理论可省的边界上界估算不超过总分的 **0.32%**（实际可兑现估算仅约 `0.1%–0.16%`），却会丢掉下投影交由硬件动态调度各专家分块的能力（见第 8 章第 5 节），所以在设计阶段直接否决。第二个是跨整层把不同形状的阶段合进单一协作大核（见第 9 章第 4 节）。把同一阶段内的同构子任务留在持久核里是划算的（见第 8 章第 2–3 节），但如果把整层多个不同矩阵形状、不同寄存器需求的阶段塞进单一全层持久协作大核，全核驻留就会被最高寄存器需求的阶段卡住上限，而且每道边界都要付同步代价。在解码与检验整层实测中，全层大核谱系比按阶段拆开再用 PDL 串联慢了 **1.05 ms**（全层持久大核的结构性惩罚估算也达 `+8.3 µs`）。

## 4. `qkv_gate` 双轨演化（第 0 级）：`gemv`（v1 → v2，Graph 重放）与 `qkv_gemm`（g0 → g1a，单核化消去独立归约核）

回到贯穿全书第一部分的阶段 1 `qkv_gate`（权重 `W [2304, 8192]` BF16，`37.75 MB`）。把本章第 0 级的做法落到两条演化轨道上，核心思路很统一：**在 `T = 1` 的 `gemv` 轨道上用整图重放消掉主机下发与节点切换空隙；在 `T = 8..256` 的 `qkv_gemm` 轨道上用尾声核内归约删掉库函数的第二次归约 kernel 启动。**

### 轨道一（`T = 1`）：`gemv v1 → v2`（把流启动链录进单张 CUDA Graph 重放）

为了测量 `gemv_kernel`（**v1**，见第 0.5 章，每线程占 22 个寄存器、每 CTA 占 512 B 共享内存、每 SM 驻留 16 个 CTA）在多层调用链里的启动开销，计时程序构造了一条三步链：入口归一化核（1 个 CTA）、`gemv_kernel` 矩阵-向量乘核（2,304 个 CTA）和后处理核（9 个 CTA）。如果主机端从 Python 逐个往流里发这三步，相邻 kernel 之间就会暴露出下发空隙。本章的 **v2** 不改 `gemv_kernel` 本身（单 kernel 冷缓存耗时仍是 `58.88 µs`），只在预热期把这条三步链录进同一张 CUDA Graph 并完成实例化，运行时一次重放。

```cuda
// v1：主机端在 stream 上逐个下发 [nb_rmsnorm, gemv_kernel, nb_post] 三步 kernel
gemv_kernel<<<2304, 128, 0, stream>>>(W, x, y, K);
// v2：预热期录制三步链并实例化为 graph_exec，运行时单次提交整张图
cudaGraphLaunch(graph_exec, stream);
```

在热缓存（不清空缓存，37.7 MB 的 `W` 留在片上缓存里）且由 Python 逐步下发（CPU 下发受限）时，改用单张 CUDA Graph 重放后，H200 实测三步链耗时从逐步流启动的 `73.02 µs` 降到 **36.19 µs**，比逐步流启动省了 **36.8 µs**。即便在冷缓存且流队列预先排满、CPU 下发已经被队列掩盖的情况下，整图重放仍然把耗时从流启动的 `67.23 µs`（热缓存预排满为 `37.89 µs`）压到 **65.15 µs**。两个节点边界合起来省了约 `2.1 µs`，平均每道边界比预先排满的流启动省约 `1 µs`。

### 轨道二（`T = 8..256`）：`qkv_gemm g0 → g1a`（消除 cuBLAS 独立归约核的第二次启动，附 `T = 256` 退化权衡）

当词元数升到 `T = 8 | 32 | 128 | 256` 时，第 0.5 章的基线 **g0** 调用 `torch.matmul(X, W.t(), out=Y)`（底层调用 cuBLAS 矩阵乘主核）。在 `T = 8, 32, 128` 这三档下，因为输出行数 `T` 很小，cuBLAS 会把内积维 `K = 8,192` 拆给多个 CTA 分段计算（下一章第 1 节详解）。这样算一次矩阵乘会在 `stream` 上连续启动**两个独立 kernel**：先跑 cuBLAS 的矩阵乘主核写出部分和，再启动一个独立的 cuBLAS 归约核把部分和加起来写回 `Y`（只有 `T = 256` 只跑 1 个 kernel）。在统一的单图重放评测口径下（每次迭代前读取 512 MiB 干净清空 L2，500 次迭代取中位数，包含空图重放固定底座 `4.96 µs`），**g0** 在 `T = 8 | 32 | 128 | 256` 四档的实测耗时分别是 **`18.20 | 18.60 | 21.32 | 22.90 µs`**。

本章第 0 级的 **g1a** 把每次矩阵乘收成**单次 kernel 启动**：删掉 cuBLAS 的独立归约核，改由主核内最后到达的那个 CTA 在核内原地完成部分和归约（也就是第 1 节讲的尾声归约融合）。H200 实测对照如下：

| 演化步 | 关键改动（第 0 级机制与评测口径） | `T = 8` (µs / GB/s) | `T = 32` (µs / GB/s) | `T = 128` (µs / GB/s) | `T = 256` (µs / GB/s) | 本步权衡（Gain vs Cost / When it loses） |
|---|---|---|---|---|---|---|
| **v1 → v2**（`T = 1` 三步链） | 入口归一化核（1 个 CTA）、`gemv_kernel`（2,304 个 CTA）与后处理核（9 个 CTA）组成的三步链（`gemv v1` 每线程 `22` 个寄存器、`512 B` SMEM、每 SM `16` 个 CTA）录进单张 CUDA Graph 重放（单核冷缓存仍为 `58.88 µs`） | — | — | — | — | 热缓存 Python 逐步下发从 `73.02` 降至 **36.19 µs**（省 **36.8 µs**）；冷缓存预排满从 `67.23` 降至 **65.15 µs**（热缓存预排满 `37.89 µs`，2 道边界共省约 `2.1 µs`、每道约 `1 µs`） |
| **g0** | `cuBLAS` 基线（`T = 8..128` 调矩阵乘主核加独立归约核共两个 kernel；`T = 256` 单核；单图重放、每次迭代前读 512 MiB 清 L2、500 次中位数、含空图底座 `4.96 µs`） | `18.20` / `2,074` | `18.60` / `2,030` | `21.32` / `1,771` | `22.90` / `1,649` | 小中批量每次矩阵乘付 2 次启动与 1 道图节点切换边 |
| **g1a** | 单核化：删掉 cuBLAS 独立归约核的启动，由最后到达 CTA 核内归约 | **`15.81`** / `2,388` (`-2.39 µs`) | **`17.92`** / `2,107` (`-0.68 µs`) | `21.57` / `1,750` (`+0.25 µs`) | `33.39` / `1,130` (**`+10.50 µs`**) | **小 `T` 赢、大 `T` 输**：`T = 8 / 32` 省掉第 2 次启动净快 **2.39 / 0.68 µs**；但 `T = 128` 持平（`+0.25 µs`），`T = 256` 反而比单核 cuBLAS **慢 10.50 µs（+46%）** |

为什么 `g1a` 省掉了第二次 kernel 启动，在 `T = 8 / 32` 上省下了 **2.39 / 0.68 µs**，到了 `T = 128` 却被追平，在 `T = 256` 反而比单核 cuBLAS 慢了 **10.50 µs（+46%）**？

原因在于，第 0 级只管“时间线上启动几个 kernel”，却没管单个 kernel 内部在整张芯片 132 个 SM 上是怎么排布的。`g1a` 在 `T = 128 / 256` 下只启动了 72 个 CTA，让全卡 132 个 SM 里的 60 个完全空闲。而且到了尾声，它让最后到达的那 1 个 CTA 独自串行读回并累加多达 `1 MB` 的部分和。

小结一下第 0 级时间线：靠 CUDA Graph 重放、算子融合和 PDL，我们消掉了主机下发和跨核切换的空隙（`gemv v2` 在预排满队列下每道边界省约 `1 µs`、相对逐步流启动省 `36.8 µs`）。`qkv_gemm g0 → g1a` 的单核化也在 `T = 8 / 32` 省下了 **2.39 / 0.68 µs**，但在 `T = 256` 因为 72-CTA 网格和单 CTA 串行归约倒输了 **10.50 µs**。要拿回 `g1a` 在 `T = 128 / 256` 丢掉的时间，就必须点开时间线上的单个 kernel，进入下一章的第 1 级（整张 H200 芯片）：看看怎样让 132 个 SM 同时干完活、挂起足够的在途字节跑满 4.8 TB/s 的 HBM，并在中央 L2 上并行合并跨 SM 的部分和。
