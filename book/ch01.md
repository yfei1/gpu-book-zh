# 第 1 章 [第 1 级]：时间线——相邻两个 kernel 之间的时间花在哪里，怎样压掉？

**本书地图：** 前言 → 导引一 → 导引二 → 导引三 → **【第 1 章 [第 1 级]】** → 第 2 章 [第 2 级] → 第 3 章 [第 3 级] → 第 4 章 [第 4 级] → 第 5 章 [第 5 级] → 第 6 章 [第 6 级] → 第 7–9 章 → 第 10 章 → 附录

导引三写出了 `gemv_kernel`（v1），并说明了三件事：同一条 CUDA 流里的命令按入队顺序执行，前一个 kernel 的写入对后一个 kernel 可见（先行发生，见导引三第 2 节），以及每次计时都含约 4.6 µs 的固定开销（见导引三第 5 节）。但在一层模型里，GPU 不是只跑这一个 kernel，而是要沿一条 CUDA 流依次启动一串 kernel。**两个相邻 kernel 之间的时间花在哪里，怎样压掉？**

图 I-1 把第一部分的六级放大画在一张图上，本章停在最外面的第 1 级：时间线。

我们把导引三的 `gemv_kernel` 放回它在一层里的位置，在前面接一个归一化 kernel，在后面接一个后处理 kernel，组成一条三 kernel 链。本章从头到尾只用这一个例子：

1. **归一化 kernel**：输入 $\shape{x}{8192}{BF16}$，输出 $\shape{x_n}{8192}{BF16}$，计算 $x_n = x \cdot r$，其中 $r = 1/\sqrt{\tfrac{1}{K}\sum_k x_k^2 + \epsilon}$（此处不乘权重向量；RMSNorm 定义见导引一第 1 节），启动 1 个 CTA、1,024 个线程。
2. **`gemv_kernel`（v1）**：计算 $y = W x_n$，权重 $\shape{W}{2304,\ 8192}{BF16}$，输出 $\shape{y}{2304}{FP32}$，启动 2,304 个 CTA、每 CTA 128 个线程。
3. **后处理 kernel**：对 $\shape{y}{2304}{FP32}$ 做逐元素运算（代替真实的 QK 归一化与位置编码），每 CTA 256 个线程，共启动 $\lceil 2304/256 \rceil = 9$ 个 CTA。

这三步只用到导引三讲过的 CTA、线程、CUDA 流和全局内存。

## 1. GPU 为什么会在两个 kernel 之间停下来？

**有两种空隙：CPU 下发比 GPU 慢时队列被取空，GPU 等 CPU；队列排满后，后一个仍要等前一个全部 CTA 退出。** 本书把前者叫作 **CPU 下发空隙**，把后者叫作**硬件交接空隙**。

<!-- FIG ch01-a: 图 1-1 同一条时间轴（µs）上的三 kernel 链三行对比：第 1 行“CPU 逐个下发”（上方 CPU 时间线，下方 GPU 时间线，红圈标出 ① 前和 ①→② 处等待 CPU 的空白，② 跑约 50 µs 期间 CPU 已排入 ③ 故 ②→③ 不等 CPU）；第 2 行“命令预先排满”（条块之间只剩硬件交接）；第 3 行“整图重放”（CPU 只提交一次，GPU 条块之间只剩节点交接缝，每道约 1.0 µs）。三个条块统一编号配色：①归一化 ②gemv ③后处理。读数：链总时间 102.6 / 61.6 / 60.0 µs，CPU 下发空隙约 41 µs（两处合计，拆分未测）。步骤卡：第 1 步 CPU 下发①（公式：无；输入：启动命令；代价：$t_{cpu}$，未单独测）；第 2 步 ①运行（公式：$x_n = x\cdot r$；输入：$\shape{x}{8192}{BF16}$ 16 KiB 在 HBM；输出：$\shape{x_n}{8192}{BF16}$ 16 KiB 写回全局内存，交给②）；第 3 步 交接（①的 CTA 全部退出 → ②的 CTA 上 SM）；第 4 步 ②运行（公式：$y = W x_n$；输入：$\shape{W}{2304,\ 8192}{BF16}$ 37.75 MB 在 HBM、$\shape{x_n}{8192}{BF16}$ 16 KiB；输出：$\shape{y}{2304}{FP32}$ 9,216 B，交给③）；第 5 步 交接；第 6 步 ③运行（公式：对 $y$ 逐元素运算；输出：$\shape{y}{2304}{FP32}$ 9,216 B）。总代价：三行的链总时间分别为 102.6 / 61.6 / 60.0 µs。 -->

先看第一种空隙。启动语句只把命令放进 CUDA 流就返回（见导引三），所以 CPU 是生产者，GPU 是消费者，CUDA 流是两者之间的队列。设每个 kernel 在 GPU 上跑的时间为 $t_{gpu}$，CPU 每次下发一条启动命令需要 $t_{cpu}$。当 $t_{cpu} > t_{gpu}$ 时，GPU 跑完上一个 kernel 时下一条命令还没送进队列，队列被取空，相邻两个 kernel 的开始间隔就变成 $t_{cpu}$，GPU 每次都要空等约 $t_{cpu} - t_{gpu}$。反过来，当 $t_{cpu} \le t_{gpu}$ 时，CPU 走在前面，队列里一直有命令，这段空等就会消失。

小 kernel 的 $t_{gpu}$ 只有几微秒，所以第一种空隙对小 kernel 最伤。章首的三 kernel 链里，1 个 CTA 的归一化和 9 个 CTA 的后处理都是这种小 kernel。本书的测量程序用 Python 调用这三次启动（所以 $t_{cpu}$ 里包含 Python 自己的开销；用 C++ 直接启动会短一些，未测）。图 1-1 前两行对比两种测法：“CPU 逐个下发”是计时开始时队列为空，CPU 从 Python 一条一条发出三次启动；“命令预先排满”是计时开始前先放一个让 GPU 忙一小段时间的 kernel，CPU 趁这段时间把三条启动命令全部排进队列。实测下来，CPU 逐个下发比命令预先排满慢了约 **41 µs**（图表见第 5 节）。按队列规则，这 41 µs 落在两处：第一次下发（计时开始时队列是空的）和 ①→② 这道边界（① 只跑几微秒）；② 跑约 50 µs，CPU 已经趁这段时间把 ③ 排进队列，②→③ 这道边界不再等 CPU。两处各占多少没有拆开测；$t_{cpu}$ 本身也没有单独测。

再看图 1-1 第二行的“命令预先排满”。即使三条命令早就排在队列里，相邻两个条块之间依然留着一道缝。这第二种空隙与 CPU 无关：同一条 CUDA 流的顺序保证（先行发生，见导引三第 2 节）是靠“前一个 kernel 完全结束、写入全部可见，后一个才开始”实现的。因此每过一道 kernel 边界，都要走完“前一个 kernel 的最后一个 CTA 退出 → 写入可见 → 下一个 kernel 的 CTA 派上 132 个 SM（导引三第 1 节）”的交接过程。在这段时间里，部分 SM 在交接时空着。

## 2. CUDA graph 去掉哪一种空隙，留下哪一种？

**CUDA graph 把整条链预先录好、一次提交，去掉了 CPU 下发空隙；但节点间约 1.0 µs 的硬件交接还在。**

**CUDA graph**（计算图）是预先录好的一串 GPU 命令及其依赖，图里的每个 kernel 叫一个**节点**。做法分两步：第一步是录制，在预热阶段把三 kernel 链的启动依次录进一张图，录完后驱动把这张图转成一份可以直接重放的命令表（叫作**实例化**）；第二步是重放，到了运行时 CPU 只调用一次 `cudaGraphLaunch`（代码见第 5 节），GPU 上的派发硬件就会自己按图走完三个节点。这样图外的 CPU 准备时间 $t_{cpu}$ 整条链只付一次，不再每个 kernel 付一次，第 1 节的第一种空隙就消失了（图 1-1 第 3 行）。

但图里的每个节点依然是一个独立的 kernel，相邻节点之间仍要遵守同一条 CUDA 流的顺序规则：后一个节点必须等前一个节点的全部 CTA 退出、写入全部可见后才能开始。因此第二种空隙还留在图里。在一个推理服务的真实计算图上逐道边界测量，相邻两个节点之间的切换中位数约 **1.0 µs**（不是本章这条链，见下图）。

拿它和第 1 节的“命令预先排满”对比：预先排满虽然也能藏住 CPU 时间，但前提是 CPU 必须一直走在 GPU 前面；整图重放则不依赖这一点。在三 kernel 链上，整图重放比命令预先排满还快约 1.6 µs（见第 5 节图表）；这 1.6 µs 的差别来自哪里，我们没有拆开测。

CUDA graph 的取舍：

- **得到什么**：消除了 CPU 下发空隙；在这条三 kernel 链上，整图重放比 CPU 从空队列逐个下发快约 **1.7 倍**（见第 5 节图表）。
- **付出什么**：预热时要多做一次录制和实例化；而且图里每个 kernel 的参数、张量形状和显存地址都是写死的，一旦输入形状变了，就要另录一张图（在线服务通常为每种词元数 $T$ 各录一张图，并把输入补齐到录过的 $T$，这一项的额外代价未测）。
- **什么时候亏本**：在这条三 kernel 链上，整图重放比两种流启动都快，没有测到比流启动慢的情况；其他场景未测。

## 3. 把两个 kernel 合成一个，省下什么、付出什么？

**融合去掉一道边界、一次启动和一次全局内存往返；代价是主 kernel 多算一步，且要求数据已在同一个 CTA 里。**

把相邻两个 kernel 的工作写进同一个 kernel、让中间结果留在寄存器或片上而不经全局内存交接，叫作 **kernel fusion**（融合）。每多一个独立 kernel，除了多一道第 2 节的交接之外，中间结果还要先写回全局内存、再由下一个 kernel 读回来。在同一台 H200 上用同一测法分别测三个 kernel 单独运行和整条链（整图重放），整条链比 `gemv_kernel` 单独运行只长了约 **5.8 µs**。

这 5.8 µs 是整条链（59.94 µs）减去 `gemv_kernel` 单独运行（54.18 µs）得到的差，是两个整体测量的差，不是各部分之和。各部分单独看：归一化比空 kernel 多约 4.4 µs，后处理多约 0.7 µs，再加两道节点切换（上一节的 1.0 µs，量自另一张图），加起来约 7.2 µs，比 5.8 µs 多出约 1.4 µs；这 1.4 µs 的来源我们没有查。5.8 µs 里包含了归一化与后处理自己的计算时间和两道交接边界；融合后两步的计算照样要做，所以实际省下的更少。

具体怎么合？先把术语定下来：kernel 主循环之前的准备叫**序言**（prologue），主循环之后、写出结果之前的逐元素计算叫**尾声**（epilogue）。

后处理并进尾声很直接：`gemv_kernel` 每个 CTA 的 0 号线程在块内归约算出这一行的内积之后、写回 `y[row]` 之前，数据本来就在它的寄存器里，而且逐元素后处理不需要别的 CTA 的结果，顺手算完再写出去就行。

归一化并进开头要多想一步。$x_n = x \cdot r$ 里的缩放因子 $r = 1/\sqrt{\tfrac{1}{K}\sum_k x_k^2 + \epsilon}$ 依赖整条 $x$ 的平方和，乍看必须等所有元素读完才能开始矩阵乘。但回头看导引三的 `v1` 循环：每一个 CTA 为了算自己那一行的内积，本来就要把整条 $x$（8,192 个元素）从头到尾读一遍。既然每个 CTA 都读全了 $x$，就可以在同一个循环里顺手多累加一个平方和 $\sum_k x_k^2$，在尾声块内归约后算出 $r$，最后再乘到内积上写出 $y[\text{row}] = r \cdot \sum_k W[\text{row}, k]\,x_k$。这是因为：

$$y = W(x \cdot r) = r\,(Wx)$$

在不乘权重向量时，这两个式子代数恒等（若乘权重向量 $g$，写成 $r\,W(g \odot x)$ 也仍然只用本 CTA 读到的数据）；和分开跑两个 kernel 相比，主要的数值差别是省去了中间结果 $x_n$ 写回全局内存时的那一次 BF16 舍入（先求和再乘 $r$ 也会改变浮点乘加的舍入顺序）。这条把归一化与后处理都并进去的 `gemv` 我们没有实测，上界就是前面的 5.8 µs。

<!-- FIG ch01-fuse-gemv: 图 1-2 把归一化与后处理融进 gemv_kernel 的解剖图：上方算法带画 v1 的一行 W[row, :] 与 x，并新增一条与 W·x 共用同一循环的 ∑x_k^2 累加带；中间硬件画一个 SM 上的一个 CTA，128 个线程各持两个寄存器累加器 acc 与 ss；下方时间线对比“三个 kernel”（①②③ 与两道交接）和“一个 kernel”（只有②，开头不再等①，结尾不再交给③）。步骤卡：第 1 步 循环：acc += W[row,k]·x[k]，ss += x[k]·x[k]（输入 W 行 16 KiB 在 HBM、x 16 KiB 在留在芯片上的缓存；代价：每元素多 1 次乘加）；第 2 步 块内归约两个和（smem 512 B → 1 KiB；代价：多一次归约）；第 3 步 r = 1/√(ss/K+ε)，y[row] = r·acc，逐元素后处理，写 y（输出 9,216 B 到全局内存）。总代价：去掉 2 道交接和 2 次启动，增加每元素 1 次乘加和一次归约；收益未测，上界 5.8 µs。 -->

融合不是白拿的。上面的 `v1` 三 kernel 链没有测融合，不过我们在本书后面的一个 `gemv` kernel 上量过：固定同一个 kernel、同为 BF16 输出，只让尾声多做 QK 归一化、位置编码和写 FP8 KV 缓存，kernel 就多花约 **1.1 µs**（见下图，和上面 5.8 µs 上界不是同一次实验）。

```chart

```

能不能合，只看一件事：后一步要的数据是不是已经在同一个 CTA 里，或者能在 CTA 里便宜地重算。归一化能合，是因为每个 CTA 本来就读全了 $x$（这 16 KiB 数据会留在芯片上的缓存里，见第 2 章第 2 节）。融合的取舍：

- **得到什么**：少 2 道硬件交接、少 2 次启动；中间结果 $x_n$（16 KiB，在 $T = 1$ 时很小）不再写回全局内存又读回来。在这条链上收益未测，上界为 5.8 µs。
- **付出什么**：主 kernel 多做一步计算（上面的实测中，尾声多做一步约多花 1.1 µs）；代码更复杂；而且 2,304 个 CTA 每个都把同一个 $r$ 重复算了一遍（每个 CTA 多做 8,192 次乘加和一次块内归约）。
- **什么时候亏本**：
  - 后一步的每个 CTA 都要读前一步许多 CTA 算出的结果（全对全依赖）时，硬合成一个 kernel（持久 kernel 的定义见第 3 章第 1 节），就要在中间加一道全卡同步：所有 CTA 停下来，等最慢的那个写完，后一步才能读；拆成两个 kernel、用下一节的办法串起来更快（见第 8 章第 6 节）。
  - 把原本可以和前一个 kernel 收尾期重叠的小 kernel 硬塞进前一个 kernel 的尾部，它就只能串行执行，实测反而变慢（见第 9 章第 6 节）。

## 4. 后一个 kernel 能不能在前一个结束之前就开始？

**能。PDL 把“允许后继上片”和“前驱写入可见”拆成两步：前驱触发后后继先上片读权重，等待返回后再读前驱输出。**

导引二第 3 节说过，静态权重不依赖前一步算出的激活，可以提前读；同时在这条三 kernel 链里，归一化 kernel 只有 1 个 CTA，它运行时只占 1 个 SM，其余 131 个 SM 都空着。但在普通 CUDA 流里，硬件把“后继能开始派发”和“前驱已经完全结束”绑在了一起。**Hopper**（H200 的架构）提供的 **PDL**（Programmatic Dependent Launch，编程依赖启动）把这两件事拆成四步（图 1-3）：

1. 主机端启动后继 kernel 时挂上一个依赖属性，声明这是一条编程依赖边。
2. 前驱的每个 CTA 在算完主循环、进入写回之前发出**触发调用**；一旦所有前驱 CTA 都已触发（或已退出），硬件派发器就**可以**把后继的 CTA 派到空闲 SM 上（规范允许提前派发，但不保证一定提前派发）。
3. 后继 CTA 上到 SM 后，先做不依赖前驱输出的工作——在“归一化 → gemv”这道边界上，就是先向 HBM 发出第一批权重 $W$ 的读取。等待调用返回之前读进来的字节必须先留在芯片上（寄存器或片上存储），等 $x_n$ 准备好再用，因此能提前读多少受片上空间限制（单层里实际能提前读多少见第 9 章第 5 节）。
4. 后继在读取前驱输出之前发出**等待调用**；等待调用返回时，前驱整个 grid 已经执行完毕，前驱的所有全局内存写入对后继全部可见。

```cuda
// 前驱：主循环结束、写回之前
cudaTriggerProgrammaticLaunchCompletion();
// 后继：先发出不依赖前驱的读取，再等待
cudaGridDependencySynchronize();   // 返回后才能读前驱的输出
```

**正确性只来自等待调用，不来自触发调用的位置。** 后继里一切读前驱输出的代码，以及写前驱还在读的缓冲区的代码，都必须放在等待调用之后。触发调用放在哪里不影响正确性，只决定后继多早能占上 SM。

按时间线推断，用 PDL 能省下的时间上界是“前驱收尾的时间”和“后继在等待之前能做的独立工作”两者中较小的那一个，再加上交接本身变短的部分。在后继只有 1 个 CTA、一进场就调用等待的独立微基准里，测得一道 PDL 交接的中位数约 **0.64 µs**（这和第 2 节约 1.0 µs 的图节点切换不是同一次实验，只用来看量级）。在这条 `gemv` 链上，PDL 的收益和亏本都没有测。

触发调用放在哪里要看前驱占多少个 SM。前驱只占少数 SM 时（如本例只有 1 个 CTA），在开头触发几乎不会挤占前驱，重叠最多；当前驱占满全卡 SM 时，因为一个 SM 同时能容纳的 CTA 数量有限（见第 3 章第 1 节），如果前驱一进函数开头就触发，后继 CTA 进场太早就会占着 SM 的位置停在等待调用上干等，反而挤占并拖慢还没算完的前驱。这只会拖慢，不会死锁：触发要等前驱的每个 CTA 都已触发或退出，那时前驱的 CTA 都已在片上，后继占位置挡不住它们。所以前驱占满 SM 时，触发调用应当放在前驱主循环结束之后、收尾写回之前。PDL 的取舍：

- **得到什么**：让后继不依赖前驱的读取与前驱收尾重叠，并缩短 kernel 之间的交接。在 `gemv` 链上未测。
- **付出什么**：后继必须在第一次读前驱数据之前插入等待调用；一旦把读取误放在等待调用之前，就会读到旧数据，而且运行时不会报错（这类错误的实测见第 9 章第 5 节）。寄存器与共享内存占用的变化未测。
- **什么时候亏本**：前驱占满 SM 时触发放得太早，后继占着 SM 空等；实测反例见第 7 章第 11 节。

**带走一句话：** kernel 之间的时间有两种来源——CPU 下发跟不上，和硬件要等前一个 kernel 的全部 CTA 退出；CUDA graph 去掉第一种，融合减少第二种出现的次数，PDL 让第二种和有用的读取重叠；三者都不改变单个 kernel 自己的耗时。
