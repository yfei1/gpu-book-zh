## 1. 队列排空、算子融合与 CUDA Graph 整图重放

**本节要回答的问题：** 为什么 CPU 逐个启动与未融合的小算子会白白浪费数微秒空隙与 HBM 往返？

<!-- FIG ch01-a: 图 1-1 画同一条 x = 时间 (µs) 轴上的三行单层时间线对比（移动块对应单层 decode 依次执行的 rmsnorm -> qkv_gate -> attention -> o 等阶段 kernel 条块）。读数显示：逐个流启动（空 kernel 流启动含事件计时约 5 µs）、CUDA Graph 重放、以及算子融合加 PDL。 -->

如图 1-1 所示，在模式选项里选“逐个流启动”。读数为：`17 次启动 · 每次准备约 4.7 µs（空 kernel，含事件计时）`；`合计约 17 × 4.7 ≈ 80 µs，而单层下界是 40 µs（滑窗层）`（这里的 4.7 µs 是单 CTA 空 kernel 单次流启动含事件计时的独立微基准，用来展示逐个启动的量级，不同于第 0.5 章 `gemv` 计时程序在预排满队列下测得的 3.68 µs）。图 1-1 第一行里，GPU 有一段时间停下空等。因为单个小 kernel 在 GPU 上只跑几微秒，当 CPU 逐个下发的准备时间比它还长时，`stream` 队列（见第 0.5 章）就会排空。所以评测程序将整层录成 **CUDA Graph**（计算图录制与重放）重放计时。预热时，`cudaStreamBeginCapture` 与 `cudaStreamEndCapture` 把整层调用顺序和固定显存地址录成静态图并实例化；运行时 CPU 只调一次 `cudaGraphLaunch`，由片上硬件派发器（从 `stream` 读命令并派发 CTA 的硬件，内部结构未公开）自主重放整张图。

但图 1-1 第二行显示，开启 CUDA Graph 后基线仍有两处损耗。第一，未融合的层间粘合小操作（归一化、门控残差、路由分桶与拆分归约）各自读写 HBM 并启动独立 kernel，在 SGLang 的单请求 decode 剖析中占了整步耗时的约四分之一。第二，同一 `stream` 里后一个图节点必须等前一个节点的所有 CTA 退出、写入全部可见后才能开始，这道隐式栅栏在相邻图节点切换时留下约 **1.0 µs** 的硬件切换空隙。选“CUDA Graph 重放”，读数为：`17 个图节点 · 每次节点切换约 1.0 µs（中位数 1.024 µs）`；`合计约 17 × 1.0 ≈ 17 µs · CPU 只调 1 次`。因此第 0 级还要做 **kernel fusion**（算子融合），把前后相连的小操作直接并进主计算 kernel 的序言或尾声：每删掉一个独立 kernel，就同时省掉一次图节点切换空隙（或约 `0.64 µs` 的 PDL 交接边）和一次中间张量的 HBM 往返，把单请求 decode（`T = 1`）的单层启动从约 17 次压到 **11** 次。选“算子融合 + PDL”，读数为：`11 个 kernel · 每条 PDL 串行边 0.64 µs`（单 CTA 实测量级）；`合计约 11 × 0.64 ≈ 7 µs · 预读权重与前序收尾重叠`。

<!-- FIG ch01-fuse-m1: 图 1-4 单请求专家（T = 1）算子融合解剖图：上方对比未融合时“独立路由核 → 上投影核 → 拆分归约 → 下投影核 → 拆分归约”的多次启动与全局往返，下方展示删去独立路由核并由上、下投影最后到达 CTA 原地完成 Split-K 归约的时间线。 -->

以阶段 6 路由专家在单请求解码（`T = 1`，即 `M = 1`）下的三次连续融合为例，解剖算子融合如何一步步砍掉启动边界与归约趟数：
- **公式**：(1) 路由映射直接由矩阵乘 CTA 读取 `topk_ids [1, 8]` 定位命中的本地专家 `e`，省去单独生成重排表的路由预处理核；(2) 上投影 `h_part[s, :] = x_2 @ dequant(W13_s[e]).T`，由沿 `K` 维切分的最后到达 CTA 原地汇总 `h = Σ_s h_part[s, :]` 并算 `inter = silu(h_gate) ⊙ h_up`；(3) 下投影 `y_part[s, :] = inter @ dequant(W2_s[e]).T`，同样由最后到达 CTA 原地累加 `y = Σ_s y_part[s, :]`。
- **输入**：池化激活 `x_2`（形状 `[1, 4096]`，BF16，8,192 B，位于 L2/HBM）、路由索引 `topk_ids`（`[1, 8]`，`int32`，32 B，位于 L2/HBM），以及命中本地专家的 4 位权重 `W13`（每专家 18.9 MB，位于 HBM）与 `W2`（每专家 9.4 MB，位于 HBM）。
- **输出**：上投影融合尾声直接写出中间激活 `inter`（`[A, 4096]`，BF16，$A$ 为本卡命中的专家数，位于 L2）；下投影融合尾声直接写出各命中专家的输出 `y`（`[A, 4096]`，BF16，位于 L2）。
- **交给下一步**：`y` 交给专家后归一化与加权求和写出 `m [1, 4096]`（BF16），再进入阶段 7 的 `unpooler`。
- **本步代价与三元权衡**：
  - **得到什么（实测收益）**：在单请求解码（`decode 1`）上，上投影核内最后到达者归约省去 **1.12 µs**，删去 `M = 1` 的独立路由核省去 **1.42 µs**（5 个种子区间 `[-1.60, -1.28] µs`），下投影核内最后到达者归约再省 **0.86 µs**（三步均比特级等价，合计省去 **3.40 µs**）。
  - **付出什么（代价）**：主矩阵乘 CTA 需在尾声维护原子到达计数器并执行最后到达者求和，额外占用少量控制逻辑（具体寄存器与 SMEM 增幅未测）。
  - **用在哪里、收益多少（跨算子算子融合台账）**：除上述单核序言/尾声融合外，利用矩阵乘行线性性质把跨阶段的 `pre_expert_norm` 拆入前后两核尾声（第 9 章第 3 节）以及整层跨分支融合（第 9 章第 4 节）也是同一机制的延伸。

| 应用场景（阶段与算例标签） | 融合内容（删掉的启动或往返） | 实测收益（Gain） | 付出的硬件与复杂度代价（Cost） |
|---|---|---|---|
| **阶段 6 专家** · `decode 1`（`M = 1`，主例） | 上投影核内最后到达者归约 + 删独立路由核 + 下投影核内归约 | 依次省 **1.12 µs**、**1.42 µs**、**0.86 µs**（合计 **-3.40 µs**，比特等价） | 尾声增加原子计数器与最后到达者累加分支；寄存器/SMEM 变化未测 |

- **什么时候变成亏本（反例与失效边界）**：
  1. **反方向的拆分实验（把单核拆成双核带来的寄存器与耗时反噬）**：在预填充 `T = 3,012` 的阶段 6 专家路由中，曾尝试反过来把路由对齐拆成两个 kernel（先跑计数再跑独立的重排散射核），结果独立的散射 kernel 每线程占用了 **205 个寄存器**、单核耗时高达 **90 µs**，导致第 4 轮整层实测倒退 **-1.4%** 被否决。
  2. **把已被 PDL 重叠的小核强行并入大核串行尾声（见第 9 章第 4 节）**：当相邻小 kernel（如合并核、专家后归一化或层间边界核）的启动与读取已经被下节的 PDL 藏在前序大核的退场阴影下时，若强行把它融进前序大核尾声，反而会把并行重叠变成核内串行尾并锁死大核的高寄存器驻留，在解码/检验与预填充的 7 项尝试中全部实测变慢（慢 `1.2–8.3 µs` 至 `145–340 µs`）。

## 2. 用 PDL（编程依赖启动）让前序收尾与后继读静态权重重叠（含触发点过早反例）

**本节要回答的问题：** 当两个阶段并行维度不同无法合一时，如何让后继 kernel 在前序尾声期提前进场预取权重？

<!-- FIG ch01-pdl: 图 1-2 画 PDL 四步交接流程与时间线：第 1 步主机端声明编程依赖属性；第 2 步前序 CTA 算完主体后调用触发函数；第 3 步后继 CTA 趁前序收尾期从 HBM 预读静态权重 W；第 4 步后继在读取前序激活前调同步等待函数等前序写入落定（对比触发点放在函数开头导致后继空占 CTA 槽位慢近 2 µs 的反例）。 -->

如图 1-1 第三行与图 1-2 所示，每个 kernel 末尾都不是同时停下的：当大部分 CTA 已结束时，仍有少数 CTA 在收尾。因为收尾期大部分 SM 已经空出，且后继读取静态权重或做入口准备不依赖前序尚未写完的激活，**Hopper**（H200 架构代号 `sm_90a`）的 **PDL**（Programmatic Dependent Launch，编程依赖启动）允许后继在前序收尾时提前进场。解剖图 1-2 的四步握手与阶段 2（分页注意力 `prologue → attention → merge` 链）及阶段 2→3（`attention → o` 投影）的跨核交接：
- **公式**：前序阶段 2 计算分页注意力并由归约核合并输出 `y = rmsnorm(Σ_s exp2(lse_s - lse) · o_s) ⊙ sigmoid(gate)`；后继阶段 3 计算输出投影 `a = y · W_o^T`。
- **输入**：在阶段 2 内部，注意力核读入序言写出的 `q_fp8` 与分页 `K_cache, V_cache`，归约核读入各分片写出的部分和 `partial_o` 与对数分母 `lse`；在阶段 2→3 边界，后继 `o` 读入前序激活 `y`（即 `o_attn`，BF16 `[1, 1024]`，2,048 B，位于 L2/HBM）与静态权重 `W_o`（BF16 `[8192, 1024]`，16.8 MB，位于 HBM）。
- **输出**：阶段 2 归约核写出 `y [1, 1024]`（BF16）；阶段 3 写出 `a [1, 8192]`（BF16，16,384 B，写回 HBM）。
- **交给下一步**：PDL 用四条原语把相邻两核的收尾与启动重叠起来，最后把 `a` 交给门控残差 1：
  1. **声明编程依赖边**：主机端启动后继 kernel 时挂上属性 `cudaLaunchAttributeProgrammaticStreamSerialization`（传入 `W_o`、`y`、`a` 三个 8 B 指针）。
  2. **前序触发**：前序每个 CTA 在算完主体循环、进入收尾写出前调用 `cudaTriggerProgrammaticLaunchCompletion()`（PTX 为 `griddepcontrol.launch_dependents`，编译为机器指令 `PREEXIT`）。当所有前序 CTA 都已触发或退出时，硬件派发器即可启动后继 kernel。
  3. **后继预读静态权重与无关准备**：后继进场后先不读前序尚未写完的激活（如 `q_fp8`、`partial_o` 或 `y`），而是先把 `W_o` 的前几块静态权重从 HBM 预读进 L2 或片上共享内存（落点由后继代码自己决定，PDL 本身不规定）。
  4. **后继等待前序数据可见**：读取前序输出之前，后继调用 `cudaGridDependencySynchronize()`（PTX 为 `griddepcontrol.wait`，编译为 `ACQBULK`）阻塞等待；直到前序整个 `grid` 执行完毕且所有全局内存写入已刷新可见，后继才跨过等待点开始计算（单 CTA 入口等待的实测串行边为 **0.64 µs**）。
- **本步代价与三元权衡**：
  - **得到什么（实测收益）**：在图 1-2 中先选“无 PDL：等前序全部退出”，读数为：`无 PDL：后继在前序全部退出后才启动`；`对照：关 PDL 比开 PDL 慢 +0.93 µs（decode 1，全层）`（测自阶段 2 单请求 `decode 1` 全长注意力的 `attention → merge` 边界，正反序配对实测关掉 PDL 慢 **+0.93 / +0.88 µs**；在 `verify 1 full` 上开启 `prologue → attention → merge` PDL 链 4 次运行省 **0.45–0.90 µs**，全套 7 个带独立合并核的算例关掉 PDL 慢 **+0.64..+1.60 µs**）。再选“PDL：触发在主体循环之后”，读数为：`PDL，触发在主体循环之后：串行边 0.64 µs`；`权重预读藏在前序收尾里 · 这是保留的写法`。
  - **付出什么（代价）**：后继核必须在首次读取前序数据前插入 `ACQBULK` 同步等待点；在 CUDA Graph 双节点分解测量中（空图固定开销 `3.39 µs` 由评测框架扣除），第 1 个核节点固定开销为 **+1.87 µs**，第 2 个挂有 PDL 属性的核节点固定开销仍需 **+1.15 µs**（协作启动属性本身占 `0.00–0.09 µs`）。
  - **用在哪里、收益多少（跨场景 PDL 启动重叠台账）**：整层 11 个 kernel 的同流 PDL 串联、共驻掩码与借空闲 SM 抢跑将在第 9 章第 4 节展开。

| 应用场景（阶段与算例标签） | PDL 重叠边与触发位置 | 实测收益（Gain） | 付出的硬件与复杂度代价（Cost） |
|---|---|---|---|
| **阶段 2 注意力** · `verify 1 full` 及全部 7 个带合并核算例（主例） | `prologue → attention → merge` 全链挂 PDL，注意力核在首读 `q8/KV` 前执行 `gdc_wait` | `verify 1 full` 省 **0.45–0.90 µs**；7 个合并算例关 PDL 慢 **+0.64..+1.60 µs**（`decode 1 full` 慢 **+0.93 / +0.88 µs**） | 后继入口需加 `gdc_wait` 同步点；寄存器与 SMEM 无变化 |
| **阶段 2 注意力** · `decode 1/16/32 full` 对 `decode 32 sliding` | 在全长 `pw` 核最后一次 `wait_group(0)` 之后、写部分和之前后置触发，隐藏 `0.67–0.70 µs` 入口空隙 | `decode 1 full` 省 **0.32 / 0.22 µs**，`decode 16 full` 省 **0.26 / 0.16 µs**，`decode 32 full` 中性 | 合并核仍需在 `gdc_wait` 处等前序全网格写完；**参数翻转（滑窗关闭）**：同一触发点放进滑窗 `pw_slide` 在 `decode 32 sliding` 上反输被关掉 |
| **阶段 6 专家** · `decode 16/32`、`verify 1/16/32`（`M ≥ 8`） | `route → gemm1` 挂 PDL，且 `gemm1/gemm2` 在 `gdc_wait` 前提前预取静态权重与缩放系数 | `route → gemm1` 省 **0.63 µs**；等待前预取静态权重在各负载汇集再省 **1.66 µs** | 仅允许预取不依赖上游的静态权重 `W` 与缩放表；寄存器增幅未测 |
| **阶段 6 专家** · 全 6 个算例（`M = 1..256`，见第 8 章第 2 节） | 专家主核向后归一化核 `pn` 挂 PDL 重叠（`pn` 本身尾耗时 `1.94–3.31 µs`） | `M = 1/8/16/32/128/256` 分别省 **0.81 / 0.31 / 0.93 / 0.83 / 0.37 / 0.65 µs** | 双节点 CUDA Graph 中第 1 节点占 `+1.87 µs`、第 2 个 PDL 节点占 `+1.15 µs` |

- **什么时候变成亏本（反例与失效边界）**：
  1. **反例一（把触发点提前到函数或循环开头，后继过早进场空占 SM 槽位）**：触发调用只放行派发，并不代表前序数据已写完。在阶段 2 全长注意力测试中，把 `griddepcontrol.launch_dependents` 提前到 `K` 循环开头（函数入口），在全部 7 个合并算例上实测慢了 **+0.1..+1.95 µs**（`decode 1 full` 正反序配对慢 **+1.95 / +1.84 µs**）。因为过早进场的后继归约 CTA 在 `ACQBULK` 等待点上空停了 **9.86 µs**，白白占住 SM 槽位（见第 3 章）拖慢前序注意力主循环，并在最后一次触发后仍留下 `1.5–1.9 µs` 的入口间隙。选图 1-2 的“PDL：触发在函数开头（反例）”，读数为：`PDL，触发在函数开头：比 ② 慢 +1.95 µs（decode 1）`；`后继 CTA 停在等待函数上 9.86 µs，空占 SM 槽位`。
  2. **反例二（跨阶段激进移动 PDL 触发/等待位置引发负载间反向退化）**：在阶段 3–8 整层流水线中尝试另外 4 种更激进的 PDL 触发与等待位置组合时，虽然大批量 `verify 16/32 full` 微涨 `+0.2%..+0.5%`，但小批量 `decode 16 sliding` 却实测倒退约 **-1%**（超出同任务 A/A 噪声带，具体硬件争用原因未测），因此整包被否决。

## 3. 什么时候该合写成一个协作大核，什么时候该拆成两个 PDL 串联核？

**本节要回答的问题：** 把相邻两阶段强塞进带 `grid.sync()` 的单一持久大核一定更快吗？

<!-- FIG ch01-b: 图 1-3 上方画专家计算的两个相连矩阵乘阶段（移动块对应 P2 专家先算上投影 w13 写出中间激活、再算下投影 w2 读该激活的算法步）。下方对比合写单一大 kernel 与拆成两个 PDL 串联 kernel 的时间线。 -->

在第 0 章阶段 6 的路由专家计算里，上投影（阶段 A）与下投影（阶段 B）首尾相连，但两阶段之间存在全对全的数据依赖：因为 `W2` 的每一行都要读完中间激活 `inter` 的全部 4,096 列，而这 4,096 列由许多 CTA 在阶段 A 分别算出写出。解剖图 1-3 的两阶段数据流与交接代价：
- **公式**：阶段 A 计算上投影 `h = x_2 · W13^T` 并经门控激活 `inter = silu(h[:, :4096]) ⊙ h[:, 4096:]` 写出中间激活；阶段 B 计算下投影 `y = inter · W2^T`。
- **输入**：阶段 A 读入某专家分到的 `n` 个词元输入 `x_2`（BF16 `[n, 4096]`，位于 HBM/L2）与上投影权重 `W13`（`uint8 [8192, 2048]` 加块缩放 `FP8 [8192, 256]`，共 **18.9 MB**，位于 HBM）；阶段 B 读入 `inter`（BF16 `[n, 4096]`，位于 L2）与下投影权重 `W2`（`uint8 [4096, 2048]` 加块缩放 `FP8 [4096, 256]`，共 **9.4 MB**，位于 HBM）。
- **输出**：阶段 A 写出 `inter [n, 4096]`（BF16，经 L2 交接）；阶段 B 写出专家输出 `y [n, 4096]`（BF16）。
- **交给下一步**：`y` 交给每专家独立均方根归一化与路由权重加权求和，产出 `m [M, 4096]`（BF16）送往阶段 7 的 `unpooler`。
- **本步代价与三元权衡**：
  - 若用 **cooperative launch**（协作启动，`cudaLaunchCooperativeKernel`）把阶段 A 与阶段 B 合写进一个持久大 kernel（全卡 132 个 CTA），两步之间必须插一道 **grid barrier**（全网格同步栅栏）。协作启动要求所有 CTA 同时驻留在芯片上（超出同时驻留容量时驱动直接拒绝启动），因为若有 CTA 没上芯片，已驻留的 CTA 在栅栏处永远等不到它就会死锁。在图 1-3 中选“合写成一个协作大 kernel”，读数为：`合写成一个协作 kernel：全网格栅栏 1.42 µs`；`132 个 CTA 必须同时驻留 · 全卡等最慢的一区`。这道全网格栅栏在 132 个 CTA 下实测耗时 **1.42 µs**（`1,419.3 ns`；264 个 CTA 下为 `1,521.5 ns`），且全卡 132 个 SM 都必须干等最慢的一个阶段 A 区域跑完，才能开始读阶段 B 的权重。
  - **得到什么（拆成双核 PDL 串联的实测收益）**：把阶段 A 与阶段 B 拆成两个由 PDL 串联的 kernel（阶段 A 也通过 PDL 接在路由核后）后，串行交接边降至 **0.64 µs**；更重要的是，先算完阶段 A 的 CTA 一退场，阶段 B 的 CTA 就能立即填进该空出的 SM，在 `griddepcontrol.wait` 之前提前把 `W2` 的权重环形缓冲预读上片（栅栏省时与预读各自占多少比例属于推断，未单独拆分测量）。选“拆成两个 PDL 串联 kernel”，读数为：`拆成两个 PDL 串联 kernel：交接边 0.64 µs`；`先算完的 SM 立即预读 w2 · 实测净快 0.70 / 0.82 µs（decode 16 / 32）`。在 `decode 16`（`M = 16`）与 `decode 32`（`M = 32`）上，拆成两个 PDL 串联核比单一协作大核实测净快 **0.70 µs**（`[-0.80, -0.60] µs`）与 **0.82 µs**（`[-0.91, -0.73] µs`，160 次配对，比特级等价）。将同一相位拆分延伸到 `verify 1`（`M = 8`）后，实测再省 **0.37 µs**（`[-0.52, -0.22] µs`）。
  - **付出什么（代价）**：拆成两核后，增加 1 个 CUDA Graph 节点，且因为阶段 A 与阶段 B 每个 CTA 的共享内存占用均超过单 SM 上限的一半（两核合计 `2 × 264 KB > 228 KiB`），阶段 B 的 CTA 无法与阶段 A 同 SM 共驻，只能按 `blockIdx.x` 顺序随阶段 A 退场逐个进场（由此带来的高编号 CTA 晚启动斜坡将在第 2 章第 2 节解决）。

| 应用场景（阶段与算例标签） | 架构选择（拆核 PDL vs 协作大核） | 实测收益（Gain） | 付出的硬件与复杂度代价（Cost） |
|---|---|---|---|
| **阶段 6 专家** · `decode 16 / 32`（`M = 16 / 32`，主例，见第 8 章第 2 节） | 将阶段 A（`w13`）与阶段 B（`w2`）从全网格栅栏协作核拆为两个 PDL 串联核，阶段 B 在等待前预填 `W2` 环 | `decode 16` 省 **0.70 µs**，`decode 32` 省 **0.82 µs**（`verify 1` 初步省 `0.21 µs`，均比特等价） | 消去 `1.42 µs` 全网格栅栏；但两核无法同 SM 共驻，阶段 B 按 `blockIdx.x` 随阶段 A 退场顺序依次进场 |
| **阶段 6 专家** · `verify 1`（`M = 8`）对比 `decode 1`（`M = 1`，见第 8 章第 2 节） | 将相位拆分扩展至 `M = 8`（配编译器版本门控的权重环栅栏）；**参数翻转（`M = 1` 关闭拆分）**：`M = 1` 保持单核协作启动 | `verify 1`（`M = 8`）净省 **0.37 µs**；而 `decode 1`（`M = 1`）对照差为 `+0.03 µs`（无拆核收益） | 在单词 `M = 1` 下，阶段 A 结束跨度极小，保持单核协作启动（压至 144 寄存器）反而便于后续归一化共驻 |

- **什么时候变成亏本（反例与失效边界）**：
  1. **反例一（在已被 `done1 + PDL` 重叠的预填充专家上强搞单一持久 `gemm1 → gemm2` 大核）**：在预填充 `T > 1,024`（阶段 6 专家）中，线上版本已通过块完成标志 `done1` 与 PDL 把 `gemm1` 和 `gemm2` 的交接边界压到极窄。此时若强行将 `gemm1` 与 `gemm2` 合写进单个持久大核，不仅理论可省的边界上界硬封顶在总分的 **≤ 0.32%**（实际可兑现估算仅约 `0.1%–0.16%`），还会丧失 `gemm2` 依靠非持久大网格由硬件块调度器动态抹平各专家负载的能力（见第 8 章第 5 节），因此作为亏本方案在设计阶段直接否决。
  2. **反例二（跨整层不同形状阶段强塞进单一协作大核，见第 9 章第 4 节）**：把同一阶段内同构子任务留在持久核内是划算的（见第 8 章第 2–3 节），但若把整层多个不同矩阵形状、不同寄存器需求的阶段强塞进单一全层持久协作大核，全核驻留会被最高寄存器阶段锁死且每道边界都要付全网格栅栏代价，在解码与预填充整层实测中比按阶段拆开再用 PDL 串联慢了 **5–8 µs** 乃至 **1.05 ms**。

## 4. `qkv_gate` 双轨演化（第 0 级）：`gemv`（v1 → v2，Graph 重放）与 `qkv_gemm`（g0 → g1a，单核化消去独立归约核）

**本节要回答的问题：** 在第 0 级时间线上，如何同时砍掉 `T = 1` 的主机下发空隙与 `T = 8..128` 库函数的双核启动边界？

回到贯穿全书第一部分的阶段 1 `qkv_gate`（权重 `W [2304, 8192]` BF16，`37.75 MB`），把本章第 0 级的两项武器——**CUDA Graph 重放**与**单核化融合（消去独立归约核启动）**——分别落实到 `T = 1` 的 `gemv` 轨道与 `T = 8..256` 的 `qkv_gemm` 轨道上。

### 轨道一（`T = 1`）：`gemv v1 → v2`（把流启动链录进单张 CUDA Graph 重放）

为测量 `gemv_kernel`（**v1**，见第 0.5 章）在多层调用链中的启动开销，计时程序构造了三步链 `[nb_rmsnorm (1 CTA), gemv_kernel (2,304 CTAs), nb_post (9 CTAs)]`（入口归一化、矩阵乘向量与 9 个 CTA 的后处理）。若主机端从 Python 逐个流启动这三步，相邻 kernel 之间会暴露下发空隙。本章的 **v2**（不改 `gemv_kernel` 本身，单 kernel 冷缓存耗时仍为 `58.88 µs`）在预热期把三步链录进同一张 CUDA Graph 并实例化，运行时单次重放。

```cuda
// v1：主机端在 stream 上逐个下发 [nb_rmsnorm, gemv_kernel, nb_post] 三步 kernel
gemv_kernel<<<2304, 128, 0, stream>>>(W, x, y, K);
// v2：预热期录制三步链并实例化为 graph_exec，运行时单次提交整张图
cudaGraphLaunch(graph_exec, stream);
```

在热缓存（不清空缓存，37.7 MB 的 `W` 留在片上缓存里）且由 Python 按步下发时，单个 kernel 跑得比 CPU 下发准备更快，导致 `stream` 队列排空。改用单张 CUDA Graph 重放后，H200 实测三步链耗时从逐个流启动的 `73.02 µs` 降至 **36.19 µs**，省去 **36.8 µs** 的队列排空等待。而在冷缓存且流队列预先排满时，CPU 下发已被队列掩盖，整图重放仍从流启动的 `67.23 µs`（热缓存预排满为 `37.89 µs`）降至 **65.15 µs**（2 个节点边界共省约 `2.1 µs`，平均每道边界比预先排满的流启动省约 `1 µs`）。

### 轨道二（`T = 8..256`）：`qkv_gemm g0 → g1a`（消除 cuBLAS 独立 `splitKreduce` 第二次启动，附 `T = 256` 退化权衡）

当词元数升至 `T = 8 | 32 | 128 | 256` 时，第 0.5 章的基线 **g0** 调用 `torch.matmul(X, W.t(), out=Y)`（底层为 cuBLASLt `nvjet`）。在 `T = 8, 32, 128` 下，因为输出行数 `T` 很小，cuBLAS 为了利用更多 SM 会沿内积维 `K = 8,192` 切分（Split-K），每次矩阵乘在 `stream` 上连续启动**两个独立 kernel**：先跑 `nvjet` 主核写出部分和，再启动 `splitKreduce_kernel` 归约核把部分和加起来写回 `Y`（唯有 `T = 256` 不切 K、只跑 1 个 kernel）。在统一的单图重放评测口径下（每次迭代前读取 512 MiB 干净清空 L2，500 次迭代中位数，含空图重放固定底座 `4.96 µs`），**g0** 在 `T = 8 | 32 | 128 | 256` 四格的实测耗时为 **`18.20 | 18.60 | 21.32 | 22.90 µs`**。

本章第 0 级的 **g1a** 将每次矩阵乘合为**单次 kernel 启动**：删掉独立的 `splitKreduce_kernel`，改由主核内最后到达的 Split-K CTA 原地完成部分和归约（第 1 节的尾声归约融合）。H200 实测 `g0 → g1a` 双轨对照如下：

| 演化步 | 关键改动（第 0 级机制） | `T = 8` (µs / GB/s) | `T = 32` (µs / GB/s) | `T = 128` (µs / GB/s) | `T = 256` (µs / GB/s) | 本步权衡（Gain vs Cost / When it loses） |
|---|---|---|---|---|---|---|
| **g0** | `cuBLAS` 基线（`T = 8..128` 调 `nvjet + splitKreduce` 双核；`T = 256` 单核） | `18.20` / `2,074` | `18.60` / `2,030` | `21.32` / `1,771` | `22.90` / `1,649` | 小中批量每次矩阵乘付 2 次启动与 1 道图节点切换边 |
| **g1a** | 单核化：删掉独立 `splitKreduce` 启动，由最后到达 CTA 核内归约 | **`15.81`** / `2,388` (`-2.39 µs`) | **`17.92`** / `2,107` (`-0.68 µs`) | `21.57` / `1,750` (`+0.25 µs`) | `33.39` / `1,130` (**`+10.50 µs`**) | **小 `T` 赢、大 `T` 输**：`T = 8 / 32` 省掉第 2 次启动净快 **2.39 / 0.68 µs**；但 `T = 128` 持平（`+0.25 µs`），`T = 256` 反而比单核 cuBLAS **慢 10.50 µs（+46%）** |

为什么 `g1a` 砍掉了第二次 kernel 启动，在 `T = 8 / 32` 上立竿见影省下 **2.39 / 0.68 µs**，到了 `T = 128` 却被追平、在 `T = 256` 更暴跌 **+10.50 µs**？因为第 0 级只管“启动几个 kernel”，却没管 kernel 内部在整张芯片 132 个 SM 上怎么排布：`g1a` 在 `T = 128 / 256` 下只启动了 72 个 CTA（让全卡 132 个 SM 中的 60 个完全闲置），而且让最后到达的那 1 个 CTA 串行读回并累加多达 `1 MB` 的部分和！这正把我们推向下一章的第 1 级（整张芯片）。

---

**带走一句话：** 第 0 级的算子融合与 CUDA Graph 重放消除了 CPU 排空（`v2` 省 `36.8 µs`、每道图边界再省 `~1 µs`）并把单请求 decode 的单层启动从约 17 次压到 11 次（阶段 6 `M = 1` 三步融合省 `3.40 µs`），PDL 与双核拆分用 `0.64 µs` 交接边取代 `1.42 µs` 全网格栅栏并藏起权重预读（省 `0.64–1.66 µs` 与 `0.70–0.82 µs`），而 `qkv_gemm g0 → g1a` 单核化虽在 `T = 8 / 32` 省下 `2.39 / 0.68 µs`，却在 `T = 256` 因 72-CTA 空闲 SM 与单 CTA 串行归约倒输 `10.50 µs`。

**下一章要回答的问题：** 点开时间线上的 1 个 kernel，如何让 132 个 SM 同时干完活、挂起足够的在途字节喂饱 4.8 TB/s HBM，并在中央 L2 上并行合并跨 SM 的 Split-K 部分和（把 `g1a` 在 `T = 128 / 256` 丢掉的时间夺回来）？→ 进入 第 2 章 [第 1 级]：整张 H200 芯片——132 个 SM 怎样铺平波次、喂饱 HBM 并在中央 L2 归约？
