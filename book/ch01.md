图 I-1 画出了第一部分的六级放大路径，从最外层的时间线一路拆到最底层的指令与比特。这一章我们先站在最外面的第 1 级：时间线。

要看清时间线上发生了什么，我们把导引三的 `gemv_kernel` 放回它在单层里的位置：前面接一个归一化 kernel，后面接一个后处理 kernel，凑成一条三 kernel 链。这一章从头到尾只看这一个例子：

1. **归一化 kernel**：读入 $\shape{x}{8192}{BF16}$，写出 $\shape{x_n}{8192}{BF16}$，计算 $x_n = x \cdot r$，其中 $r = 1/\sqrt{\tfrac{1}{K}\sum_k x_k^2 + \epsilon}$（RMSNorm 定义见导引一第 1 节，这里不乘权重向量）。这一步只启动 1 个 CTA、1,024 个线程（单个 CTA 的线程数上限就是 1,024）。
2. **`gemv_kernel`（`v1`）**：用权重 $\shape{W}{2304,\ 8192}{BF16}$ 计算 $y = W x_n$，写出 $\shape{y}{2304}{FP32}$，共启动 2,304 个 CTA，每个 CTA 128 个线程。
3. **后处理 kernel**：对 $\shape{y}{2304}{FP32}$ 做逐元素运算（用来代表真实的按头归一化与旋转位置编码，见导引二第 2 节），每个 CTA 256 个线程，共启动 $\lceil 2304/256 \rceil = 9$ 个 CTA。

这三步只用到我们在导引三里见过的四样东西：线程块（CTA）、线程、CUDA 流和全局内存。

## 1. GPU 为什么会在两个 kernel 之间停下来？

**两个 kernel 之间的空隙来自两处：一是 CPU 下发命令比 GPU 跑得慢，队列空了，GPU 只好干等 CPU；二是就算队列里有现成的命令，后一个 kernel 也必须等前一个的全部 CTA 退出。** 我们把前一种叫作 **CPU 下发空隙**，把后一种叫作**硬件交接空隙**。

先算第一种空隙的账。启动语句只是把命令放进 CUDA 流就立刻返回（见导引三），所以 CPU 是生产者，GPU 是消费者，CUDA 流就是夹在它们中间的队列。假设每个 kernel 在 GPU 上跑 $t_{gpu}$，而 CPU 每下发一条启动命令要花 $t_{cpu}$。一旦 $t_{cpu} > t_{gpu}$，GPU 跑完当前 kernel 时，下一条命令还没送进队列。队列一空，相邻两个 kernel 的开始间隔就被拉长到了 $t_{cpu}$，GPU 每次都得空等约 $t_{cpu} - t_{gpu}$。反过来，只要 $t_{cpu} \le t_{gpu}$，CPU 就一直跑在 GPU 前面，队列里总有现成的命令，这段等 CPU 的空隙也就消失了。

小 kernel 的 $t_{gpu}$ 只有几微秒，所以这种空隙对小 kernel 最伤。在我们这条三 kernel 链里，1 个 CTA 的归一化和 9 个 CTA 的后处理都是这样的小 kernel。我们的测试脚本从 Python 依次发起这三次启动，图 1-1 的前两行对比了两种下发方式：第一行“CPU 逐个下发”在计时开始时队列是空的，Python 一条一条往里发三次启动；第二行“命令预先排满”则在计时开始前先放一个让 GPU 忙一小会儿的 kernel，CPU 趁这段时间把三条启动命令提前全排进队列。

实测下来，CPU 逐个下发比命令预先排满慢了约 **41 µs**（图表见第 5 节）。按刚才的队列规则，这 41 µs 落在两处：第一次下发（计时开始时队列是空的）和 ①→② 这道边界（因为 ① 只跑几微秒）。等到 ② 在 GPU 上跑那约 50 µs 时（单独计时的 54 µs 里含约 4.6 µs 固定开销），CPU 趁机早就把 ③ 排进了队列，所以 ②→③ 这道边界不用再等 CPU。至于 $t_{cpu}$ 本身有多大、这 41 µs 在两处各占多少，我们没有单独测。

再看图 1-1 第二行的“命令预先排满”。哪怕三条命令早就排在队列里了，相邻两个条块之间依然留着一道缝。这第二种空隙跟 CPU 一点关系都没有：同一条 CUDA 流的顺序保证（先行发生，见导引三第 2 节），靠的就是“前一个 kernel 完全结束、写入全部可见之后，后一个才能开始”。所以每跨一道 kernel 边界，都得走完“前一个 kernel 的最后一个 CTA 退出 → 写入全部可见 → 片上的硬件派发器把下一个 kernel 的 CTA 分派到 SM 上”这一整套交接流程（派发见导引三第 1 节）。在前一个 kernel 最后几个 CTA 还在收尾时，先跑完退出的 SM 已经闲下来了；等最后一个 CTA 退出，直到下一个 kernel 派上 SM 之前，整张卡的 SM 全都空着。

## 2. CUDA graph 去掉哪一种空隙，留下哪一种？

**CUDA graph 把整条链预先录好、一次提交，一口气去掉了 CPU 下发空隙；但节点之间的硬件交接空隙还在。**

**CUDA graph**（计算图）就是把一串 GPU 命令和它们的依赖关系预先录好，图里的每个 kernel 叫作一个**节点**。用起来分两步。第一步是录制与**实例化**：我们在正式计时前的预热阶段，把三 kernel 链的启动依次录进一张图；实例化时，驱动（CPU 上管理 GPU 的软件）会检查整张图，把大部分启动准备工作提前做完。第二步是重放：到了运行时，CPU 只调一次 `cudaGraphLaunch`（代码见第 5 节）把整张图交出去，后面每次重放都不用再做那套准备。这样一来，CPU 的下发时间 $t_{cpu}$ 整条链只付一次，不用每个 kernel 各付一次，第 1 节的第一种空隙也就消失了（图 1-1 第 3 行）。

不过，图里的每个节点依然是一个独立的 kernel，相邻节点之间照样得遵守同一条 CUDA 流的顺序规则：后一个节点必须等前一个节点的全部 CTA 退出、写入全部可见之后才能开始。所以第二种空隙依然留在图里。在这条三 kernel 链上，每一道交接具体花多久我们没有单独测。给你两个参照数：在真实推理计算图的重放标定里，每个节点的启动开销中位数约为 **1.0 µs**。在另一个只往图里塞空 kernel 的测试里，每多加一个空 kernel，整图耗时就增加 0.37–1.19 µs。

把它和第 1 节的“命令预先排满”放在一起比：预先排满虽然也能藏住 CPU 下发时间，但前提是 CPU 必须一直跑在 GPU 前面；整图重放则完全不靠 CPU 赶进度。在这条三 kernel 链上，整图重放比命令预先排满还要略快一点（实测见第 5 节）。

用 CUDA graph 的账可以这样算：

- **得到什么**：一口气消掉了 CPU 下发空隙（三 kernel 链上的实测收益见第 5 节）。
- **付出什么**：预热时要多做一次录制和实例化。而且一旦实例化完成，图里每个 kernel 的参数、启动形状和显存地址就固定死了。要想改动它们，你必须调图更新接口（比如 `cudaGraphExecUpdate` 或 `cudaGraphExecKernelNodeSetParams`），或者干脆重新录图。如果输入词元数 $T$ 会变，常见做法是按不同的 $T$ 分别录几张图（或者把输入补齐到已经录过的 $T$）。
- **什么时候亏本**：在这条三 kernel 链上，整图重放比两种普通流启动都快；至于多录几张图、补齐输入形状要多花多少开销，以及在别的场景下会不会亏本，我们没有测。

## 3. 把两个 kernel 合成一个，省下什么、付出什么？

**把两个 kernel 合成一个，能省掉一道边界、一次启动和一次全局内存往返；代价是主 kernel 要多算一步，而且前提是后一步不用让所有 CTA 停下来互等。**

把相邻两个 kernel 的活写进同一个 kernel，让中间结果直接留在寄存器或片上存储里、不再去全局内存绕一圈，就叫 **kernel fusion**（融合）。每多拆出一个独立 kernel，你不仅要多付一道第 2 节的硬件交接，还得把中间结果先写回全局内存，再让下一个 kernel 重新读回来。在同一台 H200 上，我们统一按“命令预先排满”的普通流启动方式，分别量了三个 kernel 各自单跑与整条链串联的耗时（见下图）：整条链（61.63 µs）只比 `gemv_kernel` 单跑（54.18 µs）多出约 **7.5 µs**。

况且这约 7.5 µs 里还包含归一化和后处理本身的算术开销。把几个 kernel 合写到一处并不会凭空省掉这些运算——该算的一步也少不了——因此约 7.5 µs 只是融合最多能省下的上界。

那具体怎么合？我们先给一个位置起个名字：在 kernel 主循环跑完之后、把最终结果写出去之前的那段逐元素计算，叫作**尾声**（epilogue）。

把后处理塞进尾声非常直接：在 `gemv_kernel` 里，每个 CTA 的 0 号线程做完块内归约、算出这一行的内积之后，结果本来就已经在它的寄存器里了。既然逐元素后处理根本不需要看别的 CTA 的结果，0 号线程在写回 `y[row]` 之前顺手把它算完就行。

把归一化并进来则要多转一个弯。$x_n = x \cdot r$ 里的缩放因子 $r = 1/\sqrt{\tfrac{1}{K}\sum_k x_k^2 + \epsilon}$ 要用整条 $x$ 的平方和，乍一看，好像非得先把整条 $x$ 读完算出 $r$，才能开始算矩阵乘。但你回头看一眼导引三里的 `v1` 循环：每一个 CTA 为了算自己那一行的内积，本来就要把整条 $x$（8,192 个元素）从头到尾读一遍。既然每个 CTA 都已经把 $x$ 读全了，它完全可以在同一个循环里顺手多累加一个平方和 $\sum_k x_k^2$，到尾声做完块内归约后算出 $r$，最后直接乘到内积上写出 $y[\text{row}] = r \cdot \sum_k W[\text{row}, k]\,x_k$。道理很简单：

$$y = W(x \cdot r) = r\,(Wx)$$

在不乘归一化权重向量时，这两个式子在代数上完全相等；就算要乘权重向量，式子也只是变成 $r\,W(w_{\text{norm}} \odot x)$，用到的依然只是当前 CTA 自己读进来的数据。数值上只有两处差别：一是省掉了把 $x_n$ 写回全局内存时的一次 BF16 舍入（把 32 位浮点数存成 16 位时取最接近的 16 位值，见第 6 章第 1 节），二是乘加的舍入顺序变了。

记住，融合省掉的只是 kernel 边界和全局内存往返，被你合进来的那部分计算本身并不会消失。我们在一个更快的 `gemv` kernel 上实测过：把阶段 2 开头的按头归一化和写 FP8 的 Q、KV 缓存（见导引二第 2 节）并进阶段 1 的尾声之后，kernel 自己还是要多跑约 **1.1 µs**（见下图）。在那个 kernel 里，每个 CTA 依然算 1 行。Q 和 K 的每个头占 64 个 CTA，各自算完写出后给这个头的计数器加 1，最后到达的那个 CTA 负责做按头归一化并写出 FP8，其余 CTA 直接退出（计数器的写法见第 2 章第 6 节）。V 的 CTA 则各自直接写 FP8 V 缓存，不用计数器。至于多出来的这 1.1 µs 在各步之间怎么分摊，我们没有拆开测。

到底能不能合，归根结底只看一件事：后一步要用的数据，能不能在不让全卡所有 CTA 停下来互等的前提下拿到？能合的无非两种情况：要么数据本来就在同一个 CTA 手里；要么多个 CTA 的结果只需要汇到一处，交给最后写完的那个 CTA 收尾就行（见第 2 章第 6 节）。开头的归一化之所以能合，正是因为每个 CTA 本来就要读完整条 $x$（这 16 KiB 数据按容量推断会留在片上缓存里，见第 2 章第 2 节；命中率我们没有测）。把融合的账算清楚：

- **得到什么**：省掉 2 道硬件交接和 2 次启动，中间结果 $x_n$（16 KiB，在 $T = 1$ 时很小）也不用先写回全局内存再读回来。
- **付出什么**：主 kernel 在循环或尾声里要多算一步，代码更复杂；而且 2,304 个 CTA 每个都把同一个 $r$ 重复算了一遍（每个 CTA 多做 8,192 次乘加和一次块内归约）。
- **什么时候亏本**：
  - 如果后一步的每个 CTA 都得读前一步许多 CTA 算出来的结果，硬合成一个 kernel 就逼着全卡所有 CTA 在半路停下来做全卡同步，干等最慢的那个 CTA 写完。全卡同步还要求所有 CTA 必须同时驻留在芯片上，否则就会直接挂死（见第 2 章第 6 节）。遇到这种情况，老老实实拆成两个 kernel 往往更好——下一节我们就来看怎么让这两个独立 kernel 在时间上部分重叠。
  - 就算是上面第二种能合的情况（交给最后写完的 CTA 收尾），也有亏本的时候：如果被合进来的是一个本来能用下一节的办法提前进场的小 kernel，合进来反而逼着它排在前一个 kernel 最后一个 CTA 后面跑，丢掉了提前重叠的机会，实测反而更慢（见第 9 章第 6 节）。

## 4. 后一个 kernel 能不能在前一个结束之前就开始？

**能。PDL 让后一个 kernel 提前派上 SM 去读权重，等前一个 kernel 的写入全部可见之后，再去读它的输出。**

我们在导引二第 3 节算过，静态权重根本不依赖前一步算出来的激活，完全可以提前去读。再看我们这条三 kernel 链：归一化 kernel 只有 1 个 CTA，它在跑的时候只占 1 个 SM，其余 131 个 SM 全都空着。可在普通 CUDA 流里，硬件偏偏把“后一个 kernel（下称**后继**）开始派发”和“前一个 kernel（下称**前驱**）完全退出”死死绑在了一起。**Hopper**（H200 的架构）提供的 **PDL**（Programmatic Dependent Launch，编程依赖启动）就是用来把这两件事拆开的，用法分四步（图 1-3）：

1. CPU 启动后继 kernel 时多带一个启动参数，告诉 GPU：后继可以在前驱结束之前提前派发。
2. 前驱的每个 CTA 在跑完主循环之后、写回结果之前发出一条**触发调用**；一旦所有前驱 CTA 都发出了触发（或已经退出），硬件就**可以**把后继的 CTA 派到有空闲资源的 SM 上（规范允许提前派发，但不保证一定提前派发）。
3. 后继 CTA 派上 SM 之后，先干不依赖前驱输出的活——放在“归一化 → gemv”这道边界上，就是先向 HBM 发出第一批权重 $W$ 的读取。因为在等待调用返回之前读回来的字节必须先暂存在片上，等 $x_n$ 准备好再用（单层里具体怎么提前读，见第 9 章第 4 节），所以能提前读多少受片上空间限制。
4. 后继在真正去读前驱输出之前，发出一道**等待调用**；等这道调用返回时，前驱整个 grid 已经全部跑完，它写进全局内存的所有数据也对后继全部可见。

```cuda
// 前驱：发出触发（位置见下文）
cudaTriggerProgrammaticLaunchCompletion();
// 后继：CPU 用带 PDL 启动参数的启动接口下发后继；后继先发出不依赖前驱的读取，再等待
cudaGridDependencySynchronize();   // 返回后才能读前驱的输出
```

这里有一条铁律：**在本章的写法里，读前驱输出的代码必须放在等待调用之后**；在等待调用返回之前，后继也不能往前驱可能仍在读取的缓冲区里写数据（本章的三步链里不会碰到这一点，具体例子见第 9 章第 5 节）。至于前驱里的触发调用放在哪儿，只决定后继能多早派上 SM，不影响可见性。

顺着时间线算账，PDL 顶多能省下两块时间：一是后继的不依赖读取同“前驱收尾加交接空隙”（即等待写入可见返回之前这一整段）相重叠的部分，长度取决于两者中较短的一方；二是交接空隙本身可能缩短的部分。我们专门写了一个只测这一步的小测试程序（下面统称**微基准**）：在 1 个 CTA 的测试配置下用 PDL 串联前后两个 kernel，并让后继一启动就调等待，量出单次交接约为 **0.64 µs**。由于它与第 2 节的 1.0 µs 出自两套不同的测试，两个数字不能直接相减。

那前驱里的触发调用该放在什么位置？要是摆在函数一开头，前驱的主循环还没跑完，后继的 CTA 就可能提前进场。在第 7 章第 11 节“注意力 → 合并”链的实测中，在函数开头触发比在主循环之后触发让前驱注意力 kernel 慢了 0.07–1.65 µs——推测是因为提前分派到同一个 SM 上的后继 CTA 停在等待调用上，与仍在跑主循环的前驱 CTA 争用同 SM 资源（这一具体机理未核实）。至于像本章这样只有 1 个 CTA 的前驱（它所在的那个 SM 上同样留有空闲资源，后继 CTA 也可以同驻上来），函数开头触发与主循环后触发的差别我们没有测。

好在提早触发最多只是拖慢速度，绝不会死锁：因为硬件要等前驱的每一个 CTA 都已经触发（或退出）之后，才会开始派发后继。到那个时刻，前驱已经没有任何一个 CTA 还在排队等 SM 了，没退出的 CTA 全都在 SM 上跑着，后继根本挡不住它们。所以本章（上文第 2 步）和第 7 章都把触发调用放在前驱主循环结束之后、收尾写回之前。

把 PDL 的账算清楚：

- **得到什么**：让后继不依赖前驱输出的读取（比如提前读静态权重）同前驱的收尾及交接空隙相重叠（在这条 `gemv` 链上开启 PDL 后的耗时变化没有测）。
- **付出什么**：在本章的写法里，后继必须在第一次读前驱数据之前插入等待调用；一旦不小心把读取写在了等待调用前面，就可能偶发读到上一次重放留下的旧值，而且运行时不会报任何错（这类错误的实测复现见第 9 章第 5 节）。
- **什么时候亏本**：前驱主循环尚未跑完就在函数开头过早触发——在注意力接合并链的实测中，这反而让前驱慢了 0.07–1.65 µs（推测因同驻一个 SM 争用资源，机理未核实；见上文与第 7 章第 11 节）。

## 5. `gemv` 演化 `v1 → v2`：把三 kernel 链录进一张 CUDA graph

**同样先把命令排进流里再计时，整图重放（60.0 µs）比普通流启动（61.6 µs）快约 1.6 µs；同 CPU 从空队列逐个下发（102.6 µs）相比，两步合起来共省下约 42.6 µs（快约 1.7 倍，其中约 41 µs 来自预先排满省掉的 CPU 等待），而单个 kernel 自身的耗时不变。**

这一步我们只改启动方式，GPU 上跑的三个 kernel 机器码和 `v1` 逐字节完全相同：

```cuda
// v1：CPU 逐个把 [归一化, gemv_kernel, 后处理] 放进 CUDA 流
gemv_kernel<<<2304, 128, 0, stream>>>(W, xn, y, K);
// v2：预热时在 stream 上录制这三步并实例化成 graph_exec，运行时一次提交
cudaGraphLaunch(graph_exec, stream);
```
