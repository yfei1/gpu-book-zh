图 I-1 画出第一部分的六级，从时间线一级级放大到指令与比特；本章在最外面的第 1 级：时间线。

我们把导引三的 `gemv_kernel` 放回它在一层里的位置，在前面接一个归一化 kernel，在后面接一个后处理 kernel，组成一条三 kernel 链。本章从头到尾只用这一个例子：

1. **归一化 kernel**：输入 $\shape{x}{8192}{BF16}$，输出 $\shape{x_n}{8192}{BF16}$，计算 $x_n = x \cdot r$，其中 $r = 1/\sqrt{\tfrac{1}{K}\sum_k x_k^2 + \epsilon}$（RMSNorm 定义见导引一第 1 节，此处不乘权重向量）。这一步启动 1 个 CTA、1,024 个线程。
2. **`gemv_kernel`（v1）**：计算 $y = W x_n$，权重 $\shape{W}{2304,\ 8192}{BF16}$，输出 $\shape{y}{2304}{FP32}$，启动 2,304 个 CTA、每 CTA 128 个线程。
3. **后处理 kernel**：对 $\shape{y}{2304}{FP32}$ 做逐元素运算（代替真实的按头归一化与旋转位置编码，见导引二第 2 节），每 CTA 256 个线程，共启动 $\lceil 2304/256 \rceil = 9$ 个 CTA。

这三步只用到导引三讲过的 CTA、线程、CUDA 流和全局内存。

## 1. GPU 为什么会在两个 kernel 之间停下来？

**有两种空隙：CPU 下发比 GPU 慢时队列被取空，GPU 等 CPU；队列有命令时，后一个仍要等前一个全部 CTA 退出。** 本书把前者叫作 **CPU 下发空隙**，把后者叫作**硬件交接空隙**。

<!-- FIG ch01-a: 图 1-1 同一条时间轴（µs）上的三 kernel 链三行对比：第 1 行“CPU 逐个下发”（上方 CPU 时间线，下方 GPU 时间线，红圈标出 ① 前和 ①→② 处等待 CPU 的空白，② 跑约 54 µs 期间 CPU 已排入 ③ 故 ②→③ 不等 CPU）；第 2 行“命令预先排满”（条块之间只剩硬件交接空隙）；第 3 行“整图重放”（CPU 只提交一次，GPU 条块之间只剩硬件交接空隙，每道约 1.0 µs，量自另一张真实计算图）。三个条块统一编号配色：①归一化 ②gemv ③后处理。读数：链总时间 102.6 / 61.6 / 60.0 µs，CPU 下发空隙约 41 µs（两处合计）。步骤卡：第 1 步 CPU 下发①（公式：无；输入：启动命令；代价：$t_{cpu}$）；第 2 步 ①运行（公式：$x_n = x\cdot r$；输入：$\shape{x}{8192}{BF16}$ 16 KiB 在 HBM；输出：$\shape{x_n}{8192}{BF16}$ 16 KiB 写回全局内存，交给②）；第 3 步 交接（①的 CTA 全部退出 → ②的 CTA 派上 SM）；第 4 步 ②运行（公式：$y = W x_n$；输入：$\shape{W}{2304,\ 8192}{BF16}$ 37.75 MB 在 HBM、$\shape{x_n}{8192}{BF16}$ 16 KiB；输出：$\shape{y}{2304}{FP32}$ 9,216 B，交给③）；第 5 步 交接；第 6 步 ③运行（公式：对 $y$ 逐元素运算；输出：$\shape{y}{2304}{FP32}$ 9,216 B）。总代价：三行的链总时间分别为 102.6 / 61.6 / 60.0 µs。 -->

先看第一种空隙。启动语句只把命令放进 CUDA 流就返回（见导引三），所以 CPU 是生产者，GPU 是消费者，CUDA 流是两者之间的队列。设每个 kernel 在 GPU 上跑的时间为 $t_{gpu}$，CPU 每次下发一条启动命令需要 $t_{cpu}$。当 $t_{cpu} > t_{gpu}$ 时，GPU 跑完上一个 kernel 时下一条命令还没送进队列，队列被取空，相邻两个 kernel 的开始间隔就变成 $t_{cpu}$，GPU 每次都要空等约 $t_{cpu} - t_{gpu}$。反过来，当 $t_{cpu} \le t_{gpu}$ 时，CPU 走在前面，队列里一直有命令，这段空等就会消失。

小 kernel 的 $t_{gpu}$ 只有几微秒，所以第一种空隙对小 kernel 最伤。章首的三 kernel 链里，1 个 CTA 的归一化和 9 个 CTA 的后处理都是这种小 kernel。本书的测量程序用 Python 依次发起这三次启动。图 1-1 前两行对比两种测法。“CPU 逐个下发”是计时开始时队列为空，CPU 从 Python 一条一条发出三次启动。“命令预先排满”是计时开始前先放一个让 GPU 忙一小段时间的 kernel，CPU 趁这段时间把三条启动命令全部排进队列。

实测下来，CPU 逐个下发比命令预先排满慢了约 **41 µs**（图表见第 5 节）。按队列规则，这 41 µs 落在第一次下发（计时开始时队列是空的）和 ①→② 这道边界（① 只跑几微秒）两处；② 跑约 54 µs，CPU 已经趁这段时间把 ③ 排进队列，②→③ 这道边界不再等 CPU。$t_{cpu}$ 本身多大、41 µs 在两处各占多少、改用 C++ 启动能省多少，都没有测。

再看图 1-1 第二行的“命令预先排满”。即使三条命令早就排在队列里，相邻两个条块之间依然留着一道缝。这第二种空隙与 CPU 无关：同一条 CUDA 流的顺序保证（先行发生，见导引三第 2 节）是靠“前一个 kernel 完全结束、写入全部可见，后一个才开始”实现的。因此每过一道 kernel 边界，都要走完“前一个 kernel 的最后一个 CTA 退出 → 写入可见 → 下一个 kernel 的 CTA 派上 132 个 SM”的交接过程（派发见导引三第 1 节）。前一个 kernel 的最后几个 CTA 还在跑时，先退出的 SM 已经空着；最后一个退出后，到下一个 kernel 派上 SM 之前，全部 SM 都空着。

## 2. CUDA graph 去掉哪一种空隙，留下哪一种？

**CUDA graph 把整条链预先录好、一次提交，去掉了 CPU 下发空隙；但节点间约 1.0 µs 的硬件交接空隙还在。**

**CUDA graph**（计算图）是预先录好的一串 GPU 命令及其依赖，图里的每个 kernel 叫一个**节点**。做法分两步。第一步是录制与**实例化**：在正式计时前的预热阶段把三 kernel 链的启动依次录进一张图；实例化时驱动（CPU 上管理 GPU 的软件）检查这张图，把每次启动要做的准备提前做完。第二步是重放：到了运行时 CPU 只调用一次 `cudaGraphLaunch`（代码见第 5 节）提交整张图，之后每次启动不用重新准备。这样 CPU 的下发时间 $t_{cpu}$ 整条链只付一次，不再每个 kernel 付一次，第 1 节的第一种空隙就消失了（图 1-1 第 3 行）。

但图里的每个节点依然是一个独立的 kernel，相邻节点之间仍要遵守同一条 CUDA 流的顺序规则：后一个节点必须等前一个节点的全部 CTA 退出、写入全部可见后才能开始。因此第二种空隙还留在图里。整图重放时，相邻两个节点之间的硬件交接空隙中位数约 **1.0 µs**（在一张真实推理计算图的 93 个节点边界上标定的值取中位数；不是本章这条链的测量）。

拿它和第 1 节的“命令预先排满”对比：预先排满虽然也能藏住 CPU 时间，但前提是 CPU 必须一直走在 GPU 前面；整图重放则不依赖这一点。在三 kernel 链上，整图重放比命令预先排满还略快一点，实测见第 5 节。

CUDA graph 的取舍：

- **得到什么**：消除了 CPU 下发空隙（三 kernel 链上的实测收益见第 5 节）。
- **付出什么**：预热时要多做一次录制和实例化；而且图里每个 kernel 的参数、张量形状和显存地址都是写死的，若输入词元数 $T$ 会变，就要按不同的 $T$ 分别录图（或把输入补齐到录过的 $T$）。
- **什么时候亏本**：在这条三 kernel 链上，整图重放比两种流启动都快；多录几张图与补齐形状的额外代价、以及其他场景下是否会亏本，没有测。

## 3. 把两个 kernel 合成一个，省下什么、付出什么？

**融合去掉一道边界、一次启动和一次全局内存往返；代价是主 kernel 多算一步，且要求后一步不需要所有 CTA 停下来互相等待。**

把相邻两个 kernel 的工作写进同一个 kernel、让中间结果留在寄存器或片上而不经全局内存交接，叫作 **kernel fusion**（融合）。每多一个独立 kernel，除了多一道第 2 节的交接之外，中间结果还要先写回全局内存、再由下一个 kernel 读回来。在同一台 H200 上用同一测法分别测三个 kernel 单独运行和整条链（整图重放），整条链比 `gemv_kernel` 单独运行只长了约 **5.8 µs**。

这 5.8 µs 是两个整体测量的差，里面还包括归一化和后处理自己的计算，融合后这些计算照样要做，所以 5.8 µs 只是融合能省下的上界。

具体怎么合？先把 kernel 主循环之后、写出结果之前的逐元素计算叫作**尾声**（epilogue）。

后处理并进尾声很直接：`gemv_kernel` 每个 CTA 的 0 号线程在块内归约算出这一行的内积之后、写回 `y[row]` 之前，数据本来就在它的寄存器里，而且逐元素后处理不需要别的 CTA 的结果，顺手算完再写出去就行。

归一化并进开头要多想一步。$x_n = x \cdot r$ 里的缩放因子 $r = 1/\sqrt{\tfrac{1}{K}\sum_k x_k^2 + \epsilon}$ 依赖整条 $x$ 的平方和，乍看必须等所有元素读完才能开始矩阵乘。但回头看导引三的 `v1` 循环：每一个 CTA 为了算自己那一行的内积，本来就要把整条 $x$（8,192 个元素）从头到尾读一遍。既然每个 CTA 都读全了 $x$，就可以在同一个循环里顺手多累加一个平方和 $\sum_k x_k^2$，在尾声块内归约后算出 $r$，最后再乘到内积上写出 $y[\text{row}] = r \cdot \sum_k W[\text{row}, k]\,x_k$。这是因为：

$$y = W(x \cdot r) = r\,(Wx)$$

不乘权重向量时，这两个式子代数上相等。乘权重向量时写成 $r\,W(w_{\text{norm}} \odot x)$，也只用本 CTA 读到的数据。数值上只差两点：少了把 $x_n$ 写回全局内存时的一次 BF16 舍入（把 32 位浮点数存成 16 位时的四舍五入，见第 6 章第 1 节），乘加的舍入顺序也变了。

融合只省掉 kernel 边界和全局内存往返，合进来的计算本身不会消失。我们在一个更快的 `gemv` kernel 上量过：把阶段 2 开头的按头归一化、旋转位置编码和写 FP8 KV 缓存（导引二第 2 节）并进阶段 1 的尾声，kernel 内部仍要多花约 **1.1 µs**（见下图）。那个 kernel 仍是每个 CTA 算 1 行，一个头的 64 个 CTA 各自写完后给一个计数器加 1，最后一个加的 CTA 去做归一化和位置编码，其余直接退出（计数器的写法见第 2 章第 6 节）。多出的 1.1 µs 怎样分摊，没有测。

能不能合，只看一件事：后一步要的数据，是不是不用让全部 CTA 停下来等就能拿到。有两种情况可以合：数据已经在同一个 CTA 里；或者多个 CTA 的结果只需要汇到一处，由最后写完的那个 CTA 来做（第 2 章第 6 节）。归一化能合，是因为每个 CTA 本来就读全了 $x$（这 16 KiB 数据会留在芯片上的缓存里，见第 2 章第 2 节）。融合的取舍：

- **得到什么**：少 2 道硬件交接、少 2 次启动；中间结果 $x_n$（16 KiB，在 $T = 1$ 时很小）不再写回全局内存又读回来。
- **付出什么**：主 kernel 在循环或尾声里多算一步；代码更复杂；而且 2,304 个 CTA 每个都把同一个 $r$ 重复算了一遍（每个 CTA 多做 8,192 次乘加和一次块内归约）。
- **什么时候亏本**：
  - 后一步的每个 CTA 都要读前一步许多 CTA 算出的结果时，硬合成一个 kernel 就要让全卡所有 CTA 在中间停下来同步，等最慢的那个写完。全卡同步还要求全部 CTA 同时驻留在芯片上，否则会挂死（见第 2 章第 6 节）。这时拆成两个 kernel 往往更好；下一节讲怎样让这两个 kernel 部分重叠。
  - 第二种情况（由最后写完的 CTA 来做）也会亏：若被合进来的是一个本来可以按下一节方法提前进场的小 kernel，它就得排在前一个 kernel 最后一个 CTA 后面，失去重叠，实测反而变慢（见第 9 章第 6 节）。

## 4. 后一个 kernel 能不能在前一个结束之前就开始？

**能。PDL 让后一个 kernel 先派上 SM 读权重，等前一个的写入全部可见后再读它的输出。**

导引二第 3 节说过，静态权重不依赖前一步算出的激活，可以提前读。在这条三 kernel 链里，归一化 kernel 只有 1 个 CTA，它运行时只占 1 个 SM，其余 131 个 SM 都空着。可在普通 CUDA 流里，硬件把“后一个 kernel（下称**后继**）能开始派发”和“前一个 kernel（下称**前驱**）已经完全结束”绑在了一起。**Hopper**（H200 的架构）提供的 **PDL**（Programmatic Dependent Launch，编程依赖启动）把这两件事分开，用法分四步（图 1-3）：

1. CPU 启动后继 kernel 时多传一个启动参数，告诉 GPU：后继可以在前驱结束之前派发。
2. 前驱的每个 CTA 在算完主循环之后、写回之前发出**触发调用**；一旦所有前驱 CTA 都已触发（或已退出），硬件就**可以**把后继的 CTA 派到空闲 SM 上（规范允许提前派发，但不保证一定提前派发）。
3. 后继 CTA 派上 SM 后，先做不依赖前驱输出的工作——在“归一化 → gemv”这道边界上，就是先向 HBM 发出第一批权重 $W$ 的读取。等待调用返回之前读进来的字节要留在寄存器、共享内存，或预取进 L2（第 9 章第 4 节），等 $x_n$ 准备好再用，因此能提前读多少受片上空间限制。
4. 后继在读取前驱输出之前发出**等待调用**；等待调用返回时，前驱整个 grid 已经执行完毕，前驱的所有全局内存写入对后继全部可见。

```cuda
// 前驱：发出触发（位置见下文）
cudaTriggerProgrammaticLaunchCompletion();
// 后继：CPU 用带 PDL 启动参数的启动接口下发后继；后继先发出不依赖前驱的读取，再等待
cudaGridDependencySynchronize();   // 返回后才能读前驱的输出
```

**在本章的写法里，读前驱输出的代码必须放在等待调用之后**；等待调用之前也不能写前驱可能还在读的缓冲区（本章的链里没有这种情况，例子见第 9 章第 5 节）。触发调用的位置只决定后继多早能派上 SM。

按时间线推断，PDL 最多能省两部分：前驱收尾和后继独立工作重叠的那段（取两者里较短的），加上交接本身可能变短的部分。我们在一个只测这一步的小测试程序里量过（这种程序下称**微基准**）：两个 kernel 用 PDL 串起来，后继只有 1 个 CTA、一派上 SM 就调用等待，从前驱最后一个 CTA 结束到等待调用返回约 **0.64 µs**。它和第 2 节的 1.0 µs 来自不同实验，不能直接相减。一道边界上 PDL 单独省多少，没有测。

触发调用放在哪里要看前驱占多少个 SM。前驱只占少数 SM 时（如本例只有 1 个 CTA），在开头触发几乎不会影响前驱（没有和晚触发对比实测）。当前驱占满全卡 SM 时，如果在函数开头就触发，提前派上 SM 的后继 CTA 会停在等待调用上，占着 SM 的资源，拖慢还没算完的前驱。实测里这样做让前驱注意力 kernel 最多多花约 1.65 µs（第 7 章第 11 节）。占的是寄存器、共享内存还是 CTA 名额，没有拆开测。

这只会拖慢，不会死锁：触发要等前驱每个 CTA 都已触发或退出，那时前驱的 CTA 都已在 SM 上，后继挡不住它们。所以前驱占满 SM 时，触发调用应当放在前驱主循环结束之后、收尾写回之前。

PDL 的取舍：

- **得到什么**：让后继不依赖前驱的读取与前驱收尾重叠（在这条 `gemv` 链上用 PDL 的耗时变化没有测）。
- **付出什么**：后继必须在第一次读前驱数据之前插入等待调用；一旦把读取误放在等待调用之前，就可能偶发读到上一次重放留下的旧值，而且运行时不会报错（这类错误的实测见第 9 章第 5 节）。
- **什么时候亏本**：见上文（实测反例见第 7 章第 11 节）。

## 5. `gemv` 演化 `v1 → v2`：把三 kernel 链录进一张 CUDA graph

**整图重放比 CPU 从空队列逐个下发快约 1.7 倍，比命令预先排满快约 1.6 µs，单个 kernel 耗时不变。**

这一步改的只是启动方式，GPU 上执行的三个 kernel 与 `v1` 逐字节相同：

```cuda
// v1：CPU 逐个把 [归一化, gemv_kernel, 后处理] 放进 CUDA 流
gemv_kernel<<<2304, 128, 0, stream>>>(W, xn, y, K);
// v2：预热时在 stream 上录制这三步并实例化成 graph_exec，运行时一次提交
cudaGraphLaunch(graph_exec, stream);
```
