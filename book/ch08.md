# 第 8 章 [Part II · 阶段 6]：路由 NVFP4 混合专家——从 2.27 秒到 6 毫秒及 Prefill 大分块的五代演化（m0 → m5）

**本书地图：** 第 0.0 章 → 第 0 章 → 第 0.5 章 → 第 1 章 [第 0 级] → 第 2 章 [第 1 级] → 第 3 章 [第 2 级] → 第 4 章 [第 3 级] → 第 5 章 [第 4 级] → 第 6 章 [第 5 级] → 第 7 章 [阶段 2：分页注意力] → **【第 8 章：阶段 6 路由 NVFP4 混合专家】** → 第 9 章 [整层总装] → 第 10 章 [性能诊断法]

承接第 7 章末尾的问题：阶段 2 的分页注意力交出 `o_attn [T, 1024]` 后，数据流经阶段 3 的输出投影与第一道门控残差。接着在阶段 4（`router` 路由打分与 Top-8 选择）和阶段 5（`pooler` 降维投影）处分成两路并行计算，最后汇入单层权重体积最大的阶段 6（32 个本地路由混合专家 MoE）。

同样是这 32 个本地专家，为什么从单请求解码（`M = 1`）到大块预填充（`T = 16,384`），内核结构非要历经五代演化（`m0 → m1 → m2 → m3 → m4a/m4b → m5`）？**原因很直接：同一个本地专家在一趟计算里到底能分到几个词元。**

在看五代内核怎么演进之前，我们先算清两笔账：第一笔是评分口径与权重格式，第二笔是 **58 个词元**的算力平衡点。

在 62 层整网里，首尾的第 0 层和第 61 层专家保持 `BF16`；中间 **60 层**（第 1 至 60 层）的路由专家采用 4 位浮点格式 `NVFP4`，单张 H200 上的 32 个本地专家一共占 **`906 MB`**。因此独立专家赛题 P2 把单层耗时乘上 **60 层**，作为整网 60 个 `NVFP4` 专家层的负载总耗时（SGLang 60 层基线的 6 算例几何平均为 `13,448.5 µs`）。下文列出的各档物理下界（`11.4–108.9 µs`）以及单个算例的内核耗时（如 `28.6–109.9 µs`），则都是**单层**耗时。本章要回答三个问题：为什么第 0 代参考实现（`m0`）跑完 P2 的 60 层几何平均总耗时达到 `2,270,104.65 µs`（2.27 秒）？前四代内核（`m1 → m4b`）怎样把 60 层几何平均一步步压到实测 `6,123.21 µs`（比 SGLang 快 `2.1963×`）和估计值 `~6,033 µs`（约 `2.23×`）？第五代内核（`m5`）又怎样在整层预填充赛题 P5 下跑满 Tensor Core？

先看第 1 至 60 层 `NVFP4` 专家在单张 H200 上的五步计算与输入输出契约：
- **五步计算**：在 8 卡专家并行（EP8）下，本卡驻留 32 个本地专家 `[local_start, local_start + 32)`。在 H200（Hopper 架构）上，SGLang 基线走 **Marlin W4A16** 混合精度矩阵乘路径（Marlin 是开源的 4 位权重、16 位激活矩阵乘内核）。在这条路径上，专家输入激活 `p [T, 4096]` 保持 `BF16`，4 位 `NVFP4` 权重读进片上后先解码成 `BF16` 再做矩阵乘（把输入激活也一并量化成 `FP4` 是下一代 Blackwell 架构的路径）。对每个命中的本地 `(tok, slot, e)` 词元-专家对，依次执行五步：
  1. 门控与上投影融合矩阵乘：`[h_gate | h_up] = p[tok] @ dequant_nvfp4(W13[e], 上投影块缩放[e], 上投影全局缩放[e]).T`。输出从 `4,096` 维扩到 `8,192` 维，门控在前、上投影在后：前 `4,096` 列是门控 `h_gate`，后 `4,096` 列是上投影 `h_up`。
  2. 门控激活（SwiGLU，门控在前）：`inter = silu(h_gate) * h_up`，维度回到 `[4096]`。
  3. 下投影矩阵乘：`y = inter @ dequant_nvfp4(W2[e], 下投影块缩放[e], 下投影全局缩放[e]).T`（`[4096] → [4096]`）。
  4. 每专家独立后归一化（在跨专家加权求和之前逐对执行）：`y_norm = rmsnorm(y * (1 + w_post_expert), 1e-8)`。
  5. 按路由权重加权累加：`m[tok] += topk_weights[tok, slot] * y_norm`。其中路由权重由阶段 4 按 `topk_weights = w_raw / (sum(w_raw, dim=-1) + 1e-15)` 归一化得到；未命中本卡任何专家的词元输出全 0。
- **为什么 Marlin 路径必须在每个专家输出后跟一道 `RMSNorm`？** 这跟门控与上投影权重 `W13` 的全局缩放系数有关。在训练保存下来的模型权重文件（检查点）里，本卡 32 个专家的门控投影（`w1`）和上投影（`w3`）各有一份独立的 FP32 全局缩放标量（记为 `w1_scale_2` 与 `w3_scale_2`），合起来的上投影全局缩放形状是 **`[32, 2]`**。但 H200 上的 Marlin W4A16 内核每个专家只接受**一个**全局缩放标量，公开实现便直接把两个缩放合并成门控那一个（上下投影统一用 `w1_scale_2`）。因为门控激活 `SwiGLU(g, u) = silu(g) * u` 对上投影 `u` 是线性的（`u` 乘几倍，输出就乘几倍），把上投影原本该乘的 `w3_scale_2` 换成 `w1_scale_2`，会让该专家的下投影输出 `y` 整体多乘一个固定倍数（常数增益）`1 / r`，其中 `r = w3_scale_2 / w1_scale_2`。紧接着对每个专家单独执行一次均方根归一化（`RMSNorm`）：由于 `RMSNorm` 会除以向量自身的均方根，任何正数常数倍数都会在分子和分母里同时约掉（`rmsnorm(y / r) = rmsnorm(y)`），正好在跨专家加权求和之前把这个 `1 / r` 增益抵消掉。这就是为什么 Marlin 路径必须带每专家后归一化。独立专家赛题 P2 的评测输入同样给每个专家只存 1 个全局缩放标量（形状 `[32]`），这与 H200 Marlin 路径的做法一致。
- **输入与输出**：输入激活是降维并归一化后的 `p [T, 4096]`（BF16，每词 `8 KiB`，位于 HBM 或 L2），伴随全局选中专家编号 `topk_ids [T, 8]`（`int32`）、归一化路由权重 `topk_weights [T, 8]`（FP32）和后归一化权重 `w_post_expert [4096]`（BF16），外加常驻 HBM 的 32 个本地专家 `NVFP4` 权重。其中上投影包含码字 `W13 [32, 8192, 2048] uint8`、上投影块缩放 `[32, 8192, 256] FP8 E4M3` 与上投影全局缩放（检查点为 `[32, 2] FP32`，Marlin 合并后及 P2 评测输入为 `[32] FP32`）。下投影包含码字 `W2 [32, 4096, 2048] uint8`、下投影块缩放 `[32, 4096, 256] FP8 E4M3` 与下投影全局缩放 `[32] FP32`。每个权重占 `0.5 B` 码字加 `0.0625 B` 块缩放共 `0.5625 B`，单个专家 `50.33M × 0.5625 B = 28.3 MB`，32 个专家合计 `906 MB`。输出是加权汇总后的专家激活 `m [T, 4096]`（BF16，每词 `8 KiB`，写回 HBM 或 L2），交给阶段 7 的 `unpooler` 升维投影。

再算第二笔账：**58 个词元**的平衡点。每处理一对 `(tok, e)`，上下投影一共要做 `2 × 3 × 4096 × 4096 = 100.7 MFLOP` 的浮点运算。如果读一次专家权重只服务 1 个词元，算术强度只有 `2 ÷ 0.5625 = 3.56 FLOP/B`。要跨过 H200 的 `206 FLOP/B` 平衡点（见第 0 章第 3 节），**同一个本地专家在一趟计算里至少要分到 `206 ÷ 3.56 ≈ 58` 个词元**。这个分界把阶段 6 分成了两种不同的瓶颈区间：
- **Decode（`M = 1, 16, 32`）与 Verify（`M = 8, 128, 256`）**：哪怕到了最大的 `M = 256`，最忙卡上的 `390` 个本地命中对分散在约 `24.6` 个专家上，平均每个激活专家也只分到约 **`16` 个词元**。因为 `16 < 58`，前四代内核（`m0 → m4b`）始终受限于 HBM 读权重带宽、波次尾和同步延迟（6 档负载的单层物理下界分别为 `11.4 / 52.5 / 70.8 µs` 与 `37.3 / 101.3 / 108.9 µs`）。
- **Prefill（`T = 753, 3,012, 16,384`）**：均匀路由下，每个本地专家平均分到的词元数 `T ÷ 32` 从 `T = 753` 的 **`24` 个**（过渡区），一路涨到 `T = 3,012` 的 **`94` 个**和 `T = 16,384` 的 **`512` 个**。一旦跨过 58 词元门槛，读完 32 个专家全部 `906 MB` 权重的单层 HBM 时间上限只有 `188.7 µs`，而 `T = 16,384` 的专家部分算力下界达到 **`1,668 µs`**。第五代内核（`m5`）的主要瓶颈也随之转向跑满 Tensor Core 与指令管线。

为什么第 0 代参考实现（`m0`）跑完 6 个算例的 60 层几何平均耗时达到 `2,270,104.65 µs`（2.27 秒）？原因很直接：**它在 Python 循环里逐个专家启动内核，而且每命中一个专家，都要把 `28.3 MB` 的 4 位权重先反量化成 `100.7 MB` 的 BF16 大矩阵写回 HBM，再启动矩阵乘从 HBM 读回来算。**

算一下单个专家的显存账就能看出问题有多大：有用的压缩权重只有 `28.3 MB`，但中间写回了一趟 `100.7 MB` 的 BF16 稠密权重（体积膨胀 `3.56` 倍），紧接着又从 HBM 读回来一趟。结果每个激活专家实际搬运了 `28.3 + 100.7 + 100.7 = 229.7 MB` 数据，还外加两次独立内核的启动空隙（见第 1 章第 1 节）。

第一代跃迁（`m0 → m1`）就是去掉这笔多余的显存搬运：**用 Triton（用 Python 编写分块 GPU 内核的编译器）把逐专家循环合成为一次启动的分组专家矩阵乘（Grouped Expert GEMM），并且把 4 位反量化留在片上寄存器里完成。** 程序先把命中同一个本地专家的 `(tok, slot)` 对分桶排好，再单次启动分组矩阵乘网格。每个专家的 `0.5625 B/权重` 压缩码字与块缩放从 HBM 读进片上后，直接在寄存器里还原成 `BF16` 送入矩阵乘管线，全程不再往 HBM 写回任何反量化权重。光这一步，6 个算例的 60 层几何平均耗时就从 `2,270,104.65 µs` 降了 `79.5` 倍，压到 **`28,554.36 µs`**（图 8-1 模式 2 读数：`整个网格：1 次内核启动 · 每专家只读 28.3 MB · 写回稠密权重 0 B` / `6 算例几何平均 28,554.36 µs（比 m0 快 79.5×）→ 21,369.20 µs`）。接着把门控与上投影按 `32 + 32` 行交错排布，让同一输出行的门控和上投影落在同一个分块里。再配上无分支位运算解码与早期编程依赖启动（PDL，见第 1 章第 2 节与第 6 章第 3 节），60 层几何平均又快了 `1.34` 倍，降到 **`21,369.20 µs`**（相对 `m0` 累计快 `106` 倍，共省下 `2,241.5 ms`）。这样做的代价是矩阵乘前必须维护固定形状的词元-专家分桶索引表，且交错排布固定了离线权重布局（单独寄存器与共享内存变化未测）；它在全部 6 个评测算例上都稳赢。

进入第二代跃迁（`m1 → m2`），内核切到了寄存器源 `wgmma` 分块流水架构。这时候小批量下遇到了两个新问题：第一，下投影 `GEMM2` 的输出列数（`4,096`）比上投影（`8,192`）少一半，在 `M ≤ 32` 时分块数填不满 132 个 SM；第二，片上环形缓冲深度一旦改变每 SM 的驻留 CTA 数，不同路由种子上的耗时就会一正一负反转。

第一个问题直接用第一部分的机制解决。先按第 2 章第 1 节对 `M ≤ 32` 的下投影开启 `Split-K`（`M ≤ 8` 切 4 份、`M ≤ 32` 切 2 份），把部分和平面存成 `BF16` 交给后归一化核顺带归约，60 层几何平均从 `18,057.2 µs` 降到 **`17,362.60 µs`**。再按第 3 章第 2–4 节给权重挂上 3 槽 `cp.async` 环形缓冲（单层 `decode 16 / 32` 省 `5.25 / 5.70 µs`，`verify 1` 省 `8.45 µs`）或 2 槽纯权重环（`verify 32 / 16` 省 `18.94 / 4.64 µs`），把 HBM 读权重延迟藏进流水线。在此基础上，配合每环步消费 `2 × BK = 256`（在 `decode 32` 的上投影和下投影两项改动分别省 `3.20 µs` 与 `5.84 µs`，在 `verify 16 / 32` 省 `2.13 µs`）以及块缩放双射合并拷贝（`verify 16 / 32` 省 `3.38 / 1.50 µs`），进一步压低访存开销。上述细粒度流水项的单项额外开销与亏损边界在本阶段未单独拆测（机制代价见第 2 章第 1 节与第 3 章第 4 节）。

第二个问题引出了 MoE 特有的**波次边界定律**：为什么同一个驻留改动，在不同路由种子上会正负翻转？在稠密矩阵乘里，矩阵形状是固定的，总 CTA 数保持不变。但在 MoE 里，**每个随机路由种子命中的本地活跃专家数 $A$ 不同，全卡总块数 `A × 每专家 CTA 数` 跟着种子浮动（每专家 CTA 数由具体内核的分块形状决定）**。当某项改动把每 SM 驻留从 $k$ 提到 $k+1$ 个 CTA 时，只有当某个种子的总 CTA 数刚好从 **2 个波次跨进 1 个波次**（跨过 `132 × (k+1)` 的台阶）时，这个种子才会明显变快。而在没跨过波次台阶的种子上，更浅的缓冲或更高的同 SM 争抢反而会让内核变慢。

看两个实测例子就清楚了。在 `M = 32`（`decode 32`）的下投影 `gemm2` 中，每个活跃专家启动 `64` 个 CTA（总块数 `A × 64`）。同一项把每 SM 驻留从 7 提到 9 个 CTA 的改动，在 5 个路由种子上分别测出了 `+3.41 / +5.71 / +6.83 / -7.12 / -11.87 µs` 的分化结果。反过来，在 `verify 1`（`M = 8`）上把 `mma.sync` 换成 `wgmma`（见第 5 章第 3 节），会让每 SM 驻留从 `9` 掉到 `8` 个 CTA，单波容量从 `1,188` 缩到 `1,056`；结果 $A = 9$ 的两个种子从 1 波掉进 2 波，单种子慢了 **`+10.43 µs` 与 `+11.41 µs`**。这也定下了 MoE 优化的准入规则：任何改动必须在全部 5/5 路由种子上同时不退化才能合入。因此在 `M = 1 / 16` 下开启权重环时，必须用编译器指令把每 SM 驻留钉在 `6` 或 `7` 个 CTA，不钉住时 `decode 1` 慢 `+4.18 µs`、`decode 16` 慢 `+2.13 µs`。反过来，如果用 `__maxnreg__(56..80)` 硬压寄存器上限引发 8–18 个寄存器溢出，在 `verify 32` 上会慢 `+0.72 / +26.43 / +61.79 µs`，在 `verify 1` 上慢 `+5.14 µs`（见第 3 章第 1 节）。

钉住驻留和波次之后，第二代内核（`m2`）还剩下一项无效开销：**轻专家尾块里的空白填充行**。分桶路由要求同一个分块里的词元属于同一个专家，所以每个专家的词元数都得向上补齐到分块高度 `BM`（比如 `32` 行或 `128` 行）的整数倍。在偏斜路由下，大量轻专家只分到寥寥几个词元，重专家的最后一个尾块也往往只剩几行有效数据，底下大半截全是空白填充行（padding）。如果不做处理，`wgmma` 会照着满块高度空转矩阵周期，并把整块专家权重白读一遍。

第二代（`m2`）用 **RAG 不规则专家尾块动态裁剪（Ragged Tail-Tile Trimming）** 砍掉了这部分空转：在分块入口检查当前专家块的实际有效词元行数，对不满一块的尾块按 `BM 32 → 16 → 8` 三级台阶动态下调分块高度。在 `M = 128` 上启用全部三级裁剪；在预填充 `T = 753..16,384` 中，同样用一次标量加载检测第 `RAG` 行起是否全为填充，直接跳进窄行矩阵乘分支（见图 8-1 中间）。

算一下 RAG 尾块裁剪的得失：
- **好处**：省掉了轻专家尾块的无效填充行计算和权重重读。在单层 `verify 32`（`M = 256`）上，上投影加上 `RAG 16` 单项就省了 **`25.68 µs`**（置信区间 `[-26.08, -24.42] µs`，5/5 种子全胜且比特级恒等）；推广到下投影后在 `verify 16 / 32` 上再省 **`8.08 / 7.12 µs`**，在 `verify 16`（`M = 128`）上启用 `BM = 8` 第三级裁剪又省 **`6.37 µs`**。到了预填充 `T = 753 / 3,012 / 16,384`，它把每个有效词元对发射的 MMA 行数从 `1.68 / 1.27 / 1.06` 压到 **`1.18 / 1.08 / 1.02`**，整层直接提速 **`4.94% / 4.32% / 0.99%`**（图 8-1 模式 3 读数：`尾块 BM 32 → 16 → 8：MMA 行数 32 → 8（6 行有效，示意）· verify 32 省 25.68 µs` / `预填充每个有效对的 MMA 行数 1.68 / 1.27 / 1.06 → 1.18 / 1.08 / 1.02`）。
- **代价**：核内要生成多套窄分块分支，并在分块入口多做一次有效行数检查。在预填充里，必须用标量加载配合统一分支，才能把环槽计数留在统一寄存器 `UR`（见第 7 章第 4 节）里；如果改用块内归约去统计有效行数，环槽算术就会退回私有向量寄存器，每步 `K` 会多出 **34 条指令**。
- **什么时候亏本**：分块高度 `BM` 必须跟每专家平均词元数匹配，盲目扩块就会亏本。比如在预填充过渡区 `T = 753`（每专家平均 24 个词元）下，把分块从 `BM = 32` 扩到 `BM = 64`，同时改由消费者线程束发 TMA 搬运权重（替代线程发 `cp.async`，每线程寄存器从 `180` 压到 `151 / 150` 个，使每 SM 驻留从 `2` 个升到 `3` 个 CTA）。这样 64 个词元对共享一次解码配 TMA 权重环，能让 Tensor Core 占用率从 `40%` 升到 `57%`、`gemm1` 从 `240.0` 降到 `222.3 µs`、整层提速 **`3.87%`**（少解码与 TMA 替代 `cp.async` 两项各自的贡献未单独拆测）。但如果把这套消费者发 TMA 环直接搬到 `T = 3,012`（`BM = 128`），整层反而**倒退 `-1.6%`**。如果在同一个 `T = 753` 上继续扩到两组消费者 warpgroup 的 **`BM = 128`**，24 个词元根本填不满 128 行，填充浪费会让滑窗与全长跌到 `0.9495×` 与 `0.9782×`（整体**倒退 `-1.39%`**）。同样，在小批量 `decode 16 / 32` 上，如果无条件把单次处理粒度从 8 对扩成 **16 对**，单步指令数会涨 **`+16%`** 并在重 $A$ 种子上拖出长尾，实测反慢 **`+1.71 µs`（`decode 16`）与 `+2.54 µs`（`decode 32` 重 $A$ 种子）**。

为什么第二代分块流水核（`m2`）在 `M = 1..32`（`decode 1/16/32` 与 `verify 1`）的单层耗时上，还是会多花十多微秒？原因在于第二代（`m2`）把路由分桶、上投影 `W13` 和下投影 `W2` 拆成了三次独立的内核启动。每次启动都要重走一轮波次尾，中间激活还在 HBM 与 L2 之间来回读写。

在 `M = 1 / 8` 下，可以先用少于 SM 数的有界持久网格省掉空 CTA 的启动与退出尾巴（单层分别省 `1.22 µs` 与 `7.60 µs`）。在 `M = 1` 下还可以删掉独立路由核，改用最后到达者原语在核内归约（分别省 `1.12 / 1.42 / 0.86 µs`，见第 1 章第 1 节），再按活跃专家数 $A$ 自适应选择 `Split-K = 2/3`（省 `2.05 µs`，见第 2 章第 1 节）。但到了 `M = 8..32`，多核之间的折返依然省不掉。

第三代跃迁（`m2 → m3`）的做法是：**换用 132 个 CTA 常驻的全卡小批量持久核（权重驻留），把核内路由（Phase 0）、上投影加 SwiGLU（Phase A）和下投影（Phase B）装进同一套以 8 对词元为单位（8-pair virtual pass）的 TMA 权重流引擎。随后再把 `M = 8..32` 的上下投影从全网格栅栏拆成两个 PDL 串联核。** 围绕这套小批量持久核，第三代（`m3`）依次解决了三个问题：

第一个问题是**怎么把多核折返压进一次启动，又不在核内全网格栅栏上空等**。在 `verify 1`（`M = 8`）上，单次启动的小批量持久核用 TMA 环形缓冲流式搬运权重单元，在核内一气算完路由和上下投影。消掉多核波次尾之后，单层耗时直接降了 **`15.73 µs`**（相对 SGLang 基线的加速比从 `2.0160×` 升到 `2.0854×`）。当词数扩到 `decode 16 / 32`（`M = 16 / 32`）时，命中超过 8 对的热门专家被切成每轮 **8 对词元的虚拟轮（8-pair virtual pass）**，配合 8-warp 尾声轮转与 8-warp `__ballot_sync + __popc` 位图并行路由。这套位图路由替代了 256 步串行扫描，在整层解码与投机检验赛题 P3 的 `M = 1 / 8` 上配合首轮 TMA 错峰省下 `0.62 / 2.46 µs`（见第 4 章第 4 节）。在单块快路径先省 `13.71 µs` 的基础上，这一步在单层 `decode 16 / 32` 上一共省下 **`20.29 µs` 与 `7.70 µs`**（相对 SGLang 基线的加速比升到 `2.1963×`）。代价是超过 8 对的热门专家每跑一轮虚拟轮都要重读一次权重，到了 `M ≥ 128` 就会因权重重读过多而输给第 3 节的大批量内核。

合进单核之后，Phase A 和 Phase B 之间原本立着一道耗时 `1,419 ns`（`1.42 µs`）的全网格栅栏（`grid.sync()`）。按第 1 章第 3 节的做法，在 `M = 8 / 16 / 32` 下把这道全网格栅栏拆成 Phase A 和 Phase B 两个 PDL 串联核：后继 Phase B 在等待前序核收尾的空档里提前把权重环预载进共享内存，在 `verify 1 / decode 16 / decode 32` 上单层又净省 **`0.37 / 0.70 / 0.82 µs`**。而在 `M = 1` 下没有尾波失衡，拆核无益（对照 `+0.027 µs`），保持单核协作即可。同时需要给权重流标上 `evict_first` 提示以防冲刷 L2 里的激活（去掉该提示会慢 `+2.44 µs`，见第 2 章第 3 节）。

第二个问题是**内核刚启动时，为什么读取几千字节的激活 `x` 会等上将近 1 微秒？** 查看小批量持久核在 `M = 1` 下的入口时间戳就会发现，普通全局加载（`LDG`）和硬件 TMA 走的是同一个 DRAM/L2 请求队列。如果在序言里先一口气连发 3 槽权重 TMA，全卡 132 个 SM 瞬间往显存队列里塞进约 `14 MB` 的权重请求；紧跟着发出的激活 `x` 读取，就会堵在这 `14 MB` 权重请求后面干等 **`0.96 µs`**。（在第 3 节 `M = 128 / 256` 的大批量 18-Warp 持久 `wgmma` 核里也有同样现象：冷启动第 0 段激活收集因为排在 `14.2 MB` 权重预取后面，耗时从热态的 `0.7–1.4 µs` 涨到了 **`5.3 µs`**。）

看清队列拥堵之后，解法就是把启动顺序反过来，优先发出小数据请求。第三代（`m3`）先在 Phase 0 把上下投影的 64 个浮点全局缩放系数（全局缩放表，占 `256 B`）预载进共享内存，把每个子任务尾声的缩放查询从 `328` 周期的 L2 命中压到 `23` 周期的共享内存读取 `LDS`（静态 SASS `LDG` 从 `36` 条降到 `21` 条，在 `verify 16 / 32` 省 `0.47 / 0.55 µs`）。同时把共享内存路由计数表的行宽从 32 或 64 字填充成 **33 字**奇数行宽，错开 32 路 bank 冲突（图 8-2，表体积只多占 `128 B`），并只读一次 `topk_ids`；这两项在 P3 四个 verify 形状上省下 **`1.28–7.49 µs`**（`+0.6%–2.1%`，P2 单测 `topk_ids` 单次读省 `0.21 / 1.15 µs`）。接着**先发出激活 `x` 的 `LDG` 和第 0 槽权重 TMA，再用 GPU 的硬件纳秒计时器把第 1、2 槽权重 TMA 推迟 `500–600 ns` 错峰发出**。最后用 `__maxnreg__(144)` 卡住 `M = 1` 主核的寄存器上限，腾出空间让占 110 个寄存器的后归一化 CTA 同 SM 共驻、提前进场。

在 `decode 1` 上，这套启动解耦在 **360/360 个种子上全胜**，单层实测省下 **`1.055 µs`**。逐项叠加的累计收益依次是：单加全局缩放表预载 `-0.41 µs`，再加 `x` 提前累计 `-0.71 µs`，再加 `500 ns` 错峰累计 `-1.05 µs`；随后 `144` 寄存器共驻再省 `0.080 µs`。同一套做法在 `verify 1` 拆分核上省 **`0.755–0.82 µs`**，在 `decode 16 / 32` 省 `0.40 / 0.48 µs`（在冷加载在途期间顺带做 `mbarrier` 初始化则在 3 张 GPU 上测得 `-0.59..+0.01 µs`，落在重复测量之间的波动范围内）。当然，错峰延迟也不能拉得太长：在 `M = 8` 上延迟 `600–800 ns` 能省 `0.755–0.840 µs`，一旦拉长到 **`1,200 ns`**，就会因为人为推迟了权重供应而退化回 `-0.425 µs`；到了 `M = 32`，错峰只有 `-0.247 µs`，没超出重复测量之间的波动范围，直接设为 `0 ns`。同样在预填充 `T = 753` 的单核融合专家里，赛题规定块缩放系数必须按 1 字节无符号 8 位浮点格式 `UE4M3` 原样存放；多出的这一步片上解码，起初在第 0 号滑窗算例上带来了 **`-1.23%`**（`0.9877×`）的耗时损失（下称存储合规基线）。改在每步开头用 8 字节寄存器 `LDG` 提前读入缩放码并在步末展开后，消掉了缩放码的 `cp.async` 等待组和 `LDS` 往返，在存储合规基线之上净提速 **`+0.384%`**（10/10 全胜）。而改用 `cp.async + LDS` 搬运展开的变体虽然只多 9 条指令，却比存储合规基线还慢 `0.9962×`；至于在尾声提前读重排词元表与提前做分块写出的尝试，因为重排词元表原本就命中 L1 缓存、且提前写出卡住了环槽释放，实测变慢而被否决。

第三个问题是**后归一化核里的两处 `ptxas` 编译器退化（图 8-3）**。后归一化核通过 PDL 挂在专家主核后面（省 `0.31–0.93 µs`，见第 1 章第 2 节），并对输入做 2 组 × 4 路流水加载（省 `0.75 µs`；若改成宽幅无分支加载，每线程寄存器会从 `64` 涨到 `128+` 掉驻留，在全 6 个负载上反慢 `+0.43..+0.90 µs`）。拆开它的 SASS 反汇编后，查出了两处编译器造成退化的地方：
- 第一处是**预取加载被下沉**。序言里原本写在 `ACQBULK`（即 `griddepcontrol.wait`，第 5 条 SASS）之前的带只读缓存提示全局加载 `ld.global.nc`，被 `ptxas` 全部挪到了 `ACQBULK` 后面，导致等前序核跑完才开始发冷 DRAM 读取，PDL 预读完全失效。改用带 `volatile` 的普通全局加载内联汇编，把 6 条 16 字节预取（`LDG.E.128`）钉回 `ACQBULK` 之前后，在 `decode 1 / 16 / 32` 与 `verify 1` 上实测省下 **`0.45 / 0.67 / 0.41 / 0.27 µs`**。它的代价是放弃了只读缓存提示，而且只适用于 `M ≤ 32`。到了 **`M > 32`**（`verify 16`），前序持久专家核占满全部 132 个 SM，后归一化核在 `ACQBULK` 之前根本进不了场、没有重叠窗口，开启 `volatile` 预取反而会**变慢 `+0.45 µs`**。
- 第二处是**循环外常量被重物化**。循环外预先算好的 16 个缩放权重 `nw[i] = 1.0f + norm_w[i]`，被 `ptxas` 为了省寄存器拆回 2 相 × 8 槽的内层循环里反复重算，多出 `321` 条 `FADD`。在预计算后加一行运行期不生成任何指令的空内联汇编 `asm volatile("" : "+f"(nw[i]));`，逼编译器把这 16 个值留在寄存器里（占 16 个 FP32 寄存器即 `64 B`）。静态 SASS 指令数从 `1,603` 条降到 **`1,120` 条**（少了 **483** 条），在 `decode 1 / 16 / 32` 上实测省下 **`0.21–0.30 µs`**。

## 3. 第四代跃迁上篇（m3 → m4a，Verify 大批量 M = 128..256）：18-Warp 持久 wgmma 引擎、LPT 动态领活、按秩逆序分配与尾部 K-halves

<!-- FIG ch08-m4a-wgs: 图 8-4 画阶段 6 第四代 M20-WGS 18-Warp 持久 wgmma 作业队列与全卡尾波均衡数据流：上方展示 4 个消费者 warpgroup（512 线程，每线程 96 寄存器）与 2 个生产者 warp 从全局作业队列拉取 64 × 256 × 256 子任务（取代 4 核 Gluon 省 22.54 µs）；中间对比按填充后词元数降序的 LPT 排列（省 1.40–2.32 µs）与 T=128 生产者原子动态领活（消除 108 个 CTA 跑 6 活、24 个 CTA 跑 5 活的静态失衡，提速 1.67%）；下方画按 Phase-A 负载秩逆序分配 Phase-B（最轻 A 配最重 B，削平 9–52 µs 长尾，将全卡最晚退出时间从 189.4 / 215.0 µs 压至 176.3 / 195.0 µs）。 -->

为什么第三代小批量持久核（`m3`）在 `M ≤ 32` 下表现很好，到了 `verify 16 / 32`（`M = 128 / 256`）却跑不过分块大核？**因为词元数涨上来以后，热门专家分到的词元远不止 8 个，继续按 8 对一轮切分会让同一个热门专家的 `28.3 MB` 权重被反复重读。可要是退回第二代的 4 核分块方案，4 次独立启动之间的 L2 折返和波次尾又会多花二十多微秒。**

在 `M = 256` 下，最忙卡上的 `390` 个本地命中对落在约 `24.6` 个专家上，平均每个激活专家分到约 16 个词元，热门专家更是分到几十个词元。这时候单 warp 的 `mma.sync` 已经喂不饱矩阵管线，必须切回 4-warp 协同的寄存器源 `wgmma`，同时还得把路由和上下投影留在同一次内核启动里。

第四代跃迁上篇（`m3 → m4a`）的做法是：**在 `M = 128..256` 下合成为单次启动的 18-Warp 持久寄存器源 `wgmma` 核，让 132 个持久 CTA 围绕同一条全局子任务队列，连续跑完核内 33 字直方图路由（Phase 0，见第 2 节）、`64 × 256 × 256` 上投影加 SwiGLU（Phase A）和下投影（Phase B）。随后再用四项跨 SM 均衡手段把轻重专家混杂拖出来的长尾削平。**

先看 **18-Warp 持久 `wgmma` 核**的内部编制。每个持久 CTA 配 `576` 个线程：4 个消费者 warpgroup（共 512 个线程）并发跑 `BM = 64, BN = 256` 的寄存器源 `wgmma`，外加 2 个专职生产者 warp（第 16 号权重生产 warp 负责 TMA 权重环，第 17 号激活收集 warp 负责 `cp.async` 激活收集）。为什么这里不照搬 3 个消费者 warpgroup 每线程分 232 个寄存器的配法？算一下寄存器总数就明白了：`4 × 128 × 232 = 118,784` 个寄存器，直接超出了单 SM `65,536` 个寄存器的硬件上限。所以 18-Warp 持久 `wgmma` 核把每线程寄存器上限统一卡在 `96` 个（见第 3 章第 1 节）。热门专家的最多 64 个词元一次装进同一个 `64 × 256` 分块，权重只从 HBM 读 1 遍，中间激活 `h` 留在 L2 与全局平面里直接交给 Phase B 消费。在单层 `verify 32`（`M = 256`）上，单次启动的 18-Warp 持久 `wgmma` 核比 4 核分块方案配对实测缩短了 **`22.54 µs`**（置信区间 `[-23.23, -21.57] µs`，6 算例几何平均加速 `1.0149×`；图 8-4 模式 1 读数：`每个 CTA：576 线程 = 4 个消费者 WG（512 线程 × 96 寄存器）+ 2 个生产者 warp · 132 个持久 CTA` / `单次启动取代 4 核分块：verify 32 省 22.54 µs [−23.23, −21.57]`）。不过这套 256 列宽块不能直接照搬到 `verify 16`（`M = 128`）：在 `M = 128` 下，22 个子任务乘 16 个分块一共 `352` 个块，在 132 个 SM 上刚好折合 **`2.66` 个波次**，多出来的 `+18 µs` 分数波次尾会把单块收益抵消（实测 `[-0.26, +4.35] µs` 打平）；如果在 Phase B 每阶段再加轮询栅栏，更会慢上 **`+5.8..+9.0 µs`**。

把所有工作装进 132 个持久 CTA 之后，整核的耗时就完全取决于 **132 个 CTA 里最晚退出的那 1 个 CTA**。开启第 1 节的 RAG 尾块裁剪后，一个满载 `64` 行的重子任务（填充后词元数为 `64`）和一个只有 `8` 行的轻尾块（填充后词元数为 `8`，单活耗时 `17.15 µs`）执行时间差出一大截。怎么防止某个 SM 在最后时刻撞上大活、拖慢全卡？第四代上篇（`m4a`）从四个方向把 132 个 SM 的退出时间拉齐：

第一招是 **LPT（最长处理时间优先）降序排列**。把全局队列里的所有子任务按填充后词元数从大到小排好，让满块重活先上，把填充后词元数为 `8` 的短尾块留在最后去填补各 SM 的末尾空隙（实测全卡 CTA 结束时间极差为 `15.84 µs`）。在单层 `verify 16 / 32` 上，这比不按大小排序省下了 **`1.40 µs` 与 `2.32 µs`**；在预填充 `T = 753` 上用 LPT 把满块排在前面、RAG 短尾块排在后面，整层同样提速 **`+1.33%`**。代价是维护一张全局排序映射表（额外寄存器占用未测）；到了 32 个专家几乎全是满块的 `prefill T = 3,012 / 16,384`，没有短尾块可填，收益也就归零（`1.0017× / 0.9987×`）。

第二招是 **`M = 128` 生产者原子动态领活**。在 `M = 128`（`verify 16`）下，如果按固定步长静态分活，会有 `108` 个 CTA 分到 `6` 个子任务，剩下 `24` 个 CTA 只分到 `5` 个子任务，导致这 24 个 SM 在最后约 `17 µs` 里干等着空转。第四代上篇（`m4a`）改让每个 CTA 的权重生产 warp 在跑当前子任务时，用一次原子加（`atomicAdd`）按 LPT 顺序去全局队列里动态领下一个活，使 P3 的 `verify 16` 滑窗与全长整层分别提速 **`+1.67%`（19/20 胜）与 `+0.65%`**。这里正好可以跟第 7 章第 2 节做个对比：为什么注意力的动态偷取在 `verify 32 / 16` 全长上反慢 `+22.6 / +10.0 µs`，而 MoE 这里却稳赢？原因就是单次任务的粒度差了十倍：注意力单个 64-key 分块只有约 `0.87–2.04 µs`，动态认领加上每分块 `1,128` 次 `bar.sync` 让单块开销直接涨了 `10%`；而 MoE 单个子任务长达约 `17 µs`，一次原子加的开销放进去几乎看不见。

第三招是**按 Phase-A 负载秩逆序分配 Phase-B**。早期版本里，Phase A（上投影）和 Phase B（下投影）共用同一套来回交替（蛇形）的顺序领活。结果**最重的 Phase-B 子任务，又落在了刚刚跑完最重 Phase-A 子任务的那批 CTA 头上**，两段重活叠在一起拖出了 `9–52 µs` 的长尾。解法是记下每个 CTA 在 Phase A 的实际负载排名（秩），到了 Phase B 反过来派活，让 Phase A 最轻的 CTA 优先去领最重的 Phase B 子任务。这一倒序把 `verify 32` 滑窗与全长最慢 CTA 的退出时间从 `189.4 / 215.0 µs` 压到了 **`176.3 / 195.0 µs`**，核尾提前 **`2.6 / 13.1 / 20.0 µs`**（对应 `verify 16` 滑窗 / `verify 32` 滑窗 / `verify 32` 全长）。最终使 `verify 32` 滑窗与全长整层提速 **`+5.2%`（20/20 全胜）与 `+1.47%`**（图 8-4 模式 4 读数：`最轻 Phase A 配最重 Phase B：最慢 CTA 退出 189.4 / 215.0 → 176.3 / 195.0 µs（verify 32 滑窗 / 全长）` / `核尾提前 2.6 / 13.1 / 20.0 µs · 整层 +5.2%（20/20）/ +1.47% · 长尾 9–52 µs 被削平`；亏损边界未测）。

第四招是**尾部 66 活 K-halves 对半切分与小批量派发微调**。当 Phase B 最后一轮剩余子任务数不超过 `66`（填不满 132 个 SM 的一半）且倒数第 5 个子任务填充后词元数为 `8` 时，把最后 66 个 Phase-B 子任务沿 `K` 维对半劈成 `2 × 66 = 132` 个半程活（前半程写出 FP32 部分和并立下就绪标志，后半程等标志到了再累加，见第 2 章第 1 节）。这一切分在单层 `verify 16 / 32` 上平均省下 **`0.54 / 1.95 µs`**，在剩余 `12` 个子任务的种子上省下 **`4.53–5.07 µs`**。不过在不触发切分的满波种子上，分支与标志检查会慢 `+0.52..+0.75 µs`，所以必须用剩余子任务数 `≤ 66` 严格门控。而在小批量持久核那一侧，也顺带做了两项派发微调：一是当 `M = 1` 且活跃专家数 `≤ 3` 时，按 `blockIdx.x + 132 j` 轮转派发 Phase-A 单元，让 132 个并发 TMA 请求在显存地址上紧挨着；单块节拍从 `1.21 µs` 缩到 `1.10–1.15 µs`，在 `decode 1` 上省下 **`0.664 µs`**（反过来如果把权重环加深到 4、5、6 槽，反而会慢 `+0.59 / +1.07 / +1.30 µs`）。二是在 `decode 16 / 32` 拆核后，硬件按 `blockIdx.x` 顺序派发 Phase-B 块，导致最后进场的 **`131` 号块**比前序块晚了约 `2 µs` 才启动（在 `62% / 81%` 的种子里成为最慢块）。于是对 `100..131` 号高编号 CTA（`blockIdx.x ≥ 100`）按二次曲线少分一点 Phase-B 单元，又省下 **`0.27 / 0.31 µs`**（见第 2 章第 2 节；但如果在不含双倍虚拟轮［2 轮］段的种子上无门控开启，会把过多工作推给前序 CTA，反慢 `+0.42 / +0.49 µs`）。

| **Phase-A 轮转派发与 Phase-B `blockIdx ≥ 100` 二次倾斜（配尾部 K-halves）** | `decode 1`（活跃专家数 `≤ 3`）、`decode 16 / 32`（含双倍虚拟轮 `2` 轮）、`verify 16 / 32`（剩余子任务数 `≤ 66`） | `decode 1` 轮转派发使 132 TMA 紧邻（`1.21 → 1.10 µs/单元`）省 **`0.664 µs`**；`decode 16/32` 对 `100..131` 号块倾斜补偿 `#131` 晚启动 `~2 µs` 省 **`0.27 / 0.31 µs`**；尾部 66 活 K-halves（见第 2 章第 1 节）省 **`0.54 / 1.95 µs`**（剩余 `12` 个子任务省 `5.07 µs`） | 条件门控分支与 K-halves FP32 部分和累加 | `decode 1` 将环加深到 `4/5/6` 槽反慢 **`+0.59/+1.07/+1.30 µs`**；不含双倍虚拟轮（`2` 轮）强开块倾斜反慢 **`+0.42 / +0.49 µs`**；K-halves 在不切分种子上慢 `+0.52 / +0.75 µs` |

**演化收尾（`m3 → m4a`）：** 第四代上篇（`m4a`）在 `M = 128..256` 下切入 18-Warp 持久 `wgmma` 核（单层 `verify 32` 配对省 `22.54 µs`）。在此基础上，叠加 LPT 降序（省 `1.40–2.32 µs`）、`M = 128` 原子动态领活（`+1.67%`）、按 Phase-A 秩逆序分配 Phase-B（核末提前 `20.0 µs`，`+5.2%`）与尾部 66 活 K-halves（省 `1.95 µs`），将大批量专家的跨 SM 波次尾与负载失衡削平。

## 4. 第四代跃迁下篇（m4a → m4b）：延迟上投影完成标志（-29.9 µs）、fence.proxy.async、独占 Warp 18 异步释放、奇偶双账本与 SwiGLU 缩放折叠

把 18 个 warp 装进同一个 18-Warp 持久 `wgmma` 核之后，为什么消费者线程束还是会频繁停下来等同步？**原因在于 `wgmma` 要求整个 128 线程的 warpgroup 锁步齐发（`sync.aligned`）。只要消费者路径上留着一条全卡可见的设备级内存栅栏（`MEMBAR.ALL.GPU`），或者在 L2 原子单元上排起长队，整条 Tensor Core 管线就会跟着一起停摆。**

在动手改同步协议之前，剖析器先抓出了三处主要的流水线阻塞：
1. 在 `wgmma` 流水区间里混入了非矩阵写操作，触发了 `ptxas` 寄存器读写串行化告警（见第 6 章第 1 节），每条 `HGMMA` 后面都被编译器插进 `DEPBAR`，慢了 **`+8.10 µs`**；同时未合并的激活收集耗去了 `22.5 µs`。把非矩阵写移出流水区间、并将收集改成 16 字节合并写出（`STG.E.128`）后，直接省下 **`8.10 µs` 与 `13.10 µs`**。
2. 如果让 4 个消费者 warpgroup 的 **512 个线程同时往 L2 计数器发 `red.release.gpu`**，全卡成千上万个原子请求会在中央 L2 原子单元上同时排队，单这一项就让单层 `verify 32` 慢了 **`+93.3 µs`**。改成每个 warp 只由 `lane 0` 发 1 次释放（512 次请求缩成 16 次），这 `93.3 µs` 的排队开销随之消除（图 8-5 模式 1 读数：`512 个线程同时 red.release：512 个请求排队，verify 32 增加 +93.3 µs` / `每 warp 由 lane 0 发 1 次：16 个请求（512 ÷ 32），这 93.3 µs 随之消失`）。
3. 就算改成了每 warp 释放，消费者在每个 Phase-A 子任务末尾发布上投影完成标志时，依然要执行一次设备级栅栏 `MEMBAR.ALL.GPU`。这条指令每次停顿 `400–700` 个周期（负载下达 `0.6–1.3 µs`），直接卡在两个子任务的 `wgmma` 之间。

第四代跃迁下篇（`m4a → m4b`）围绕这第 3 个问题做了一系列减法：**先把上投影完成标志的刷新推迟到下一个子任务的 `wg_wait<0>` 之后，再用异步代理栅栏（`fence.proxy.async`）、独占的第 18 号释放 Warp 和奇偶双账本，把所有 GPU 级同步从消费者关键路径上剥离出去，最后把发射槽受限的 SwiGLU 尾声压短 2 条指令。**

第一步是**把上投影完成标志刷新推迟到下一个子任务的 `wg_wait<0>` 之后，并用 `fence.proxy.async` 替换重型栅栏**。消费者刚算完当前 Phase-A 子任务、发出写出中间激活 `h` 的指令时，为什么不能马上刷新上投影完成标志？因为这时候写出的数据还在飞往 L2 的路上，而且消费者马上就要发下一个子任务的第一轮 `wgmma`。这时候插一道全局栅栏，等于逼着矩阵管线停下来等显存写排空。

第四代下篇（`m4b`）的做法是：当前子任务写完 `h` 先不刷新标志，直接去发下一个子任务的第一轮 `wgmma`；**等下一个子任务完成了 `wg_wait<0>` 之后，再回过头刷新上一个子任务的上投影完成标志**。这时候上一个子任务写出的 `h` 早就排空到 L2 了，刷新几乎不再卡停矩阵管线。在单层 `verify 32`（`M = 256`）上，光延迟刷新上投影完成标志这一项改动，首轮就省下 **`20.50 µs`**，复测确认省下 **`29.92 µs`**（置信区间 `[-31.5, -28.7] µs`；配合双指令交替派活初版比基线省 `18.32 µs`）。它的代价只是让 Phase B 看到该标志的时间晚了 1 个 `wgmma` 组。反过来，如果在小批量 `M = 1..32` 的小批量持久核上，也想用每段 `red.release / ld.acquire` 细粒度计数器、或者把 `h` 预填 `0xFFFF` 轮询数据标志去替掉 `1.42 µs` 的全网格栅栏，结果反而会变慢。因为经由 L2 交接 `h` 怎么都要付约 `1 µs` 的写排空延迟，细粒度计数器在 `M = 8 / 32` 上会慢 **`+0.30..+0.46 µs` 与 `+0.10..+0.42 µs`**，数据内嵌标志在 `decode 1` 上反慢 **`+1.06 µs`**（这也反证了小批量下第 2 节的双核 PDL 串联才是正路）。

与此同时，在激活收集与就绪释放里，用单条跨代理栅栏 `fence.proxy.async.global`（编译成 `FENCE.VIEW.ASYNC.G`）加线程 0 的单次 `red.release.gpu`，替掉每个存储线程 5 条指令的 `fence.acq_rel.gpu`（见第 2 章第 4 节）。这一步在单层 `verify 16 / 32` 上又省下 **`0.52 µs` 与 `0.70 µs`**（1,670 万次调用零竞态；图 8-5 模式 2 读数：`延迟上投影完成标志：verify 32 省 29.92 µs，CI [−31.5, −28.7]（首轮 −20.50 µs）` / `每次 MEMBAR.ALL.GPU 停顿 400–700 周期（负载下 0.6–1.3 µs）；fence.proxy.async 再省 0.52 / 0.70 µs`）。同一思路放到 P3 整层验证核里，删掉已由前序作业排空的每线程 GPU 栅栏（静态 `MEMBAR` 从 `68` 条降到 `40` 条）能提速 `+0.30%–0.86%`。放到 P5 预填充里，在 `T = 753` 下把代理栅栏挪到 `cp.async` 发出之后、TMA 重填之前并配 4 槽环能省下 `8.3 µs`（整层 **`+1.37%`**；但在无栅栏上界仅 **`-9.7 µs`** 的约束下，若强行把 `fence.proxy.async` 和 TMA 选举提前到 K 步第 1 条指令，实测反而会倒退 `-0.150%` 与 `-0.319%`）；在 `T > 1,024` 下把每步 K 的 2 个 CTA 屏障合为 1 个能提速 **`+1.48%–1.70%`**（配 `FULL` 屏障合并包 `+0.63%`）。此外，在激活环上改由每个消费者 warp 的 `lane 0` 独立向激活环空信号报到，在权重环上把权重环空信号报到推迟到激活环满信号等待之后，清零了待决 `LDS` 的写后读竞态（付出 `+0.4..+1.6 µs`、P3 `-0.55%` 的实测代价，见第 3 章第 4 节）。

第二步是**把残留的 `MEMBAR.ALL.GPU` 移出消费者，交给独占的第 18 号释放 Warp（`576 → 608` 线程）**。为了让 4 个消费者 warpgroup 连子任务末尾那一次 `red.release.gpu` 都不用发，消费者改为只对共享内存计数器做片上释放 `red.release.cta`（只需几十个周期）。另派一个专职释放线程在旁边轮询片上计数器、代发 GPU 级的 `red.release.gpu`（静态 `MEMBAR` 从 `25` 处降到 `9` 处，P3 整层 `BAR.SYNC` 从 `69` 处降到 `13` 处）。这一步在单层 `verify 16 / 32` 上省下 **`1.49 µs` 与 `1.74 µs`**（在 P3 四格提速 `+0.47%–1.11%`，在 P5 `T > 1,024` 将阶段 1 与阶段 2 完成标志移交空闲收集通道和 TMA 生产者通道提速 `+0.164%`）。

但这里起初遇到了一个同 warp 指令流阻塞问题（见第 4 章第 3 节）。起初为了省线程，这个专职释放线程被塞在了第 16 号权重生产 warp 的 `lane 1`。**同一个 warp 的 32 个线程共用唯一一条指令流**：当 `lane 1` 在那里轮询计数器或卡在 `MEMBAR.ALL.GPU` 上时，同一个 warp 里的 `lane 0` 就没法及时发出下一轮权重 TMA。为了验证这一点，第四代下篇（`m4b`）给每个 CTA 多开 1 个 warp（从 `576` 扩到 **`608` 个线程**），把释放线程挪到**独占的第 18 号释放 Warp（`lane 0`）**，单层 `verify 16 / 32` 又省下 **`0.77 µs` 与 `0.85 µs`**。如果在原位置直接把 `MEMBAR` 删掉再测（见第 10 章），只能省下 `0.44 / 0.15 µs`。换句话说，迁往第 18 号释放 warp 的收益里，有一大半来自不再耽误第 16 号权重生产 warp 的 `lane 0` 发射 TMA。此外，不要让这个释放线程顺带去按阶段发信令提前唤醒后归一化核：把等待删掉再测（见第 10 章），隐藏后归一化核尾部的收益上界只有 `-1.06..-2.21 µs`，而在主核里加信令本身就要花掉 **`+2.2..+3.2 µs`**。实测三个变体反而分别慢了 **`+1.0..+2.1 µs`、`+12..+21 µs` 与 `+0.9..+2.7 µs`**（P3 把尾声释放交给异步通道也只动了 `+0.04%–0.11%`，落在重复测量之间的波动范围内）。

第三步是**用奇偶双账本省掉核尾的清零链**。在 CUDA Graph 反复重放时，全局的上投影完成标志计数器每一趟跑完都得归零。如果在核尾让最后一个退出的 CTA 去清零，就得多跑一串栅栏和同步。第四代下篇（`m4b`）直接把计数器显存翻倍，开辟偶账本（下标 `0..1023`）和奇账本（下标 `1024..2047`，两本共占 `8 KiB`）。每次启动把全局序号加 1（在 `0` 到 `2G` 之间循环），按奇偶挑其中一本用，同时让空闲的生产者通道在后台顺手把另一本清零。核尾的重置链删掉之后（`MEMBAR` 从 `29` 降到 `25`、`BAR.SYNC` 从 `16` 降到 `14`），单层 `verify 16 / 32` 又省下 **`0.286 µs` 与 `0.331 µs`**（亏损边界未测）。

第四步是**精简反量化指令，并在发射槽受限的 SwiGLU 尾声里折叠缩放系数**。在主循环内，第四代下篇（`m4b`）集成了第 5 章第 1 节与第 6 章第 3–4 节的寄存器解码改进：把左移改写成走 FMA 管线的 `IMAD.SHL`（6 负载几何平均 `1.0271×`），并用 `__byte_perm` 成对解码块缩放（省 `1.04–2.40 µs`）。同时把常数 `0x60006000` 放进常量池配三输入 `LOP3`（每 16 字从 `13` 条压到 `9` 条指令，省 `0.58–0.99 µs`），再用预处理异或重排实现 **8 条整数指令解码 NVFP4**（在 P2 组合包省 `0.55–2.94 µs`，在 P3 全算例几何平均提速 `0.58%`、`decode 32` 滑窗最高 `+1.01%`；P3 大批量核还启用了 6 位无损缩放压缩，省 `2.78%` 字节、提速 `+0.38%–0.66%`）。

接着看子任务之间的切换间隙（Phase A `1.26 µs`、Phase B `1.75 µs`，加起来占全核耗时的 `6.1%`）。起初怀疑这是寄存器缓冲不够深，尝试加第 3 套 A 寄存器缓冲（`wait_group<2>`）去盖住它，结果 `warpgroup_arrive` 停顿只从 `14.6%` 动到 `14.3%`，毫无收益。把特殊函数指令删掉再测（保持总指令数不变，见第 10 章），才揪出真正的瓶颈：**卡住 Phase-A 尾声的是 SMSP 指令发射槽（`932` 个发射周期 > `768` 个 MUFU 周期），而不是第 0 槽数据等待或特殊函数单元吞吐。**

既然瓶颈在指令条数，第四代下篇（`m4b`）就利用 `SwiGLU(g, u) = silu(g) * u` 对上投影 `u` 的线性齐次性，把反量化缩放系数 `s` 直接折进指数参数 `arg = dg * (-s * log2e)` 和分母 `FFMA(e, k, k)`（其中 `k = 1 / s^2` 是缩放系数的倒数平方）。再用 `ld.shared.v4` 向量化读取作业描述符，把每个元素的尾声指令从 `9` 条砍到 **`7` 条**，在单层 `verify 16 / 32` 上实测省下 **`0.54 µs` 与 `0.60 µs`**。顺着同一条路，把 `silu` 改写成 `0.5 * g * (1 + tanh(0.5 * g)) * u` 能再少 `80` 条指令（省 `0.20–0.34 µs`，分块对照在 `±0.13 µs` 内中性）；用 `ex2.approx.ftz` 去掉 `-126` 以下的次正规数补救分支每线程少 `48` 条指令（省 `0.28 / 0.48 µs`）；把路由切分的运行期整数除法改成编译期常数除数又能少 `88–96` 条指令（估计每次启动省 `≤ 0.4 µs`）。当然，这套尾声折叠只有在内核受发射槽限制时才管用：在 `decode` 下它的收益是 `0.00 µs`；把它移植到不受发射槽限制的 P3 verify 专家变体上时（把整个解码删掉再测，收益上界只有 `2.73%–4.20%`），尽管砍掉了 `22%–41%` 的尾声指令，12 算例几何平均仍是 **`0.99938×`**，没有任何收益。

**演化收尾（`m4a → m4b`）：** 第四代下篇（`m4b`）在 18-Warp 持久 `wgmma` 核内消除 `ptxas` 串行化告警（见第 6 章第 1 节）与 512 线程并发原子排队（恢复 `93.3 µs`）。在此基础上，合入延迟刷新上投影完成标志（单层 `verify 32` 省 `29.92 µs`）、`fence.proxy.async`（省 `0.52–0.70 µs`）、独占第 18 号释放 Warp 异步释放（合计省 `2.26–2.59 µs`）与奇偶双账本（省 `0.29–0.33 µs`）。再配合 8 指令异或反量化（组合包省 `0.55–2.94 µs`，见第 6 章第 3 节）与 SwiGLU 缩放折叠（省 `0.54–0.60 µs`），将 P2 全 6 档负载的 **60 层几何平均总耗时**从 `2,270,104.65 µs` 推进至预计约 **`6,033 µs`**（估计值，相对 SGLang 60 层基线 `13,448.5 µs` 加速比约 **`2.23×`**）。

## 5. 第五代跃迁（m4b → m5，区间 III Prefill T = 753..16,384）：32 专家全激活分桶、分块数上限、BM64 票据融合环、BM128 4-Warp 收集 + 块完成 mbarrier、非持久 gemm2 恢复与 F2FP 成对舍入

<!-- FIG ch08-p5-moe: 图 8-6 画阶段 6 Prefill 路由专家（Grouped NVFP4 GEMM）的四步硬件流水线（对应将乱序词元按 32 个本地专家分桶重排并裁剪末尾填充行 RAG 尾块与 77% 空退出网格 a_cap、4-warp 收集线程束配 TMA 权重环与 4 组旋转寄存器保持 wait_group<2> 跨管线重叠、gemm1 SwiGLU 尾声用打包 cvt.rn.bf16x2.f32［F2FP］将 F2F 从 224 条压至 96 条使 XU 管线占用从 5.74% 降至 3.08%、以及单通道释放 done1/done2 消除消费者 MEMBAR.ALL.GPU 的算法步）。 -->

当输入从逐词解码和 8 词检验跨进长序列预填充（Prefill：多轮对话追加 `T = 753`、`T = 3,012` 与首轮长提示词分块 `T = 16,384`）时，阶段 6 的瓶颈从显存带宽受限转向了算力受限。**本卡 32 个本地专家全部被激活，均匀路由下每个专家分到的平均词元数 `T ÷ 32` 从 `T = 753` 的 `24` 个（过渡区），跳到 `T = 3,012` 的 `94` 个和 `T = 16,384` 的 `512` 个，跨过了 58 个词元的平衡点。**

在 `T = 16,384` 下，把 32 个本地专家的 `906 MB` 权重从 HBM 完整读一遍只需要 `188.7 µs`；但专家部分的矩阵运算量达到 `1,649 GFLOP`，光算力下界就要 **`1,668 µs`**。面对几千到上万个本地 `(tok, slot, e)` 命中对，第四代面向 `M ≤ 256` 的片上直方图扫描已经装不下，必须切成第五代（`m4b → m5`）分组矩阵乘（Grouped NVFP4 GEMM）流水线（图 8-6）。

第五代（`m5`）的改造顺着数据流分成三步：先在入口砍掉无效槽位和空转 CTA，再按词数 $T$ 分成过渡区（`T ≤ 1,024`）和纯算力区（`T > 1,024`）两条主循环，最后把尾声里的类型转换从拥挤的特殊函数管线上挪开。

第一步是**只生成本卡 32 个专家的紧凑分桶表，并用分块数上限砍掉 `77%` 的空退出 CTA**。在小批量下，后归一化核直接跳过非本地专家槽位，把中间平面 `y` 的大小缩成 `本地命中对数 × 8,192 B`（从 `M = 1` 的 `25 KB` 到 `M = 256` 的 `2.6 MB`，后归一化尾耗时只有 `1.94–3.31 µs`，占全核 `0.89%–2.32%`，单步独立配对增益与亏损边界未测）。到了预填充下，专用路由对齐核直接输出**只包含本卡 32 个本地专家（`0..31`）分块的重排词元表与每块对应的专家表**，从源头剔除 `-1` 非本地空块（代价是预先分配固定大小的缓冲显存以供 CUDA Graph 反复重放复用，单步独立增益与亏损边界未测）。紧接着启用第 1 节的 **RAG 尾块裁剪**（`T = 753 / 3,012 / 16,384` 提速 `+4.94% / +4.32% / +0.99%`）和第 3 节的 **LPT 满块优先映射**（`T = 753` 提速 `+1.33%`）。

即便剔除了非本地专家，主网格的大小还有一个问题。为了兼容 CUDA Graph 静态图捕捉，`gemm1` 和 `gemm2` 的网格原本按最坏情况（假设所有词元的 8 个路由槽位全落在本卡，外加 32 个专家的填充块）开到了 `1,056` 个 `BM = 128` 分块 CTA。但在 `T = 16,384` 下统计发现，这 `1,056` 个 CTA 里有 **`77%`** 一进场发现没有有效分块、转头就空退出。于是第五代（`m5`）把 `T > 3,012` 的 `gemm1` 和 `gemm2` 主网格截断在 `分块数上限 = ⌈(2T + 32 × 127) / 128⌉`（`T = 16,384` 时上限为 **`288`** 个分块），再另外启动一个每 SM 1 个 CTA（共 132 个）的持久溢出兜底核，去处理万一超出分块数上限的分块（评测负载下无溢出分块，兜底核单独耗时未测）。砍掉那 `77%` 的空 CTA 后，`T = 16,384` 的 `gemm1` 从 `2,905 µs` 压到 **`2,831 µs`**，`gemm2` 从 `1,406 µs` 压到 **`1,376 µs`**，首轮整层直接提速 **`+1.07%`**（仅在 `T > 3,012` 开启，`T ≤ 3,012` 下的空块比例与盈亏边界未测）。

第二步是**按词元数 $T$ 拆成两条专用主循环，并在 `T = 16,384` 的 `gemm2` 上从持久核退回 `9,216`-CTA 非持久网格**：
- 在 **`T = 753`（过渡区，每专家平均 24 个词元）**：分块数还不够多，走的是 `BM = 64` 单核融合路径。它合并使用了前面各章调好的多项机制：先用第 1 节的 `BM = 64` 配消费者发 TMA 权重环（`+3.87%`），再用第 1 章第 1 节的单核票据排序把 `gemm1 + SwiGLU + gemm2` 融进同一个网格省掉核间启动空隙。这项单核融合与 `BM = 128` 3 环超前 2 步、4 套旋转 A 寄存器缓冲配 `wait_group<2>` 及 128 寄存器瘦身打包提交，在 **`T = 753` 上提速 `+2.04%`**、在 `T = 3,012` 上提速 `+1.82%`、在 `T = 16,384` 上提速 `+4.98%`（三档负载几何平均提速 **`+2.94%`**）。接着合入第 5 章第 4 节的每 32 位权重字发 1 组 `wgmma` 配 `wait_group<1>`，使循环内 MMA 等待采样从 `36.8%` 降到 `17.8%`（在 `T = 753 / 3,012 / 16,384` 三档负载上分别提速 **`+1.35% / +1.40% / +1.04%`**）。随后再合入第 4 节的后置 `fence.proxy.async` 配 4 槽环（`T = 753` 提速 `+1.37%`）和第 2 节的顶部 8 字节 `LDG` 预取 `UE4M3` 缩放码（`+0.384%`）。在此基础上，再叠加第 5 章第 1 节的 `IMAD.SHL` 左移分流（ALU 管线占用 `55.6% → 48.9%`，`T = 753` 提速 `+1.02%`）与第 6 章第 3 节的异或重排解码（`13 → 12` 条指令，`+0.20%`）。最后按第 6 章第 1 节做 1:1 CUDA C++ 移植，并用循环携带槽计数器把每步 K 指令从 `341` 条压到 `328` 条（`T = 753` 滑窗从 `288.5` 压到 `281.75 µs`）。
- 在 **`T = 3,012 / 16,384`（纯算力区，每专家平均 94 与 512 个词元）**：分块扩到 `BM = 128`。因为 Hopper 的硬件 TMA 没法按重排词元表（`pair // 8`）去离散收集激活行（见第 3 章第 3 节），`gemm1` 专门划出 **4 个收集 warp（限 40 个寄存器）用 `cp.async` 收集离散激活行 `x`，同时用 TMA 搬运连续权重装填 3 套环形缓冲**。把 `cp.async` 和代理栅栏移出消费者主循环后（代价是收集 warp 占去 128 个线程），在 `T = 3,012 / 16,384` 上提速 **`+1.21% / +2.03%`**；配合每步 K 单次 CTA 屏障再提速 `+1.48% / +1.70%`，配 4 套旋转寄存器 `wait_group<2>` 保持 2 组 `wgmma` 在途使首轮打包提速 `+4.98%`。在此基础上，把 `gemm1` 改成持久网格（`G = min(2 × SMs, 分块数上限 × 64)`），并加上一道**分块完成 `mbarrier`**。当消费者还在跑当前分块的 SwiGLU 尾声和 `STSM` 写出时，收集 warp 已经跨分块提前去预取下一块的激活了，使 `T = 3,012` 滑窗从 `942.75` 降到 **`916.75 µs`**（提速 `+0.71%–1.0%`）。下投影 `gemm2` 的满块也采用同样的 **1 个 TMA 生产者 warp + 4 个消费者 warp 的 2 槽 `mbarrier` 环分工**（`maxnreg 128`，消去主循环里的 `cp.async` 与步末等待），在 `T = 3,012 / 16,384` 上提速 **`+1.70% / +1.95%`**。至于能不能在 `T ≤ 3,012` 下把 `gemm1` 改成更宽的词元分块、在核内由生产者 warp 做激活收集？把收集步骤删掉再测（见第 10 章）就会发现，在 `T = 3,012` 下完全免掉收集的收益上界也只有 `+1.7% / +0.7%`；而核内宽块收集破坏了寄存器配额与环流水，在 `T = 753` 上零收益，在 `T = 3,012` 上所有变体全线亏本（**`0.8659×..0.9861×`**）。
- **为什么到了 `T = 16,384` 的 `gemm2`，反而要从 `264`-CTA 持久核退回 `9,216`-CTA 非持久网格？** 这是个反直觉的实测结果。此前曾把 `gemm2` 写成 `264` 个 CTA（`2 × 132`）的持久核，让每个 CTA 按固定步长（`idx += gridDim.x`）静态领分块。但在 `T = 16,384` 下，各个专家分块的完成时间和 RAG 裁剪长度参差不齐，固定步长根本没法跨 SM 动态挪活。剖析器一测，`gemm2` 核内的 **SM 空闲时间达到 `60.3 µs`**，SM 之间的有效周期极差拉开到 `94.0 µs`，连带着挂在后面的归一化核也在 PDL 等待里干等了约 **`118–119 µs`**。第五代（`m5`）退回非持久的 **`9,216` 个 CTA 网格（`288 × 32`）**，直接交给硬件块调度器把下一个分块派给最先腾出空的 SM。这一退，把 `gemm2` 核内的 SM 空闲时间从 `60.3 µs` 压到了 **`18.6 µs`**（SM 间极差压到 `45.5 µs`），单核耗时从 `1,468.96` 缩到 `1,443.17 µs`（省下 **`25.8 µs`**，配对几何平均 `1.0086×`；空闲时间差 `41.7 µs` 与核耗时差 `25.8 µs` 未完全重合的原因未测）。

第三步是**在 `gemm1` SwiGLU 尾声用 `F2FP` 成对打包舍入（两个浮点一起转 `BF16`）替代 `F2F`（单个浮点转 `BF16`），给拥挤的 4 通道 XU 管线减负（图 8-6 下方）**。在 `T > 1,024` 的 `gemm1` 尾声里，把单个单精度浮点数转成 `BF16` 的标量转换指令 `F2F`，和算指数的 `MUFU.EX2` 指令走的都是同一条 4 通道特殊函数与类型转换管线（XU），两条指令流排在同一个队列里互相等待。第五代（`m5`）把标量转换改成了两个浮点数一起打包舍入的指令 `cvt.rn.bf16x2.f32`（编译为走 16 通道 ALU 管线的 **`F2FP`**，静态条数从 `56` 升到 `120`）。这样一来，静态 `F2F` 指令从 `224` 条砍到了 **`96` 条**，剖析器实测 XU 管线占用率从 `5.74%` 降到 **`3.08%`**（SM 周期 `-0.6%`），单改这一项就让 P5 整层提速 **`+0.33%`**（10/10 全胜）。它的代价是需要用移位和按位与把打包半字拆开，而且尾声变成延迟受限；如果把它移植到第 4 节的 P3 解码/检验专家核里，因为那边的尾声不在关键路径上，实测为中性。最后再配上第 4 节的阶段 1 与阶段 2 完成标志单通道释放（`+0.164%`）和第 3 章第 4 节的无条件 4 次 `pack_bf16x2` 先打包后释放（清零待决 `LDS` 写后读风险），第五代预填充专家流水线就完整成型了。
