## 1. 计算 `qkv_gate`（`y = W · x`）的核心 CUDA 代码

<!-- FIG ch00_5-a: 图 0.5-1 左栏显示 gemv_kernel 源码与启动语句，右栏画出语言层面的三重并行嵌套框（Grid -> 单个 CTA -> 单个 thread）与全局内存 W/x/y（移动块对应第 row 号 CTA 的第 tid 号线程读取 W[row * K + k] 与 x[k] 累加进 acc、再经 smem[tid] 归约写出 y[row] 的算法步）。 -->

在 CPU 上写矩阵乘向量 `y = W · x`，最外层总会写一个遍历 `row = 0..M-1` 的行循环。但在下面的 CUDA 函数里，这个外层循环不见了。**CUDA 编程的核心做法，就是把原本在时间上顺次跑的外层循环，直接展开成空间上同时跑的一组并行线程块。**

在 62 层模型的每一层里，阶段 1（`qkv_gate`）都是单层数据流的起点。当 `T = 1` 时，它要对 `row = 0..2303` 计算内积 `y[row] = sum_{k=0}^{8191} float(W[row, k]) * float(x[k])`。输入是 HBM 里的权重 `W`（`[2304, 8192]`，BF16，37.7 MB）和入口激活 `x`（`[8192]`，BF16，16 KiB）；输出是写回 HBM 的 `y [2304]`（下例为突出主干把 `y` 写成 FP32，真实阶段 1 输出为 BF16），算完后切分为 `q | k | v | gate` 交给阶段 2（注意力）。

为了并行算完这 `M = 2,304` 行，启动语句 `<<<M, 128, 0, stream>>>` 把外层行循环展开成了 `M` 个并行的 **CTA**（Cooperative Thread Array，协作线程阵列，代码里写作 `block`，即共同处理一块任务的一组线程）。每个 CTA 认领矩阵的 1 行，再派出 128 个 **thread**（执行代码的单个线程）分段累加这一行的 `K = 8,192` 列。代码里的 `__bfloat162float` 是 CUDA 内置的类型转换函数，把读出来的 16 位 BF16 元素转成 32 位 FP32 再做乘加。每个线程按步长 128 循环 `8,192 ÷ 128 = 64` 轮，128 个线程合起来正好读完一行 16 KiB 的 `W` 和 16 KiB 的 `x`。

```cuda
// 省去了 #include <cuda_bf16.h> 与显存分配；stream 为已创建的命令流队列
__global__ void gemv_kernel(const __nv_bfloat16* W, const __nv_bfloat16* x,
                            float* y, int K) {                 // → 第 1 章, 第 2 章
    __shared__ float smem[128];                                // → 第 3 章
    int row = blockIdx.x;                                      // → 第 2 章
    int tid = threadIdx.x;                                     // → 第 3 章, 第 4 章
    float acc = 0.0f;                                          // → 第 3 章, 第 5 章
    for (int k = tid; k < K; k += blockDim.x) {
        acc += __bfloat162float(W[row * K + k])                // BF16 转 FP32
             * __bfloat162float(x[k]);                         // → 第 5 章, 第 6 章
    }
    smem[tid] = acc;
    __syncthreads();                                           // → 第 3 章
    if (tid == 0) {                                            // → 第 4 章
        float sum = 0.0f;
        for (int i = 0; i < blockDim.x; ++i) sum += smem[i];
        y[row] = sum;
    }
}
gemv_kernel<<<M, 128, 0, stream>>>(W, x, y, K);                // → 第 1 章..第 3 章
```

在图 0.5-1 里拖动 `row` 与 `tid` 滑块并播放时间轴，就能看到任意一个线程在每一轮读哪两个元素、怎样经 `smem` 汇总写出 `y[row]`。

## 2. 启动语句与五个关键字各规定了什么？

上面这段十几行的代码，定下了 GPU 程序从发起到写回结果的五组规则：**CPU 怎么把启动命令放进流队列，每个线程怎么算出自己负责的行号和列号，数据放在哪一级存储里，以及 128 个线程算出来的部分和怎么安全加到一起。**

- **kernel 与 `__global__`**：**kernel** 是在 GPU 上运行的函数。函数开头的 `__global__` 关键字声明 `gemv_kernel` 由 CPU 发起调用、在 GPU 上执行。
- **stream 与异步启动 `<<<M, 128, 0, stream>>>`**：当 CPU 执行完最后一行启动语句继续往下走时，输出数组 `y` 往往还没有算出来。这是因为启动语句只把命令放进 **stream**（按顺序执行 GPU 命令的流队列）就立刻返回，不等 GPU 算完。在 `<<<M, 128, 0, stream>>>` 中，前两个参数是 CTA 数 `M = 2,304` 与每 CTA 线程数 `128`，第三个参数是运行时额外申请的动态共享内存字节数 `0`（本例 `smem[128]` 的大小已在代码里固定为 `128 × 4 = 512 B`），第四个参数是目标 `stream`。同一条 `stream` 里的命令按入队顺序依次执行，这一顺序本身就是一道 **happens-before**（先行发生）保证：前一个 kernel 对全局内存的所有写入，不用在用户代码里另加栅栏，对同一条 `stream` 里的后一个 kernel 自然可见；当 CPU 调用 `cudaStreamSynchronize(stream)` 等待流队列做完时，此前流内所有写入也对 CPU 可见。
- **grid 与内置坐标 `blockIdx.x` / `threadIdx.x` / `blockDim.x`**：**grid** 是同一次启动的全部 `M` 个 CTA 组成的网格。所有线程跑的是同一份代码，靠内置坐标（无符号 32 位整数）认领各自的任务：每个 CTA 靠 `row = blockIdx.x`（赋给 4 B 的有符号整数 `int`）认领 `W` 的第 `row` 行；每个 thread 靠块内编号 `tid = threadIdx.x`（`0..127`）与块宽 `blockDim.x`（`128`），在第 `r` 轮循环访问列 `k = tid + 128 * (r - 1)`。
- **三级存储：全局内存、片上共享内存与私有寄存器**：参数指针 `W, x, y`（保存显存地址的 64 位指针，各占 8 B）都指向 **global memory**（所有 CTA 都可读写的全局内存，位于 HBM）。`row, tid, acc`（`acc` 为 FP32，占 4 B）存放在每个 thread 独占的私有**寄存器**（register，芯片上直接连着算术单元、读写最快但只有当前线程自己能看的存储格，见第 3 章）里。而 `__shared__ float smem[128]`（FP32，占 `512 B`）位于片上**共享内存**（shared memory，位于芯片上、仅当前 CTA 的 128 个 thread 可共享读写的暂存区，见第 3 章）。
- **reduction 与 `__syncthreads()`**：64 轮算完后，一行的内积还分散在 128 个线程各自的 `acc` 里，需要做一次 **reduction**（归约，把多个部分和汇总成一个值的操作）。第 `tid` 号线程先执行 `smem[tid] = acc`，把寄存器里的部分和写进片上 `smem[128]`，随后调用 `__syncthreads()`。这句调用同时做两件事：第一，它是块内执行同步屏障，强制本 CTA 的 128 个线程全部走到这一行，防止 0 号线程在别的线程还没写完 `smem[i]` 时就提前去读；第二，它是本 CTA 的 **memory fence**（内存栅栏），因为 GPU 内存默认不保证跨线程的写入可见顺序，光靠普通变量轮询并不安全，`__syncthreads()` 保证此前所有线程对 `smem`（及全局内存）的写入对本块全体线程可见。跨过屏障后，只有 0 号线程进入 `if (tid == 0)` 分支做 128 次顺序加法并把 `sum` 写回 HBM 的 `y[row]`，块内其余 127 个线程在这一步只能空等（为什么同组线程会互相干等、怎样改成并行归约，见第 4 章）。

## 3. `gemv` 演化起点（`v0 → v1`）：为什么一行要派一个 CTA 而不是一个线程？

既然 `qkv_gate` 有 `M = 2,304` 行，为什么要派 2,304 个 CTA、让 128 个线程分段合算 1 行，而不是直接派 2,304 个线程、让每个线程各自把 1 行 8,192 列从头算到尾？**把这两种写法放到 H200 上一测，耗时差出 `12.5×`：每行派 1 个线程的 `v0` 要 `674.58 µs`，而每行派 1 个 CTA 的 `v1` 只要 `54.08 µs`。**

在 `qkv_gate`（`M = 2304, K = 8192`）上，当 `T = 1` 时，最朴素的 **v0** 启动 `<<<18, 128, 0, stream>>>`（`2,304 ÷ 128 = 18`），全卡共 2,304 个线程，每个线程独自循环 8,192 步算完 1 行。本章第 1 节的 **v1**（上方 `gemv_kernel`）则启动 `<<<2304, 128, 0, stream>>>`，改成每行派 1 个 128 线程的 CTA。

```cuda
// v0：每个线程独自算完 1 行（int row = blockIdx.x * 128 + threadIdx.x;）
for (int k = 0; k < K; ++k) acc += __bfloat162float(W[row * K + k]) * __bfloat162float(x[k]);
// v1：1 个 CTA 的 128 个相邻线程协作分段读同一行（见第 1 节完整代码）
for (int k = tid; k < K; k += 128) acc += __bfloat162float(W[row * K + k]) * __bfloat162float(x[k]);
```

为什么在 CPU 上很顺手的 `v0` 写法，搬到 GPU 上会慢十倍以上？这正是最容易拿 CPU 直觉套 GPU 的地方。

第一个原因是芯片上的计算单元没派满。GPU 上执行指令的独立计算单元叫 **SM**（Streaming Multiprocessor，流式多处理器），一张 H200 上一共有 132 个 SM。硬件按 CTA 为单位把任务分派到各个 SM 上运行（怎样分派见第 2 章）。`v0` 一共只启动了 18 个 CTA，全卡 132 个 SM 里最多只有 18 个分到了活，剩下 114 个 SM 完全空着。

第二个原因是访存方向反了。在 CPU 上，一个线程顺着时间先后去读同一行里连续的地址，硬件预取器就能顺畅工作；但在 GPU 上，编号相邻的一组线程会在同一拍一起发出读取指令，而显存每次至少搬回一小段连续字节。`v0` 里相邻两个线程分别算相邻两行，同一拍去读的权重地址彼此隔着一整行（`16 KiB`），结果每个线程都要单独去显存搬一段，搬回来的字节绝大部分当场浪费；而 `v1` 让同一 CTA 的 128 个相邻线程在同一拍并排读取同一行里紧挨着的 `256 B`，硬件就能把它们合成几次连续搬运（硬件怎么合并相邻线程的读取，见第 3 章）。

把 `v0` 改成 `v1`，好处是 2,304 个 CTA 铺满了全部 132 个 SM，而且相邻线程并排读连续字节；在 H200 上实测（每次测量前先清空片上缓存确保从 HBM 重读权重，跑多次取中位数），单核耗时从 `674.58 µs` 降到 `54.08 µs`（快了 `12.5×`，达到 `7.9 µs` 带宽下界的 `14.6%`）。付出的代价是每个 CTA 多用了 `512 B` 共享内存、1 次 `__syncthreads()` 同步屏障和 0 号线程的 128 次顺序加法，而且 2,304 个 CTA 各自重读了一遍输入向量 `x`（`16 KiB`；为什么重复读 `x` 不会真的去 HBM 搬 2,304 遍，见第 2 章第 3 节）。在 `T = 1` 下，这点块内归约开销远小于用满 132 个 SM 和连续访存省下的时间，`v1` 相对 `v0` 没有变慢的情况（当输入词数 `T` 增大到 `8..256` 时，同一阶段的多词矩阵乘演化链见第 6 章第 4 节）。

看实测数字时还要留心一项固定底座：在本书第一部分的 `gemv` 单核计时里，CPU 事先把启动命令排进流队列，再用 GPU 事件记录首尾时间；就算跑一个什么都不算的空 kernel，这套启动加事件计时本身也要花 `4.6 µs`（空 kernel 的实测中位数，计时方法与 `gemv` 各版本相同）。后续各章的 `gemv` 单核实测中位数都包含这 `4.6 µs` 固定底座，所以单核实测读数不会等于纯传输时间（如果在未预排满的流上逐个启动，或者录进计算图按节点切换，固定开销分别是多少，下一章第 1 节接着拆）。

---

**带走一句话：** CUDA 把外层循环展开成并行的 CTA 与线程；让每个 CTA 的 128 个相邻线程并排合算一行，才能用满 132 个 SM 并连续读取显存，把 `qkv_gate` 的单核耗时从 `674.58 µs` 压到 `54.08 µs`。
