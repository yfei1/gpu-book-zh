承接第 0 章末尾的问题（准备章：最小 CUDA 程序）：单层阶段 1 的 `qkv_gate` 在单请求 `decode`（`T = 1`）下要把 `[2304, 8192]` 的 BF16 权重矩阵 `W` 乘上长 `8,192` 的输入向量 `x`（理论下界 7.9 µs），这个计算写成一段最小的 **CUDA C++** 程序长什么样，代码里的每个关键字规定了什么并行与共享规则？

## 1. 计算 `qkv_gate`（`y = W · x`）的核心 CUDA 代码

<!-- FIG ch00_5-a: 图 0.5-1 左栏显示 gemv_kernel 源码与启动语句，右栏画出语言层面的三重并行嵌套框（Grid -> 单个 CTA -> 单个 thread）与全局内存 W/x/y（移动块对应第 row 号 CTA 的第 tid 号线程读取 W[row * K + k] 与 x[k] 累加进 acc、再经 smem[tid] 归约写出 y[row] 的算法步）。 -->

在 62 层模型的每一层里，阶段 1（`qkv_gate`）都是单层数据流的第一棒。当 `T = 1` 时，它计算 `y[row] = sum_{k=0}^{8191} float(W[row, k]) * float(x[k])`（`row = 0..2303`）。输入是 HBM 里的权重 `W`（`[2304, 8192]`，BF16，37.7 MB）与入口激活 `x`（`[8192]`，BF16，16 KiB）。输出是写回 HBM 的 `y [2304]`（下例为 FP32 占 9,216 B，真实阶段 1 为 BF16 占 4,608 B）。`y` 算完后切分为 `q | k | v | gate`，交给阶段 2（P1 注意力）。

下方函数内部没有遍历 `0..M-1` 的外层行循环，却能一次算出全部 `M = 2,304` 行结果。这是启动语句 `<<<M, 128, 0, stream>>>` 把外层行循环展开成了 `M` 个并行 **CTA**（Cooperative Thread Array，协作线程阵列，代码写作 `block`）的缘故。每个 CTA 派 128 个 **thread**（线程）分段累加一行的 `K` 列。每个线程按步长 128 循环 `8,192 ÷ 128 = 64` 轮，各读 128 B 的 `W` 与 128 B 的 `x`（全块合读一行 16 KiB 的 `W` 与 16 KiB 的 `x`）。

```cuda
// 省去了 #include <cuda_bf16.h> 与显存分配；stream 为已创建的命令流队列
__global__ void gemv_kernel(const __nv_bfloat16* W, const __nv_bfloat16* x,
                            float* y, int K) {                 // → 第 1 章, 第 2 章
    __shared__ float smem[128];                                // → 第 3 章
    int row = blockIdx.x;                                      // → 第 2 章
    int tid = threadIdx.x;                                     // → 第 3 章, 第 4 章
    float acc = 0.0f;                                          // → 第 3 章, 第 5 章
    for (int k = tid; k < K; k += blockDim.x) {
        acc += __bfloat162float(W[row * K + k])                // BF16 转 FP32
             * __bfloat162float(x[k]);                         // → 第 5 章, 第 6 章
    }
    smem[tid] = acc;
    __syncthreads();                                           // → 第 3 章
    if (tid == 0) {                                            // → 第 4 章
        float sum = 0.0f;
        for (int i = 0; i < blockDim.x; ++i) sum += smem[i];
        y[row] = sum;
    }
}
gemv_kernel<<<M, 128, 0, stream>>>(W, x, y, K);                // → 第 1 章..第 3 章
```

如图 0.5-1 所示，用 row 与 tid 滑块选定一个线程并播放时间轴，即可查看它每一步的公式、张量与读数。例如 `row = 2`、`tid = 5` 的线程读到第 24 轮时，读数第一行为“row = 2 · tid = 5 · 第 24 / 64 轮 · k = 2949”。第二行为“读 W[19333] 与 x[2949]，各 2 B · acc 已累加 24 项”。

## 2. 启动语句与五个关键字各规定了什么？

当 CPU 执行完最后一行启动语句继续往下走时，输出数组 `y` 往往还没有算出来（此时 GPU 可能还没开始算第 0 行）。这是由于启动语句只把命令放进队列就立刻返回，不等 GPU 算完。函数的启动与块内交接遵循下面五组规则。
- `__global__` 与 **kernel**（GPU 函数）。`__global__` 声明 `gemv_kernel` 由 CPU 发起调用、在 GPU 上执行。
- `<<<M, 128, 0, stream>>>` 异步启动与 **stream**（命令流）。前两个参数为 CTA 数 `M = 2,304` 与每 CTA 线程数 `128`。第三个参数为动态共享内存字节数 `0`（本例 `smem[128]` 大小已固定为 `128 × 4 = 512 B`）。第四个参数是顺序命令队列 `stream`，CPU 需读取结果时调用 `cudaStreamSynchronize(stream)` 等待队列做完。
- **grid**（网格）与编号变量。全部 `M` 个 CTA 合称一个 `grid`。每个 CTA 靠 `row = blockIdx.x`（`int32`，`4 B`，位于寄存器）认领 `W` 的第 `row` 行。每个 thread 靠块内编号 `tid = threadIdx.x`（`0..127`）与块宽 `blockDim.x`（`128`）在每轮访问列 `k = tid + 128 * (r - 1)`。
- 三种变量空间。指针 `W, x, y`（各 `8 B` 64 位地址）指向所有 CTA 可读写的 **global memory**（全局内存，位于 HBM）。`__shared__ float smem[128]`（FP32，占 `512 B`，位于片上共享内存）仅当前 CTA 的 128 个 thread 共享读写。`row, tid, acc`（`acc` 为 FP32，`4 B`）为每个 thread 独占的私有寄存器变量。
- `__syncthreads()` 块内同步与 **reduction**（归约）。第 `tid` 号线程算完 64 轮后执行 `smem[tid] = acc`，把寄存器里的部分和写进片上 `smem [128]`（FP32，`512 B`）。`__syncthreads()` 先作为执行同步屏障等本块 128 个 thread 全部到达。它同时是本 CTA 的 **memory fence**（内存栅栏），保证 `smem` 写入对全块可见后再交给 `tid == 0`。最后 0 号线程执行 `sum = sum_{i=0}^{127} smem[i]`（至少 512 个周期，其余 127 个线程空等），把归约结果 `sum`（FP32，`4 B`）写回 HBM 的 `y[row]`。

## 3. 双轨起点：`T = 1` 的 `gemv`（`v0 → v1`）与 `T = 8..256` 的 `qkv_gemm`（`g0`）基线

在 `qkv_gate`（`M = 2304, K = 8192`）上，当 `T = 1` 时，最朴素的 **v0** 启动 `<<<18, 128, 0, stream>>>`（`2,304 ÷ 128 = 18`），全卡共 2,304 个线程，每个线程独自循环 8,192 步算完 1 行。本章的 **v1**（上方 `gemv_kernel`）启动 `<<<2304, 128, 0, stream>>>`，改为每行 1 个 128 线程的 CTA。

```cuda
// v0：每个线程独自算完 1 行（int row = blockIdx.x * 128 + threadIdx.x;）
for (int k = 0; k < K; ++k) acc += __bfloat162float(W[row * K + k]) * __bfloat162float(x[k]);
// v1：1 个 CTA 的 128 个相邻线程协作分段读同一行（见第 1 节完整代码）
for (int k = tid; k < K; k += 128) acc += __bfloat162float(W[row * K + k]) * __bfloat162float(x[k]);
```

v0 只有 18 个 CTA，全卡 132 个 **SM**（Streaming Multiprocessor，流式多处理器，即执行指令的独立处理器）里只有 18 个分到工作，且相邻线程读的地址相隔一整行（16 KiB）。v1 的取舍如下：
- 得到什么：派出 2,304 个 CTA 铺满全部 132 个 SM，并让每个 CTA 的 128 个相邻线程紧挨着读同一行的相邻元素（见第 2、3 章）。H200 实测（每次迭代前写 512 MiB 清空缓存的冷缓存中位数，下同）：`675.71 → 58.88 µs`（**11.5×**），约为 7.9 µs 下界的 `13.4%`。
- 付出什么：每个 CTA 新增 `512 B` 共享内存（每线程寄存器从 29 个变为 22 个）、1 次 `__syncthreads()` 块内屏障与 0 号线程的 128 步串行归约，且输入向量 `x`（`16 KiB`）被 2,304 个 CTA 重复读取。
- 什么时候变成亏本：当词元数 `T` 增大到多词矩阵乘时，每线程标量乘加与重复拆包会卡死发射槽（见第 5 章第 2 节）。

在本书 `gemv` 计时程序（队列预先排满、CUDA 事件包裹单次启动）下，空 kernel 的启动加事件计时固定开销为 3.68 µs（第 1 章图 1-1 的 4.7 µs 则是另一项单次流启动含事件计时的独立微基准）。后续各版本 `gemv` 的实测都含这 3.68 µs 固定开销，所以单次实测达不到下界的 100%。把图 0.5-1 的时间轴拖到最后一步，读数写着“整个 kernel 实测 58.88 µs（下界 7.9 µs 的 13.4%）”。

当同一个 `qkv_gate` 的词数扩大到 `T = 8 | 32 | 128 | 256` 时，第一部分同时追踪第二条矩阵乘演化链 **`qkv_gemm`（`g0 → g5`）**。其起点 **`g0`** 直接调用 `torch.matmul(X, W.t(), out=Y)`（底层由 cuBLASLt 派发 `nvjet` 矩阵乘核，并在 `T ≤ 128` 时把求和维 `K` 切成多段并行算完后再额外启动一次 `splitKreduce` 归约核，见第 1 章第 4 节与第 2 章第 1 节）。在 H200 单图重放（干净只读 512 MiB 冲刷，含约 `4.96 µs` 空图开销）下，`g0` 在 `T = 8 | 32 | 128 | 256` 的实测中位数依次为 **`18.20 | 18.60 | 21.32 | 22.90 µs`**（如何在第 1–6 章一步步超越它，见第 1 章第 4 节起）。

---

**带走一句话：** v1 用 2,304 个 128 线程 CTA 铺满全卡 132 个 SM，使 `qkv_gate` 实测耗时从 675.71 µs 降到 58.88 µs（11.5 倍）。
