## 1. CUDA 怎样把 $y = Wx$ 的行循环变成并行？

**外层的行循环消失了：每一行分给一组线程，一共 2,304 组，分批驻留到 132 个 SM 上；每一行内部的 8,192 列，则由组里的 128 个线程分工累加。**

我们要算的是导引二阶段 1 里的矩阵乘向量 $y = W x$：$\shape{W}{2304,\ 8192}{BF16}$ 和 $\shape{x}{8192}{BF16}$ 都放在 HBM 里，输出的第 $r$ 行是 $y_r = \sum_{k=0}^{8191} W_{r,k}\, x_k$。我们把行数记作 $M = 2{,}304$，列数记作 $K = 8{,}192$。为了让代码尽量简短，下面这段程序把输出 $y$ 直接写成了 FP32；真实的阶段 1 会写成 BF16，并按列切成 `q`、`k`、`v`、`gate` 交给阶段 2。代码每一行末尾的箭头，指向后面专门拆解那一行硬件机制的章节。

```cuda
// 省去了 #include <cuda_bf16.h> 与显存分配；stream 是已经创建好的 CUDA 流
__global__ void gemv_kernel(const __nv_bfloat16* W, const __nv_bfloat16* x,
                            float* y, int K) {
    __shared__ float smem[128];                                // → 第 3 章
    int row = blockIdx.x;                                      // → 第 2 章
    int tid = threadIdx.x;                                     // → 第 3 章
    float acc = 0.0f;                                          // → 第 3 章
    for (int k = tid; k < K; k += blockDim.x) {
        acc += __bfloat162float(W[row * K + k])                // → 第 3 章（读）, 第 6 章（转换）
             * __bfloat162float(x[k]);                         // → 第 5 章（乘加）
    }
    smem[tid] = acc;
    __syncthreads();                                           // → 第 4 章
    if (tid == 0) {                                            // → 第 4 章
        float sum = 0.0f;
        for (int i = 0; i < blockDim.x; ++i) sum += smem[i];
        y[row] = sum;
    }
}
gemv_kernel<<<M, 128, 0, stream>>>(W, x, y, K);                // → 第 1 章, 第 2 章
```

我们从上往下读一遍这段代码。函数开头的 `__global__` 把它标记成一个 **kernel**——也就是由 CPU 发起一次启动、在 GPU 上由成千上万个线程同时执行的函数。CUDA 把协同处理同一块任务的一组线程叫作一个 **CTA**（cooperative thread array，代码里叫 `block`），一次启动开出来的全部 CTA 合起来叫 **grid**。最后一行启动语句一口气开出 $M = 2{,}304$ 个 CTA，每个 CTA 里装 128 个**线程**（**thread**），每个线程都从头到尾跑一遍这段函数（每 CTA 取 128 个线程只是本章的起步选法，为什么选 128 本章没有查明，也没有调参比较；CTA 大小怎样决定单个 SM 的驻留数，见第 3 章第 1 节）。在循环内部，`__bfloat162float` 先把读进来的 2 字节 BF16 升宽成 4 字节 FP32，再乘加进线程自己的 `acc` 里，防止 8,192 项连加丢精度。

你看，写 CPU 代码时我们要写一层外层循环，按时间一行一行往下扫；到了 CUDA 里，这层外层循环直接被摊平了，变成 2,304 个 CTA，一行分一个。片上的**硬件派发器**（hardware dispatcher）会把这些 CTA 按批派发到 **SM**（streaming multiprocessor，流式多处理器）上执行。SM 是 GPU 上真正执行指令的计算核心，一张 H200 上有 **132** 个 SM；每一个 CTA 从启动到结束都固定在同一个 SM 上跑。不过每个 SM 同时能驻留的 CTA 个数是有上限的，一时塞不下的 CTA 就得在外面排队，等前面的 CTA 跑完腾出位置再顶上去（一个 SM 到底能塞几个、为什么，见第 2 章第 1 节和第 3 章第 1 节；本章第 7 节会算排在后面的还剩几个 CTA）。

## 2. 每个线程怎样知道自己该算哪一段？

**靠硬件给每个线程的内置坐标：`blockIdx.x` 标出它在第几个 CTA，`threadIdx.x` 标出它在组里排第几，`blockDim.x` 是每个 CTA 的线程数，循环每步就跨这么远。**

成千上万个线程跑的是同一份代码，每个线程怎么知道自己该读哪个数？全靠硬件放在**内置特殊寄存器**里发给每个线程的坐标。先看 `row = blockIdx.x`：CTA 的编号从 $0$ 排到 $2{,}303$，直接对应这个 CTA 认领的 $W$ 行号。再看 `tid = threadIdx.x`（$0..127$）和 `blockDim.x`（128）：它们把同一行的列分给了 CTA 里的 128 个线程。在第 $r$ 轮循环（$r = 1..64$）里，`tid` 号线程去读的列号就是 $k = \mathrm{tid} + 128\,(r - 1)$。

一行共有 8,192 列，由 128 个线程分着读，每个线程正好跑 $8{,}192 / 128 = 64$ 轮；64 轮跑完，128 个线程合起来刚好读完一整行 16 KiB 的 $W$ 和 16 KiB 的 $x$。更重要的是，在每一轮循环里，编号相邻的线程读的也是同一行里紧挨着的地址，128 个线程合起来正好盖住连续的 256 B。硬件把每 32 个相邻线程编成一个 **warp**（线程束）一起发读指令，而显存每次请求至少搬回 **32 B** 的一小段（一个 warp 怎么发读指令、硬件怎么把相邻地址合并成更少的请求，我们在第 3 章第 1–2 节细讲）：这里 1 个 warp 的 32 个相邻线程在同一轮紧挨着读 $32 \times 2\ \text{B} = 64\ \text{B}$，刚好落在 2 个 32 B 小段上。反过来（由代码步幅与 32 B 最小请求段推导），要是改成让每个线程各包一段连续的 64 列，相邻两个线程在同一轮读的地址就会隔开 64 列（128 B），一条 warp 读指令便会散落到彼此分开的多个 32 B 小段上——这正是第 6 节在 `v0` 上讲的分散读取形态。

你可以在图 导三-1 里把滑块拉到 `row = 2`、`tid = 5`、第 24 轮（$r = 24$），亲手核对一下这个公式：这一轮它读的列号是 $k = 5 + 128 \times 23 = 2{,}949$，取出来的两个元素分别是 `W[2 * 8192 + 2949] = W[19333]` 和 `x[2949]`。

## 3. 128 个部分和怎样安全地加成一个数？

**每个线程把部分和写进本 CTA 共享的 `smem`，`__syncthreads()` 等 128 个线程都写完才放行，再由 0 号线程加起来写回 $y_r$。**

代码里的三类变量各自住在不同的存储层。`row`、`tid`、`acc` 放在**寄存器**（**register**）里，每个线程各管自己那一份。`__shared__ float smem[128]`（$128 \times 4\ \text{B} = 512\ \text{B}$）住在芯片上的**共享内存**（**shared memory**）里，同一个 CTA 里的 128 个线程都能读写它，而别的 CTA 看不见（这两级片上存储见第 3 章第 1 节）。至于 `W`、`x`、`y`，它们住在 HBM 的**全局内存**（**global memory**）里，所有 CTA 都能读写。

把许多份部分和汇总成一个总和，这一步叫**归约**（**reduction**）。由于各线程的 `acc` 分别留在各自的私有寄存器中，这版代码通过共享内存 `smem` 把 128 个部分和聚到一起：每个线程先写一句 `smem[tid] = acc`。

紧接着就是一句 `__syncthreads()`（块内屏障）。它像一道闸门，把本 CTA 的 128 个线程拦在这一行，等所有人都写完了才一起放行；跨过这道屏障之后，刚才 128 个线程写进 `smem` 的数，本 CTA 里的每一个线程就都能稳稳读到了。注意这道屏障只管同一个 CTA 内部；如果要在不同 CTA 之间交换数据，得用另一套同步规矩（见第 2 章第 6 节）。如果省掉这句 `__syncthreads()`，0 号线程去读 `smem[i]` 的时候，第 `i` 号线程可能还没把自己的部分和写进去。

跨过屏障之后，只留 0 号线程把 `smem[0..127]` 挨个加起来写回 `y[row]`；其余 127 个线程直接退出，但整个 CTA 的驻留槽位和 512 B 共享内存还得一直占着，直到 0 号线程算完才能释放。因为同一批上场的 CTA（无论第一批还是排在后面的尾批）几乎同时起步，也会在差不多的时刻一起走完 64 轮读数来到这一步，这时同一个 SM 上可能没有别的 CTA 还在发显存读请求，也就可能已经没有别的**在途读取**（已发出但数据还没回来的显存读请求，见导引二第 4 节）能拿来重叠掩盖这段串行加法了，它才可能落进总耗时里。

把第 1–3 节出现的软件概念和硬件单元拢成一张对照表，这版 `gemv_kernel`（`v1`）在芯片上的规模和归属就一目了然了：

| 软件概念 / 变量 | 对应的硬件单元 | 这版 `gemv_kernel`（`v1`）里的数量或大小 | 谁能访问 / 驻留规矩 |
| :--- | :--- | :--- | :--- |
| **CTA**（`block`） | 单个 **SM** 上的驻留槽位 | 每行 1 个 CTA（全 **grid** 共 2,304 个 CTA、294,912 个线程） | 整个 CTA 固定在同一个 SM 上跑完；每 SM 同时驻留的 CTA 数有上限（具体几个见第 2 章第 1 节、第 3 章第 1 节） |
| **warp**（线程束） | SM 内一起发读指令的一组相邻线程 | 每 32 个相邻线程 1 个 warp，每 CTA **4 个 warp** | 每轮合读连续 64 B 的 $W$ 和 64 B 的 $x$（见第 3 章第 1–2 节） |
| **线程**与局部变量（`row`、`tid`、`acc`、`k`、`sum`） | 线程私有**寄存器**（register） | 每 CTA **128 个线程**；机器码实测每线程占 **22 个寄存器**（编译器连同地址与中间值一起分配，见第 3 章第 1 节） | 仅该线程自己可见 |
| `__shared__ float smem[128]` | 片上**共享内存**（shared memory） | 每 CTA **512 B**（128 个 FP32；驱动另留系统开销见第 3 章第 1 节） | 本 CTA 的 128 个线程共享读写，别的 CTA 看不见；配 1 次 `__syncthreads()` 块内屏障 |
| `W`、`x`、`y` | 片外 HBM 的**全局内存**（global memory） | $W$：**37.75 MB**（每行 16 KiB）；$x$：**16 KiB**；$y$：**9,216 B**（每行 4 B） | 所有 SM 上的所有 CTA 都能读写 |

这种由 0 号线程串行收尾的写法算出来的 $y_r$ 完全正确，付出的三笔代价（每 CTA 512 B 共享内存、1 次块内屏障、128 次前后相依的串行加法）合起来在 `v1` 里也很小——按编译后机器码的停顿计步估算，每个 CTA 这段收尾约 970 个周期（按约 1.8 GHz 折算约 **0.54 µs**；这是机器码计步估算，不是实测计时，这一项耗时我们没有单独拆出来测）。后面到第 4 章第 5–6 节，我们会看怎么让线程并行做归约。

## 4. 启动语句做了什么，$y$ 什么时候算好？

**启动语句只把命令放进 CUDA 流就立刻返回，这时 $y$ 还没算；默认情况下，同一个 CUDA 流里后一个 kernel 一定看得到前一个写的数据。**

再看最后一行 `gemv_kernel<<<M, 128, 0, stream>>>` 里的三重尖括号。第一个参数是这次启动开出的 CTA 个数 $M = 2{,}304$；第二个参数是每个 CTA 里的线程数 128；第三个参数是这次启动给每个 CTA 额外动态申请的共享内存字节数，这里用不着，直接传 0；第四个参数则是目标 **CUDA 流**（按入队顺序依次执行的一条 GPU 命令队列，代码里的变量名就叫 `stream`）。调用这行启动语句时，CPU 只是往队列里塞了一条命令就立刻往下走了，根本不等 GPU 算完——这种机制叫**异步启动**。

在默认设置下，同一个 CUDA 流里的命令严格按入队顺序执行，前一个 kernel **happens-before**（先行发生于）后一个 kernel：你不需要额外写任何同步代码，后一个 kernel 就一定能看见前一个 kernel 写进显存的数据。如果 CPU 自己要等结果算完，就调用 `cudaStreamSynchronize(stream)`，把 CPU 拦住直到这条流排空。把这一层的启动命令补回第 3 节的落位表：

| 软件概念 / 变量 | 对应的硬件单元 | 这版 `gemv_kernel`（`v1`）里的数量或大小 | 谁能访问 / 驻留规矩 |
| :--- | :--- | :--- | :--- |
| 一次启动命令与 **grid** | **CUDA 流** → 整张 GPU（**132 个 SM**） | 1 条启动命令，开出 **2,304 个 CTA**（共 294,912 个线程） | CPU 入队后立刻返回；流内默认按入队顺序执行 |

## 5. 这里的耗时是怎么量的，里面有什么不属于 kernel？

**每轮测量先冲刷片上缓存，再用 GPU 事件卡住单次启动、连测 500 次取中位数；哪怕启动一个空 kernel，这里面也带有约 4.6 µs 的固定开销。**

第一部分里所有 gemv 版本都按同一套规矩计时：每次启动计时之前，我们先去读一块 **512 MiB** 毫不相干的数据，把芯片上的高速小存储（**片上缓存**）彻底冲掉，逼着 GPU 真的从 HBM 里把 $W$ 读进来。接着，我们在一次启动的一头一尾各打一个 **GPU 事件**（也就是让 GPU 在 CUDA 流里记下两个时间戳），先预热 20 次，再连测 500 次取中位数。每次先冲掉缓存，正好对应导引二里单请求 decode 的真实处境（为什么一致，见第 2 章第 2 节）。

如果我们用一模一样的办法去量一个什么都不干的空 kernel（1 个 CTA、32 个线程），实测耗时同样要约 **4.6 µs**——本书把这笔底数叫作**固定开销**。注意计时脚本在打起始事件之前已经先让 GPU 流排满等待，因此主机侧 CPU 把启动命令塞进队列的时间并不在这 4.6 µs 里；它纯粹是 GPU 侧起止两个事件记录时间戳，连同负责接收命令流、下发网格的 **GPU 前端**处理这次空启动并跑完的底数（至于里面事件打点与 GPU 前端处理空网格各自占多少，我们没有测，第 10 章第 1 节会再对比事件计时与剖析器计时的差值）。第一部分报告的所有实测耗时都原样包含这 4.6 µs，不做扣除；而导引二算出来的 7.86 µs 带宽下界是不含它的。在连续启动的多个 kernel 之间还会有别的交接开销，见第 1 章第 1 节。

## 6. 为什么一行派一组线程，而不是一个线程？（gemv v0 → v1）

**每线程算一行的写法只开出 18 个 CTA，132 个 SM 大多闲着，而且相邻线程读的地址隔着一整行；改成每行一个 CTA 后快了约 12.5 倍。**

接下来我们给 gemv 的每个演进版本依次编号，拿 **v0** 当起点。如果照搬写 CPU 循环的直觉，最容易写出来的 v0 是让每个线程各自包揽一整行：`row = blockIdx.x * 128 + threadIdx.x`，启动 `<<<18, 128, 0, stream>>>`（$2{,}304 / 128 = 18$ 个 CTA），每个线程自己在那一行的 8,192 列上从头加到尾。而 **v1** 就是第 1 节那段代码，启动 `<<<2304, 128, 0, stream>>>`，每一行派一整组 128 线程的 CTA 上去合算：

```cuda
// v0：每个线程独自算完 1 行（int row = blockIdx.x * 128 + threadIdx.x;）
for (int k = 0; k < K; ++k) acc += __bfloat162float(W[row * K + k]) * __bfloat162float(x[k]);
// v1：1 个 CTA 的 128 个相邻线程协作分段读同一行（见第 1 节完整代码）
for (int k = tid; k < K; k += 128) acc += __bfloat162float(W[row * K + k]) * __bfloat162float(x[k]);
```


足足 12.5 倍的差距，出在两个地方。第一是 SM 绝大部分都空着：硬件按 CTA 为单位把活派到 SM 上（怎么分派见第 2 章第 1 节），v0 一共才开出 18 个 CTA，最多只能让 132 个 SM 里的 18 个干活，剩下 114 个 SM 全程旁观。

第二是读显存的步幅。如第 2 节所说，一个 warp 里的 32 个相邻线程会一起发出一条读指令，而显存每次请求至少搬回 32 B 的一小段（合并读取见第 3 章第 2 节）。在 v0 里，这 32 个线程要读的是 32 个彼此隔着整整一行（16 KiB）的地址：一条读指令被迫向片上请求 $32 \times 32 = 1{,}024$ B，当轮却只用上了其中的 64 B。搬回来的每个 32 B 小段里装着那一行接下来的 16 个 BF16，本轮只拿走 1 个；其余 15 个要等后面 15 轮才用，到时候也许还留在片上缓存里（紧接着隔一段就用剖析器读数核对这一点，片上缓存细节见第 3 章第 2 节）。

换到 v1 之后，同样的 32 个相邻线程在同一轮读的是紧挨着的 64 B：每次只需要搬回 2 个 32 B 小段，搬回来的每一个字节当轮全部派上用场。

芯片在片外 HBM 上会为这些额外请求买单吗？不会。先看 $W$ 的读取：v0 那 16 倍的小段扇出并没有让片外 HBM 真的搬运 16 遍 $W$。在首轮锁基准频率的剖析器冷启动测量中（剖析器会把 SM 时钟锁在较低的基准频率，因此它测出的 862.05 µs 和下文 v1 的 56.54 µs 都比第 5 节不锁频的事件计时更长），v0 耗时 862.05 µs、HBM 带宽占用为 0.9%，和只把 37.75 MB 的 $W$ 搬一次算出来的 $37.75\ \text{MB} \div 862.05\ \mu\text{s} = 43.8\ \text{GB/s}$（占 4.8 TB/s 的 0.91%，由实测推导）吻合——也就是说整块片上缓存把后面 15 轮要用的元素接住了，片外 HBM 实际搬运量仍约为 1 遍 $W$。

再看 $x$ 的读取：在 v0 里，同一个 warp 的 32 个线程在同一轮读的是同一个 `x[k]`，相当于 32 行共享一次读取；而在 v1 里，每个 CTA 都要自己读一遍 16 KiB 的 $x$，2,304 个 CTA 合起来发出的 $x$ 读取请求量跟 $W$ 一样都是 37.75 MB，不过片上缓存同样接住了这些重复请求，片外 HBM 依然只搬约 1 遍 $W$（同样由首轮锁基准频率的剖析器实测推导：v1 耗时 56.54 µs、HBM 带宽占用 14.2%，与只搬 1 遍 $W$ 的 13.9% 吻合；缓存细节见第 2 章第 2 节）。

此外还有一处编译器联动变化：经机器码核实，编译器把 v0 的内层循环展开了 16 倍——在第一次使用读回的数据之前先交替发出 13 条 $W$ 和 $x$ 的 2 B 读指令，其中属于 $W$ 的约 7 条（单线程同时挂起约 $7 \times 2\ \text{B} = 14\ \text{B}$ 的 $W$ 读取），却没有展开 v1（单线程仅 $1 \times 2\ \text{B}$；为什么编译器展开了 v0 却没有展开 v1，本章没有查明）。不过硬件实测本核在每个 SM 上最多同时驻留 **16 个 CTA**（为什么上限偏偏是 16 个，见第 3 章第 1 节）：v0 全卡只有 18 个 CTA，按 132 个 SM 平摊下来每 SM 在途 $W$ 字节估算只有 $18 \times 128 \times 14\ \text{B} \div 132 \approx$ **0.2 KiB/SM**；而 v1 第一批铺满全部 132 个 SM、每 SM 驻满 16 个 CTA（每 CTA 单轮合读 $128 \times 2\ \text{B} = 256\ \text{B}$），每 SM 在途 $W$ 字节反而涨到了 $16 \times 256\ \text{B} =$ **4.0 KiB/SM**。

把两版的所有账目摆进同一张表里，得失一眼就能看清（把一行从 1 个线程改成 1 个 CTA 同时改变了驻留 SM 数、读取步幅、编译器展开倍数与块内归约，因此这 **12.5 倍**提速里“铺满 132 个 SM”和“合并连续读取”各自占多少，我们**没有单独拆开测**）：

| 对比项 | `gemv v0`（每行 1 个线程） | `gemv v1`（每行 1 个 CTA = 128 线程） | 依据与说明 |
| :--- | :--- | :--- | :--- |
| 启动规模（CTA 数 × 每 CTA 线程数） | `18 × 128`（共 2,304 线程） | `2,304 × 128`（共 294,912 线程） | 代码给定 |

| 实测耗时（含约 4.6 µs 固定开销） | **674.58 µs** | **54.08 µs**（快约 **12.5 倍**；各子项拆分占比**没有测**） | 第 5 节干净事件计时实测 |

## 7. 为什么 v1 还是比 7.86 µs 下界慢约 7 倍？

**后面四章由外向内要拆开的四笔开销拦在前面：单次启动约 4.6 µs 的固定开销、最后 192 个 CTA 要再跑第二波 64 轮、每 SM 同时在途的 $W$ 读取字节太少，外加一小段串行归约收尾。**

回头看第 6 节的图表：就算快了 12.5 倍，v1 的实测耗时（54.08 µs）依然是 7.86 µs 下界的约 7 倍（6.88 倍）；哪怕扣掉 4.6 µs 的固定开销，它读 $W$ 的估算有效带宽也只有约 0.76 TB/s，约占 4.8 TB/s 的六分之一。为什么铺满了 132 个 SM、读的也是连续地址，却还是差这么远？后面四章会由外向内逐一拆解这四笔账：
- **单次启动带约 4.6 µs 固定开销（实测，见第 1 章第 1–3 节）**：目前已占 v1 总耗时的 8.5%，kernel 本体越压越短时它会越来越显眼。
- **最后一批 192 个 CTA 要再跑第二波 64 轮（见第 2 章第 1 节与第 7 节）**：如第 6 节所说，硬件实测本核每个 SM 最多同时驻留 **16** 个 CTA（为什么上限偏偏是 16 个，见第 3 章第 1 节），第一批最多装 $132 \times 16 = 2{,}112$ 个，扣掉后还剩 $2{,}304 - 2{,}112 =$ **192 个 CTA** 排在后面（由实测单 SM 驻留上限推导），等前一批腾出槽位后还得从头再走完一整条 64 轮串行读取链。
- **每个 SM 同时挂在路上的 $W$ 字节太少（见第 2 章第 3 节、第 3 章第 3 节、第 4 章第 3 节）**：在单线程内部，每一轮的乘加 `acc += ...` 都必须等这一轮的 `W[...]` 和 `x[k]` 两笔读取全都回到寄存器后才能执行；而且经机器码核实，编译器没有把 `v1` 这层跨 128 列的循环展开去提前发下一轮的读，所以单个线程同一时刻挂在路上的 $W$ 读取只有 $1 \times 2\ \text{B}$（即图 导三-1 第 4 步卡所写；指令按顺序发射见第 4 章第 2 节），算满一个 SM（$16 \times 256\ \text{B}$）也只有约 **4.0 KiB/SM**（由机器码估算），远低于跑满 HBM 带宽平台所需的几十 KiB/SM 量级（实测 16 B 读取达平台 95% 需 24–40 KiB/SM，到 64 KiB/SM 已超 98%，见第 2 章第 3 节），导致 64 轮循环几乎每一轮都在干等显存往返。
- **0 号线程的 128 次串行加法收尾（估算约占 2%，没有单独拆测，见第 4 章第 5–6 节）**：每个 CTA 约 0.54 µs（机器码停顿计步估算），就算前后两批 CTA 都把它暴露出来也只约 1.1 µs（约占 v1 总耗时 54.08 µs 的 2%），占比较小。

把这几笔账合起来粗对一下总耗时：第 2 章第 2 节按空载 HBM 往返约 0.33 µs 粗算，单批 64 轮串行读取链约 $64 \times 0.33 \approx 21\ \mu\text{s}$，前后两波共约 $2 \times 64 \times 0.33 + 4.6 \approx 47\ \mu\text{s}$（估算，比实测 54.08 µs 少约 7 µs；两波各自的实际耗时与四项加总拆分都没有直接打时间戳单测，第 2 章第 7 节会再用 `v1` 与 `v3` 的实测差框定两波的上下界）。

**带走一句话：** CUDA 把外层循环摊成 2,304 个分批上 SM 的 CTA；让一组相邻线程合算一行，才铺得满 132 个 SM、读得到连续的字节。
