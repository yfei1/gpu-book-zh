## 1. 计算 `qkv_gate`（`y = W · x`）的核心 CUDA 代码

<!-- FIG ch00_5-a: 图 0.5-1 左栏显示 gemv_kernel 源码与启动语句，右栏画出语言层面的三重并行嵌套框（Grid -> 单个 CTA -> 单个 thread）与全局内存 W/x/y（移动块对应第 row 号 CTA 的第 tid 号线程读取 W[row * K + k] 与 x[k] 累加进 acc、再经 smem[tid] 归约写出 y[row] 的算法步）。 -->

在 CPU 上写矩阵乘向量 `y = W · x`，最外层总会写一个遍历 `row = 0..M-1` 的行循环。但在下面的 CUDA 函数里，这个外层循环不见了。**CUDA 编程的核心做法，就是把原本在时间上顺次跑的外层循环，直接展开成空间上同时跑的一组并行线程块。**

在 62 层模型的每一层里，阶段 1（`qkv_gate`）都是单层数据流的起点。当 `T = 1` 时，它要对 `row = 0..2303` 计算内积 `y[row] = sum_{k=0}^{8191} float(W[row, k]) * float(x[k])`。输入是 HBM 里的权重 `W`（`[2304, 8192]`，BF16，37.7 MB）与入口激活 `x`（`[8192]`，BF16，16 KiB）。输出是写回 HBM 的 `y [2304]`（下例为突出主干写成 FP32 占 9,216 B，真实阶段 1 为 BF16 占 4,608 B），算完后切分为 `q | k | v | gate` 交给阶段 2（P1 注意力）。

为了并行算完这 `M = 2,304` 行，启动语句 `<<<M, 128, 0, stream>>>` 把外层行循环展开成了 `M` 个并行的 **CTA**（Cooperative Thread Array，协作线程阵列，代码里写作 `block`，即共同处理一块任务的一组线程）。每个 CTA 认领矩阵的 1 行，再派出 128 个 **thread**（执行代码的单个线程）分段累加这一行的 `K = 8,192` 列。每个线程按步长 128 循环 `8,192 ÷ 128 = 64` 轮，各自读取 128 B 的 `W` 与 128 B 的 `x`（全块 128 个线程合起来读完一行 16 KiB 的 `W` 与 16 KiB 的 `x`）。

```cuda
// 省去了 #include <cuda_bf16.h> 与显存分配；stream 为已创建的命令流队列
__global__ void gemv_kernel(const __nv_bfloat16* W, const __nv_bfloat16* x,
                            float* y, int K) {                 // → 第 1 章, 第 2 章
    __shared__ float smem[128];                                // → 第 3 章
    int row = blockIdx.x;                                      // → 第 2 章
    int tid = threadIdx.x;                                     // → 第 3 章, 第 4 章
    float acc = 0.0f;                                          // → 第 3 章, 第 5 章
    for (int k = tid; k < K; k += blockDim.x) {
        acc += __bfloat162float(W[row * K + k])                // BF16 转 FP32
             * __bfloat162float(x[k]);                         // → 第 5 章, 第 6 章
    }
    smem[tid] = acc;
    __syncthreads();                                           // → 第 3 章
    if (tid == 0) {                                            // → 第 4 章
        float sum = 0.0f;
        for (int i = 0; i < blockDim.x; ++i) sum += smem[i];
        y[row] = sum;
    }
}
gemv_kernel<<<M, 128, 0, stream>>>(W, x, y, K);                // → 第 1 章..第 3 章
```

如图 0.5-1 所示，用 `row` 与 `tid` 滑块选定一个线程并播放时间轴，即可查看它每一步的公式、张量与读数。例如 `row = 2`、`tid = 5` 的线程读到第 24 轮时，读数第一行为“row = 2 · tid = 5 · 第 24 / 64 轮 · k = 2949”，第二行为“读 W[19333] 与 x[2949]，各 2 B · acc 已累加 24 项”。

## 2. 启动语句与五个关键字各规定了什么？

上面这段十几行的代码，定下了 GPU 程序从发起到写回结果的五组规则：**CPU 怎么把启动命令放进流队列，每个线程怎么算出自己负责的行号和列号，数据放在哪一级存储里，以及 128 个线程算出来的部分和怎么加到一起。**

- **kernel 与 `__global__`**：**kernel** 是在 GPU 上运行的函数。函数开头的 `__global__` 关键字声明 `gemv_kernel` 由 CPU 发起调用、在 GPU 上执行。
- **stream 与异步启动 `<<<M, 128, 0, stream>>>`**：当 CPU 执行完最后一行启动语句继续往下走时，输出数组 `y` 往往还没有算出来（此时 GPU 可能还没开始算第 0 行）。这是因为启动语句只把命令放进 **stream**（按顺序执行 GPU 命令的流队列）就立刻返回，不等 GPU 算完。在 `<<<M, 128, 0, stream>>>` 中，前两个参数是 CTA 数 `M = 2,304` 与每 CTA 线程数 `128`，第三个参数是动态共享内存字节数 `0`（本例 `smem[128]` 的大小已固定为 `128 × 4 = 512 B`），第四个参数即目标 `stream`。CPU 需要读取结果时，调用 `cudaStreamSynchronize(stream)` 等待队列做完。
- **grid 与内置坐标 `blockIdx.x` / `threadIdx.x` / `blockDim.x`**：**grid** 是同一次启动的全部 `M` 个 CTA 组成的网格。所有线程跑的是同一份代码，靠内置坐标认领各自的任务：每个 CTA 靠 `row = blockIdx.x`（`int32`，`4 B`）认领 `W` 的第 `row` 行；每个 thread 靠块内编号 `tid = threadIdx.x`（`0..127`）与块宽 `blockDim.x`（`128`），在第 `r` 轮循环访问列 `k = tid + 128 * (r - 1)`。
- **三级存储：全局内存、片上共享内存与私有寄存器**：参数指针 `W, x, y`（各 `8 B` 64 位地址）都指向 **global memory**（所有 CTA 都可读写的全局内存，位于 HBM）。`row, tid, acc`（`acc` 为 FP32，`4 B`）存放在每个 thread 独占的私有**寄存器**（register，芯片上直接连着算术单元、读写最快但只有当前线程自己能看的存储格，见第 3 章）里。而 `__shared__ float smem[128]`（FP32，占 `512 B`）位于片上**共享内存**（shared memory，位于芯片上、仅当前 CTA 的 128 个 thread 可共享读写的暂存区，见第 3 章）。
- **reduction 与 `__syncthreads()`（同步屏障兼内存栅栏）**：64 轮算完后，一行的内积还分散在 128 个线程各自的 `acc` 里，需要做一次 **reduction**（归约，把多个部分和汇总成一个值的操作）。第 `tid` 号线程先执行 `smem[tid] = acc`，把寄存器里的部分和写进片上 `smem [128]`（FP32，`512 B`）。因为 128 个线程跑得有快有慢，中间必须调用 `__syncthreads()`：它既是块内执行同步屏障（等本块 128 个 thread 全部到达），又是本 CTA 的 **memory fence**（内存栅栏，保证内存写入对其他线程可见，即保证 `smem` 写入对全块可见后再交给 `tid == 0`）。最后，0 号线程执行 `sum = sum_{i=0}^{127} smem[i]`（128 次顺序加法，其余 127 个线程空等，见第 4 章第 3–4 节），把归约结果 `sum`（FP32，`4 B`）写回 HBM 的 `y[row]`。

## 3. 双轨起点：`T = 1` 的 `gemv`（`v0 → v1`）与 `T = 8..256` 的 `qkv_gemm`（`g0`）基线

既然 `qkv_gate` 有 `M = 2,304` 行，为什么要派 2,304 个 CTA、让 128 个线程分段合算 1 行，而不是直接派 2,304 个线程、让每个线程各自把 1 行 8,192 列从头算到尾？**把这两种写法放到 H200 上一测，耗时差出 11.5 倍：前者（`v0`）要 `675.71 µs`，后者（`v1`）只要 `58.88 µs`。**

在 `qkv_gate`（`M = 2304, K = 8192`）上，当 `T = 1` 时，最朴素的 **v0** 启动 `<<<18, 128, 0, stream>>>`（`2,304 ÷ 128 = 18`），全卡共 2,304 个线程，每个线程独自循环 8,192 步算完 1 行。本章第 1 节的 **v1**（上方 `gemv_kernel`）则启动 `<<<2304, 128, 0, stream>>>`，改成每行派 1 个 128 线程的 CTA。

```cuda
// v0：每个线程独自算完 1 行（int row = blockIdx.x * 128 + threadIdx.x;）
for (int k = 0; k < K; ++k) acc += __bfloat162float(W[row * K + k]) * __bfloat162float(x[k]);
// v1：1 个 CTA 的 128 个相邻线程协作分段读同一行（见第 1 节完整代码）
for (int k = tid; k < K; k += 128) acc += __bfloat162float(W[row * K + k]) * __bfloat162float(x[k]);
```

为什么 `v0` 会慢这么多？这里要先认识芯片上的 **SM**（Streaming Multiprocessor，流式多处理器）。它是 GPU 上执行指令的独立计算单元，一张 H200 上一共有 132 个 SM，每个 CTA 都会被分配到一个 SM 上运行（见第 2 章）。`v0` 一共只派了 18 个 CTA，全卡 132 个 SM 里只有 18 个分到了 CTA，剩下 114 个 SM 完全空着。不仅如此，`v0` 里相邻两个线程分别算相邻两行，同一拍去读的权重地址隔着一整行（16 KiB）。

切成 `v1` 之后，得失直接对应到两组数字上：
- **好处**：派出 2,304 个 CTA 用满全部 132 个 SM（平均每个 SM 分到 17–18 个 CTA），并让每个 CTA 的 128 个相邻线程并排读同一行连续的 256 B（见第 2、3 章）。在 H200 上实测（每次测量前清空缓存，确保从 HBM 重新读取权重，下同），耗时从 `675.71 µs` 降到 `58.88 µs`（快了 **11.5×**），达到 `7.9 µs` 理论下界的 `13.4%`。把图 0.5-1 的时间轴拖到最后一步，读数写着“整个 kernel 实测 58.88 µs（下界 7.9 µs 的 13.4%）”。
- **代价**：每个 CTA 新增了 `512 B` 共享内存、1 次 `__syncthreads()` 块内同步屏障和 0 号线程的 128 次顺序加法；而且输入向量 `x`（`16 KiB`）被 2,304 个 CTA 重复读取（合计读取 `37.7 MB`）。
- **什么时候亏本**：在单词 `T = 1` 下，这点额外开销远小于用满 132 个 SM 和连续访存省下的时间（`675.71 → 58.88 µs`），`v1` 相对 `v0` 没有退化反例（当词数 `T` 增大时在何处切换计算路径，见第 5 章第 2 节）。

看实测数字时还要留心一项固定开销：在本书的 `gemv` 单核计时程序下，就算跑一个什么都不算的空 kernel，发起启动和计时本身也要花 `3.68 µs`（这笔启动开销怎么产生、怎么在整层里省掉，见第 1 章第 1 节）。后续各版本 `gemv` 的单核实测都包含这 `3.68 µs` 固定开销，所以单次实测达不到下界的 100%。

当同一个 `qkv_gate` 的输入词数扩大到 `T = 8 | 32 | 128 | 256` 时，第一部分同时追踪多词矩阵乘演化链 **`qkv_gemm`（`g0 → g5`）**。它的起点 **`g0`** 直接调用 PyTorch 的 `torch.matmul(X, W.t(), out=Y)`（底层调用通用矩阵乘库 cuBLAS）。在 H200 上，`g0` 在 `T = 8 | 32 | 128 | 256` 的实测中位数依次为 **`18.20 | 18.60 | 21.32 | 22.90 µs`**（计时方式见第 1 章第 1 节，如何在第 1–6 章一步步超越它见第 1 章第 4 节起）。

| 演化轨道与版本 | 词数 `T` | 启动配置或调用入口 | 关键特征与固定开销 | H200 实测中位数 |
|---|---|---|---|---|
| `gemv` 朴素版 **v0** | `T = 1` | `<<<18, 128, 0, stream>>>` | 全卡 2,304 线程，每线程独自循环 8,192 步算 1 行；仅用 18/132 个 SM，相邻线程地址相隔 16 KiB；含空核启动与计时固定开销 `3.68 µs` | `675.71 µs` |
| `gemv` 协作版 **v1** | `T = 1` | `<<<2304, 128, 0, stream>>>` | 每行 1 个 CTA、128 线程分段读相邻元素，用满 132 个 SM；每 CTA 多用 `512 B` `smem`、1 次同步屏障、128 次顺序加，`x` 重复读 `37.7 MB`；含 `3.68 µs` 固定开销 | `58.88 µs`（较 v0 快 **11.5×**，为 `7.9 µs` 下界的 `13.4%`） |
| `qkv_gemm` 基线 **g0** | `T = 8 \| 32 \| 128 \| 256` | `torch.matmul(X, W.t(), out=Y)` | 底层调用 cuBLAS 矩阵乘库（计时方式与固定开销见第 1 章第 1 节） | **`18.20 \| 18.60 \| 21.32 \| 22.90 µs`** |

---

**带走一句话：** `v1` 用 2,304 个 128 线程 CTA 用满全卡 132 个 SM，把 `T = 1` 的 `qkv_gate` 实测耗时从 `675.71 µs` 压到 `58.88 µs`（快了 11.5 倍），并与 `T = 8..256` 的 `g0`（`18.20..22.90 µs`）一起构成第一部分的双轨演化起点。
