## 1. CUDA 怎样把 $y = Wx$ 的行循环变成并行？

<!-- FIG ch00_5-a: 图 导三-1 左栏显示 gemv_kernel 源码与启动语句（注释写“stream 是已经创建好的 CUDA 流”），右栏画出同一次启动里的 grid、CTA、thread 与全局内存 W/x/y。步骤 1 卡写“CUDA 流”，代价为“1 条命令，CPU 立刻返回”；步骤 2 代价为“每个 SM 同时放 16 个 CTA（为什么是 16，见第 3 章第 1 节）”；步骤 4 与读数写“第 0 组 32 个线程里的第 5 号”；步骤 6 代价为“1 次块内屏障”；步骤 7 代价为“128 次前后相依的加法，其余 127 个线程空等”；步骤 9 总计为“54.08 µs，下界 7.86 µs 的 14.5%（含 4.6 µs 固定开销）”。保留 row 与 tid 滑块、播放按钮及读数“row = 2 · tid = 5 · 第 24 / 64 轮 · k = 2949 · 读 W[19333] 与 x[2949]”。图注：左边是 kernel 源码，右边是同一次启动里的 CTA、线程和它们读的数据。拖动 row 和 tid，看任一线程每一轮读哪两个数，最后怎样汇总成 y_r。 -->

在 CPU 上算 $y = W x$ 要写两层循环；在 GPU 上，这两层循环去哪了？**外层的行循环不见了：每一行交给一组线程（CTA），2,304 组同时跑；内层的 8,192 列由组里的 128 个线程分着累加。**

要算的是导引二阶段 1 的 $y = W x$：$\shape{W}{2304,\ 8192}{BF16}$ 和 $\shape{x}{8192}{BF16}$ 都在 HBM 里，每一行 $y_r = \sum_{k=0}^{8191} W_{r,k}\, x_k$。把行数记作 $M = 2{,}304$，列数记作 $K = 8{,}192$。下面这段代码为了写得简短，把输出 $y$ 写成 FP32；真实的阶段 1 写出 BF16，再切成 `q`、`k`、`v`、`gate` 交给阶段 2。

```cuda
// 省去了 #include <cuda_bf16.h> 与显存分配；stream 是已经创建好的 CUDA 流
__global__ void gemv_kernel(const __nv_bfloat16* W, const __nv_bfloat16* x,
                            float* y, int K) {                 // → 第 1 章
    __shared__ float smem[128];                                // → 第 3 章
    int row = blockIdx.x;                                      // → 第 2 章
    int tid = threadIdx.x;                                     // → 第 3 章
    float acc = 0.0f;                                          // → 第 3 章
    for (int k = tid; k < K; k += blockDim.x) {
        acc += __bfloat162float(W[row * K + k])                // → 第 3 章（读）, 第 6 章（转换）
             * __bfloat162float(x[k]);                         // → 第 5 章（乘加）
    }
    smem[tid] = acc;
    __syncthreads();                                           // → 第 4 章
    if (tid == 0) {                                            // → 第 4 章
        float sum = 0.0f;
        for (int i = 0; i < blockDim.x; ++i) sum += smem[i];
        y[row] = sum;
    }
}
gemv_kernel<<<M, 128, 0, stream>>>(W, x, y, K);                // → 第 1 章, 第 2 章
```

从上往下看这段代码：函数开头的 `__global__` 声明这是一个 **kernel**（在 GPU 上跑、由 CPU 发起的函数）。最后一行启动语句一次开出 $M = 2{,}304$ 个 **CTA**（cooperative thread array，一起处理一块任务的一组线程，代码里叫 `block`；同一次启动的全部 CTA 合称 **grid**），每个 CTA 里有 128 个 **thread**（执行这段代码的一个线程）。函数内部，`row` 标出这个 CTA 负责哪一行，`tid` 标出当前是组里的第几个线程；循环里每个线程每隔 128 列取一个数，用 `__bfloat162float` 把 2 字节的 BF16 转成 4 字节的 FP32 再乘加进自己的 `acc`（转换在硬件上花多少，见第 6 章）；循环结束后，把 128 个部分和合起来，由 0 号线程写出 $y_r$。

CUDA 的做法，是把原来按时间一行一行走的外层循环，摊成同时存在的 2,304 个 CTA。GPU 把这 2,304 个 CTA 一个一个分到 **SM** 上去跑。SM（streaming multiprocessor）是执行指令的计算单元，H200 上有 **132** 个；一个 CTA 从头到尾只在一个 SM 上跑。怎样分派见第 2 章第 1 节，SM 内部见第 3 章第 1 节。

代码最后一行把这 2,304 个 CTA 交给了 GPU。这一行执行完时，$y$ 算好了吗？

## 2. 启动语句做了什么，$y$ 什么时候算好？

启动语句执行完以后，$y$ 什么时候才能被下一个 kernel 安全地读到？**还没有：启动语句只把一条命令放进 CUDA 流就返回；同一个 CUDA 流里的命令按顺序执行，前一个 kernel 写的所有数据，后一个 kernel 一定能看到。**

看最后一行 `gemv_kernel<<<M, 128, 0, stream>>>` 的三重尖括号。第一个参数是这次启动的 CTA 个数 $M = 2{,}304$。第二个参数是每个 CTA 里的线程数 128。第三个参数是额外申请的动态共享内存字节数 0（本例的 `smem` 大小写死在代码里）。第四个参数是目标 **CUDA 流**（代码里的变量名写作 `stream`）。

这行调用是**异步启动**：它只把一条命令放进 **CUDA 流**（按放入顺序执行的一队 GPU 命令）就立刻返回，CPU 接着往下走时，GPU 还没开始算。

那后面要用 $y$ 的代码怎么知道 $y$ 已经写好了？同一个 CUDA 流里的命令按放入顺序执行，前一个 kernel 写的所有数据，同一个 CUDA 流里的后一个命令一定能看到，不用另加任何同步；若 CPU 自己要等结果，调用 `cudaStreamSynchronize(stream)` 等这条队列执行完，此前写入的数据对 CPU 也可见。这种“前一个写完、后一个一定看得到”的保证，叫先行发生（happens-before）。每次启动都有一笔固定开销（第 5 节量出它有多大），而且同一个 CUDA 流按顺序执行也意味着后一个 kernel 默认要等前一个跑完才能开始。一层要在同一个 CUDA 流里接连放进一串 kernel；它们之间的空隙从哪来、怎样重叠，见第 1 章第 1 节与第 1 章第 4 节。

命令到了 GPU，2,304 个 CTA 跑的是同一份代码。它们怎样各自认领不同的数据？

## 3. 每个线程怎样知道自己该算哪一段？

所有线程跑同一份代码，第 2 行的第 5 号线程怎样知道它该读哪几个数？**靠硬件给每个线程的内置坐标：`blockIdx.x` 说它在第几个 CTA（第几行），`threadIdx.x` 说它是 CTA 里的第几个线程（从哪一列起步），`blockDim.x` 说一步跨多远。**

先看 `row = blockIdx.x`：CTA 的编号是 $0..2{,}303$，直接对应它负责的 $W$ 的行号。再看 `tid = threadIdx.x`（$0..127$）和 `blockDim.x`（128）：在第 $r$ 轮循环（$r = 1..64$）里，`tid` 号线程读的列号是 $k = \mathrm{tid} + 128\,(r - 1)$。

一行共 8,192 列，分给 128 个线程后，每个线程跑 $8{,}192 / 128 = 64$ 轮；128 个线程合起来正好读完一整行 16 KiB 的 $W$ 和 16 KiB 的 $x$。在同一轮循环里，相邻线程同时读同一行里紧挨着的地址，128 个线程合起来盖住连续的 256 B；哪些线程真正在同一时刻发出读取，见第 4 章第 4 节。

在图 导三-1 里把滑块拉到 `row = 2`、`tid = 5`、第 24 轮（$r = 24$），就能直接核对这个公式：这一轮读的列号是 $k = 5 + 128 \times 23 = 2{,}949$，读出的两个元素分别是 `W[2 * 8192 + 2949] = W[19333]` 和 `x[2949]`。

64 轮之后，一行的内积散在 128 个线程各自的 `acc` 里。要把它们加成一个数，得先知道每个变量放在哪、谁能看见。

## 4. 128 个部分和怎样安全地加成一个数？

128 个线程各有一个部分和，0 号线程怎样拿到一个确定已经写好的全部 128 个数？**每个线程把部分和写进本 CTA 共享的 `smem`，`__syncthreads()` 让 128 个线程都写完之后才放行，然后 0 号线程把 128 个数依次加起来写回 $y_r$。**

这要先看代码里的变量放在哪、谁能看见。`row`、`tid`、`acc` 放在**寄存器**（**register**）里，是每个线程自己的，别的线程看不见（见第 3 章第 1 节）。`__shared__ float smem[128]`（$128 \times 4\ \text{B} = 512\ \text{B}$）放在芯片上的**共享内存**（**shared memory**）里，本 CTA 的 128 个线程都能读写，别的 CTA 看不见（见第 3 章第 1 节）。`W`、`x`、`y` 放在 HBM 的**全局内存**（**global memory**）里，所有 CTA 都能读写。

把很多个部分和合成一个值的操作叫**归约**（**reduction**）。因为 `acc` 是线程私有的，128 个部分和必须先借道 `smem`：每个线程先执行 `smem[tid] = acc`。

紧接着是一句 `__syncthreads()`（块内屏障）。它让本 CTA 的 128 个线程都走到这一行之后才一起往下走；走过它以后，这 128 个线程之前写进 `smem` 的数，本 CTA 里每个线程都能读到。这个保证只管同一个 CTA；不同 CTA 之间要交换数据，得用另外的规则，第 2 章第 6 节讲。要是没有这句 `__syncthreads()`，0 号线程去读 `smem[i]` 时，第 `i` 号线程可能还没把数写进去。

走过屏障后，0 号线程把 128 个数一个接一个加起来写回 `y[row]`，其余 127 个线程在旁边等着。这种写法用最简单的代码得到了正确的 $y_r$，代价是每个 CTA 要占 512 B 共享内存、做 1 次块内屏障，并且由 1 个线程串行做 128 次前后相依的加法、其余 127 个线程空等；一旦这段归约处在关键路径上就会吃亏。怎样让 128 个线程一起归约，见第 4 章第 5–6 节。

代码已经完整。在 H200 上跑它要多久？先说清这本书怎么量时间。

## 5. 书里的耗时是怎么量的，里面有什么不属于 kernel？

图表里一个 gemv 版本的“耗时”，到底量的是哪一段时间？**量的是 GPU 事件夹住的一次启动，先冲掉缓存、重复几百次取中位数；这段时间里有约 4.6 µs 是启动和计时本身，一个什么都不做的空 kernel 也要这么久。**

本书第一部分所有 gemv 版本都按同一套方法计时：每次计时启动之前，先读一大块无关数据把片上缓存冲掉，让 $W$ 真的从 HBM 读进来（这正对应导引二单请求 decode 的场景；要是缓存没冲掉，一部分 $W$ 会从片上缓存直接命中而显得更快，层内真实运行时缓存里是否还留着 $W$，见第 2 章第 2 节）。然后在一次启动前后各打一个 **GPU 事件**（GPU 在 CUDA 流里记录的时间戳），热身之后重复测几百次取中位数，再在两台 H200 机器上按正反两种顺序复测。

拿同样的方法去量一个什么都不做的空 kernel，测出来的时间是约 **4.6 µs**。这个空 kernel 用同样方法测出来的时间，叫作**固定开销**。

第一部分每个 gemv 版本的实测耗时都包含这 **4.6 µs**，不从读数里扣除。因此实测时间从来不等于纯读数时间，而导引二算的 **7.86 µs** 下界并不包含这 4.6 µs。kernel 与 kernel 之间还有别的开销，见第 1 章第 1 节。

有了量法，就可以比较两种写法了。

## 6. 为什么一行派一组线程，而不是一个线程？（gemv v0 → v1）

既然有 2,304 行，为什么不派 2,304 个线程、每个线程从头算完一行，而要每行派一个 128 线程的 CTA？**因为每线程一行的写法只开出 18 个 CTA，132 个 SM 大多闲着，而且相邻线程读的地址隔着一整行；改成每行一个 CTA 后，H200 上快了约 12.5 倍。**

本书给 gemv 的每个版本编号，**v0** 是起点。按写 CPU 循环的习惯，v0 让每个线程独自算完一整行：`row = blockIdx.x * 128 + threadIdx.x`，启动 `<<<18, 128, 0, stream>>>`（$2{,}304 / 128 = 18$ 个 CTA），每个线程自己在这一行的 8,192 列上从头循环到尾。**v1** 就是第 1 节的 kernel，启动 `<<<2304, 128, 0, stream>>>`，每行派一个 128 线程的 CTA：

```cuda
// v0：每个线程独自算完 1 行（int row = blockIdx.x * 128 + threadIdx.x;）
for (int k = 0; k < K; ++k) acc += __bfloat162float(W[row * K + k]) * __bfloat162float(x[k]);
// v1：1 个 CTA 的 128 个相邻线程协作分段读同一行（见第 1 节完整代码）
for (int k = tid; k < K; k += 128) acc += __bfloat162float(W[row * K + k]) * __bfloat162float(x[k]);
```

用第 5 节的量法在 H200 上一测，**v1 比 v0 快约 12.5 倍**（见下方图表）：


差距来自两处。第一是 SM 大多空着：任务按 CTA 一个一个分派到 SM 上（怎样分派，见第 2 章第 1 节），18 个 CTA 最多只能让 132 个 SM 里的 18 个忙起来。

第二是读显存的步幅。GPU 上相邻的 32 个线程一起发出一条读指令（这组线程的名字见第 3 章第 1 节），显存每次至少搬回 32 字节的一小段。在 v0 里，这 32 个线程读的是 32 个彼此隔着 16 KiB 的地址：一条读指令搬回 $32 \times 32 = 1{,}024$ B，当轮只用 64 B。一小段 32 B 装着这一行接下来的 16 个 BF16 数，本线程这一轮只用 1 个；剩下 15 个要等它后面 15 轮才用。它们可能还留在 SM 里的缓存中（见第 3 章第 2 节），但到底有多少真被再用上，我们没有测。在 v1 里，同样的 32 个线程读的是连续的 64 B：搬回 2 小段，所有字节当轮全用上。这两个原因各占了 12.5 倍里的多少，我们没有单独测。

把 v0 改成 v1，换来的是 2,304 个 CTA 铺满 132 个 SM、相邻线程读连续字节；付出的代价是每个 CTA 占 512 B 共享内存和 1 次块内屏障，0 号线程做 128 次串行加法（第 4 节），而且每个 CTA 都要把整条 $x$（16 KiB）读一遍，逻辑上 $x$ 被重读了 2,304 次（字节数和 $W$ 一样大）——至于其中有多少次真的去读了 HBM，我们在 v1 上没有测（片上缓存怎样接住重复读取，见第 2 章第 2 节）。在 $T = 1$ 下，我们没有测到 v1 输给 v0 的情况。即便如此，v1 也只达到 7.86 µs 下界的 **14.5%**；为什么还差这么远，是第 2–4 章要回答的问题。

---

**带走一句话：** CUDA 把外层循环摊成一组组并行的线程；让一组相邻线程合算一行，才铺得满 132 个 SM、读得到连续的字节。
