## 1. 计算 `qkv_gate`（`y = W · x`）的核心 CUDA 代码

<!-- FIG ch00_5-a: 图 0.5-1 左栏显示 gemv_kernel 源码与启动语句，右栏画出语言层面的三重并行嵌套框（Grid -> 单个 CTA -> 单个 thread）与全局内存 W/x/y（移动块对应第 row 号 CTA 的第 tid 号线程读取 W[row * K + k] 与 x[k] 累加进 acc、再经 smem[tid] 归约写出 y[row] 的算法步）。点击代码行可查看它对应的语言结构与后续硬件章节。 -->

下方这段函数计算 `y = W · x`（`W` 为 `M` 行 `K` 列按行存放的 BF16 矩阵）。函数内部没有遍历 `0..M-1` 的外层循环，却能一次算出全部 `M` 行结果。这是启动语句 `<<<M, 128, 0, stream>>>` 把外层行循环展开成了 `M` 个并行 **CTA**（Cooperative Thread Array，协作线程阵列，代码写作 `block`）的缘故。每个 CTA 内派 128 个 **thread**（线程）分段累加一行的 `K` 列。

```cuda
// 省去了 #include <cuda_bf16.h> 与显存分配；stream 为已创建的命令流队列
__global__ void gemv_kernel(const __nv_bfloat16* W, const __nv_bfloat16* x,
                            float* y, int K) {                 // → 第 1 章, 第 2 章
    __shared__ float smem[128];                                // → 第 3 章
    int row = blockIdx.x;                                      // → 第 2 章
    int tid = threadIdx.x;                                     // → 第 3 章, 第 4 章
    float acc = 0.0f;                                          // → 第 3 章, 第 5 章
    for (int k = tid; k < K; k += blockDim.x) {
        acc += __bfloat162float(W[row * K + k])
             * __bfloat162float(x[k]);                         // → 第 5 章, 第 6 章
    }
    smem[tid] = acc;
    __syncthreads();                                           // → 第 3 章
    if (tid == 0) {                                            // → 第 4 章
        float sum = 0.0f;
        for (int i = 0; i < blockDim.x; ++i) sum += smem[i];
        y[row] = sum;
    }
}
gemv_kernel<<<M, 128, 0, stream>>>(W, x, y, K);                // → 第 1 章..第 3 章
```

## 2. 启动语句与五个关键字各规定了什么？

当 CPU 执行完最后一行启动语句继续往下走时，输出数组 `y` 往往还没有算出来（此时 GPU 可能还没开始算第 0 行）。这是由于启动语句只把命令放进队列就立刻返回，不等 GPU 算完。函数的启动与块内共享遵循下面五组规则。
- `__global__` 与 **kernel**（GPU 函数）。`__global__` 声明 `gemv_kernel` 由 CPU 发起调用、在 GPU 上执行。
- `<<<M, 128, 0, stream>>>` 异步启动与 **stream**（命令流）。前两个参数为 CTA 数 `M` 与每 CTA 线程数 `128`。第三个参数为动态共享内存字节数 `0`（本例 `smem[128]` 大小已写死在代码里）。第四个参数是顺序命令队列 `stream`，CPU 要读结果时需调用 `cudaStreamSynchronize(stream)` 等待队列做完。
- **grid**（网格）与编号变量。全部 `M` 个 CTA 合称一个 `grid`。在 `gemv_kernel` 中，每个 CTA 靠 `blockIdx.x` 认领第 `row` 行。每个 thread 靠块内编号 `threadIdx.x` 与块宽 `blockDim.x`（128）跨列读取元素。
- 三种变量空间。指针 `W, x, y` 指向所有 CTA 可读写的 **global memory**（全局内存，位于第 0 章的 HBM）。`__shared__ float smem[128]` 仅当前 CTA 内部所有 thread 共享读写。`row, tid, acc` 为每个 thread 独占的私有局部变量。
- `__syncthreads()` 块内同步与 **reduction**（归约）。`__syncthreads()` 先作为执行同步屏障，等本块 128 个 thread 全部到达这一行。它同时是本 CTA 范围的 **memory fence**（内存栅栏），保证此前对 `smem` 的写入对全块可见后再放行。随后 `if (tid == 0)` 让 0 号 thread 把 `smem` 的 128 个值加成 1 个总和（即归约）写回 `y[row]`。

## 3. gemv 演化（v0 → v1）：从单线程算一行到 128 线程协作算一行

在 `qkv_gate`（`M = 2304, K = 8192`）上，最朴素的 **v0** 启动 `<<<18, 128, 0, stream>>>`，全卡共 2,304 个线程，每个线程独自循环 8,192 步算完 1 行。本章的 **v1**（上方 `gemv_kernel`）启动 `<<<2304, 128, 0, stream>>>`，改为每行 1 个 128 线程的 CTA。

```cuda
// v0：每个线程独自算完 1 行（int row = blockIdx.x * 128 + threadIdx.x;）
for (int k = 0; k < K; ++k) acc += __bfloat162float(W[row * K + k]) * __bfloat162float(x[k]);
// v1：1 个 CTA 的 128 个相邻线程协作分段读同一行（见第 1 节完整代码）
for (int k = tid; k < K; k += 128) acc += __bfloat162float(W[row * K + k]) * __bfloat162float(x[k]);
```

v0 只有 18 个 CTA，全卡 132 个 **SM**（Streaming Multiprocessor，流式多处理器，即执行指令的独立处理器）里只有 18 个分到工作。并且 v0 相邻线程读的地址相隔一整行（16 KiB）。v1 派出 2,304 个 CTA 铺满全部 132 个 SM，让每个 CTA 的 128 个相邻线程紧挨着读同一行的相邻元素（为什么铺满 SM 与相邻地址能拉高带宽，见第 2、3 章）。H200 实测（每次迭代前写 512 MiB 清空缓存的冷缓存中位数，下同）：`675.71 →` **58.88 µs**（`11.5×`），约为 7.9 µs 下界的 `13.4%`。同一测具下空 kernel 的启动与事件计时固定开销约为 3.68 µs，后续各版本的实测耗时都包含这约 3.7 µs 固定开销，因此单次实测永远不会达到下界的 100%。
