## 1. CUDA 怎样把 $y = Wx$ 的行循环变成并行？

<!-- FIG ch00_5-a: 图 导三-1 左栏显示 gemv_kernel 源码与启动语句（注释写“stream 是已经创建好的 CUDA 流”），右栏画出同一次启动里的 grid、CTA（内部标“128 个线程（每 32 个相邻线程一组）”）、thread 与全局内存 W/x/y；步骤卡读取路径写“HBM → 寄存器”，片上暂存统一写“共享内存”。步骤 1 卡写“CUDA 流”，代价为“1 条命令，CPU 立刻返回”；步骤 2 代价为“每个 SM 同时能放的 CTA 个数有上限，放不下的等位置空出来再上”；步骤 3 与读数写“第 0 组（32 个线程）里的第 5 号”；步骤 6 代价为“1 次块内屏障”；步骤 7 代价为“128 次前后相依的加法；其余 127 个线程直接结束，但 CTA 仍占着位置等 0 号线程算完”；步骤 9 总计为“54.08 µs，下界 7.86 µs 的 14.5%（含 4.6 µs 固定开销）”。保留 row 与 tid 滑块、播放按钮及读数“row = 2 · tid = 5 · 第 24 / 64 轮 · k = 2949 · 读 W[19333] 与 x[2949]”。图注：左边是 kernel 源码，右边是同一次启动里的 CTA、线程和它们读的数据。拖动 row 和 tid，看任一线程每一轮读哪两个数，最后怎样汇总成 y_r。 -->

**外层的行循环消失了：每一行分给一组线程，一共 2,304 组，分批驻留到 132 个 SM 上；每一行内部的 8,192 列，则由组里的 128 个线程分工累加。**

我们要算的是导引二阶段 1 里的矩阵乘向量 $y = W x$：$\shape{W}{2304,\ 8192}{BF16}$ 和 $\shape{x}{8192}{BF16}$ 都放在 HBM 里，输出的第 $r$ 行是 $y_r = \sum_{k=0}^{8191} W_{r,k}\, x_k$。我们把行数记作 $M = 2{,}304$，列数记作 $K = 8{,}192$。为了让代码尽量简短，下面这段程序把输出 $y$ 直接写成了 FP32；真实的阶段 1 会写成 BF16，并按列切成 `q`、`k`、`v`、`gate` 交给阶段 2。代码每一行末尾的箭头，指向后面专门拆解那一行硬件机制的章节。

```cuda
// 省去了 #include <cuda_bf16.h> 与显存分配；stream 是已经创建好的 CUDA 流
__global__ void gemv_kernel(const __nv_bfloat16* W, const __nv_bfloat16* x,
                            float* y, int K) {
    __shared__ float smem[128];                                // → 第 3 章
    int row = blockIdx.x;                                      // → 第 2 章
    int tid = threadIdx.x;                                     // → 第 3 章
    float acc = 0.0f;                                          // → 第 3 章
    for (int k = tid; k < K; k += blockDim.x) {
        acc += __bfloat162float(W[row * K + k])                // → 第 3 章（读）, 第 6 章（转换）
             * __bfloat162float(x[k]);                         // → 第 5 章（乘加）
    }
    smem[tid] = acc;
    __syncthreads();                                           // → 第 4 章
    if (tid == 0) {                                            // → 第 4 章
        float sum = 0.0f;
        for (int i = 0; i < blockDim.x; ++i) sum += smem[i];
        y[row] = sum;
    }
}
gemv_kernel<<<M, 128, 0, stream>>>(W, x, y, K);                // → 第 1 章, 第 2 章
```

我们从上往下读一遍这段代码。函数开头的 `__global__` 把它标记成一个 **kernel**——也就是由 CPU 发起一次启动、在 GPU 上由成千上万个线程同时执行的函数。CUDA 把协同处理同一块任务的一组线程叫作一个 **CTA**（cooperative thread array，代码里叫 `block`），一次启动开出来的全部 CTA 合起来叫 **grid**。最后一行启动语句一口气开出 $M = 2{,}304$ 个 CTA，每个 CTA 里装 128 个**线程**（**thread**），每个线程都从头到尾跑一遍这段函数。在循环内部，`__bfloat162float` 先把读进来的 2 字节 BF16 转成 4 字节 FP32，再乘加进线程自己的 `acc` 里（这一步类型转换在硬件上花多少代价，见第 6 章）。

你看，写 CPU 代码时我们要写一层外层循环，按时间一行一行往下扫；到了 CUDA 里，这层外层循环直接被摊平了，变成 2,304 个 CTA，一行分一个。GPU 硬件会把这些 CTA 派发到 **SM**（streaming multiprocessor，流式多处理器）上执行。SM 是 GPU 上真正执行指令的计算核心，一张 H200 上有 **132** 个 SM；每一个 CTA 从启动到结束都固定在同一个 SM 上跑。不过每个 SM 同时能驻留的 CTA 个数是有上限的，一时塞不下的 CTA 就得在外面排队，等前面的 CTA 跑完腾出位置再顶上去（一个 SM 到底能塞几个、为什么，见第 2 章第 1 节和第 3 章第 1 节）。

## 2. 启动语句做了什么，$y$ 什么时候算好？

**启动语句只把命令放进 CUDA 流就立刻返回，这时 $y$ 还没算；默认情况下，同一个 CUDA 流里后一个 kernel 一定看得到前一个写的数据。**

再看最后一行 `gemv_kernel<<<M, 128, 0, stream>>>` 里的三重尖括号。第一个参数是这次启动开出的 CTA 个数 $M = 2{,}304$；第二个参数是每个 CTA 里的线程数 128；第三个参数是这次启动给每个 CTA 额外动态申请的共享内存字节数，这里用不着，直接传 0；第四个参数则是目标 **CUDA 流**（按入队顺序依次执行的一条 GPU 命令队列，代码里的变量名就叫 `stream`）。调用这行启动语句时，CPU 只是往队列里塞了一条命令就立刻往下走了，根本不等 GPU 算完——这种机制叫**异步启动**。

在默认设置下，同一个 CUDA 流里的命令严格按入队顺序执行，前一个 kernel **happens-before**（先行发生于）后一个 kernel：你不需要额外写任何同步代码，后一个 kernel 就一定能看见前一个 kernel 写进显存的数据。当然，我们也可以特地让后一个 kernel 提前进场重叠执行，那时候的同步规矩见第 1 章第 4 节。如果 CPU 自己要等结果算完，就调用 `cudaStreamSynchronize(stream)`，把 CPU 拦住直到这条流排空。

## 3. 每个线程怎样知道自己该算哪一段？

**靠硬件给每个线程的内置坐标：`blockIdx.x` 标出它在第几个 CTA，`threadIdx.x` 标出它在组里排第几，`blockDim.x` 是每个 CTA 的线程数，循环每步就跨这么远。**

成千上万个线程跑的是同一份代码，每个线程怎么知道自己该读哪个数？全靠硬件发给每个线程的内置坐标。先看 `row = blockIdx.x`：CTA 的编号从 $0$ 排到 $2{,}303$，直接对应这个 CTA 认领的 $W$ 行号。再看 `tid = threadIdx.x`（$0..127$）和 `blockDim.x`（128）：它们把同一行的列分给了 CTA 里的 128 个线程。在第 $r$ 轮循环（$r = 1..64$）里，`tid` 号线程去读的列号就是 $k = \mathrm{tid} + 128\,(r - 1)$。

一行共有 8,192 列，由 128 个线程分着读，每个线程正好跑 $8{,}192 / 128 = 64$ 轮；64 轮跑完，128 个线程合起来刚好读完一整行 16 KiB 的 $W$ 和 16 KiB 的 $x$。更重要的是，在每一轮循环里，编号相邻的线程读的也是同一行里紧挨着的地址，128 个线程合起来正好盖住连续的 256 B。硬件把每 32 个相邻线程编成一个 **warp**（线程束）；一个 warp 怎么一起发读指令、硬件又怎么把相邻地址合并成更少的显存请求，我们在第 3 章第 1–2 节细讲。

你可以在图 导三-1 里把滑块拉到 `row = 2`、`tid = 5`、第 24 轮（$r = 24$），亲手核对一下这个公式：这一轮它读的列号是 $k = 5 + 128 \times 23 = 2{,}949$，取出来的两个元素分别是 `W[2 * 8192 + 2949] = W[19333]` 和 `x[2949]`。

## 4. 128 个部分和怎样安全地加成一个数？

**每个线程把部分和写进本 CTA 共享的 `smem`，`__syncthreads()` 等 128 个线程都写完才放行，再由 0 号线程加起来写回 $y_r$。**

代码里的三类变量各自住在不同的存储层。`row`、`tid`、`acc` 放在**寄存器**（**register**）里，每个线程各管自己那一份。`__shared__ float smem[128]`（$128 \times 4\ \text{B} = 512\ \text{B}$）住在芯片上的**共享内存**（**shared memory**）里，同一个 CTA 里的 128 个线程都能读写它，而默认情况下别的 CTA 看不见（这两级片上存储见第 3 章第 1 节；把几个 CTA 编成一组互读对方共享内存的做法，见第 7 章第 12 节）。至于 `W`、`x`、`y`，它们住在 HBM 的**全局内存**（**global memory**）里，所有 CTA 都能读写。

把许多份部分和汇总成一个总和，这一步叫**归约**（**reduction**）。由于各线程的 `acc` 分别留在各自的私有寄存器中，这版代码通过共享内存 `smem` 把 128 个部分和聚到一起：每个线程先写一句 `smem[tid] = acc`。

紧接着就是一句 `__syncthreads()`（块内屏障）。它像一道闸门，把本 CTA 的 128 个线程拦在这一行，等所有人都写完了才一起放行；跨过这道屏障之后，刚才 128 个线程写进 `smem` 的数，本 CTA 里的每一个线程就都能稳稳读到了。注意这道屏障只管同一个 CTA 内部；如果要在不同 CTA 之间交换数据，得用另一套同步规矩（见第 2 章第 6 节）。如果省掉这句 `__syncthreads()`，0 号线程去读 `smem[i]` 的时候，第 `i` 号线程可能还没把自己的部分和写进去。

跨过屏障之后，只留 0 号线程一个人在 `for` 循环里把 128 个数挨个加起来、写回 `y[row]`；其余 127 个线程直接退出，不再干活，但整个 CTA 的槽位还得一直占着，直到 0 号线程算完才能腾出来。这种写法代码最简单，算出来的 $y_r$ 也完全正确，但代价有三笔：每个 CTA 要占 512 B 共享内存、要做 1 次块内屏障，最后还要由 1 个线程串行做 128 次前后相依的加法。因为第一批上场的 CTA 几乎同时起步，也会在差不多的时刻走到这一步，这时同一个 SM 上可能已经没有别的在途显存读取能拿来掩盖这段收尾了，这 128 次串行加法就可能实打实地加进总耗时里（这一项耗时我们没有单独拆出来测）。后面到第 4 章第 5–6 节，我们会看怎么让全部 128 个线程一起动手做归约。

## 5. 这里的耗时是怎么量的，里面有什么不属于 kernel？

**每轮测量先冲刷片上缓存，再用 GPU 事件卡住单次启动、连测 500 次取中位数；哪怕启动一个空 kernel，这里面也带有约 4.6 µs 的固定开销。**

第一部分里所有 gemv 版本都按同一套规矩计时：每次启动计时之前，我们先去读一大块毫不相干的数据，把芯片上的高速小存储（**片上缓存**）彻底冲掉，逼着 GPU 真的从 HBM 里把 $W$ 读进来。接着，我们在一次启动的一头一尾各打一个 **GPU 事件**（也就是让 GPU 在 CUDA 流里记下两个时间戳），先预热 20 次，再连测 500 次取中位数。每次先冲掉缓存，正好对应导引二里单请求 decode 的真实处境（为什么一致，见第 2 章第 2 节）。

如果我们用一模一样的办法去量一个什么都不干的空 kernel，耗时同样要约 4.6 µs——本书把这笔底数叫作**固定开销**。第一部分报告的所有实测耗时都原样包含这 4.6 µs，不做扣除；而导引二算出来的 7.86 µs 带宽下界是不含它的。在连续启动的多个 kernel 之间还会有别的交接开销，见第 1 章第 1 节。

## 6. 为什么一行派一组线程，而不是一个线程？（gemv v0 → v1）

**每线程算一行的写法只开出 18 个 CTA，132 个 SM 大多闲着，而且相邻线程读的地址隔着一整行；改成每行一个 CTA 后快了约 12.5 倍。**

接下来我们给 gemv 的每个演进版本依次编号，拿 **v0** 当起点。如果照搬写 CPU 循环的直觉，最容易写出来的 v0 是让每个线程各自包揽一整行：`row = blockIdx.x * 128 + threadIdx.x`，启动 `<<<18, 128, 0, stream>>>`（$2{,}304 / 128 = 18$ 个 CTA），每个线程自己在那一行的 8,192 列上从头加到尾。而 **v1** 就是第 1 节那段代码，启动 `<<<2304, 128, 0, stream>>>`，每一行派一整组 128 线程的 CTA 上去合算：

```cuda
// v0：每个线程独自算完 1 行（int row = blockIdx.x * 128 + threadIdx.x;）
for (int k = 0; k < K; ++k) acc += __bfloat162float(W[row * K + k]) * __bfloat162float(x[k]);
// v1：1 个 CTA 的 128 个相邻线程协作分段读同一行（见第 1 节完整代码）
for (int k = tid; k < K; k += 128) acc += __bfloat162float(W[row * K + k]) * __bfloat162float(x[k]);
```


足足 12.5 倍的差距，出在两个地方。第一是 SM 绝大部分都空着：硬件按 CTA 为单位把活派到 SM 上（怎么分派见第 2 章第 1 节），v0 一共才开出 18 个 CTA，最多只能让 132 个 SM 里的 18 个干活，剩下 114 个 SM 全程旁观。

第二是读显存的步幅。在 GPU 上，一个 warp 里的 32 个相邻线程会一起发出一条读指令，而显存每次请求至少搬回 32 字节的一小段（合并读取见第 3 章第 2 节）。在 v0 里，这 32 个线程要读的是 32 个彼此隔着整整一行（16 KiB）的地址：一条读指令被迫搬回 $32 \times 32 = 1{,}024$ B，当轮却只用上了其中的 64 B。搬回来的每个 32 B 小段里装着那一行接下来的 16 个 BF16，本轮只拿走 1 个；其余 15 个要等后面 15 轮才用，到时候也许还留在片上缓存里（见第 3 章第 2 节）。

换到 v1 之后，同样的 32 个相邻线程在同一轮读的是紧挨着的 64 B：显存只需要搬回 2 个 32 B 小段，搬回来的每一个字节当轮全部派上用场。

所以把 v0 改成 v1，我们赢回来两件事：2,304 个 CTA 铺满全部 132 个 SM，外加相邻线程读连续字节；为此付出的代价，就是第 4 节算过的那三笔：512 B 共享内存、1 次块内屏障和 128 次串行加法。

另外还有一个顺带的变化：在 v0 里，同一个 warp 的 32 个线程在同一轮读的是同一个 `x[k]`，相当于 32 行共享一次读取；而在 v1 里，每个 CTA 都要自己从头到尾读一遍 16 KiB 的 $x$，2,304 个 CTA 合起来读的 $x$ 字节数跟 $W$ 一样多（片上缓存怎么接住这些重复读取，见第 2 章第 2 节）。

顺便想一步：要是矩阵的行数本来就少于 132 行，那就算每行派 1 个 CTA 也铺不满 132 个 SM，这时候就得把同一行再拆给好几个 CTA 一起算（见第 2 章第 5 节）。

不过你看上面的图表：就算快了 12.5 倍，v1 的实测耗时依然是 7.86 µs 下界的约 7 倍。哪怕扣掉 4.6 µs 的固定开销，它读 $W$ 跑出来的有效带宽也只有 4.8 TB/s 的约六分之一。为什么铺满了 132 个 SM 还是差这么远？这正是第 2–4 章要一层层揭开的问题。

**带走一句话：** CUDA 把外层循环摊成 2,304 个分批上 SM 的 CTA；让一组相邻线程合算一行，才铺得满 132 个 SM、读得到连续的字节。
