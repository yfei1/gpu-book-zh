1. 单层模型的七个计算阶段与层间小操作

每个用户的输入文本是一个 request（请求）。它被切成一串 token（词元）。自回归生成每步都要用刚算出的词去预测下一个词，所以在 decode（逐词生成）阶段，每个请求每步只输入 1 个新 token。每个 token 在层内是一个固定宽度的浮点数向量，叫 residual stream（残差流）。各阶段从残差流读入向量并输出中间向量。这些中间向量统称 activation（激活），其中 o 与 unpooler 把结果加回残差流。

本层是 MoE（混合专家）结构，共有 256 组独立的专家权重矩阵，每步只为每个 token 挑 8 个专家。线上由 8 张 H200 分担同一层。卡间通信不计入赛题耗时，所以本书只测单张卡分到的部分。每张卡放 32 个专家，单 token 挑出的 8 个专家平摊到各卡上平均每卡只有 8 × 32 ÷ 256 = 1 个。但挑中的专家不会均匀落到各卡上，均匀抽取时命中最多专家的那张最忙卡平均分到约 2.5 个不同专家。一步推理必须等最忙卡算完。赛题下界给该期望值乘上 0.75 的路由折扣，按 2.5 × 0.75 ≈ 1.87 个专家（约 53 MB，接近平均数的两倍）计入耗时（图 0-1）。

按播放或拖动图 0-1 的时间滑块，可以看到 1 个 token 依次流过七个核心阶段（o 与 unpooler 处标有“+”加回残差流，各阶段前后还夹着不读大矩阵权重的归一化小操作）。

  • qkv_gate 投影（读 37.7 MB）。把残差流乘上 BF16（脑浮点，每参数 2 字节）权重矩阵，算出查询（Q）、键（K）、值（V）与门控向量。
  • attention（注意力，即 P1）。用当前 token 的 Q 与可见历史 token 的 K 求权重，再按权重对 V 加权求和。历史 K、V 按 FP8（8 位浮点，1 字节）存进 KV cache（键值缓存）。只看最近固定数量历史 token 的滑窗层读 0.5 MB，看全部历史 token 的全长层读 20.5 MB。
  • o 输出投影（读 16.8 MB）。把注意力输出乘上 BF16 矩阵，加回残差流。
  • router（路由器，读 8.4 MB）。用 FP32（单精度浮点，每参数 4 字节）矩阵为每个 token 给 256 个专家打分，挑出得分最高的 8 个。
  • pooler（降维投影，读 67.1 MB）。用 BF16 矩阵把残差流压窄一半，送入专家。
  • MoE 专家计算（即 P2，最忙卡读约 53 MB）。每个被选中的本地专家执行上投影 w13 与下投影 w2 两次矩阵乘，权重存为 NVFP4（4 位浮点，见第 6 章）。
  • unpooler（升维投影，小批量切片读 8.4 MB）。用 BF16 矩阵把专家输出升回残差流宽度，加回残差流。

同一步里一起算的所有 token 合称一个 batch（批量，总数记作 T）。一次算完用户整段输入的所有 token 则称为 prefill（预填充）。不同阶段的瓶颈类型不同，所以竞赛把单层拆成 5 道计时题分别评测：P1 注意力、P2 专家、P3 小批量整层、P4 五个稠密矩阵乘（第 1、3、4、5、7 阶段）、P5 预填充整层。

2. 算术强度、平衡点与单层理论下界

图 0-2（图还在画）

单层权重超过百兆字节，远大于片上缓存容量。所以每步推理都必须把权重和历史 KV cache 从 HBM（高带宽主显存）重新读进芯片。H200 读取 HBM 的标称带宽上限是 4.8 TB/s，稠密 BF16 矩阵乘加的标称算力上限是 989 TFLOP/s。假设显存读取与矩阵运算重叠执行。按题目给定权重格式算出的单层 floor（理论下界），就是显存读取耗时与矩阵运算耗时中的较大值（换更小位宽的格式时下界随之下降，见第 6 章）。

floor = max( 总搬运字节数 Bytes ÷ 4.8 TB/s , 总浮点运算次数 FLOPs ÷ 989 TFLOP/s )

一个阶段的总浮点运算次数除以总显存读写字节数称为 arithmetic intensity（算术强度，单位 FLOP/B）。用算力上限除以带宽上限得到 989 ÷ 4.8 ≈ 206 FLOP/B，称为 ridge point（平衡点）。算术强度低于 206 时，读 1 字节的耗时比矩阵单元算完对应运算还长，所以计算单元等 HBM 返回数据。高于 206 时，数据等矩阵单元。

小模型先猜候选词、再由大模型一次并行检验的做法称为 speculative decoding（投机解码），这一检验步称为 verify。32 个并发请求各检验 8 个候选词时，全批总词数 T 增大到 256。在图 0-2 中，只有 qkv_gate、pooler、unpooler 这 3 个大矩阵乘略微跨过了 206。o、router 与注意力依然留在平衡点以下。1 次乘加含 2 FLOP，1 个 BF16 权重占 2 字节，权重被 T 个 token 共享后仅按权重算强度为 2 × T ÷ 2 = T FLOP/B（计入激活读写后 qkv_gate 约为 224）。但 router 权重是 4 字节 FP32，仅按权重算强度减半为 T ÷ 2 = 128，加上激活读写后降至约 84。历史 KV cache 属于每个请求私有、无法跨请求共享，所以注意力强度不随 T 增大。

T = 1 时，BF16 稠密层强度只有 2 × 1 ÷ 2 = 1 FLOP/B。全层所有阶段都远低于 206，所以单请求 decode 下 GPU 绝大部分时间在等 HBM。在图 0-1 中选滑窗层，读数为“滑窗层：一步共读 191.9 MB”。第二行读数为“最短用时 40.0 µs（读得最多的是 pooler 和 MoE 专家）”，这正是全书追踪的 40 µs 单层基准下界。切到全长层，读数变为“全长层：一步共读 211.9 MB”与“最短用时 44.1 µs（读得最多的是 pooler 和 MoE 专家）”。其中第一阶段 qkv_gate 单独读 37.7 MB，下界约 7.9 µs，这是后续各章 gemv（矩阵乘向量，即 y = W · x）演化的终点线。

带走一句话： 单请求 decode 下滑窗层读 192 MB 权重与缓存，按 4.8 TB/s 算出的单层下界是 40 µs（其中 qkv_gate 占 7.9 µs）。

1. 计算 qkv_gate（y = W · x）的核心 CUDA 代码

图 0.5-1（图还在画）

下方这段函数计算 y = W · x（W 为 M 行 K 列按行存放的 BF16 矩阵）。函数内部没有遍历 0..M-1 的外层循环，却能一次算出全部 M 行结果。这是启动语句 <<<M, 128, 0, stream>>> 把外层行循环展开成了 M 个并行 CTA（Cooperative Thread Array，协作线程阵列，代码写作 block）的缘故。每个 CTA 内派 128 个 thread（线程）分段累加一行的 K 列。

// 省去了 #include <cuda_bf16.h> 与显存分配；stream 为已创建的命令流队列
__global__ void gemv_kernel(const __nv_bfloat16* W, const __nv_bfloat16* x,
                            float* y, int K) {                 // → 第 1 章, 第 2 章
    __shared__ float smem[128];                                // → 第 3 章
    int row = blockIdx.x;                                      // → 第 2 章
    int tid = threadIdx.x;                                     // → 第 3 章, 第 4 章
    float acc = 0.0f;                                          // → 第 3 章, 第 5 章
    for (int k = tid; k < K; k += blockDim.x) {
        acc += __bfloat162float(W[row * K + k])
             * __bfloat162float(x[k]);                         // → 第 5 章, 第 6 章
    }
    smem[tid] = acc;
    __syncthreads();                                           // → 第 3 章
    if (tid == 0) {                                            // → 第 4 章
        float sum = 0.0f;
        for (int i = 0; i < blockDim.x; ++i) sum += smem[i];
        y[row] = sum;
    }
}
gemv_kernel<<<M, 128, 0, stream>>>(W, x, y, K);                // → 第 1 章..第 3 章

2. 启动语句与五个关键字各规定了什么？

当 CPU 执行完最后一行启动语句继续往下走时，输出数组 y 往往还没有算出来（此时 GPU 可能还没开始算第 0 行）。这是由于启动语句只把命令放进队列就立刻返回，不等 GPU 算完。函数的启动与块内共享遵循下面五组规则。

  • __global__ 与 kernel（GPU 函数）。__global__ 声明 gemv_kernel 由 CPU 发起调用、在 GPU 上执行。
  • <<<M, 128, 0, stream>>> 异步启动与 stream（命令流）。前两个参数为 CTA 数 M 与每 CTA 线程数 128。第三个参数为动态共享内存字节数 0（本例 smem[128] 大小已写死在代码里）。第四个参数是顺序命令队列 stream，CPU 要读结果时需调用 cudaStreamSynchronize(stream) 等待队列做完。
  • grid（网格）与编号变量。全部 M 个 CTA 合称一个 grid。在 gemv_kernel 中，每个 CTA 靠 blockIdx.x 认领第 row 行。每个 thread 靠块内编号 threadIdx.x 与块宽 blockDim.x（128）跨列读取元素。
  • 三种变量空间。指针 W, x, y 指向所有 CTA 可读写的 global memory（全局内存，位于第 0 章的 HBM）。__shared__ float smem[128] 仅当前 CTA 内部所有 thread 共享读写。row, tid, acc 为每个 thread 独占的私有局部变量。
  • __syncthreads() 块内同步与 reduction（归约）。__syncthreads() 先作为执行同步屏障，等本块 128 个 thread 全部到达这一行。它同时是本 CTA 范围的 memory fence（内存栅栏），保证此前对 smem 的写入对全块可见后再放行。随后 if (tid == 0) 让 0 号 thread 把 smem 的 128 个值加成 1 个总和（即归约）写回 y[row]。

3. gemv 演化（v0 → v1）：从单线程算一行到 128 线程协作算一行

在 qkv_gate（M = 2304, K = 8192）上，最朴素的 v0 启动 <<<18, 128, 0, stream>>>，全卡共 2,304 个线程，每个线程独自循环 8,192 步算完 1 行。本章的 v1（上方 gemv_kernel）启动 <<<2304, 128, 0, stream>>>，改为每行 1 个 128 线程的 CTA。

// v0：每个线程独自算完 1 行（int row = blockIdx.x * 128 + threadIdx.x;）
for (int k = 0; k < K; ++k) acc += __bfloat162float(W[row * K + k]) * __bfloat162float(x[k]);
// v1：1 个 CTA 的 128 个相邻线程协作分段读同一行（见第 1 节完整代码）
for (int k = tid; k < K; k += 128) acc += __bfloat162float(W[row * K + k]) * __bfloat162float(x[k]);

v0 只有 18 个 CTA，全卡 132 个 SM（Streaming Multiprocessor，流式多处理器，即执行指令的独立处理器）里只有 18 个分到工作。并且 v0 相邻线程读的地址相隔一整行（16 KiB）。v1 派出 2,304 个 CTA 铺满全部 132 个 SM，让每个 CTA 的 128 个相邻线程紧挨着读同一行的相邻元素（为什么铺满 SM 与相邻地址能拉高带宽，见第 2、3 章）。H200 实测（每次迭代前写 512 MiB 清空缓存的冷缓存中位数，下同）：675.71 → 58.88 µs（11.5×），约为 7.9 µs 下界的 13.4%。同一测具下空 kernel 的启动与事件计时固定开销约为 3.68 µs，后续各版本的实测耗时都包含这约 3.7 µs 固定开销，因此单次实测永远不会达到下界的 100%。

带走一句话： v1 用 2,304 个 128 线程 CTA 铺满全卡 132 个 SM，使 qkv_gate 实测耗时从 675.71 µs 降到 58.88 µs（11.5 倍）。

图 1-1 第一行里，GPU 有一段时间停下空等。单个小 kernel 在 GPU 上只跑几微秒，而逐个流启动的准备时间比它还长。由于 CPU 跟不上 GPU，stream 队列（见第 0.5 章）就会排空。所以在线推理服务默认启用 CUDA Graph（计算图录制与重放），SGLang 的 decode 基线也是这样。预热时，cudaStreamBeginCapture 与 cudaStreamEndCapture 把整层调用顺序和固定显存地址录成静态图并实例化。运行时 CPU 只调一次 cudaGraphLaunch，由片上硬件派发器（从 stream 读命令并派发 CTA 的硬件，NVIDIA 未公开其内部结构）自主重放整张图。

但图 1-1 第二行显示，开启 CUDA Graph 后基线仍有两处损耗。第一，未融合的层间小操作各自把中间向量写回 HBM 再读出来，占了单请求 decode 单层耗时的约四分之一。第二，同一 stream 里后一个图节点必须等前一个节点的所有 CTA 退出、写入全部可见后才能开始。这道隐式栅栏在相邻图节点切换时留下约 1 µs 的硬件切换空隙。因此第 0 级的第一步优化是做 kernel fusion（算子融合），把层间小操作融进相邻的矩阵乘与注意力 kernel 中。每少一次启动就省掉一次切换空隙和一次 HBM 往返，这把单请求 decode（T = 1）的单层启动从 SGLang 基线估计的约 17 次压到 11 次。

2. 用 PDL（编程依赖启动）让前序收尾与后继读权重重叠

图 1-2（图还在画）

如图 1-1 第三行与图 1-2 所示，每个 kernel 末尾都不是同时停下的。大部分 CTA 已结束时，仍有少数 CTA 在收尾。收尾期大部分计算单元已经空出，且后继预读静态权重不依赖前序刚算出的激活。所以 Hopper 的 PDL（Programmatic Dependent Launch，编程依赖启动）允许后继在前序收尾时提前进场。PDL 按下面四步工作。

  • 声明编程依赖边。主机端启动后继时挂上属性 cudaLaunchAttributeProgrammaticStreamSerialization。
  • 前序触发。前序每个 CTA 在算完主体循环、进入收尾期前调用 cudaTriggerProgrammaticLaunchCompletion()。所有前序 CTA 都已触发或退出时，硬件派发器即可启动后继 kernel。
  • 后继预读静态权重。后继 kernel（如 o 或 pooler）进场后先不读前序尚未写完的激活向量，而是先从 HBM 预读自己最先要用的几块静态权重分块。
  • 后继等待前序数据可见。读取前序激活之前，后继调用 cudaGridDependencySynchronize() 停下等待，等前序显存写入全部落定后再继续执行。

在 P1 全长层 decode（T = 1）测试中，把触发点放在前序函数开头反而比放在主体循环之后慢了近 2 µs。触发调用并不代表前序数据已写完。过早进场的后继 CTA 只能停在等待函数上，空占芯片上的 CTA 位置（见第 3 章）。

3. 合写成一个协作大 kernel 还是拆成两个 PDL 串联 kernel？

第 0 章的专家计算（P2）里，每个专家先乘 w13，再乘 w2。w2 的每一行都要读 w13 的全部输出，而这些输出由许多 CTA 分别写出。若用协作启动（cudaLaunchCooperativeKernel）把两步合写进一个大 kernel，两步之间就必须插一道全网格同步栅栏。协作启动要求所有 CTA 同时驻留在芯片上，否则没上芯片的 CTA 永远到不了栅栏就会死锁。而芯片一次能同时驻留的 CTA 数量有限（见第 3 章）。图 1-3 的 P2（decode 批量 16–32）对比中，拆成两个 PDL 串联 kernel 的写法反而净快约 0.7–0.8 µs。可能的原因是全网格栅栏本身耗时约 1.4 µs，且全卡 CTA 都要空等最慢的那个算完 w13。拆开后两个 kernel 之间的 PDL 交接只需约 0.6 µs，而且先算完 w13 的 CTA 一退场，w2 的 CTA 就能进场预读权重分块。

4. gemv 演化（v1 → v2）：把流启动链录进单张 CUDA Graph 重放

单层里 v1（见第 0.5 章）的 gemv_kernel 前后紧跟归一化（rmsnorm）与写缓存后处理（rope_kv）。若主机端从 Python 逐个流启动 [rmsnorm, gemv_kernel, rope_kv]，相邻 kernel 之间会暴露下发空隙。本章的 v2 在预热期把三步调用链录进同一张 CUDA Graph 并实例化，运行时单次重放。

// v1：主机端在 stream 上逐个下发三步 kernel
gemv_kernel<<<2304, 128, 0, stream>>>(W, x, y, K);
// v2：预热期录制三步链并实例化为 graph_exec，运行时单次提交整张图
cudaGraphLaunch(graph_exec, stream);

整图重放由片上硬件派发器自主启动，消除了 CPU 逐个下发的排空等待。三步链的 H200 实测：由 CPU 逐步流启动（热缓存）耗时 73.02 µs，改为单张 CUDA Graph 重放后降至 36.19 µs（省去 36.8 µs 下发空隙）。在冷缓存且流队列预先排满时，整图重放也从流启动的 67.23 µs 降至 65.15 µs（2 个节点边界共省约 2.1 µs，平均每个边界省约 1 µs）。

1. 132 个 SM 上的 wave、tail 与 K-halves

图 2-1 上方画出了 H200 芯片表面，裸片上的每个小方块是 1 个 SM（全卡共 132 个）。先假设每个 SM 一次只跑 1 个 CTA 来演示波次概念。第 3 章会算出 v1 / v2 实际每 SM 驻留 16 个 CTA（全卡一轮容量为 132 × 16 = 2,112 个，2,304 = 2,112 + 192 实际分两轮跑完）。全卡齐步跑完的一轮 CTA 称为一个 wave（波次）。在图 2-1 的单 CTA 模型中，启动 2,304 个 CTA 与启动 2,376 个 CTA 都要跑 ⌈2304 ÷ 132⌉ = 18 个 wave。第 18 个 wave 无论有 60 个还是 132 个 SM 在算，整个 kernel 都要等这一波跑完才结束。

只要总 CTA 数不是单轮容量的整数倍，最后一个 wave 就只有余数 r 个块在算（图 2-1 中 r = 60）。其余 132 − r（72）个 SM 空等到终点线，这段空等就是 tail（尾波）。图 2-1 按每个 CTA 用时固定画出了尾波上界。受 HBM 带宽限制的 kernel 在尾波里在算的 SM 更少、排队更短，单个 CTA 会跑得略快，所以实际尾波损失小于图中的上界。当最后一波的余数 r 不超过单轮容量的一半（单 CTA 模型下 2r ≤ 132，即 r ≤ 66）时，可把队尾工作块沿 K 维对半切开。这一做法称为 K-halves（勾选图 2-1 的切半开关可见）。切开后的 2r 个半块刚好放进最后一轮的空闲位置里，两半结果经跨 SM 同步合并（见第 4 节）即可把尾波缩短约半个 wave。

2. PDL 提前进场时发生了什么：观察到的 CTA 派发顺序

按第 1 章的触发规则，PDL 后继 CTA 会落进图 2-1 最后一个 wave 里那些刚空闲出来的 SM 中。P2 的后继阶段采用了 persistent kernel（持久 kernel）。全卡每个 SM 启动 1 个 CTA，依次处理按 blockIdx.x 预先分给它的工作块。本来每个 CTA 分到的工作量相同，应该同时结束。但实测发现编号最大的 131 号 CTA 比编号小的 CTA 晚开始约 2–3 µs，在 decode 批量 16–32 的多数输入种子下成为最慢的 CTA。前序 kernel 的 SM 是一批批退场的，H200 的硬件派发器在交接处按 blockIdx.x 从小到大的顺序把新 CTA 依次派给刚退出的 SM。所以在代码里给编号大的 CTA 略微少分一点工作量，就能让各 CTA 的结束时间更接近。

3. 全卡内存层次与利特尔法则：为什么每个 SM 要挂起约 64 KiB 在途读取？

如图 2-2 所示，全卡 SM 读写全局指针 W, x, y 时，全部连向芯片中央共享的 L2 cache（L2 缓存，容量 60 MiB）。L2 未命中时再去芯片两侧的 HBM 读取。第 0 章算下界用的 4.8 TB/s 是手册标称峰值，而全卡用普通向量读取指令持续流式读 HBM 的实测可达上限约为 4.54 TB/s。平摊到每个 SM，目标带宽约为 4.54 TB/s ÷ 132 ≈ 34 GB/s。一条读取发出后、数据返回前，它请求的字节叫 bytes in flight（在途数据量）。图 2-2 把 W 的 1 整行（16 KiB = 32 条每次 512 字节的线程束读取，见第 3 章）画作 1 个在途单元。图 2-2 横轴用“▲”标出了 v1–v10 各版本的在途位置，其中 v1–v4 每线程只发 2 字节读取，每 SM 在途仅 4.0 KiB。根据 Little's Law（利特尔法则），要跑满单 SM 的目标带宽，SM 上同时保持的在途字节数必须覆盖往返延迟。

所需在途数据量（Bytes in flight） = 单 SM 目标带宽 × 包含排队在内的往返延迟

先按空载延迟估算。当全卡只有 1 个请求在路上时（空载），读 HBM 往返约 0.33 µs，算出每 SM 只需挂起 34 GB/s × 0.33 µs ≈ 11 KiB。切换图 2-2 的档位。选“每个 SM 在途 16 KiB（同时读 1 行 W）”时，读数为“全卡 2.29 TB/s，是标称的 48%；一行往返约 0.94 µs”。再切到“每个 SM 在途 64 KiB（同时读 4 行 W）”。此时读数到达拐点“全卡 4.49 TB/s，是标称的 94%；一行往返约 1.92 µs”。满载往返约为空载延迟的 6 倍（可继续切到 80 与 96 KiB 档位查看读数）。超过约 64 KiB 后，增加在途字节只会拉长在 L2 与显存控制器前的排队时间，带宽停在约 4.54 TB/s。

4. 跨 SM 交换数据：为什么必须走 L2 同步？

图 2-3（图还在画）

同一 cluster（线程块集群）内的 CTA 可直接互读片上内存。但 K-halves 的两半与 P1 的各拆分块由任意空闲 SM 接手，不保证在同一 cluster 内。所以跨任意 SM 汇总必须走全卡唯一的一致点 L2。

在 P1 注意力中，各拆分块的部分和用无返回值的全局原子加法累加到同一个 FP32 工作区地址。L2 内部的硬件原子加法器把“读旧值、相加、写回”一步完成，发送方不用等旧值返回。

在 K-halves 中，两半各算完半行部分和后需要在 L2 汇合。x86 CPU 的 TSO（总存储序）内存模型保证同一核发出的写入按程序顺序对其他核可见。ARM 等弱序 CPU 不保证跨地址顺序，而硬件缓存一致性本身只保证同一地址的写入顺序。但在 GPU 上，各 SM 的私有缓存（见第 3 章的 L1 cache）之间硬件不自动保持一致。普通写入也不保证跨地址顺序：计数器的更新可能先于部分和到达 L2，后半块的普通读取也可能命中自己私有的旧缓存行。因此跨 SM 交接必须指定 device（全卡作用域）的 release / acquire（释放/获取）内存序。实战中把两步合成一个带 acq_rel（兼具 release 与 acquire）的原子计数。每个半块写完部分和后，对 L2 中的计数器执行一次 fetch_add(1, memory_order_acq_rel)。拿到旧值 1 的后到半块读取另一半的部分和并相加写回 y[row]，同时把计数器复位为 0 供下一次重放（后到者合并不必自旋等待）。

#include <cuda/atomic>
// 每个半块块内归约后，0 号线程写出本半块部分和，并以 device 级 acq_rel 递增计数器
__syncthreads();
if (threadIdx.x == 0) {
    partial[half_id * M + row] = sum;
    cuda::atomic_ref<int, cuda::thread_scope_device> cnt(done_cnt[row]);
    if (cnt.fetch_add(1, cuda::memory_order_acq_rel) == 1) {
        y[row] = partial[row] + partial[M + row];
        cnt.store(0, cuda::memory_order_relaxed); // 复位供下一次 CUDA Graph 重放
    }
}

在图 2-3 的测试中，跨 SM 经 L2 交接一次的中位耗时约为 0.67 µs。这与第 1 章两个 kernel 之间的 PDL 交接（约 0.6 µs）同量级。所以能留在单 SM 内部完成的计算不跨 SM 交接。

5. gemv 演化（v2 → v3 → v4）：K-halves 切尾波与 L2 缓存留存提示

按第 3 章的驻留规则，v2（<<<2304, 128>>>）每 SM 驻留 16 个 CTA，全卡单轮容量为 2,112 个 CTA，第二轮留下 r = 192 个尾波 CTA。由于 192 ≤ 2,112 ÷ 2 满足第 1 节“余数不超过单轮容量一半”的切半条件，v3（在途 4.0 KiB/SM）把最后 192 行拆成 384 个半行 K/2 的 CTA（启动 2,496 个 CTA），两半按第 4 节的 L2 acq_rel 原子计数由后到者合并写回。尾波里每个 CTA 只有 128 × 2 B = 256 字节在途，算完一整行要走 8,192 ÷ 128 = 64 次串行往返（按单次约 0.33 µs 估算，图 2-4 读数为“不切半：一个 CTA 64 轮，约 21.4 µs”）。切半后每个半块只走 32 次往返，图 2-4 读数变为“切半：两个 CTA 各 32 轮 + L2 合并，约 11.2 µs”（估算省约 10 µs），第三行读数“实测（整个 kernel）：v1 58.88 µs → v3 48.26 µs”（1.22×，约为 7.9 µs 下界的 16.3%，实测省 10.6 µs）与这一估算吻合。

接着 v4（每 SM 16 个 CTA，在途 4.0 KiB/SM）用 createpolicy 为中央 L2 加上留存提示（.L1::evict_first 同时提示本 SM 的 L1 优先淘汰流式数据）。权重 W 每字节只读 1 次，标为 evict_first（读完优先淘汰）；向量 x（16 KiB）被重复读取，标为 evict_last（优先留在 L2）。

// v4：用 createpolicy 生成 L2 策略描述符，W 标 evict_first，x 标 evict_last
asm volatile("createpolicy.fractional.L2::evict_first.b64 %0, 1.0;\n"

asm volatile("createpolicy.fractional.L2::evict_last.b64 %0, 1.0;\n"
             "ld.global.L2::cache_hint.b16 %1, [%2], %0;" : "=l"(pX), "=h"(xv) : "l"(xp));

测具在每次冷缓存计时前写入 512 MiB 清空 60 MiB 的 L2，H200 冷缓存实测：48.26 → 43.94 µs（1.10×），约为 7.9 µs 下界的 17.9%。但在不清空 L2 的热缓存重复测试中，单层 W（37.7 MB）本可装进 60 MiB 的 L2。此时 evict_first 阻止了 W 留在 L2，使热缓存耗时反而从 29.02 µs 退化到 42.88 µs（真实多层推理中其他层本就会冲掉 W，冷缓存才是真实工作点）。

1. 四项容量上限与 gemv_kernel 的驻留 CTA 数

如图 3-1 所示，1 个 SM 内部对称切分为 4 个 SMSP（SM 子分区，见第 4 章）。当 1 个 CTA 派给某个 SM 后，硬件将其内部的 thread 按每 32 个连续编号编成 1 个 warp（线程束）。每 4 个连续 warp 组成 1 个 warpgroup（线程束组）。第 0.5 章的 gemv_kernel 选 128 个 thread，它恰好组成 1 个含 4 个 warp 的 warpgroup。这样通常可让 4 个 SMSP 各分到 1 个 warp。

1 个 SM 能同时驻留几个 CTA，决定了它的 occupancy（占用率，即驻留活跃 warp 数除以硬件上限 64）。把 gemv_kernel（v1 实测占 22 个寄存器）代进四项上限，每项算出一个可驻留的 CTA 数。

  • warp 槽位（上限 64 个）。每个 CTA 含 128 ÷ 32 = 4 个 warp，最多放 64 ÷ 4 = 16 个 CTA。
  • CTA 槽位（上限 32 个）。最多放 32 个 CTA。
  • SMEM（上限 228 KiB，即 __shared__ 数组）。每 CTA 占 0.5 KiB，加系统保留的 1 KiB 共 1.5 KiB，可放 ⌊228 ÷ 1.5⌋ = 152 个 CTA。
  • 寄存器（上限 65,536 个）。每线程不超过 65,536 ÷ 2048 = 32 个寄存器时至少可放 16 个 CTA；v1 占 22 个寄存器，不先触顶。

取四项的最小值，1 个 SM 最多驻留 16 个 CTA。图 3-1 默认预设“gemv_kernel（22 个寄存器）”的读数为“驻留 16 个 CTA，共 64 个 warp（occupancy 100%）”。第二行读数为“先满的是：warp 槽位”。点击“寄存器加到 32”或拖动滑块，可观察先满的池子如何切换到寄存器或 SMEM。

2. 全局内存合并访问：为什么相邻线程要读相邻地址？

decode 受 HBM 带宽限制，所以一个 warp 读回的每个字节都应该有用。LSU（Load/Store Unit，读写单元）负责处理线程读写请求。coalescing（全局内存合并访问）是指 LSU 把一个 warp 的 32 个线程地址合成尽量少的 sector（扇区）请求。一个扇区长 32 字节（L1 与 L2 的请求粒度），一条 128 字节的 cache line（缓存行）含 4 个扇区。

切换图 3-2 的三种写法对比扇区数。选第一种（第 0.5 章的 v0，相邻线程各读不同行，地址相隔 16 KiB），32 个线程落进 32 个不同扇区。每个 32 字节扇区当次只用 2 字节，读数显示“1 条 warp 读指令：取回 32 个扇区”与“搬 1024 字节，有用 64 字节（6%）”。选第二种（v1 的 gemv_kernel，k = tid），相邻线程读相邻的 2 字节 BF16。32 个线程共读 32 × 2 = 64 字节，读数显示“1 条 warp 读指令：取回 2 个扇区”与“搬 64 字节，有用 64 字节（100%）”。选第三种（本章第 6 节的 v5，每线程用 uint4 读 16 字节），一条 warp 指令读 32 × 16 = 512 字节。此时读数显示“1 条 warp 读指令：取回 16 个扇区”与“搬 512 字节，有用 512 字节（100%）”。单条指令搬回的有用字节扩大了 8 倍，凑够第 2 章约 64 KiB 在途量所需的指令条数降为原来的八分之一。

3. 把矩阵分块搬进 SMEM 的四种方式

要把一块固定大小的矩阵切片——称为一个 tile（分块）——从 HBM 经 L2 搬进 SMEM，共有图 3-3 所示的四种硬件通路。

  • 方式 1（普通指针读入寄存器再写 SMEM）。每个 thread 各自算地址，通过 LSU 先把数据装进私有寄存器中转，等数据返回后再发写指令拷进 SMEM。
  • 方式 2（逐线程异步拷贝 cp.async）。每个 thread 仍各自算地址并发拷贝指令，但数据从 L2 写进 SMEM、不经过私有寄存器。P1 注意力读取分页 KV cache（按固定页存放、由页表给出离散页地址）时就用 cp.async，因为下一条的专用搬运硬件不支持按索引列表收集离散行。
  • 方式 3 与方式 4（专用硬件 TMA 整块与张量分块拷贝）。方式 3 传入全局地址与字节数搬运连续字节流。方式 4 传入主机端建好的张量描述符 CUtensorMap 与分块坐标搬运多维矩阵分块（越界自动填零并可重排存放顺序，见第 5 节）。两种方式都把整个分块交给专用硬件 TMA（张量内存加速器），由 TMA 在后台独立写进 SMEM。

在图 3-3 中选方式 1，读数为“64 条 warp 指令（32 条读 + 32 条写）· 每个线程自己算地址”。第二行读数为“数据先进寄存器：每个线程最多占 32 个寄存器”。再选方式 4，读数变为“1 条指令 · TMA 单元按描述符搬，每行内部再重排（第 5 节）”。此时“寄存器里的数据”一行是空的。TMA 单元自己算地址、自己搬数据，只需 1 个线程发 1 条命令，占 0 个数据寄存器。其余 warp 在搬运期间可以做别的事，只在使用数据前等一次片上屏障。

4. 有界环形缓冲：为什么总槽数等于 在途槽数 + 1？

专用 TMA 硬件由单条命令整块派发、不占线程寄存器，全卡流式测试在每 SM 挂起约 48 KiB 在途请求时即到达带宽平台。SMEM 里的 N 个缓冲槽组成生产者-消费者有界环形队列（图 3-4），用来保持这 48 KiB 在途量。当前正在被消费者读取计算的 1 个槽已经到齐，不属于在途状态。所以在稳态下，路上的在途槽数等于 N − 1。

所需缓冲槽总数 N = ⌈ 所需在途字节数 ÷ 每个分块的字节数 ⌉ + 1

在 P2 专家 kernel 中，每次 TMA 搬运的权重分块为 36 KiB。在图 3-4 中选 2 个槽，读数显示“2 个槽：消费者在算时，最多 1 个槽在途（36 KiB）”与“消费者要停下来等数据”。按上式开辟 ⌈48 ÷ 36⌉ + 1 = 3 个槽后，读数变为“3 个槽：消费者在算时，最多 2 个槽在途（72 KiB）”与“消费者一直有数据可算”。这 3 个槽占 3 × 36 = 108 KiB SMEM，连同其他缓冲后整个 P2 CTA 约占 132 KiB（超过 228 KiB 的一半）。所以每个 SM 只驻留 1 个持久 CTA，靠 3 槽环形缓冲保持在途字节。

每个槽 s 配一对驻留在 SMEM 中的硬件计数屏障 mbarrier，因为调用 __syncthreads() 会让全块所有线程停下。初始化时向屏障写入期望报到的线程数，full[s] 表示已填满可读，empty[s] 表示已用完可覆写。

生产者在下一圈填第 s 槽前先等 empty[s] 翻转（相当于第 2 章的 acquire）。随后生产者发 TMA 读取，并对 full[s] 执行 mbarrier.arrive.expect_tx 登记期望到达的字节数，同时完成生产者的 1 次报到。TMA 每写完一批字节自动扣减计数。当报到计数与剩余字节计数双双归零时，full[s] 的 parity bit（相位位，交替翻转以区分相邻两圈）翻转。这会唤醒消费者，并保证 TMA 写入的字节对其可见。

消费者从第 s 槽发出读取命令后，数据要过几十个时钟周期（见第 4 章）才进到寄存器或计算单元。若消费者刚发出读取就提前报到，图 3-4 第三档读数会显示“消费者一直有数据可算 · 覆写了还在读的槽 9 次”，即发生 WAR（write-after-read，读后写冲突）。因此消费者必须先用完寄存器值或等第 5 章异步矩阵乘返回，确认读取结束后再向 empty[s] 报到（相当于 release），放行下一圈覆写。

5. SMEM 的 32 个 bank、填充代价与 XOR Swizzle

图 3-5（图还在画）

硬件上，SMEM 被切成 32 个并排的 bank（存储体），每个 bank 宽 4 字节，所以每连续 128 字节依次横跨全部 32 个 bank。当 1 个 warp 的 32 个 thread 在同一时刻访问不同 bank（或读同一地址触发广播）时，1 次即可读完。但当 1 个 warp 的 32 个 thread 同时读取每行 128 字节数组的同一列时，同列地址相差 128 字节的整数倍。这 32 个地址全部撞进同一个 bank。硬件把它们拆成 32 次串行请求，称为 bank conflict（存储体冲突），使读取吞吐量降为原来的 1/32。

对于 32 个线程各读一行、同读单个 4 字节列的小数组（如路由计数表），可在每行末尾多填 1 个 4 字节空白字。行宽变为 128 + 4 = 132 字节后，每行向后错开 1 个 bank，32 行正好落进 32 个不同 bank（代价是多占 SMEM 且破坏 16 字节对齐）。

对 TMA 搬运的矩阵分块，第 5 章的矩阵乘硬件每次让 8 个线程同时读取 8 行里同一列位置的 16 字节块（见图 3-5）。若 TMA 不开交错、按每行 128 字节直接存进 SMEM，这 8 行同列块的地址相差 128 字节，会撞在同一组 bank 上产生 8 路冲突。在张量描述符里打开 XOR Swizzle（异或地址交错，图 3-5）。TMA 写入时把每个 16 字节块的列块号与行号低三位按位异或（每 8 行一个周期）。这样不浪费任何 SMEM，就能让这 8 行 16 字节块散落在不同 bank 上。

6. gemv 演化（v4 → v5 → v6）：16 字节合并向量读取与单波次 32 线程 CTA

在 v4（<<<2496, 128>>>，在途 4.0 KiB/SM）基础上，v5（每 SM 16 个 CTA，共 64 个 warp）用 uint4 每次读取 16 字节（8 个 BF16）。随后用 __bfloat1622float2 转为浮点数乘加，使每 SM 在途字节跃升至 64 × 512 B = 32.0 KiB/SM。H200 实测：43.94 → 17.76 µs（2.47×），约为 7.9 µs 下界的 44.3%。接着 v6 把每 CTA 缩为 32 个线程（1 个 warp 算 1 行，启动 <<<2304, 32>>>），并撤掉 v3 的尾波切半。

// v5：沿用 v4 的 L2 提示，每次用 uint4 读 16 字节（8 个 BF16），转 float2 累加
uint4 w_vec = reinterpret_cast<const uint4*>(&W[row * K])[k];
float2 wf0 = __bfloat1622float2(*reinterpret_cast<const __nv_bfloat162*>(&w_vec.x));
// v6：每 CTA 缩为 32 线程（1 个 warp 算 1 行），全卡 2,304 行在一轮内同时驻留
gemv_v6<<<2304, 32, 0, stream>>>(W, x, y, K);

v6 换来的是：每 SM 最多可放 32 个单 warp CTA（图 3-1 选“每个 CTA 32 线程”可见全卡容量 4,224 个）。因此 2,304 个 CTA 一轮即可全部驻留（平均每 SM 17.45 个 warp），消除了第二轮尾波与跨 warp 的 SMEM 归约。但它的代价是每 SM 驻留的 warp 数从 64 降到了 17.45。每线程只挂 1 条读取时，在途量跌至 17.45 × 512 B ≈ 8.7 KiB/SM（远低于图 2-2 的 64 KiB 拐点），利特尔法则预测它会比 v5 更慢。H200 实测证实了这一预测：17.76 → 21.86 µs（0.81×，约为 7.9 µs 下界的 36.0%，实测占用率从 79.3% 跌至 25.8%），必须靠第 4 章增加单线程在途读取深度来补回。

带走一句话： v5 靠 16 字节合并读取将耗时从 43.94 µs 压到 17.76 µs，而 v6 虽换来单轮驻留却因在途量跌至 8.7 KiB/SM 退化到 21.86 µs。

1. 每个周期选 1 个就绪 warp，以及什么是 no eligible

一个 clock cycle（时钟周期，简称周期）是硬件调度的最小时间步。如图 4-1 所示，每个周期，SMSP 的 warp scheduler（线程束调度器）扫描本分区的驻留 warp。下一条指令的操作数和执行单元都已就绪的 warp 叫 eligible（就绪）。调度器每周期只有一个 issue slot（发射槽，即每周期从 1 个选中的 warp 发出指令的机会），所以它从中挑 1 个发射。其余就绪 warp 在 profiler 里显示为 not selected（未选中）。因此一个周期里即便有 15 个驻留 warp 处于 not selected，发射槽利用率仍是 100%。只有一个 eligible 都没有时，这个周期才叫 no eligible（无就绪周期），发射槽空置并拉长总耗时。每个驻留 warp 的私有寄存器在 CTA 启动时就已固定分配在本 SMSP 的寄存器文件里（见第 3 章）。所以切换 warp 不需要保存或恢复上下文，耗时为 0 个周期。

2. 顺序发射、scoreboard（记分牌）与掩盖延迟的两个条件

图 4-2（图还在画）

与乱序执行的 CPU 核心不同，GPU 的每个 warp 按程序顺序发射指令。当 warp 发出一条内存读取（如 W[row * K + k] 或 smem[i]）时，请求本身不阻塞该 warp。硬件只是在 scoreboard（记分牌，记录每个寄存器是否还在等数据返回的硬件表）上把目标寄存器标为“未就绪”。该 warp 可继续发射后续不读该寄存器的独立指令。直到遇到第一条使用该目标寄存器的指令时，它才被挂起，由调度器换另一个 eligible warp 上场。按每周期发射 1 条指令计算，让 SMSP 发射槽不空所需的驻留 warp 数为：

所需驻留 warp 数 ≈ ⌈ 读取返回延迟（周期） ÷ 从发出读取到首次使用前本 warp 能发出的指令数 n ⌉

第一个条件是让 SMSP 发射槽不空（掩盖片上 SMEM 短延迟）。从 SMEM 读取数据返回约需 23 个周期。若每个 warp 发出 1 条读取后紧跟 3 条独立指令（共 n = 4 条），单个 SMSP 只需驻留 ⌈23 ÷ 4⌉ = 6 个 warp。这 6 个 warp 轮流发射，就能实现 0 个 no eligible 空周期（图 4-2 下行）。若写成 idx = len[i]; p = table[idx]; v = data[p]; 这样后一步地址依赖前一步结果的串行链，每步 n = 1。此时单个 warp 会连续停在记分牌上，必须提前为下一轮预取地址表以增大 n。

第二个条件是让 HBM 带宽跑满，它与发射槽不空是两个独立条件。第 2 章约 0.33 µs 的空载单请求 HBM 读取折合约 600 个周期（按 1.8 GHz 换算，满载排队时更长）。若想靠条件一的轮流发射来掩盖 HBM 延迟，每个 warp 每次只挂 1 条读取（n = 4）时，600 ÷ 4 需要 150 个 warp，远超单 SMSP 的 16 个上限。这说明靠 warp 轮流发射掩盖不了 HBM 长延迟，必须靠第 2 章的在途字节数（见第 2 章第 3 节）。程序要么让每个线程同时挂起多条独立的 16 字节向量读取，要么像第 3 章那样用 TMA 环形缓冲把在途字节装进 SMEM。

回头看第 0.5 章的 gemv_kernel（v1）。每个线程每轮只从 HBM 挂起 1 条 2 字节的 W 读取（x 仅 16 KiB，被所有 CTA 重复读取时命中缓存）。即使单 SM 驻留满 16 个 CTA（每个 128 线程），不展开循环时全 SM 同时在途的 HBM 读取也只有 16 × 128 × 2 B = 4.0 KiB。要凑够第 2 章图 2-2 普通读取约 64 KiB 的拐点，每个线程须同时挂起 64 ÷ 4 = 16 轮 2 字节读取。在图 4-1 中选 v1，读数为“发射槽忙 17% 的周期 · no eligible（没有可发射的 warp） 83% · 本 SMSP 最多同时在途 1.0 KiB”。再选第 4 节的 v7（图 4-1 按每 SMSP 4 个 warp 建模）。此时读数变为“发射槽忙 19% 的周期 · no eligible（没有可发射的 warp） 81% · 本 SMSP 最多同时在途 16 KiB”。此时 4 个 SMSP 合计最多同时在途 64 KiB（实际每 SM 平均 17.45 个 warp，合 69.8 KiB），到达图 2-2 的 64 KiB 拐点。两种配置下调度器都有超过八成的周期处于 no eligible 空闲，但 v7 的峰值在途字节是 v1 的 16 倍。单 token decode 受 HBM 带宽限制，只要满足条件二把 HBM 喂饱，即使发射槽有大量 no eligible 空周期也不会损失显存吞吐。

3. 条件掩码、branch divergence（分支分化）与锁步屏障规则

图 4-3（图还在画）

同一个 warp 的 32 个 thread 按 SIMT（单指令多线程）方式运行。warp 每次为走同一路径的活跃线程发一条指令，其余线程被掩码关闭。同一路径上的线程齐步执行，叫 lockstep（锁步）。每个 thread 有自己的程序位置（Independent Thread Scheduling，独立线程调度）。所以硬件不保证分开的线程自动回到锁步。

编译器常把简短条件改写为 predication（谓词执行），由条件掩码控制哪几个 thread 写回结果，整个 warp 1 遍走完。单侧长分支（如第 0.5 章的 if (tid == 0)）会让其余 31 个 thread 被掩码屏蔽等待。若 if 和 else 两支都很长且同 warp 内不同 thread 走向不同分支，就会发生 branch divergence（分支分化，图 4-3）。此时调度器必须先跑完 if 子集再跑 else 子集，耗时为两支之和。

分化后的线程要靠 __syncwarp() 等带掩码的同步原语才能强制本 warp 重新汇合。而 __syncthreads() 要求本 CTA 内的所有 thread 走同一控制流全员到达。若把 __syncthreads() 写进只有部分 thread 进入的分支，进了分支的 thread 永远等不到其余 thread。CUDA 规定这是未定义行为，常见结果是死锁。

4. gemv 演化（v6 → v7 → v8）：每线程挂起 8 条向量读取与 warp 洗牌归约

第 3 章的 v6（<<<2304, 32>>>）每 SM 平均驻留 17.45 个单 warp CTA，在途仅 8.7 KiB/SM。本章的 v7 让每个线程在首次乘加前先连发 8 条独立的 uint4 读取（单线程在途 8 × 16 = 128 字节）。v7 编译占 83 个寄存器（按 8 的倍数分配 88 个），寄存器池限制每 SM 最多放 ⌊65,536 ÷ (32 × 88)⌋ = 23 个 CTA。每 SM 实际只需驻留 17.45 个（低于 23），所以全部行仍在一轮内同时驻留。全 SM 在途 W 字节跃升至 17.45 × 32 × 128 B ≈ 69.8 KiB/SM，跨过了图 2-2 的 64 KiB 拐点。H200 实测：21.86 → 15.68 µs（1.39×），约为 7.9 µs 下界的 50.2%（实测显存带宽 2,409 GB/s，一举反超 cuBLAS torch.mv 的 21.12 µs）。

接着 v8 引入图 4-4 所示的 warp shuffle（线程束洗牌：同一 warp 的线程直接读对方寄存器，5 层树形折半把 32 个值归约为 1 个总和）。在图 4-4 中选写法 1（v1），读数为“写法 1：128 次串行加法 + 1 次屏障”与“至少约 537 个周期 · 用到 SMEM”。再选写法 2（v8），读数变为“写法 2：5 层 shuffle”与“至少约 141 个周期 · 不用 SMEM”。

// v7：每线程连发 8 条独立 uint4 读取（128 B 在途），随后再做乘加
uint4 w0 = W_vec[k + 0], w1 = W_vec[k + 32], ..., w7 = W_vec[k + 224];
// v8：单 warp 内用 __shfl_down_sync 5 步折半归约，无需 smem 与 __syncthreads()
for (int offset = 16; offset > 0; offset >>= 1) acc += __shfl_down_sync(0xffffffff, acc, offset);

编译器在 v8 中保持每线程 7 条而非 8 条读取同时在途，全 SM 在途略降为 17.45 × 32 × 112 B ≈ 61.1 KiB/SM，紧贴图 2-2 的 64 KiB 拐点（4.49 TB/s）。H200 实测：15.68 → 15.62 µs（1.00×，约为 7.9 µs 下界的 50.4%），因为整个 kernel 在等 HBM 返回数据，洗牌归约省下的几百个周期被藏在了显存等待里。

带走一句话： v7 靠每线程连发 8 条 16 字节读取把全 SM 在途量从 8.7 KiB 推到 69.8 KiB（跨过 64 KiB 拐点），将耗时从 21.86 µs 压到 15.68 µs。

承接第 4 章末尾的问题（第 4 级：执行管线与 Tensor Core）：第 4 章中 SMSP 调度器每周期挑出 1 个就绪 warp 发出指令。指令发出后会进入背后的哪条物理管线，怎样让所有管线同时忙碌以缩短总周期数？

1. 发射间隔（32 ÷ 通道数）与结果延迟

图 5-1（图还在画）

衡量图 5-1 的执行管线需区分两个周期数。issue interval（发射间隔，即管线吞吐率的倒数）是管线收下 1 条 warp 指令后被占用的周期数。在这段周期内，该管线不能接收下一条同类指令。它等于 32 ÷ 管线硬件通道数（1 条通道每周期处理 1 个 thread 的 1 次运算）。latency（结果延迟）则是从指令发出到结果写回寄存器可供读取的总周期数（图 5-1 读数）。每个 SMSP 背后的四条基础管线彼此并联独立。

  • FMA（fused multiply-add，融合乘加，发射间隔 1 周期）管线。共 32 条通道，执行单精度浮点乘加、加法与乘法；其重型子管线也执行整数乘加 IMAD（第 6 章用它分担移位）。
  • ALU（arithmetic logic unit，算术逻辑单元，发射间隔 2 周期）管线。共 16 条通道，执行整数加法、移位、比较与按位逻辑。
  • SFU（Special Function Unit，特殊函数单元，发射间隔 8 周期）管线。共 4 条通道，执行快速指数 exp2f、倒数与平方根倒数 rsqrtf 等超越函数。
  • LSU（见第 3 章）。执行全局与共享内存读写地址生成。

调度器在前一周期把指令发给某条管线后，下一周期可立刻把另一条指令发给其他管线。当本 SMSP 上的 warp 向同一管线发指令的速度超过它的发射间隔时，管线队列排满，调度器就会因 back-pressure（回压）停发。因此一段循环的理论最短周期数由累计占用周期数最多的那条最慢管线（或每周期 1 条的共享发射槽上限）决定。在 gemv 的 v9 循环（见第 4 节）中，每处理 1 个装有两个 BF16 的 32 位字，需要 2 条 ALU 整数移位掩码指令拆包，再配 2 条 FMA 乘加指令。FMA、ALU 与 SFU 的发射间隔相差 1 : 2 : 8。每 2 个元素的 FMA 只占 2 个周期，而 2 条 ALU 拆包要占 2 × 2 = 4 个周期，使 ALU 成为该循环的最慢管线。注意力采用 online Softmax（在线 Softmax，即边读分块边做指数归一化，FlashAttention 的做法）。同理，其中每个元素做 2 条 FMA 配 1 条 8 周期的 exp2f，SFU 就是最慢管线。

2. 最宽的矩阵管线 Tensor Core：mma.sync（16 行）与 wgmma（64 行）

图 5-2（图还在画）

单 token decode 的 gemv 不用矩阵单元。但在 verify / prefill 与多 token 专家计算中，主力算力来自每个 SMSP 的 1 个 Tensor Core。它专门计算矩阵分块乘加 D = A × B + C。用来反复累加乘积结果的寄存器集合 C / D 称为 accumulator（累加器，对应第 0.5 章的 acc）。先从第 0 章的 989 TFLOP/s 标称峰值算出单个 Tensor Core 每周期的运算量。全卡有 132 个 SM，每 SM 含 4 个 SMSP。按标称峰值对应的 1.83 GHz 时钟（即第 4 章的约 1.8 GHz）计，每个 Tensor Core 每周期完成 989 TFLOP/s ÷ 132 ÷ 4 ÷ 1.83 GHz ≈ 1,024 次 BF16 运算。整 SM 4 个分区每周期合计完成 4,096 次运算。一条 64 × N × 16（N ≥ 64）的 BF16 矩阵乘共做 2 × 64 × N × 16 = 2,048 × N 次运算，除以 4,096 即得理论耗时 N / 2 个周期（图 5-2 读数）。

如图 5-2 所示，Hopper 提供两条不同粒度的 Tensor Core 指令族。

  • mma.sync（单 warp 同步矩阵乘，每次算 16 行）。由本 SMSP 的 1 个 warp 独立驱动 Tensor Core。输入分块 A、B（需先从 SMEM 读入寄存器）与累加器 D 全在私有寄存器里。
  • wgmma（warpgroup 异步矩阵乘，每次算 64 行 × N 列）。由 1 个 warpgroup（见第 3 章）的全部 128 个线程联手发起。这要求 4 个 warp 都不分化、128 个线程同时走到同一条 wgmma（分化见第 4 章），若分支让部分线程跳过该指令，硬件行为是未定义的。其右矩阵 B 由硬件根据 matrix descriptor（矩阵描述符，编码 SMEM 地址、步长与 swizzle 模式的整数）从 SMEM 读取。
  • wgmma 的两种左矩阵模式。左矩阵 A 可选从 SMEM 读取的 SS mode（Shared-Shared 模式，N ≥ 64 时耗时约 N / 2 周期）。它也可选从私有寄存器读取的 RS mode（Register-Shared 模式）。例如注意力里刚算出的权重已在寄存器中，用 RS 模式即可省掉写回 SMEM 的步骤。

如果某个专家只分到 1 个 token 并直接放在 wgmma 固定 64 行的那一维，64 行里只有 1 ÷ 64 ≈ 1.6% 的行有用，其余 63 行全是零填充（图 5-2）。在 decode 下，这些空行会锁住 4 个 warp 和它们的累加器寄存器；一旦进入受算力限制的区间，空算更会拖慢耗时。因此当 token 数很少时，要么利用转置恒等式 (A · B)^T = B^T · A^T 交换 A 和 B 让权重的输出维填满 64 行、把少量 token 放在 N 维，要么改用只占 16 行的 mma.sync。

3. 异步矩阵乘的寄存器所有权与 wait_group<1> 跨管线重叠

图 5-3（图还在画）

要让总耗时只等于最慢管线、而不是各管线之和，就必须让 Tensor Core 与算术管线同时忙碌。wgmma 发出后，warp 无需停下等待，下一周期即可向 FMA、ALU 或 SFU 管线发射其他指令。这与第 4 章受 scoreboard 自动保护的普通指令不同。在 wgmma 后台运行期间，硬件 scoreboard 不会阻止线程读写正在被 Tensor Core 使用的累加器或 RS 模式输入寄存器 A。如果不加等待就读取累加器，硬件不会停顿，结果是未定义的（可能读到尚未写完的值）。

因此，程序必须用 commit_group 把已发出的 wgmma 打包成组。访问相关寄存器或向第 3 章的 empty[s] 报到前，程序必须调用 wait_group<N>（阻塞等待，直到在途未完成的 wgmma 组数不超过 N）。最后一条指令发出到结果写回累加器的尾延迟称为 drain latency（排空延迟）。如图 5-3 所示，wait_group<0> 每次都会暴露约 53 个周期的排空延迟。反之，在寄存器里准备两套交替使用的输入缓冲，发完前一组 wgmma 后立刻用 ALU 和 FMA 管线准备下一组数据。等下一组也提交后再调 wait_group<1>。这会等到最多剩 1 组在途（前一组已完成，最新 1 组在 Tensor Core 上算），使算术管线与 Tensor Core 并行重叠。

4. gemv 演化（v8 → v9）：ALU 整数位移拆包与 8 路独立累加链

图 5-4（图还在画）

如图 5-4 所示，在 v8（第 4 章，在途 61.1 KiB/SM）基础上，每条 uint4 装有 8 个 BF16（打包在 4 个 32 位字里）。BF16 正好是 FP32 的高 16 位（见第 6 章第 2 节）。本章的 v9（在途 61.1 KiB/SM）用 ALU 管线的左移（<< 16）与按位与（& 0xffff0000u）把权重字 w 和输入字 xv 各自拆成两路 FP32，并分别加进 8 个独立的累加器变量 acc0..acc7。

// v9：用 ALU 位运算把 32 位打包字 w 与 xv 各拆成两个 FP32，分 8 路独立累加器乘加
float w_lo = __uint_as_float(w << 16), w_hi = __uint_as_float(w & 0xffff0000u);
float x_lo = __uint_as_float(xv << 16), x_hi = __uint_as_float(xv & 0xffff0000u);
acc0 += w_lo * x_lo; acc1 += w_hi * x_hi; // 共 8 路独立累加链

warp 按程序顺序发射指令（见第 4 章），拆成 8 路独立累加链可避免单条串行累加链阻塞后续读取发射。剖析器显示全核执行的指令总数从 2.67 M 降到 2.02 M（减少 24%）。但由于单 token decode 受 HBM 带宽限制，H200 实测耗时为 15.62 → 15.58 µs（1.00×，约为 7.9 µs 下界的 50.5%），印证了总耗时由最慢资源决定。

带走一句话： FMA、ALU 与 SFU 按 1 : 2 : 8 的发射间隔并行工作，异步 wgmma 配合双缓冲与 wait_group<1> 可隐藏约 53 周期的排空延迟。

1. 从 CUDA C++ 到 PTX 再到 SASS：为什么一个分支会让 wgmma 串行化？

图 6-1（图还在画）

CUDA C++ 代码经两步编译在 H200 上运行。前端编译器先把 C++ 翻译成虚拟汇编 PTX（Parallel Thread Execution）。后端编译器 ptxas 再针对 H200（sm_90a）做寄存器分配和编译期指令调度，生成 128 位 SASS 机器指令。GPU 不在运行时重排指令（见第 4 章），每条指令的操作码与寄存器编号都在编译期由 ptxas 写死在 128 位指令字里。

从发出 wgmma 到对应 wait_group 返回之间的指令段称为 asynchronous region（异步区间）。在 SASS 中，第 5 章的 wgmma 叫 HGMMA，wait_group 叫 WARPGROUP.DEPBAR.LE。异步区间里一旦混进条件分支，ptxas 就报出性能告警 C7515。同时 ptxas 会在每一条 HGMMA 紧后面插入一条 WARPGROUP.DEPBAR.LE 0（即 wait_group<0>）。每条矩阵乘都要等排空才发下一条，异步执行退化成了串行执行。在 P4 批量 T = 128 个 token 的 qkv_gate 矩阵乘中，这使主循环耗时从 8.84 µs 变成 20.74 µs（图 6-1）。所以 wgmma 主循环的异步区间里不能写条件分支，编译后要检查 ptxas 告警和 SASS 反汇编。

2. 32 位寄存器里的浮点比特排布：FP32、BF16 与 4 位 NVFP4

图 6-2（图还在画）

一条 SASS 指令操作的每个线程寄存器都是 32 位宽，可以把不同位宽的数值打包存放在同一个寄存器里（图 6-2）。4 位浮点 NVFP4 编码为 E2M1（1 位符号、2 位指数、1 位尾数），每 16 个权重配 1 个 8 位 E4M3（1+4+3 位）缩放因子。H200 上没有把 E2M1 直接转成 BF16 的硬件指令，但解码时不需要查表或逐位算指数。把 4 位权重的符号位对齐到 BF16 最高位，再把低 3 位数值位放到 BF16 指数最低两位与尾数最高位上（其余位清零）。这样拼出的 16 位比特串在数学上就等于原始权重乘上 2^-126（图 6-2 下方，如 E2M1 的 0 01 1 = 1.5 放入对应位得 BF16 的 0 00000001 1000000 = 1.5 × 2^-126）。这是由于两者的符号、指数与尾数位域顺序一致，只差一个固定指数偏置。

  • 标准单精度 FP32 与 16 位 BF16。BF16 截去 FP32 的低 16 位尾数，保留了与 FP32 相同的 1 位符号与 8 位指数。因此把 BF16 升成 FP32（如 __bfloat162float 与第 5 章的 v9）无需走 SFU。编译器只需生成 1 条字节重排指令 PRMT（按字节重排寄存器内容，走 ALU 管线）或移位掩码，把高 16 位对齐、低 16 位补零。
  • 4 位浮点 NVFP4 与 BF16 的位域对齐。指数位全零的小数称为 subnormal（非规格化数）。硬件 BF16 乘法默认保留非规格化数不归零，使得规格化与非规格化的 E2M1 放入 BF16 对应位后都满足同一个 2^-126 缩放关系。

3. 用 8 条整数指令在 ALU 与 FMA 管线上解码 4 位权重

图 6-3（图还在画）

单 token decode 等的是 HBM，解码指令藏在显存等待里。但在算力受限的 verify / prefill 阶段，解码指令的管线占用决定 Tensor Core 会不会停下等权重。单 warp mma.sync 路径也是如此，因为每个 warp 每步都要在寄存器里解码权重。加载模型权重时先对权重字节做一次按位重排。随后在 kernel 内只需执行 8 条整数位运算指令（图 6-3），就能把 1 个 32 位寄存器里的 8 个 4 位权重拆成 4 个打包的 BF16x2 寄存器。如果把这 8 条整数指令全塞给 ALU 管线（每条占 2 个周期，见第 5 章），每解 1 个源寄存器就要占 8 × 2 = 16 个周期。把其中 2 条移位改用 FMA 重型子管线分担后，ALU 管线只剩 6 条指令，周期负担降至 (2 + 4) × 2 = 12 个周期（减掉四分之一）。这是因为 ALU 管线与 FMA 重型子管线是两条独立管线，可以并行分担移位。

  • 平摊到两条管线的移位。结合双寄存器移位 SHF（2 条，走 ALU 管线）与整数乘加移位 IMAD.SHL（2 条，走 FMA 重型子管线），把各权重的数值位移到目标寄存器的对应位置。
  • 三输入按位逻辑合并（LOP3）。执行 4 条三输入按位逻辑指令 LOP3（走 ALU 管线），用掩码一步把符号位与数值位合并、其余位清零。
  • 缩放因子解包与偏置补偿。先把块缩放因子解包成打包 BF16，并加上固定指数偏置常量。再用打包乘法 HMUL2（走 FMA 管线）乘到刚拼好的寄存器上，即可送进 Tensor Core。

4. gemv 演化（v9 → v10，排行榜提交版）：12 位无损打包与寄存器位运算解码

进入最终版前，先设对照版 v10c。排行榜提交内核在单个 CTA 内合并处理 4 行输出，并在尾声融合归一化。它采用每 CTA 4 个 warp 各算 1 行的形状（启动 576 个 CTA，每 SM 驻留 17.45 个 warp）。v10c 只换这一形状并把每线程在途读取减为 4 条（在途降为 34.9 KiB/SM），同时保留 16 位 BF16 权重，用来单独隔离 12 位权重格式的收益。由于 34.9 KiB/SM 掉到了第 2 章图 2-2 拐点（64 KiB）以下，H200 实测 v10c 退化为 15.58 → 20.00 µs（0.78×，约为 7.9 µs 下界的 39.3%）。

图 6-4（图还在画）

如图 6-4 所示，最后排行榜提交的 v10 利用了赛题权重分布的一个特殊性质：绝大多数 BF16 权重的指数高 7 位落在同一个 8 值窗口内。该性质只对本赛题给定的权重成立，不适用于任意模型。预处理保留每个权重的低字节（最低 1 位指数与 7 位尾数），把符号与 3 位指数偏移压成半字节，合为 12 位 C12 无损格式。这把主权重从 37.7 MB 压到 28.3 MB（连同窗口外旁路表合计约 28.4 MB），按 4.8 TB/s 算出的理论下界从 7.9 µs 移至 28.4 MB ÷ 4.8 TB/s ≈ 5.9 µs。

// v10（C12）：在寄存器中用按位与（0x87878787）、整数加法与漏斗移位把 12 位权重还原为 BF16/FP32
asm("shf.r.wrap.b32 %0, %1, %2, 4;" : "=r"(hi_nibbles) : "r"(packed), "r"(packed));
uint32_t bf16_pair = (( hi_nibbles & 0x87878787u ) + EXP_BASE) ...; // 再经异或补丁修正窗口外权重

但 v10 每线程只保持 3 条 16 字节 C12 平面在途，全 SM 在途进一步降至 26.2 KiB/SM。对照第 2 章图 2-2 在 16 与 32 KiB 之间的曲线（约 3.2 TB/s），少读 25% 字节的收益几乎被较低的在途带宽抵消。H200 实测印证了这笔账：v10 耗时为 20.00 → 15.49 µs（相对同形状的 v10c 提速 1.29×，相对在途充足的 v9 为 1.01×）。这一成绩约为 7.9 µs BF16 下界的 50.8%、自身 5.92 µs C12 下界的 38.2%。同时 v10 融合了 QK 归一化、RoPE 与写 KV 缓存尾声，且 v7–v10 均显著快于 cuBLAS torch.mv 的 21.12 µs。
